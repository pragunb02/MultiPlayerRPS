The 186 `ERR_WS_UPGRADE` entries in CC-319's Chromium network logs were not failed WebSocket upgrades: Chromium closes the HTTP request of every WebSocket that upgraded successfully with that code (`net_error_list.h`: "When a WebSocket handshake is done successfully and the connection has been upgraded, the URLRequest is cancelled with this error code"). They were every WebSocket of the run and about 5% of all requests, which is why CC-319's fix did not change the count. A new network log of the same tests gave 186 handshakes, all answered 101, all ending `ERR_WS_UPGRADE`, none any other way. The TLS front, a polling upgrade (the app is WebSocket only), the server's checks and teardown were each ruled out. Production is not affected and the app does not change. A new browser test, `realtime-upgrade.spec.js`, shows that the players check fails a test when the server really refuses an upgrade (its origin check, in Chromium, Firefox and WebKit), and stays clean for the closes of a reload or a person leaving.
