Our own feature flags. One registry in code (`packages/shared/src/flags.js`): each flag has a description, its ticket, `default` off, a `removeBy` day, a rollout (off, on or a whole percentage) and an audience (everyone, signed-in, adults through CC-152's age rule, or console admins). The server works out a player's bucket from a keyed hash of the player id under its own label, so it never leaves the server, and the web app gets only booleans from `GET /api/flags` (`no-store`) through `useFlag(name)`. The owner sets a rollout without a deploy in the console's new Flags tab; overrides live in a new `feature_flags` collection, are read every 30 seconds, and when the database cannot be read the last good ones stay for 5 minutes before the code's rollout applies. Exposures and one success event per flag are counted per India day and side in a new `feature_flag_counts` collection with no id of anyone, kept 90 days, and shown with the small-group rule. CI fails on a flag past its removal date, on a flag name that is not registered, and on a flag without a `flagPaths` suite that runs it on and off. PROCESS.md says how a feature ships: behind a flag, ramp, remove. The first flag, `console_flag_check`, is an admins-only canary on the Flags tab, to be removed by 2026-12-31.
