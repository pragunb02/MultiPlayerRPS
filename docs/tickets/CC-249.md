## Research (written before any code)

### 1. How our code does it today (origin/main at `c35daaa`, read on 2026-10-18)

1. `apps/server/src/utils/networkKey.js` (CC-107): `createNetworkKey({ secret })` returns
   `address => HMAC-SHA-256(secret, address)`, cut to 16 hex characters. `server.js` and `testing/testApp.js` pass
   `config.sessionSecret`, so the key is `SESSION_SECRET`, the same secret that signs the `cc.sid` cookie.
2. The gateway (`service/realtime/gateway.js`) works out `socket.data.network = networkOf(addressKey(address))` once,
   when a socket connects. `roomHandlers.js` and `botHandlers.js` pass it to `roomComponent.createRoom` and
   `botComponent.playComputer`.
3. `roomComponent.checkRoomLimits` counts the open rooms with that exact name (`roomAccessor.countByNetwork`,
   `roomDao.countByNetwork`, an index on `network`) and refuses a 31st (`openRoomsPerAddress`, ADR-035). Nothing
   else reads `network`. It is never sent to a client and is not copied to `closed_rooms`.
4. The room stores `network` for its whole life (30 minutes to 24 hours, CC-101) and the nightly backup keeps a copy
   for 30 days (CC-108).
5. **The gap (CC-241 F2).** There are about four billion IPv4 addresses. With `SESSION_SECRET`, one laptop hashes
   all of them in minutes and finds the address behind every `network` in the database or in any backup of the last
   30 days. The same key for every day also links the rooms of one network across days. So the hash is
   pseudonymous personal data, and its protection is exactly as good as the session secret's.

### 2. How others do it (sources fetched 2026-10-18)

1. **Plausible Analytics** counts unique visitors with `hash(daily_salt + website_domain + ip_address + user_agent)`.
   The salt is "rotated and deleted every 24 hours", and "old salts are deleted to avoid the possibility of linking
   visitor information from one day to the next" (https://plausible.io/data-policy,
   https://plausible.io/blog/google-analytics-cookies). In the code (`lib/plausible/session/salts.ex`), a salt is
   `:crypto.strong_rand_bytes(16)`, the current and the previous salts are kept, and salts older than 48 hours are
   deleted. Plausible keeps the salts in its database because it runs many nodes that must agree.
2. **Cloudflare** rate limits count by `ip.src`, or by "IP with NAT support", which "relies on a cookie-based visitor
   identification mechanism" and "privacy-preserving techniques"
   (https://developers.cloudflare.com/waf/rate-limiting-rules/parameters/). The counter is what matters, not the
   address, and the counter lives only for the rule's period.
3. **OWASP Authentication Cheat Sheet** asks for counters tied to what is being protected and for lockouts that
   cannot be used to lock other people out. It says nothing about keeping addresses, so keeping less is free
   (https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html).
4. **RFC 5869 (HKDF)** is for turning one secret into several independent keys, each bound to a purpose (`info`) and
   optionally a salt. It makes keys independent of each other. It cannot make a key stronger than the secret it
   comes from: whoever holds the input secret can derive every output key again.

### 3. What is best for ClassiCade

Three ways to give the hash its own key were compared.

| Way                                                             | New env var | Who can find an address from a stored hash                                                      | Cost                                                                                               |
| --------------------------------------------------------------- | ----------- | ----------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| A. HKDF from `SESSION_SECRET` plus the UTC date                 | no          | anyone with `SESSION_SECRET`, for every day, because the room's `createdAt` gives the date      | none, but F2 stays: the same people can still reverse it                                           |
| B. HKDF from a new secret (`NETWORK_HASH_SECRET`) plus the date | yes         | anyone with the new secret, for every past day. It sits in Render next to `SESSION_SECRET`      | the owner sets a secret before the merge. A Render leak gives both secrets at once                 |
| C. A random key made in memory each UTC day, forgotten after it | no          | nobody once the day is over, not even the owner, and not from a backup or with every env secret | a restart (a deploy) makes a new key, so rooms still open from before it stop counting for the cap |

**C is best for us**, the way Plausible does it, with one change: the key lives only in the server's memory, never
in MongoDB. Plausible stores its salts because many nodes must agree. We run one instance (a second one is CC-061, deferred, ADR-035), and our
database credential leaked in git history and is not rotated yet (CC-105), so a key in the database would be
readable by exactly the people this ticket protects against.

1. **Why not HKDF.** HKDF only helps when the input is a long lived secret that must give several keys. A and B are
   that, and both leave the hash reversible by whoever holds the input for as long as backups exist. With C the key
   is 32 fresh random bytes, which is already a full strength HMAC key, so HKDF would add nothing. If a second
   instance (CC-061) ever needs a shared key, B with HKDF (`info` = `"classicade room network"`, salt = the UTC day)
   is the fallback, and that ticket adds the env var.
2. **The cost of C is small.** The per-network cap (30 open rooms) is one of four limits. The 3 waiting rooms per
   player, 2000 rooms on the server and the socket caps per address still hold across a restart. Rooms close within
   30 minutes to 24 hours, so after a deploy or at midnight UTC the cap counts in full again within a day, and in
   practice within 30 minutes (waiting rooms). At worst one network gets 30 more rooms for that time. Render's free
   instance also sleeps when nobody uses it, which is exactly when nobody is abusing it.
3. **Kept only for the room's life.** `network` already goes when the room is deleted, and `closed_rooms` never had
   it. With a key that is forgotten at the end of its day, a copy left in a backup can no longer be turned into an
   address by anyone, so the hash means something only while its room is open.
4. **Rooms already stored keep working.** `network` is an optional, opaque field (rooms before CC-107 have none).
   A room stored with an old `SESSION_SECRET` hash loads, plays, finishes and closes as before. Its hash simply no
   longer matches any new one, so it stops counting for the cap, and it is gone when the room closes (24 hours at
   most). Backups taken before the merge keep old hashes until they age out (30 days). That cannot be undone from
   the code, and it is written in DATA.md.
5. The hash stays 16 hex characters (64 bits). With at most 2000 open rooms, two networks sharing a name is far less
   likely than one in a billion.

## Why

Anyone holding `SESSION_SECRET` can find the address of every room's host, today and in 30 days of backups
(CC-241 F2). The privacy page says we do not record your IP address with your games, which is only true while that
secret is safe.

## Scope

- In: `utils/networkKey.js` with a random key per UTC day, kept in memory only. The wiring in `server.js` and the
  test app. Tests. DATA.md and the privacy page (with CC-248).
- Out: shared keys for several instances (CC-061). Removing old hashes from backups (they age out in 30 days). The
  in-memory HTTP and socket limits, which keep addresses for minutes or while connected (DATA.md, server memory).

## Acceptance criteria

- [ ] The hash changes from one UTC day to the next, and cannot be recomputed from `SESSION_SECRET` alone
- [ ] The day's key is random, never stored, and dropped when the next day starts
- [ ] No new env var
- [ ] Rooms stored before the change keep working
- [ ] Tests cover the change
- [ ] `npm run lint`, `npm run format:check`, `npm test` pass
- [ ] Docs updated (DATA.md, the privacy page. The board, KNOWN_ISSUES and PROGRESS are updated by the owner)

## Plan / notes

1. A failing test first: the same address on two days gives two names, two keys made on the same day with the same
   config differ, and neither equals `HMAC(SESSION_SECRET, address)`.
2. `createNetworkKey({ now, randomKey })`: `now` is the server clock, `randomKey` defaults to 32 bytes from
   `crypto.randomBytes` and is injectable so tests can see when a new key is made.
3. The gateway still works the name out when a socket connects, so a socket connected before midnight keeps the
   name of its own day. That is the same short gap as point 2 above.
