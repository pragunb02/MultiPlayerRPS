## Research (written before any code)

### 1. How our code does it today (origin/main at `61b3bb2`, read on 2026-10-18)

There is no single list. What is stored is spread over the DAOs in `apps/server/src/persistence/`, the session
middleware, the in-memory limiters, the logger and the backup scripts. Read for this ticket:

1. **MongoDB collections owned by the new server:** `accounts` (accountDao.js), `player_sessions` (sessionStore.js,
   connect-mongo with a native TTL index), `rooms` and `closed_rooms` (roomDao.js, lifetimes in
   `domain/rooms/roomLifetimes.js`), `matches` (matchDao.js, with the full move `log` and the `seed`),
   `player_progress` (progressDao.js), `player_stats` (statsDao.js), `player_achievements` (achievementDao.js),
   `player_quests` (questDao.js, TTL on `expiresAt`, 8 days after the day per `data/gamificationAccessor.js`),
   `leaderboard_entries` (leaderboardDao.js, TTL on `expiresAt` for weekly boards only, 28 days after the week per
   `domain/leaderboards/boards.js`) and `player_transfers` (playerTransferDao.js).
2. **Legacy collections.** `users` is read through legacyUserDao.js, which has no write method and reads only
   `username`, `email` and `password`. The legacy app (deleted in CC-029, see `git show c9eb13f^`) also wrote
   `sessions` (connect-mongodb-session), `chessdatas`, `rpsdatas` and `tictactoedatas` (player names and choices per
   room). Nothing in the new code reads or deletes them, so the code cannot say whether they still exist in
   production.
3. **Server memory.** express-rate-limit with its default memory store (rateLimits.js), the login throttle
   (loginThrottle.js, which keeps email and address pairs for up to 30 days while the process lives), socket
   admission counts per session, address and player (socketAdmission.js), session renewals (session.js), sign-out
   counts per player (gateway.js), background tasks and the housekeeping timer (server.js). The network hash from #57
   (utils/networkKey.js) is computed in memory, but it is also **written** to every room as `network`.
4. **Browser.** The `cc.sid` cookie (session.js: httpOnly, SameSite Lax, Secure in production, rolling 30 days) and
   `cc.sound` in localStorage (lib/sound/soundPreferences.js). No other storage key or cookie in `apps/web/src`.
5. **Logs.** pino JSON on stdout (utils/logger.js) with redaction of `password`, `token`, `sessionId`, `email`,
   `secret` and cookie headers. An access line per request (requestLogger.js: method, path, status, duration and only
   the count of `X-Forwarded-For` entries), plus event lines that carry player ids, socket ids, room codes and match
   ids. Render keeps them.
6. **Backups.** `.github/workflows/backup.yml` and `scripts/backup/dump-and-encrypt.sh`: a full `mongodump` of the
   database, encrypted with age, kept 30 days by the bucket's lifecycle rule (runbooks/backup-restore.md).
7. **The privacy page** (`apps/web/src/pages/LegalPages/PrivacyPage.jsx`, CC-046) was written from the server of
   2026-10-16. Rooms in MongoDB (CC-101), the network hash (CC-107), the login throttle (CC-117) and backups (CC-108)
   came after it.

### 2. How others do it (sources fetched 2026-10-18)

1. **A record of processing.** The UK ICO lists what a controller documents under GDPR Article 30: purposes, the
   kinds of people and data, recipients, transfers abroad, "retention periods for each category of data, where
   possible" and the security measures
   (https://ico.org.uk/for-organisations/uk-gdpr-guidance-and-resources/accountability-and-governance/documentation/what-do-we-need-to-document-under-article-30-of-the-gdpr/).
   That is close to the columns the owner asked for.
2. **Lichess**, a free chess site run by a small team, organises its privacy policy by purpose. Each purpose names
   the data, the legal basis and the retention, with a summary table at the end. Connection data (IP address,
   browser) is kept one year, account data for the life of the account (https://lichess.org/privacy, last updated
   16 March 2022).
3. **India's DPDP Rules 2025** (notified 14 November 2025, most duties apply from 13 May 2027, as ADR-028 records).
   Rule 6(1)(e) asks a data fiduciary to keep logs for one year to detect and investigate unauthorised access, and
   rule 8(3) to keep personal data, traffic data and logs for at least one year from the processing
   (https://dpdpa.com/dpdparules/rule6.html, https://dpdpa.com/dpdparules/rule8.html). Render keeps service logs for
   7 days on the Hobby plan and 14 on Pro (https://render.com/docs/logging).
4. **Section 8(7) of the DPDP Act** asks for erasure once the purpose is no longer served. That is the rule behind
   CC-098 (guest data that nobody can sign in to again).

### 3. What is best for ClassiCade

1. One file, `docs/DATA.md`, with one row per store and the same columns everywhere: what it holds, personal data or
   not, who can read it, how long it is kept, how it is deleted, and the code that shows it. Each row names the file
   and constant, so a reviewer can check it, and a change to the code shows which row to update.
2. Written against origin/main only. Work in open pull requests (the owner console in #64, room event history in
   CC-242, telemetry in CC-173 to CC-178) gets a short "coming" note, not a row.
3. The privacy page is checked line by line against the file. Every mismatch becomes a finding with a suggested
   ticket. The page and the code are not changed here: the owner reviews the wording, and the feature freeze allows
   only security, test and bug tickets, so each suggestion says which of those it is or which existing ticket covers
   it.
4. Unknowns are written as unknowns (the legacy collections in production, the fields of Render's own request
   logs), with the check the owner can make. Nothing is guessed.

## Why

The owner asked what is stored and what is not (2026-10-18). The answer is spread over code: MongoDB collections (accounts, legacy users read only, sessions, rooms, closed_rooms, matches, progress, stats, achievements, quests, leaderboards, player transfers), server memory, the session cookie, `cc.sound` in web storage, Render logs and the encrypted backups. Nobody can check the privacy page against it in one place.

## Scope

- In: docs/DATA.md with one row per store: what it holds, personal data or not, who can read it, how long it is kept and how it is deleted; the privacy page checked against it; every gap a ticket.
- Out: changing retention (that goes in the gap tickets).

## Acceptance criteria

- [ ] Every collection, cookie, storage key, log and backup is listed, checked against the code

- [ ] Tests cover the change
- [ ] `npm run lint`, `npm run format:check`, `npm test` pass
- [ ] Docs updated (BACKLOG status, KNOWN_ISSUES, PROGRESS)
