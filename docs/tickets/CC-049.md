## Why

Nobody notices when production is down until a player complains. The free part we can do today is an outside check
that opens an issue when the site stops answering and closes it when it is back.

## Scope

- In (this branch): `.github/workflows/uptime.yml` every 10 minutes: `/health` (200, database up) then `/` (200,
  HTML), with retries for free plan cold starts (doubling waits, up to 90 s for `/health`, 30 s for the page). Two
  failed checks in a row open an issue labelled `incident` with timings, later failures update it, the first passing
  check comments the outage length and closes it. No secrets. Documented in docs/DEPLOYMENT.md, Uptime monitoring,
  including what it does not cover.
- Out (later in this ticket): error tracking, metrics, latency, paging.

## Acceptance criteria

- [x] Scheduled every 10 minutes and runnable by hand, no secrets
- [x] Cold starts allowed for (retry with backoff up to about 90 s)
- [x] Down twice in a row opens or updates an `incident` issue with timings, closes it when health is back
- [x] Logic in tested scripts the YAML calls, YAML checked by actionlint in CI
- [x] docs/DEPLOYMENT.md says what it covers and what not
- [ ] Owner: Watch the repository for issues so incidents notify
- [ ] Error tracking, metrics, alerts (rest of the ticket)

## ADR-0xx (proposed) — Uptime: GitHub Actions schedule, incidents as GitHub issues

**Decision.** The check runs as a scheduled workflow. It keeps no state of its own: whether the previous check
failed is read from the previous run of the same workflow, where a step named "Site is down" runs only on failure
(its conclusion is `success` or `skipped`). The incident is an issue with the `incident` label and a hidden marker,
and its body carries a small JSON state (first failure time, failed checks in a row). Only issues with the marker are
ever edited or closed.

**Alternatives.** An external free monitor (UptimeRobot and similar: another account, and incidents would live
outside the repository). Keeping state in the Actions cache (one new cache entry every 10 minutes) or a repository
variable (needs a token with admin rights). Failing the run when the site is down (an email every 10 minutes for the
whole outage).

**Consequences.** GitHub's schedule is best effort (often minutes late, sometimes skipped). Renaming the step breaks
the "twice in a row" logic, so a test pins the step name to the constant in `scripts/uptime/incident.mjs`. The pings
keep the free Render instance awake.

## Verification

- Unit tests with a fake clock and fetch: cold start ridden out with 5/10/20 s waits, budget exhausted with every
  attempt recorded, last wait shortened to leave room for one more attempt, late wakeups still get a real timeout,
  health and page judged correctly (503, wrong body, not HTML, no content type).
- Monitor against an in memory fake of the site and the GitHub API: up and nothing open (no extra API calls), first
  failure only warns, first ever run counts as up, second failure opens the issue (creating the label if needed),
  further failures update it without reading earlier runs, recovery comments and closes, hand filed incidents and
  issues without a body are left alone, a body that lost its state falls back to the issue's creation time, broken
  monitor exits 1 with an error annotation.
- A test pins the workflow's "Site is down" step and its condition, the schedule and the permissions.
- Real probe against https://nocapgaming.onrender.com: up, health 464 ms, page 264 ms. Against an unknown host:
  down with ENOTFOUND attempts at 0, 1, 3, 7, 15 and 18 s (with a short test budget).
- actionlint 1.7.12 clean.
