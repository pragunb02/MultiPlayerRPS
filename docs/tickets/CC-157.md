## Research (written before any code)

### 1. How our code does it today

What open PR #67 (CC-159, CC-160, CC-207, CC-158, CC-036, CC-208) changes on the room page, read with
`gh pr diff 67` on 2026-10-18:

- `RequestBanner` is rendered first in the room section, sticky at `top: 0`, with Incoming (Accept, Decline, Hide,
  countdown), Outgoing (Cancel, countdown, "No answer" choices) and the Answer shown for 4 s. `RoomRequests.jsx` is
  deleted.
- `ClaimWin` sits at the top of the stage (claim the win when the opponent is gone for 60 s).
- Requests are actions `{ type: "ask", requestType }` and `{ type: "answer", requestType, answer }`, sent with
  `room.ask` and `room.answer`. Boards receive a new `onAsk` prop (chess uses it for Offer draw).
- `gameNumber(room)` becomes `room.game?.number` (the server numbers games from 1), and aborted games (no first move
  in 60 s) finish without counting in the series.
- `Seats` gains `PresenceChip` and a polite presence announcement; `Layout` gains `ConnectionBanner` and
  `SiteRequests` under the header; toasts gain categories and a hold while a request is open (CC-208).

So #67 already builds two of the eight shell parts (request banner and presence). CC-157 must be built **on top
of #67**, not beside it: rebuilding the room page before #67 merges would be the "naive merge" trap the audit
warned about for #42 (MATCH_EXPERIENCE.md §1, "What the open PRs change").

Other facts that shape the shell:

- `RoomPage.jsx` is 298 lines and owns routing, joining, closed rooms, errors, the leave modal and the match. CC-131
  plans to split it. The shell is the natural cut: the page keeps routing and room states, the shell gets the match.
- Boards are lazy chunks (`games/lazyBoard.js`). Motion (ADR-016) is loaded only by the chess chunk, so anything the
  shell animates with Motion would pull Motion into every game's first load.
- `e2e/match-shell.spec.js` already presses every `data-cc-control` in every state and checks the main controls of
  each state are on screen at 1280×720 and 390×844; six chess states are `test.fail` for CC-172.

### 3. What is best for ClassiCade, and why

1. **One `MatchShell` component that owns the frame, and a game module that only fills slots.** The room page
   renders `<MatchShell room={view} game={gameView(view.gameId)} … />` and never names a game (open/closed, as the
   registry already is). It matches lichess's single grid and BGA's single action bar, and it is the cut CC-131
   wants for `RoomPage`.
2. **Extend the existing registry entry, do not add a second registry.** `GAME_VIEWS` already carries `Board`,
   `soundsFor`, `reasonPhrase` and (#67) `requestTexts`. The shell adds optional fields, and a game without them
   still works (it renders like today inside the stage), so the three games move one PR at a time (CC-166 to 168).
3. **Take #67's parts as they are.** `RequestBanner`, `PresenceChip`/`Seats`, `ConnectionBanner`, `ClaimWin` and the
   `ask`/`answer` actions become shell slots without rewriting them. CC-157 starts after #67 merges.
4. **Server-authoritative stays as it is.** Slots get the RoomView and callbacks that send intents (`onMove`,
   `onAsk`, `onAnswer`); nothing in the shell decides a result. Action reasons come from the view (`playReason`,
   `useAskReason` from #67), so a disabled control always says why (ADR-038).
5. **No Motion in the shell.** Shell animations (banner in, score bump, sheet up) are CSS keyframes on `transform`
   and `opacity` (ADR-012 point 3), so RPS and TTT do not download Motion. Reduced motion already zeroes durations
   in `global.css`.
6. **Accessibility is part of the contract, not a later pass**: one polite and one assertive announcer per match
   (MATCH_EXPERIENCE.md §2 item 8), the request never takes focus (as #67), the result card takes no focus but is
   announced assertively, every control is a `Button` with `data-cc-control`, targets at least 44 px for main
   controls (ADR-020 constraint; WCAG 2.5.5 AAA) and never under 24 px (2.5.8 AA).

## Why

Every P0 match finding (A1 to A6) needs something that exists in one place for every game: a match bar, a request
banner, presence, an action bar and a result card. Today each board draws its own pieces of that, so fixes land three
times and a new game (Ludo, phase 3) would start from nothing.

## Scope

- In: `MatchShell` with the slots below; the registry fields; the room page rendering the shell for playing and
  finished rooms (waiting, closed and error states stay in `RoomPage`); moving #67's banner, presence and claim-win
  into slots; one action bar holding Leave (and, at the end, Rematch and New opponent); the result card slot holding
  today's result content; the announcer; `data-cc-phase` and `data-cc-request` kept.
- Out: the series history and dots (CC-161), the fixed-height layout, board sizing, the sticky mobile bar and the
  bottom sheet (CC-172), moving each game's own pieces into slots (CC-166, CC-167, CC-168), turn timers (CC-165),
  outcome moments and the reward queue (CC-163, CC-099), emotes (CC-169).

## Plan / notes

### The contract (proposed)

The registry entry grows optional fields. All are pure functions of the RoomView or components that receive it.

```js
/**
 * @typedef {Object} GameViewEntry                    (games/registry.js)
 * @property {ComponentType} [Options]                lobby form (today)
 * @property {ComponentType<BoardProps>} [Board]      the board, in the stage slot (today)
 * @property {(prev, next, you) => string[]} [soundsFor]          (today)
 * @property {(reason: string) => string} [reasonPhrase]          (today, CC-162)
 * @property {Record<string, RequestTexts>} [requestTexts]        (#67, CC-159)
 * @property {(room) => GameAction[]} [actions]       buttons for the action bar while playing (chess: Offer draw, Resign)
 * @property {(room) => InGameScore | undefined} [inGameScore]   score inside one game, for the match bar (RPS rounds)
 * @property {ComponentType<{ room }>} [Panel]        the side panel (chess moves, RPS rounds), under the board on a phone
 * @property {(room, playerId) => SeatClock | undefined} [clockFor]  a clock beside a player (chess), CC-165 later
 * @property {"square" | "content"} [fit]            how the stage sizes the board (CC-172): square boards get min(width, height)
 */

/** @typedef {{ id: string, label: string, control: string, reason: string,
 *   intent: { type: "move", move: unknown } | { type: "ask", requestType: string },
 *   confirm?: { title: string, body: string, confirmLabel: string, keepLabel: string },
 *   variant?: "secondary" | "ghost" }} GameAction */

/** @typedef {{ room: RoomView, onMove, onAsk, reason: string }} BoardProps   (as today plus #67's onAsk) */
```

`actions` returns data, not buttons, so the shell renders every action the same way (ADR-038 states, a confirm
dialog instead of chess's own resign `Modal`, the same disabled reason) and the action bar can cap at four (BGA).

### Tests

- Unit: the slot picker (which slots a phase shows: waiting, my-turn, their-turn, finished, watching), the action
  list (game actions plus shell actions, reasons, the cap of four), an action's intent turned into `onMove`/`onAsk`.
- Component, with a fake game entry (fakes over mocks, ENGINEERING.md): a `Board`-only game renders and plays; a game
  with `actions` gets them in the bar with their reasons; a confirm action opens the shell's dialog; the result slot
  shows Rematch first; the banner never moves focus.
- Contract test kit for the web side, like `@classicade/games/testing` on the server: every entry in `GAME_VIEWS`
  passes the same checks (actions have controls and reasons, `inGameScore` is pure).
- Browser: `match-shell.spec.js` unchanged and green; `requests.spec.js` and `rematch.spec.js` green.

### Risks

- #67 is large (about 12,800 diff lines) and still open; starting before it merges means conflicts in `RoomPage`,
  `RematchPanel`, `Seats` and the registry. Mitigation: wait for #67.
- The browser suite is near its time budget (CC-236, #67 needs 35 minutes). The shell must not add new e2e files;
  it reuses the state builders in `e2e/matchStates.js`.
- Two results on screen for chess (`GameOver` and the room result) until CC-168. Acceptable for one or two PRs.
- A contract that is too wide too early. Mitigation: only fields a current game needs; Ludo adds its own later.

### Owner decisions

1. Start CC-157 only after #67 merges (recommended), or in parallel on top of the #67 branch.
2. The PR order above, with CC-172's frame before the three game moves.
3. Game actions are data (`actions(room)`) rendered by the shell, with the shell's confirm dialog replacing chess's
   own resign modal (recommended), or games render their own buttons into the action bar.
4. Shell animations in CSS keyframes, not Motion, so RPS and TTT stay Motion free (recommended; ADR-016's
   amendment says Motion is the only animation library, and CSS was already allowed by ADR-012).
