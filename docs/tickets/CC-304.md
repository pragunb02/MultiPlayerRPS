## Research (written before any code)

### 1. How our code does it today

1. `models/playerIdShape.js` `hasPlayerIdShape(value)` is true for any string that starts with `guest_`, `user_`,
   `bot_` or `deleted_`. `domain/identity/idShapes.js` `renameIdShapes` runs it over every value and key of a room
   view (`roomComponent.withSeatIds`) and of a match history answer (`matchComponent`, CC-297), after the players it
   knows about are renamed, and replaces every hit with a keyed id (ADR-057.5).
2. Match history runs the last pass over the whole answer, so `players[].displayName` goes through it. A room view
   runs it over the parts that come from the game and the room's records (`game`, `requests`, `series`,
   `fairness`), while `seats[].displayName`, `names` in a request push and `rematch.leftName` are built beside it.
   `createIdentity` allows any `[A-Za-z0-9_-]{3,24}` name, and `parseUsername` (`models/credentials.js`) allows
   `user_bob` and `deleted_bob` today (`isReservedName` already refuses `guest_bob` and `bot_bob`, through the words
   "guest" and "bot", not through the prefix). So an opponent called `user_bob` is shown as a 22 character hash in
   match history, and any text in a room view's renamed parts that starts like an id (a game's own view that shows
   a name, for example) is turned into a hash too. Checked on `main`: the seat's own name in a room view is shown as
   typed today, and the new room test that puts `user_bob` in a game's view fails.
3. The real grammars exist, but in three places: `models/identity.js` has `guest_<36 of [0-9a-f-]>` and
   `user_<24 hex>` (private `ID_PATTERNS`), `models/botIdentity.js` builds `bot_<character>_<level>` from
   `BOT_CHARACTERS`, and `models/deletedPlayer.js` builds `deleted_<randomUUID()>`. The prefixes are exported from
   those three files, and `playerIdShape.js` imports them.
4. Existing names. Accounts are never re-validated on read: `identityOf` in `accountComponent.js` hands the stored
   username to `createIdentity`, which checks the shape only. Legacy names (CC-078) are cleaned by `normaliseLegacyUsername`
   once, when the new account is made, and a name `isReservedName` refuses becomes `Player_<n>` (CC-119). CC-185 is
   the open ticket for accounts already made under older rules: a one-off report, then a rename prompt once profiles
   can be edited. It changes nothing on read.

### 2. How other products do it

1. Stripe gives every object id a type prefix and a fixed body (`ch_3MmlLrLkdIwHu7ix0snN0B15`, `txn_…`, `card_…`,
   https://docs.stripe.com/api/charges/object, read 2026-10-20). Free text fields such as `description` are never
   taken for ids, because code that reads an id knows which field it is in. A prefix alone names the kind of an id,
   not that a string is one.
2. ADR-022 (CC-119) already reserves names that pass as staff, a bot or a game, which is the same idea as reserving
   names that pass as one of our ids.

### 3. What is best for ClassiCade

Two guards, each enough alone for the bug, together closing it from both sides:

1. The last pass matches a whole id, not a prefix: the exact grammar of each of the four kinds. A display name
   that is not an id stays as it is. A real id in a field nobody listed is still renamed, so ADR-057.5 still fails
   closed for every id we make.
2. No new name can start with a player id prefix, in any case (`User_bob` too). Then no new name can ever match a
   grammar, even one that changes later. Existing accounts keep their names (CC-185 handles names that break newer
   rules). A legacy name that starts with a prefix becomes `Player_<n>` when its account is made, as every other
   reserved legacy name does (CC-119).

## Root cause

`hasPlayerIdShape` checked the prefix only, and the name rules never reserved the prefixes, so a chosen name and an
id could look the same to the last pass.

## Design

1. `models/playerIdShape.js` is the one module for every id kind's prefix and pattern: `GUEST_ID_PREFIX`,
   `ACCOUNT_ID_PREFIX`, `BOT_ID_PREFIX`, `DELETED_ID_PREFIX`, `PLAYER_ID_PREFIXES` and `PLAYER_ID_PATTERNS` (guest,
   user, bot, deleted). `identity.js`, `botIdentity.js` and `deletedPlayer.js` import from it and re-export their
   prefixes, so their importers do not change.
2. Patterns: guest `^guest_[0-9a-f-]{36}$` and user `^user_[0-9a-f]{24}$` (unchanged, now shared with
   `createIdentity`, which still accepts only those two kinds). Bot: `^bot_(?:<character>_<level>|…)$`, every pair
   in `BOT_CHARACTERS`, which is exactly what `botIdentity` can make. Deleted: `^deleted_<uuid>$`, a lowercase
   8-4-4-4-12 hex UUID, which is what `randomUUID` gives.
3. `hasPlayerIdShape` is true when any pattern matches the whole string.
4. `isReservedName` also refuses a name whose lowercase form starts with any of `PLAYER_ID_PREFIXES`. So
   `parseUsername` (sign-up), `normaliseLegacyUsername` (legacy accounts) and the guest name check all refuse it with
   the existing kind message.
5. ADR-057 point 5 gains a dated amendment: the last pass matches whole ids, and names cannot start with a prefix.

## Scope

- In: the id grammar, the reserved prefixes, tests, ADR-057 amendment.
- Out: renaming accounts that already have such a name (CC-185). Tightening the guest pattern to an exact UUID (it
  is what `createIdentity` accepts for sessions, so it stays as it is).

## Acceptance criteria

- [x] An opponent named `user_bob` keeps that name in a room view (its seat, the request push, and text in a
      game's view) and in match history, and a real id in the same answer is still renamed.
- [x] `hasPlayerIdShape` is true for every id kind's real shape and false for names that only start like one.
- [x] `parseUsername` refuses `user_bob`, `User_Bob`, `guest_x`, `bot_x` and `deleted_x`. A legacy name that would
      start with a prefix becomes `Player_<n>`. Existing accounts are not re-checked.
- [x] Tests failed before the fix.
- [x] Docs: this file, ADR-057 amended.
