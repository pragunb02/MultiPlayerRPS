## Research (written before any code)

### 1. How our code does it today

Read on 2026-10-18 at `origin/main` 61b3bb2.

1. **Email normalisation.** `parseEmail` (`models/credentials.js`) trims and lower-cases the whole address, then checks
   a loose shape (`[^\s@]+@[^\s@]+\.[^\s@]+`, at most 254 characters). There is no Unicode normalisation. So
   `josé@example.com` typed with a composed `é` (NFC) and with `e` plus a combining accent (NFD) are two different
   accounts, and so are `riya@example.com` and `ｒｉｙａ@example.com` (full-width letters, which phone keyboards
   in some languages produce). Invisible characters such as a zero-width space are accepted inside the address.
2. **The login throttle normalises separately.** `authRoutes.js` has its own `normalisedEmail` (trim and lower-case)
   for the per-email failure counts of CC-117. Today it matches `parseEmail`, but nothing keeps the two the same:
   once `parseEmail` normalises more, a second spelling of one email would get its own failure budget.
3. **Accounts.** `accountDao.js` stores the normalised email with a unique index on `email`, and the username as
   typed plus a unique `usernameKey` (lower-cased). Usernames are ASCII `[A-Za-z0-9_]{3,20}` only, so there are no
   Unicode look-alikes. CC-119 already reads leetspeak and separators for reserved and rude names.
4. **Indexes in production.** `server.js` awaits `ensureIndexes()` on every DAO at boot, which runs Mongoose
   `syncIndexes()`: it builds the indexes the schema declares and drops any others. If the unique index cannot be
   built (for example because duplicates already exist) boot fails, so a running server always has them. No test
   reads the indexes back from MongoDB, and no test sends two sign-ups with the same email at the same moment to
   the real database.
5. **Legacy players (CC-078).** `legacyUserDao.getByEmail` runs `findOne` with a case-insensitive regex
   `^<email>$`. The old app stored emails exactly as typed until CC-003 (`git show 361c32d~1:client/routes/auth.js`:
   no trim, no lower-case, no format check, and the unique index compared exact strings). So:
   1. Two legacy rows can differ only in case (`Sam@x.com` and `sam@x.com`). `findOne` returns one of them, and
      the other player can never log in.
   2. A legacy row can have spaces around the email. The regex does not match it, so the sign-up check misses it:
      anyone can sign up with that email, and then the legacy player can never claim their account.
   3. A legacy email in another Unicode form cannot be matched by a MongoDB query at all (MongoDB cannot
      normalise Unicode inside a query).
6. **Login answers.** One message, "Invalid email or password", for every failure. For an unknown email the server
   runs `verifyAgainstDummy` (one scrypt). But the work differs by case:
   1. An account's email: one indexed read and one scrypt.
   2. An unknown email: one indexed read, one full scan of the legacy `users` collection (a case-insensitive regex
      cannot use an index), and one scrypt.
   3. A legacy email not yet migrated, with a wrong password: the same two reads and one bcrypt at cost 10 instead
      of a scrypt.
      So the response time can tell an account's email, a legacy player's email and an unknown email apart.
7. **Sign-up answers.** Hash first (CC-118), then the legacy check, then the insert. Both an account's email and a
   legacy email answer 409 "That email can't be used" on `details.field: "email"`. The same string is written in
   two places (`accountComponent.js` and `accountAccessor.js`). The page shows it under the email field and offers
   nothing else: that is the dead end of CC-238.
8. **Double submit.** `useAction` (CC-164) runs one press at a time, so a double click sends one request. If two do
   reach the server (two tabs, a retry), the unique index lets one through and the other gets the 409.
9. **Guest to account (ADR-014).** `player_transfers` has a unique `from`, every participant is safe to run twice,
   and `guestCarryOver.test.js` already races two logins from one guest session. Two sign-ups racing from one guest
   session is not tested.
10. **Password messages.** Changing the password needs a signed-in session and says "That is not your current
    password", which tells nothing about other people. There is no password reset yet (CC-033).

### 2. How others do it

1. **Not revealing who has an account.** OWASP Authentication Cheat Sheet, section "Authentication Responses"
   (read 2026-10-18,
   <https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html>): login, recovery and account
   creation answer with one generic message whether or not the account exists. For account creation the correct
   example is "A link to activate your account has been emailed to the address provided." The same section warns
   that a quick exit for unknown users makes the response time differ, and says the code should "go through the
   same process no matter what the user or the password is". The Forgot Password Cheat Sheet (same date,
   <https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html>) asks for "a consistent message
   for both existent and non-existent accounts" and a uniform response time, by following the same logic path.
   The OWASP testing guide (WSTG-IDNT-04, account enumeration) tests exactly these answers and timings.
2. **The usual sign-up pattern without email.** A site that cannot send email yet cannot say "check your inbox".
   The common middle ground is one message for every unavailable email that points the real owner somewhere useful:
   "That email can't be used. If it's yours, log in or reset your password." It still says the email is unavailable,
   so it slows enumeration (with rate limits) rather than stopping it. The full fix is the email-first flow: answer
   "check your email" to every valid sign-up, and the email says either "confirm your account" or "someone tried to
   sign up with your address". That needs CC-033.
3. **Same work either way.** The standard trick is to run the same password check against a dummy hash when there
   is no account (we do this for scrypt). When two hash formats exist (our bcrypt legacy rows), the same idea means
   every path runs one of each, and every path does the same reads.
4. **Email comparison.** OWASP Email Validation and Verification Cheat Sheet (read 2026-10-18,
   <https://cheatsheetseries.owasp.org/cheatsheets/Email_Validation_and_Verification_Cheat_Sheet.html>): lower-case
   the domain, normalise Unicode input, apply one comparison policy across registration, login and every other
   flow, and avoid provider-specific rules such as Gmail dot removal. RFC 5321 §2.4 says the local part may be case
   sensitive, but in practice the large providers (Gmail, Outlook, Yahoo, iCloud) are not, and almost every
   consumer site treats `Riya@x.com` and `riya@x.com` as one person. RFC 8264/8265 (PRECIS, the IETF rules for
   comparing user names) map full-width characters to their normal width, map case, and normalise to one Unicode
   form, and they disallow control and invisible formatting characters. Unicode NFKC does the width mapping and
   the composition in one step.
5. **Gmail dots and plus.** Gmail ignores dots in the local part and delivers `riya+games@gmail.com` to `riya`.
   Most sites do not normalise either, because:
   1. It is true only for some providers. Other providers treat dots as real (`a.b@` and `ab@` are different
      people), and some use `-` or nothing at all for sub-addresses. A rule written for Gmail merges different
      people elsewhere.
   2. Google Workspace domains (any company domain) follow Gmail's rules, and nobody can tell from the address.
   3. A plus address is often how a person keeps one account per site or tells two accounts apart on purpose, for
      example a parent signing up two children with `parent+a@` and `parent+b@`.
   4. What it would block is someone making many accounts from one mailbox. That only matters when email is
      verified and accounts are scarce (free trials). We do not verify email yet, so anyone can type any address
      anyway.

### 3. What is best for ClassiCade

1. **One normaliser, used everywhere an email is compared:** trim, Unicode NFKC, lower-case the whole address, NFKC
   again (lower-casing can in rare cases leave a form NFKC would change). Refuse control, invisible formatting and
   unassigned characters (`\p{C}`) as "Enter a valid email address". Lower-casing the whole address, not only the
   domain, because our players use consumer mailboxes, two accounts for `Riya@` and `riya@` would only confuse
   them, and the old app did the same. The login throttle uses the same function.
2. **No Gmail dot or plus folding,** for the reasons above. Revisit only if email verification (CC-033) makes
   accounts worth farming.
3. **Usernames:** keep uniqueness case-insensitive and ASCII-only. Do not fold ASCII look-alikes (`l`/`I`/`1`,
   `O`/`0`, `rn`/`m`) for uniqueness. GitHub, Reddit and Discord do not either, it would refuse many ordinary names,
   and CC-119 already folds them where it matters (reserved staff, bot and game names).
4. **Legacy lookups match the way accounts do, as far as a read-only collection allows:** ignore case and spaces
   around the stored email, and return every matching row, so the login checks the password against each and
   migrates the one it opens. Unicode forms in legacy rows cannot be matched in a query. Since the old app took
   any text, we write that down with a read-only query the owner can run to count such rows (see Plan).
5. **Login does the same work in every case:** read both the account and the legacy row at the same time, then run
   exactly one scrypt and one bcrypt (cost 10, the old app's cost) whatever the case, with a dummy hash where a real
   one is missing. This costs one bcrypt (tens of milliseconds) per login, which the login limits make cheap.
6. **Sign-up keeps one message for every unavailable email** (CC-238), defined once in `@classicade/shared`, and the
   page turns "log in" into a link to `/login` that keeps `next`. The email never goes in a URL. "Reset your
   password" stays plain text until CC-033 builds it.
7. **Tests that fail first** for every gap, plus tests that pin what already works: the unique indexes read back
   from MongoDB, two sign-ups with one email at the same moment against the real database, a double-clicked submit,
   and two sign-ups racing from one guest session.

## Why

Sign-up refuses an email held by a legacy player or an account with one message ("That email can't be used", `accountComponent.js`, `accountAccessor.js`), and login answers the same for an unknown email and a wrong password. Nobody has checked every way two identities can collide or one can be claimed twice. Security, so P0 by default; P1 while the security batch (CC-107, #57) is in progress.

## Scope

- In: how emails are normalised (case, spaces, Unicode forms; decide on Gmail dots and plus) and whether legacy emails get the same normalisation; usernames (case, look-alikes from CC-119); unique indexes; two sign-ups with the same email at the same moment; a double-clicked submit; a guest moving to an account exactly once; every message checked for leaking who has an account.
- Out: email verification (a separate ticket if needed).

2. **Two sign-ups at the same moment.** One is stored and the other gets `DuplicateKey` on the right field, for the

4. **A guest moves to an account exactly once.** Existing tests already cover a repeated transfer and two racing

5. **Usernames.** Case-insensitive through `usernameKey`, ASCII only, so no Unicode look-alikes. ASCII look-alikes

## Plan / notes

1. **Still open, written down on purpose.**
   1. SEC-17 stays partly open: sign-up still says an email can't be used. The full fix is the email-first sign-up
      of CC-033.
   2. A legacy email stored in a Unicode form NFKC would change (for example full-width letters) cannot be matched,
      because MongoDB cannot normalise inside a query. The owner can count such rows with the read-only query below.
      If there are any, a small follow-up can match them in memory.
   3. **Known limit, legacy case twins (for KNOWN_ISSUES with BUG-30).** One address gets one account. A login
      checks one twin row, the one written in the capitals the player types, else the oldest, so a twin who types
      their old capitals can claim theirs. Once either twin has the account, the other row cannot be opened any
      more, because the address now belongs to an account whose password is the first twin's. Reasons: twins are
      almost always one person who signed up twice before the old app lower-cased emails. A second account for the
      same address would break the rule every other duplicate check rests on (one address, one account). Checking
      every row would cost one bcrypt per row and bring back the timing leak SEC-20 closes. A second twin who is
      really a different person can be helped by hand, and by password reset once CC-033 exists.
   4. Every login now spends one bcrypt at cost 10 more than before for accounts (about 50 to 100 ms of CPU, run
      at the same time as the scrypt). The login limits keep that small.
   5. **The legacy read on every login.** Every login reads the legacy `users` collection with a case-insensitive
      regex, which cannot use an index, so MongoDB scans the collection. It cannot get an indexed key: the
      collection is read-only by design (CC-078), and building an index on it would change it. The old app was a
      small project and its collection is frozen, so it is expected to hold hundreds of rows, at most a few
      thousand. A scan of that size takes about a millisecond, well inside the hash time. The owner can confirm the
      size with the read-only `db.users.estimatedDocumentCount()`. If it is ever large, the fix is a list of
      normalised legacy emails read once at boot.
   6. **A failing legacy read.** The legacy store is needed only for an email without an account. When it fails, an
      account's login goes on as usual, and any other login answers the usual 401 after the usual work, so the
      failure tells nothing about the email. The login route logs the failure as an error, without the email, so
      it is not missed. Sign-up still fails closed (500) when the legacy check cannot run, because it must never
      hand out a legacy player's email.
2. **Existing accounts.** Normalisation only changes text that is not plain ASCII. An account stored before this
   change with such an email would no longer be found at login. Read-only checks for the owner to run against
   production before merging (both should print 0):

   ```js
   // mongosh, read-only. Accounts whose stored email is not in today's one spelling.
   db.accounts
     .find({}, { email: 1 })
     .toArray()
     .filter(
       (a) =>
         a.email !== a.email.normalize("NFKC").trim().toLowerCase().normalize("NFKC") ||
         /\p{C}/u.test(a.email),
     ).length;
   // Legacy rows whose email changes under NFKC, so the lookup cannot find them.
   db.users
     .find({}, { email: 1 })
     .toArray()
     .filter(
       (u) =>
         typeof u.email === "string" &&
         u.email.trim().toLowerCase() !== u.email.normalize("NFKC").trim().toLowerCase(),
     ).length;
   ```

3. `createLegacyPasswordChecker` replaces `verifyLegacyPassword` and is passed into the account component, so tests
   use a cheap dummy hash (cost 4) and production uses the old app's cost 10. The dummy is made at the first login
   that needs it, so boot does not wait for it.
