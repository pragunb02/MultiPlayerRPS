## Research (added 2026-10-19, after the work, for the Social and sharing domain)

This ticket was built before the working agreement's rule 4 (research first), so this note is written afterwards.
The leaderboards are a social surface of [the Social and sharing domain](../domains/SOCIAL_AND_SHARING.md); how
scores are computed stays with Progression.

1. **Our code today.** `leaderboardComponent.js` serves the public boards (accounts only, ADR-015). Since CC-152 a
   name is shown only for an adult and is "Hidden player" for everyone else, worked out when the board is read
   (`accountComponent.adultsAmong`, ADR-048.10). The ADR-029 fallback for a tab with fewer than 25 entries ("Your
   week") is not built yet (CC-228). The weekly reset is still 00:00 UTC until CC-146 (ADR-015 amendment).
2. **Others.** Lichess and Chess.com show public leaderboards of usernames for adults' and children's accounts
   alike, with a kid mode or a separate children's site (ChessKid) for the youngest (general knowledge, medium
   confidence; Lichess kid mode in `modules/core/src/main/user.scala`, https://github.com/lichess-org/lila, read
   2026-10-19). Telegram posts a game's high scores into the chat it was shared in
   (https://core.telegram.org/bots/games, cited in PRODUCT_VISION.md §4.6), the model for a circle board.
3. **Best for ClassiCade.** Keep the public boards with hidden names for minors and unknown ages. The social value
   comes from boards of people you know: the friends filter (CC-140) and the circle board (CC-214), each behind its
   ADR-029 gate.

## Why

Players need a reason to come back and a sense of status. An all-time board is out of reach for new players, so
there is also a weekly board that resets every Monday, and one board per game. Guests are invited to sign up to get
on the boards (the "play first, then save your progress" nudge).

## Scope

- In:
  - Public catalog `LEADERBOARDS` in `@classicade/shared` (`overall`, `weekly`, one wins board per game in `GAMES`).
  - Server: `leaderboard_entries` collection (DAO + in-memory twin + shared contract), `leaderboardAccessor`,
    `leaderboardComponent` (pure `isoWeek`, `boards`), `matchDao.countWins`, `isAccountId`,
    `GET /api/leaderboards` and `GET /api/leaderboards/:boardId?limit=` (public, rate-limited), match pipeline
    step after progression and gamification (it runs even when gamification failed, on the match as followed to
    the account, and shows the latest XP/level so quest bonuses from the same match never lower it), a subscription for quest bonus XP (`PROGRESSION_EVENTS.UPDATED` with
    `source: "quest"`, CC-089), and `transferPlayer` for ADR-014 — wired last in the player-transfer participants
    (composition root and `testApp`).
  - Web: `/leaderboards/:board` (tabs are links, one URL per board; `/leaderboards` → `/leaderboards/overall`,
    replace; unknown boards are "Page not found"), header link "Leaderboards", "Your rank" card on the profile.
- Out:
  - Seasons, per-opponent caps on wins (farming), friends-only boards (future tickets).

## ADR-015 — accepted, see DECISIONS.md — Leaderboards and rematch

**Context.** We need global, per-game and weekly leaderboards (FR-PROG-3) that stay correct when a match is applied
twice, when quest XP arrives outside matches, and when a guest's data moves to an account (ADR-014).

**Decision.**

1. **Accounts only.** Entries are written only for `user_…` ids (`isAccountId`). Guest XP is never stored on a board;
   it reaches the boards through the account once the guest signs up.
2. **One collection, keyed by board and period**: `leaderboard_entries { board: "xp" | "wins:<gameId>", period:
"all" | "2026-W42", playerId, displayName, level, score, recentKeys, updatedAt, expiresAt? }`. Unique
   `{board, period, playerId}`; list index `{board, period, score: -1, updatedAt: 1, playerId: 1}` (the player id
   makes the order total, so the index serves the sort); TTL on `expiresAt` (weekly entries: week end + 28 days).
3. **Two idempotent writes only.**
   - `raiseScore` for totals (overall XP from the player's progress, wins per game from `matchDao.countWins`): the
     score only rises, `updatedAt` changes only when it does. Re-applying a total is a no-op; it also self-heals:
     wins before this feature count as soon as the player wins again.
   - `addOnce` for this week's XP, keyed by match id or quest key (last 200 keys remembered, like progress).
4. **Ranks**: list position for the top entries; "your rank" = entries ahead of yours + 1, using the same order
   (higher score; on a tie, earlier `updatedAt`; then lower player id). The brief said "number with a higher score +
   1" — that would disagree with the tie-broken list, so the list's order is used for both.
5. **Board ids are URL slugs** generated from `GAMES` (a new game gets a board with no code changes); the catalog
   lives in `@classicade/shared`, so the web app renders tabs without a request and paths can validate.
6. **Public endpoints** with their own rate limit (120/min per IP, raised for browser tests like the other limits).
7. **Rematch** (CC-037) is a transition inside the room state machine: `finished → playing` in the same room code,
   new match id and seed, same options, seats reversed. The room keeps `rematch { requestedBy, available }` and a
   `series { games, wins }`. See `docs/tickets/CC-037.md`.

**Consequences.** Weekly scores are kept for four weeks for history; older ones vanish via TTL. A player's weekly
score after a guest transfer is recomputed from this week's matches (scores only rise, so quest XP already on the
weekly entry is not lost, but a guest's quest XP from this week is not added). Leaderboards trust progression for
XP; if progression is ever recomputed downwards, boards keep the higher value until a dedicated rebuild job exists.

## Plan / notes

- Pipeline order: `recordFinished → (A: follow) → progression.applyMatch → (B: gamification) →
leaderboards.applyMatch({ match, updates })`. Only updates progression actually applied are used, so a match
  applied twice changes nothing.
- Medal and highlight colours use the CC-087 tokens with fallbacks to today's tokens
  (`var(--color-tier-gold, var(--color-warning))`), so the page restyles itself once the arcade theme lands.
  Contrast (AA) with the fallbacks: white on `#a35b00` 5.2:1, white on `#c4314b` 5.4:1, white on `#5c6077` 6.5:1;
  dark theme `#0f1020` on `#ffb547` 10.7:1, on `#ff7a90` 7.5:1, on `#a3a7c2` 7.8:1.
- Found along the way: the server could not serve `index.html` when the web build lives under a hidden directory
  (`res.sendFile` with an absolute path refuses dot-segments). Fixed on `main` by another workstream; this branch
  uses that fix (its own copy was dropped in the rebase).
