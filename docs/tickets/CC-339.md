## Problem

`e2e/friends.spec.js:52` failed in CI on the CC-333 branch (desktop + mobile, part 1 of 4): Arjun never saw
"<riya> wants to be your friend" after Riya clicked Add friend on the result screen.

### Root cause

A race in the test, not in the app. Arjun opens `/leaderboards` with a full page load, which ends his realtime
connection, and Playwright's `goto` returns at the page's `load` event. His new page connects again a little after
that (the session answer, then the socket). Riya clicks Add friend at once. The server sends the friend request
push to Arjun's player channel (`friendPushes.js`) while his browser has no socket in it, so it reaches nobody, and
the toast (`FriendRequestToasts.jsx`) only shows a push. The realtime client of CC-333 kept the subscription and
connected as designed: the subscription was attached before connect, Socket.IO was downloaded, and no reconnect
dropped a handler. It fails on `main` from before CC-333 just the same once the browser is slow, as on a CI machine
running the chess press tests beside it.

## Fix

The spec waits for Arjun's browser to be connected again (Socket.IO's "connected" packet) before Riya sends the
request. Counting those packets moved from `restart.spec.js` into `e2e/realtime.js`, with a unit test, so both
specs use it. No retries, no longer timeouts.

### Research

How our code does it: `restart.spec.js` already waits for each browser's "connected" packet to count up after a
restart (CC-101), and `gateway.js` joins a socket to its player channel in the same tick as it accepts the
connection, so once the packet arrives a push to the player reaches the page. Socket.IO's own documentation says a
packet sent to a room reaches only the sockets in that room when it is sent, with no buffering for clients that
connect later (socket.io/docs/v4/rooms and /docs/v4/delivery-guarantees: "at most once" by default). A player who
gets a request while no page of theirs is connected still sees it on the friends page, which loads the requests.

Measured on this machine, desktop project, `--workers=1`, Arjun's CPU throttled with
`Emulation.setCPUThrottlingRate` to stand in for a busy CI machine (the throttle was a temporary probe, not
committed):

| Build                           | No throttling | 3x          | 6x          |
| ------------------------------- | ------------- | ----------- | ----------- |
| `main` before CC-333 (df8710f4) | 5 of 5 pass   | 4 of 5 pass | 0 of 5 pass |
| CC-333 branch (ca339d20)        | 5 of 5 pass   | 3 of 5 pass | 0 of 3 pass |
| CC-333 branch with this fix     | 30 of 30 pass | 5 of 5 pass | 5 of 5 pass |

At 3x, Arjun's WebSocket opened 103 to 179 ms after his navigation started on old `main` and 138 to 168 ms on the
CC-333 branch, so the lazy socket did not make the window noticeably wider. Each failure had Riya's request sent
before Arjun's socket opened, and no friends frame reached Arjun afterwards.

## Acceptance criteria

- **AC-1** Given Arjun has just opened a new page, when Riya sends him a friend request, then the spec sends it only
  after Arjun's browser is connected again, and he sees the request, also with his CPU throttled 6x.

## Test

`e2e/realtime.test.js` failed first (no `realtime.js`), then passed. The friends spec failed at line 65 with Arjun's
CPU throttled before the fix (table above) and passes after it; the before and after runs at `--repeat-each=10` are
in the pull request.
