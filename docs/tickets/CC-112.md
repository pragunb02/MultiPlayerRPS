## Research (written before any code)

### 1. How our code does it today

1. `roomComponent.joinRoom` (`apps/server/src/domain/rooms/roomComponent.js`) seats the joiner and starts the game
   the moment the last seat is taken: `seated.seats.length === engine.players.max ? start(seated, now) : seated`.
   It never looks at `seat.connected`. All our games have two seats, so a waiting room always holds just its host.
2. The host's seat says `connected: false` only after their socket closes (`playerDisconnected` from the gateway's
   `disconnect` handler) or after a restart (`markEveryoneAway`). It stays `connected: true` while the host is on
   another page of the site, because the single-page app keeps the socket open.
3. `apps/web/src/hooks/useRoom.js` joins on mount and does nothing on unmount ("Leaving the page does not leave the
   room"). So a host who opens the room, copies the link and goes back to the home page still holds a seat that
   looks connected.
4. Together that is BUG-17. A friend opens the link a minute later and the game starts at once: chess clocks run,
   Rock Paper Scissors waits for a choice from someone who is not there. With CC-036 (not merged) an idle game
   ends as abandoned, but the friend still met a dead game.
5. The seat follows a guest who signs in (CC-083): the guest goes to `/signup?next=<room>` and comes back to the
   same room with their account. `e2e/guest.spec.js` pins that journey, so "leave on unmount" must not break it.
6. A reload does not unmount React components. The socket closes and the seat shows as disconnected, which is the
   honest state, and the player rejoins on the next connect.

### 2. How others do it

1. Lichess, Board API "Create a seek" (read 2026-10-18, `lichess-org/api` spec `api-board-seek.yaml`): "Keep the
   connection open to keep the seek active. If the client closes the connection, the seek is canceled. This way,
   if the client terminates, the user won't be paired in a game they wouldn't play."
2. Lichess, "Create a challenge" (same spec, `api-challenge-username.yaml`): a real time challenge expires after
   20 s unless the challenger keeps a stream open (`keepAliveStream`), and is kept alive "until the connection is
   closed by the client".
3. Both rules say the same thing: an offer to play is only open while the person who made it is present, and a
   game is never started for someone who has gone.
4. React, "Synchronizing with Effects" (react.dev, read 2026-10-18): the cleanup of an effect is where a component
   stops what it started, and in development Strict Mode mounts, cleans up and mounts again once. Our app runs in
   `<StrictMode>`, so the cleanup must be safe to run before the join was answered.

### 3. What is best for ClassiCade

1. **Server, the rule that matters.** A game starts only when every seat is taken **and** every seated player is
   connected. A joiner who finds the host away is seated and waits. The game starts the moment the host comes back
   (their `joinRoom` as a seated player), or the joiner can leave. Nobody else can join a full waiting room
   ("This room is full"). The rule lives in one small function, so the presence work in CC-207 can swap
   "connected" for its own "here" without touching the callers.
2. **Web, the page tells the truth.** When the waiting room is full but someone is away, the room page says who
   is away and that the game starts when they come back, instead of "Invite a friend".
3. **Web, leaving the page leaves a waiting room.** When the room page unmounts while the viewer holds a seat in a
   waiting room, `useRoom` sends `room:leave`. A game in progress or a finished game keeps its seat (CC-207 makes
   those "away"). Two exceptions keep existing journeys: the page you go to is this same room (a legacy or
   differently spelled link), or it is the log in or sign up page with `next` pointing back at this room (CC-083,
   the seat follows the new account). The cleanup reads the address bar, which the router has already changed
   when the old page unmounts.
4. Why both halves: the server rule alone does not help while the host's socket stays open on another page, and
   leaving on unmount alone does not help when the host closed the tab (no unmount runs). Together the game only
   starts with everyone there.
5. Constraints: one instance, rooms in MongoDB (ADR-017), so the rule is part of the stored room's state machine
   and survives a restart (after a restart everyone is away until they reconnect, so nothing starts by itself).

## Why

A friend who opens an invite should never land in a game against someone who has already gone.

## Scope

- In: the start rule in `roomComponent` (join and reconnect), "room is full" for a third player, the waiting
  card on the room page, leaving a waiting room when the room page unmounts (with the two exceptions), tests.
- Out: away and offline presence for running and finished games (CC-207), idle game deadlines (CC-036).

## Acceptance criteria

- [ ] A player who joins while the host is disconnected is seated, and the game does not start
- [ ] The game starts when the host reconnects, and a third player is refused
- [ ] The room page says the host is away while it waits
- [ ] Leaving the room page leaves a waiting room, but not on the way to sign in or sign up and back
- [ ] Tests cover the change, each fix with a test that failed first
- [ ] `npm run lint`, `npm run format:check`, `npm test` pass

## Plan / notes

1. Overlap with PR #67 (CC-207, not merged): it rewrites `joinRoom`'s seat shape and the `useRoom` unmount (it
   sends `room:away`). This change keeps to a new helper and one line in `joinRoom`, and a separate effect in
   `useRoom`. After both merge, a waiting room on unmount should send `room:leave` and any other room `room:away`.
