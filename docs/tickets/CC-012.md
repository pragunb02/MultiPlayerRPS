## Why

Every later ticket throws errors and needs to log. Without one error vocabulary and one translation point, each
handler invents its own status codes and messages (the legacy app returns `299`, swallows errors, and leaks nothing
useful to logs). Logs must be structured, correlated per request, and never contain secrets or personal data.

## Scope

- In:
  - `@classicade/shared` `ERROR_CODES` — the error vocabulary the web app will also switch on.
  - `utils/errors.js` — `AppError` (abstract) + `ValidationError`, `UnauthorizedError`, `ForbiddenError`,
    `NotFoundError`, `ConflictError`; stable `code`, optional frozen `details`, `cause` chaining.
  - `utils/logger.js` — pino JSON logger, ISO timestamps, redaction of passwords/tokens/emails/cookies/auth headers.
  - `service/http/requestLogger.js` — request id (`X-Request-Id`, validated if supplied), per-request child logger,
    one access-log line per request with status, duration and error code.
  - `service/http/errorMiddleware.js` — the **single** translation point: typed errors → HTTP status + JSON body;
    body-parser errors → 400/413 with fixed messages; anything else → 500 with no internals; 5xx logged with stack.
  - Config: `LOG_LEVEL` (validated; default `info`, `silent` under `NODE_ENV=test`).
  - Composition root injects the logger; process-level `uncaughtException`/`unhandledRejection` logged as fatal → exit 1.
  - `no-console` enforced by ESLint in new server code.
- Out: socket error translation (CC-013), log shipping/metrics (CC-049).

## Acceptance criteria

- [x] Every error response has the shape `{ error: { code, message, requestId, details? } }`
- [x] Typed errors map to 400/401/403/404/409; malformed JSON → 400; oversized body → 413; unknown → 500 without internals
- [x] Responses carry `X-Request-Id`; a valid incoming id is propagated, a malformed one is replaced
- [x] One structured access-log line per request; 5xx also logs the error with stack and cause
- [x] Secrets and personal data are redacted from logs (proved by tests)
- [x] Invalid `LOG_LEVEL` fails boot; no `console` in new server code (lint)
- [x] Tests, lint, format, coverage, audit pass; server run for real

## Plan / notes

- Error classes carry a domain `code`, not an HTTP status — HTTP is a service-layer concern (ENGINEERING.md §1).
- `AppError` cannot be instantiated directly, so every thrown error has a known code (fail fast).
- Access log levels: 2xx/3xx `info`, 4xx `warn`, 5xx `error`.
