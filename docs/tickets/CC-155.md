## Research (written before any code)

### How our code does it today

- `e2e/visual.spec.js` (CC-087) checks the arcade look by **assertions only**: each themed screen renders in light
  and dark with art present, no CSP violation and no console error, celebrations play, and reduced motion stops
  them. Nothing compares pixels, so a broken layout, a wrong colour or a missing gap passes as long as the element
  is there. LOOK_AND_FEEL.md §6 puts CC-155 in step 1 "baselines before the polish so every later PR shows a diff".
- `e2e/playwright.config.js` already keeps a trace (`trace: "retain-on-failure"`) and a screenshot on failure, and
  `ci.yml` uploads `e2e/test-results/` for 14 days when a part fails. There is no video.
- The browser suites run in 4 parts per engine, about 8 minutes of machine time on the longest path (CC-236). They
  run on `ubuntu-latest` with whatever fonts the runner image has, and a Mac or a laptop has others.
- The app uses **system fonts only** (`--font-sans: system-ui, ...`, `--font-display: ui-rounded, ...` in
  `styles/tokens.css`), no web font. So the same page draws different glyphs on macOS, on an Ubuntu runner and on
  Ubuntu with other fonts installed. Any pixel baseline must come from one fixed set of fonts.
- Random or time-bound content on screens: guest names (`Guest-…`), test account names (`riya_<digits>`, from the
  clock), room codes and invite links, the daily quests (chosen by player and date), match dates in the history,
  chess clocks counting down, leaderboard rows (whoever played before in the same server) and toasts that leave on
  a timer.

### Playwright `toHaveScreenshot` (playwright.dev, read 2026-10-19, Playwright 1.64.1)

- `await expect(page).toHaveScreenshot(name, options)` takes screenshots until **two in a row are identical**, then
  compares the last with the stored image (docs/api/class-pageassertions). That waiting already absorbs fonts or
  images still loading.
- Defaults that help determinism: `animations: "disabled"` (finite CSS animations jump to their end, infinite ones
  are cancelled), `caret: "hide"`, `scale: "css"` (one image pixel per CSS pixel whatever the device pixel ratio, so a
  phone image is 390 px wide, not 1170).
- Tolerance: `threshold` (per-pixel colour distance, 0 to 1, default 0.2, pixelmatch), `maxDiffPixels` and
  `maxDiffPixelRatio` (how many pixels may differ, unset by default, meaning zero). All can be set in the config
  under `expect.toHaveScreenshot` (docs/api/class-testconfig).
- Dynamic content: `mask: [locator, ...]` paints those boxes in `maskColor` (default `#FF00FF`), and `stylePath`
  applies a stylesheet only while capturing ("filtering out dynamic or volatile elements, hence improving the
  screenshot determinism", docs/test-snapshots). Hover shows in screenshots, so the mouse is moved away first.
- Where baselines live: by default `<file>-snapshots/<name>-<project>-<platform>.png`. `snapshotPathTemplate` (or
  `expect.toHaveScreenshot.pathTemplate`) sets the path with tokens such as `{testDir}`, `{testFileName}`, `{arg}`,
  `{projectName}`, `{platform}` and `{ext}` (docs/api/class-testconfig).
- Updating: `--update-snapshots` with modes `all`, `changed`, `missing`, `none`. By default a missing image is
  written but **the test fails**, "so that the run does not silently pass in CI" (docs/api/class-testconfig).
- Across machines: "Screenshots differ between browsers and platforms due to different rendering, fonts and more",
  so "run tests in the same environment where the baseline screenshots were generated" (docs/test-snapshots).

### A fixed container (playwright.dev/docs/docker, read 2026-10-19)

- The official image is `mcr.microsoft.com/playwright:v<version>-<ubuntu>`, for example `v1.64.1-noble` (Ubuntu
  24.04). "It is recommended to always pin your Docker image to a specific version", and the image's browsers only
  match the same `@playwright/test` version.
- Run flags: `--ipc=host` for Chromium (otherwise it can run out of shared memory and crash) and `--init` (no zombie
  processes). It runs as root, which disables Chromium's sandbox, acceptable for tests against our own local server.
- GitHub Actions runs a job inside such an image with `container:` (docs.github.com, "Running jobs in a container",
  general knowledge, confidence high). The runner's own fonts then do not matter.
- CPU architecture also changes rasterisation slightly (Skia picks different SIMD paths). CI is x86_64; a builder on
  an Apple Silicon Mac must run the image as `linux/amd64` to make the same pixels (Playwright issue tracker, many
  reports of arm64 versus amd64 one-pixel antialiasing diffs, general knowledge, confidence medium). The CI job is
  therefore the source of truth, and the local script runs the same image and platform.

### How baselines are reviewed and updated elsewhere

- **Playwright's own guidance**: commit the images; run `--update-snapshots` on purpose and review the change in
  the pull request like code (docs/test-snapshots).
- **Workflow that commits the new images to the PR branch**: a `workflow_dispatch` (or a PR label) job runs
  `--update-snapshots` in the CI container and pushes a commit; the images then show in the PR's Files tab, where
  GitHub renders image diffs (2-up, swipe, onion skin), and a person approves the PR. Used widely in open source
  Playwright projects (general knowledge, confidence high). A label trigger runs on every label change and needs
  care with forks; `workflow_dispatch` can only be started by people with write access.
- A catch: "events triggered by the `GITHUB_TOKEN` will not create a new workflow run", except `workflow_dispatch`
  and `repository_dispatch` (docs.github.com, "GITHUB_TOKEN", read 2026-10-19). So the bot's commit does not run
  CI by itself, and the required checks wait. A person pushing the next commit (their approval) runs it.
- **Hosted review services**: Chromatic (Storybook), Percy (BrowserStack) and Argos keep baselines off the repo,
  show diffs in their own UI and gate the PR with a status. They charge per snapshot over a free tier (around 5,000
  snapshots a month free on each, chromatic.com/pricing, percy.io/pricing, argos-ci.com/pricing, general knowledge,
  confidence medium) and need an account and a secret. At about 50 images per run and many runs a day we would pass
  a free tier, and the repository is public, so a secret in PR jobs from forks is a risk.

### Cost, and which screens give the most value

- Each image is a full-page PNG. At 1280×720 a screen is about 50 to 200 KB, a phone screen about 30 to 150 KB
  (our pages are flat colours and SVG, which compress well). 13 states × 2 sizes × 2 themes is 52 images, a few MB,
  and each update adds its changed images to git history. Acceptable for a small app. If it grows, `type: "webp"` or
  Git LFS later.
- Time: the screenshots themselves take well under a second each. The cost is reaching the states for real (a room
  with two players, a game in progress, a win), the container pull (about 2 GB uncompressed for the Playwright
  image, under a minute on a hosted runner) and `npm ci`. Run in parallel with the other jobs, it does not lengthen
  the 8 minute browser path as long as it stays shorter. It adds one runner per PR to the 20-job account queue.
- Most value: the screens every new player sees and the ones a style change breaks most often. Home, the lobby, the
  room while waiting, each game's board mid-game (three different layouts), the result after a win (the card and
  celebration), the leaderboard, the player's profile and the visitor's preview, login, sign-up and the 404. Phone
  and desktop differ the most (the phone header and menu, CC-259), light and dark change every token. Less value:
  every press state (CC-207 already presses through them), the owner console (one person uses it), legal pages
  (text only).

### Recordings

- `video` and `trace` share the modes `off`, `on`, `retain-on-failure`, `on-first-retry`, `retain-on-first-failure`
  and others. `retain-on-failure` records every test and keeps it only when the test fails. Video costs CPU to encode
  (25 fps by default), and the retain modes pay the recording cost on every run (docs/api/class-testoptions, read
  2026-10-19).
- Our 100 ms press checks (ADR-038) are timed in the browser on a 3-worker machine (CC-236). Turning video on for the
  whole suite adds encoding load on exactly those machines, and a trace on every passing test (the board row's "trace
  and video for every test on every run") would be thousands of files a day. A failing run is what someone opens.

### What is best for ClassiCade

1. **A separate visual suite**, `e2e/baselines.visual.js` with its own config `e2e/playwright.visual.config.js`, so
   the four-part suites stay as they are (not one more file in `shards.js`) and the screenshots only run where the
   pixels are fixed. It uses the `players` fixture, so every screen still gets the console, CSP and leak checks.
2. **Desktop 1280×720 and phone 390×844** (Chromium, touch, phone header), light and dark, full page. The 13 states
   above, each reached for real (a second player joins, moves are played, a win is played). The 360×800 size in
   LOOK_AND_FEEL §7 is CC-154's layout check, not a baseline here, to keep the count down.
3. **Masks** for guest and account names, room codes and invite links, the daily quests, match dates, chess clocks
   and the leaderboard rows. The mouse is moved away. Toasts are hidden while capturing by a capture stylesheet.
   Zero tolerance first is too strict for antialiasing in a container that Rosetta never runs: `threshold` stays at
   the default 0.2 and `maxDiffPixels` is small (a handful), never a ratio that would hide a moved button.
4. **One pinned image**, `mcr.microsoft.com/playwright:v1.64.1-noble`, for the CI job (`container:`), for the update
   workflow and for the local scripts (`npm run test:visual`, `npm run test:visual:update`, run through Docker as
   `linux/amd64`). A unit test pins the image tag to the installed Playwright version, so an upgrade cannot leave them
   apart. Baselines have no platform in their name, because only one platform makes them.
5. **Update path**: `npm run test:visual:update` locally, or the `Visual baselines (update)` workflow
   (`workflow_dispatch`, a branch name, refuses `main`) which regenerates in the CI image and commits the images to the
   PR branch. A person reviews the image diffs in the PR and pushes the next commit, which runs CI. No hosted service.
6. **Recordings**: the visual job keeps a video and a trace on failure (`retain-on-failure`), plus Playwright's
   expected, actual and diff images, uploaded for 14 days with the HTML report. The main suites keep their trace on
   failure and add no video, so the 100 ms checks are not loaded further.
7. **Advisory first.** The check runs on every PR but is not one of the 8 required checks for a week, so a font or
   antialiasing flake shows up without blocking anyone. After a green week the owner decides whether to require it.

## Why

A change to a token, a CSS module or the header can move or recolour a screen while every assertion still passes.
Before the look and feel polish (CC-153, CC-281) lands, each PR should show what it changed on every main screen,
and a reviewer should approve the new pictures.

## Scope

- In: a visual spec and config, baselines, `ci.yml` visual job, an update workflow, npm scripts, a Docker run script,
  workflow tests, docs.
- Out: production code, the four-part suites' tests, a hosted review service, a gallery comment on each PR (the HTML
  report and the PR's image diffs cover it for now), traces of passing tests.

## Plan / notes

As built, following "What is best for ClassiCade" (ADR-056):

1. `e2e/baselines.visual.js` and `e2e/playwright.visual.config.js`: projects `desktop` (Desktop Chrome, 1280×720)
   and `mobile` (Pixel 7, 390×844), reduced motion, `en-GB`, UTC. 14 states, light and dark, full page: 56 PNGs
   (7.3 MB) in `e2e/visual-baselines/<screen>-<theme>-<project>.png`. Screens: home as a visitor and as a guest,
   the chess lobby, a Tic-Tac-Toe room waiting, RPS while choosing, the result after an RPS win, Tic-Tac-Toe after
   the first move, chess after 1. e4 (Black's view), the overall leaderboard, a new account's profile, the visitor
   profile, login, sign-up and the 404.
2. Found on the way: Playwright's `mask`, `animations: "disabled"`, `caret: "hide"` and `stylePath` each add a
   `<style>` element, which the CSP blocks, so the `players` fixture failed every test on the console error. The
   spec does the same from script, which the CSP allows (ADR-016 point 4): stand-ins of the same length for guest
   names, test account names and emails (kept up to date by a MutationObserver, since React redraws texts), a fixed
   room code, painted boxes over the invite link, every `[data-cc-ticker]` clock, `time` elements and the daily
   quests (at a fixed height), and the run-dependent level and XP after the win. Toasts are hidden. No check of the
   fixture was turned off.
3. Who moves first is drawn at random and changes the screen (seat badges, board side). The spec opens new rooms
   until the host moves first, at most ten (one chance in 1024 of all failing). The page under test is always the
   same player's.
4. Videos: Playwright records only its own `page`, and our tests open browsers through the `players` fixture. The
   fixture now records each browser when the project asks for video and attaches the video only when the test
   fails. The four-part suites do not set `video`, so nothing changes for them.
5. `scripts/visual/docker.mjs` (tested) and `scripts/bin/visual.mjs`: `docker run --platform linux/amd64 --init
--ipc=host` with the pinned image, copying the repository in without `node_modules`, `npm ci` inside, and copying
   back the report, the results and, when updating, the baselines. npm and MongoDB caches in Docker volumes.
6. `ci.yml` job `visual`, "Visual baselines (advisory)", in `container:` with the same image, 2 workers. The HTML
   report always, the results (images, videos, traces) on failure, 14 days. **Pull requests only**
   (`if: github.event_name == 'pull_request'`): on a push to `main` a visual diff would turn main's CI red, and a red
   `main` stops every merge, which an advisory check must not do (review of #104). Each change is compared in its PR
   before it merges, so `main` loses no coverage. If the owner makes it required, it stays a PR check.
7. `.github/workflows/visual-update.yml`: `workflow_dispatch` run **on the ticket branch itself** ("Use workflow
   from" the branch, or `gh workflow run visual-update.yml --ref cc-153-name -f ticket=CC-153`), which must match
   `cc-###-name`, never `main`. Job `render` makes the images in the image with a read-only token and no stored
   credentials, job `commit` (contents: write, runs no project code) commits the changed images as `CC-###: update
the visual baselines` and pushes. GitHub runs no workflow for that push, so the reviewer's next push reruns CI.
   Both jobs check the ticket with bash `[[ "$TICKET" =~ ^CC-[0-9]{3}$ ]]`, which matches the whole value (the first
   version used `grep`, which passed a value whose first line matched, review of #104), and the ticket reaches the
   scripts only through `env`. The compare run never touches the checkout's baselines (not copied, removed or
   given away), and its test fails if the script mentions them.
   The first version ran on `main` with the branch as an input, and CodeQL flagged it (high, cache poisoning): code
   from an unreviewed branch would have run with `main`'s cache scope. Running on the branch keeps it in the
   branch's own scope.
8. **Advisory for a week, not required now.** It is new, the first week shows whether fonts or antialiasing ever
   flake in the container, and a red visual check should not block other builders while that is learnt. The owner
   decides afterwards whether it becomes the ninth required check.
9. Not built: a gallery comment on each PR and traces of passing tests (the board row asks for both). The HTML
   report and the PR's own image diffs cover review for now. The 360×800 size stays with CC-154.
