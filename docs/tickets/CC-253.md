### 2. The threat

1. **An account id dates the account.** `user_` is followed by a MongoDB ObjectId, whose first 4 bytes are "a 4-byte
   timestamp, representing the ObjectId's creation, measured in seconds since the Unix epoch"
   (https://www.mongodb.com/docs/manual/reference/method/ObjectId/). Anyone who sat in a room with an account
   learns to the second when it was made. For a child that narrows down a lot (CC-241 F11).
2. **One id across every room.** The same id in every room lets anyone who meets a player twice, or two people who
   compare notes, link the rooms. A guest's id is the same for the whole session. Quick match (CC-051) will seat
   strangers, so this becomes "a stranger can follow a player from room to room".
3. **Ids as handles for later features.** Public profiles (CC-034), friends (CC-052) and challenges (CC-277) will
   look players up. An id learned in a room must not become a key for any of them (OWASP IDOR, below).
4. **What it is not.** Knowing an id does not let anyone act as that player: identity comes from the session only.
   So this is a privacy leak (low in CC-241), made P0 by the working agreement and ADR-051.9 before strangers meet.

### 3. How others do it

1. **OWASP, Insecure Direct Object Reference Prevention**
   (https://cheatsheetseries.owasp.org/cheatsheets/Insecure_Direct_Object_Reference_Prevention_Cheat_Sheet.html):
   "avoid exposing identifiers in URLs and POST bodies if possible", take the current user from the session, and "as
   an additional defense-in-depth measure, replace enumerable numeric identifiers with more complex, random
   identifiers". It also warns "Avoid encrypting identifiers as it can be challenging to do so securely", and that
   "even with complex identifiers, access control checks are essential".
2. **Discord** documents that its ids carry time: the first 42 bits are "Milliseconds since Discord Epoch"
   (https://docs.discord.com/developers/reference). It is the same leak as ours, accepted there because accounts
   are public. Ours are not.
3. **Lichess and Chess.com** show usernames, never internal ids, in games (general knowledge, high confidence). A
   username is a public handle the player chose. Our room views already show the display name, so the id adds only
   the creation time and a link between rooms that the name does not make for guests.
4. **Keyed hashes for unlinkable ids.** Naming something by an HMAC under a server key, scoped to a context, is the
   usual way to give a stable name that is different in each context and cannot be turned back without the key
   (general knowledge, high confidence. Our own `utils/networkKey.js` names network addresses this way, CC-249, and
   `domain/bots/seals.js` derives its key from the session secret with a label).

### 4. What is best for ClassiCade

Two designs were compared.

| Question                                  | A. Random seat id stored in the room                                                                                  | B. Keyed hash of the room and the player, worked out on every view (chosen)                                                                                                                                             |
| ----------------------------------------- | --------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Derivable from the player id or its time? | No                                                                                                                    | No: HMAC-SHA-256 under a key only the server has                                                                                                                                                                        |
| Stable in a room, rematches included      | Yes                                                                                                                   | Yes: the input is the room (code and creation time) and the player, neither changes in a rematch                                                                                                                        |
| Linkable across rooms                     | No                                                                                                                    | No: a different room gives an unrelated id. A code that comes back a day later is a new room with a new creation time                                                                                                   |
| Rooms already in production MongoDB       | Have no ids. Need a migration at startup, and rooms written by the old server during Render's overlap still lack them | Nothing to migrate: every stored room works at once                                                                                                                                                                     |
| Players who left the room                 | Their id must be kept in the room, or their wins, requests and game state would show the raw id                       | Any id has its seat id, kept or not                                                                                                                                                                                     |
| Rollback                                  | Old server ignores the new field                                                                                      | Nothing was stored                                                                                                                                                                                                      |
| Cost                                      | A new stored field, a migration and a fallback for rooms without it                                                   | One HMAC per player per view (microseconds). The key is derived from `SESSION_SECRET` with its own label, so no new setting. Rotating that secret gives open rooms new seat ids, which only closes an open block dialog |

**B is best.** It meets every rule with no stored data and no migration, so production data stays exactly as it is.

The rules, written as ADR-057:

1. **Every player in a room view is named by their seat id**: `HMAC-SHA-256(key, [roomCode, createdAt, playerId])`,
   the first 16 bytes in base64url (22 characters). The key is `HMAC-SHA-256(SESSION_SECRET, "classicade room seat
ids")`.
2. **The view keeps its field names** (`seats[].playerId`, `hostId`, `you`, `requests[].from/to`, `winners`,
   `activePlayers`, `series.wins` keys, `fairness.*.playerId` and the engine's view). Only the values change: in a
   room view each of them now holds a seat id. Renaming the fields would touch about 190 lines of the web app and
   its tests for no gain in safety, and the block request already calls the value `seatId`.
3. **`you` is the viewer's own seat id** ("" for a viewer without a seat), so the page compares seats with `you` as it
   does today. The player's own player id is never needed in a room view: it stays in `GET /api/session`.
4. **The engine's view is renamed as a whole.** Every player of the game (the seats, the players a game started
   with, and anyone named by the result, series, requests or log) is replaced wherever the view holds them, as a
   value or as a key, the way `renamePlayer` already moves a guest's seat to their account. So a new game's view can
   never leak an id, and engines do not change. A room now records the players its game started with
   (`game.players`), so a player who leaves a finished game is still renamed. Games started before this change
   name their players in the log, the result and the series.
5. **`request:updated` is made for each player**: `names` keyed by seat id, requests by seat id, and `you`.
6. **Blocks keep working.** `POST /api/blocks` still takes `{ roomCode, seat, seatId }`. The server works out the
   seat id of the person in that seat and blocks only when it equals `seatId`. The pattern of `seatId` becomes
   exactly the seat id's shape (22 base64url characters), so a raw player id is refused as malformed.
7. **A deleted player's stand-in** is labelled `deleted: true` on its seat, so the page knows it cannot be blocked
   without reading anything from its id.
8. **Seat id changes with the player id.** A guest who signs in during a game becomes another player id, so their
   seat id changes, as their name does. A stand-in for a deleted player gets a new seat id. Both are what the
   opponent already sees from the name.
9. **For later tickets.** Public profiles (CC-034), chat and emotes (CC-169), spectating (CC-056), quick match
   (CC-051) and challenges (CC-277) name another player by seat id or by an id made for them, never by a player id.

**Out of scope, for a new ticket (the coordinator gives the ID):** match history (row 6) still sends past opponents'
player ids to the participants, including the account creation time. The fix is the same idea as the export: name
other players by a per-match label in `GET /api/matches` and `/api/matches/:id`, while the block route keeps reading
the real record. It is a separate change to `matchComponent` and the profile page.

## Why

Before quick match lets strangers meet (CC-051, ADR-051.9), a room must not tell a stranger when someone's account
was made, or give them a handle that follows that player from room to room.

## Scope

- In: room views, `request:updated`, the block route's seat check, the web pages that read them, tests, ADR-057, DATA.md.
- Out: match history (new ticket, above), renaming view fields, public profiles (CC-034).

## Acceptance criteria

- [ ] No room view, room push or request push carries any player id, for players, spectators, after a rematch, after a
      player leaves a finished game, or against a computer player.
- [ ] A player's seat id is the same in every view of the room and across rematches, different in another room, and
      not computable without the server's key.
- [ ] Blocking from a seat works with the seat id, and a player id sent as `seatId` is refused.
- [ ] Production rooms stored before the change show seat ids at once, nothing is migrated or deleted.
- [ ] Tests cover the change. `npm run lint`, `npm run format:check`, `npm test`, coverage and the relevant browser specs pass.

## Plan / notes

1. `domain/rooms/seatIds.js`: `createSeatIds({ secret })` answers `seatIdOf(room, playerId)`, and
   `seatSecretFrom(sessionSecret)` derives the key. Pure apart from the hash.
2. `roomComponent`: takes `seatIds`. `viewFor` and `requestsView(room, viewerId)` rename every player of the room to
   their seat id. `start` records `game.players`. `handedOver` renames it. The seat of a stand-in gets `deleted: true`.
3. `blockComponent`: takes the same `seatIds` and compares the seat's seat id with `seatId`.
4. `roomHandlers`: `request:updated` is built per player.
5. Web: the request popup compares with the push's `you`. The seat menu reads `deleted` instead of the id's prefix.
6. Composition root: one `seatIds` from `SESSION_SECRET` for both components.
