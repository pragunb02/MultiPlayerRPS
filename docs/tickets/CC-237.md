## Research (written before any code)

### 1. What failed, and why

CI run 39055903179 (after #58), job "Browser persona tests", desktop, `e2e/invite.spec.js:90`. The failing line is
not in the test body but in its helper `existingAccount`, which signs an account up in its own browser first:

1. `expect(owner.page).toHaveURL("/")` timed out on `/signup`.
2. The fixture's clean check for "account owner" reported `HTTP 400 POST /api/auth/signup`.
3. The error context from the `playwright-report` artifact shows the sign-up form with the username
   `riya_cp8um06316` marked invalid and the message "That name is reserved. Please choose another name."

So there is no timing race in the app or in the test. The sign-up was refused, and it was refused correctly.

`newAccount()` in `e2e/personas.js` builds the username from the clock in base 36 plus four random digits:
`riya_${(Date.now().toString(36) + random).slice(-10)}`. Base 36 uses every letter, so the tag sometimes spells a
word that the public name rules from CC-119 (`apps/server/src/models/publicName.js`) refuse:

1. `riya_cp8um06316`: the checker drops the `8` (it is not a leetspeak digit), reads `riyacpum…`, and finds `cpu`,
   which is a bot word reserved anywhere in a name.
2. Running the same generator 200,000 times against `parseUsername` refused 0.06 % of names, for example
   `cycunt1293` (offensive anywhere), `d2hbot4181` (ends like a bot) and `cys5h19178` (`5h1` reads as `shi`, then
   the next letters).

About 27 places in the browser suite call `newAccount()`, on two projects, so roughly one run in thirty draws a
refused name. That matches "now and then". The test that fails moves around in principle; this one is simply the
first to call `newAccount()` in its file. `e2e/guest.spec.js` has the same problem with `g_${Date.now().toString(36)}`.

### 2. How others make test data that cannot clash with the product's rules

1. Playwright's parallelism guide (playwright.dev/docs/test-parallel, read 2026-10-18) recommends giving each worker
   its own data, named from `testInfo.workerIndex`, so parallel tests never share or clash.
2. The common advice for generated test data (Faker and similar libraries) is to keep generated values inside the
   domain the product accepts, rather than retrying until one passes. A retry hides the cause and makes the run
   slower and less predictable.

### 3. What is best for ClassiCade

Generate names that the rules can never refuse, by construction, and prove it with a unit test:

1. The tag becomes digits only. The name rules read a part made only of digits as a number, not a word
   (`plainLetters` in `publicName.js`), so the name's only word is `riya`. In the squeezed whole name, digits read
   as leetspeak give only `o i e a s t`, and no reserved or offensive entry can be spelled from `riya` followed by
   those letters (none of them starts with `riya` or is made only of those letters outside the whole word lists).
2. The tag is the last 6 digits of `Date.now()` plus 4 random digits, so the username stays 15 characters, the
   same length as before. Two accounts clash only when made in the same millisecond (modulo about 17 minutes) with
   the same 4 random digits. A first version used 11 clock digits (a 20 character name, the most sign-up allows),
   and CI showed that such a name breaks the mobile layout: in the header the name covers Log out, and on the
   profile a form covers "Sign out other devices" (`navigation.spec.js:252` and `user.spec.js:122` timed out on
   mobile in run 39072590323, the traces say the name and the form "intercept pointer events"). That is a real
   app bug for players with long names, now CC-254 and BUG-30, out of scope here.
3. A unit test (`e2e/personas.test.js`, run by `npm test`) feeds many generated names through the server's own
   `parseUsername`, so a future change to the name lists that would refuse a test name fails fast in unit tests,
   not as a flaky browser test.
4. `guest.spec.js` uses the same generator instead of its own.
5. The random digits come from `node:crypto` `randomInt`, because they are part of the test password and CodeQL
   flags `Math.random` there. The clock and the random number can be passed in, so the unit test needs no mocks.

No waits or retries are added.
