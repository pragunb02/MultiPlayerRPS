## Why

Only sign-up, login, guest creation and leaderboards had rate limits. Most reads (session, matches, progress,
gamification) had none, so one script could keep the server and the database busy with no limit at all.

## Scope

1. In: one limiter for everything under `/api`, 300 requests a minute by default, configurable by the composition
   root (`limits.api`) like the other limits and raised for the end-to-end server. It counts per session when the
   request has a guest or signed-in player and per address otherwise (the address comes from CC-106). The answer
   over the budget is the standard 429 body with `Retry-After` and `RateLimit` headers.
2. Out: socket event limits (already per connection). Shared limiter storage across several server instances (one
   instance today, see CC-028).

## Acceptance criteria

- [x] `createApiRateLimit` is mounted on `/api` after the session middleware, so it can count by session.
- [x] The stricter route limits still apply inside the bigger budget.
- [x] `/health`, `/api/health`, the web app and the realtime connection are not limited.
- [x] `e2e/app.mjs` raises the budget, because every test player connects from 127.0.0.1.
- [x] Unit and app tests cover the budget, both keys, the 429 body, and the `Retry-After`, `RateLimit-Policy` and
      `RateLimit` headers.
- [x] Tests cover the change. `npm run lint`, `npm run format:check`, `npm run test:coverage` pass.

## Plan / notes

1. Counting by session means players behind one shared address (a school, an office, a mobile carrier) do not use up
   each other's budget. A request without a session is counted by address, which also covers guest creation.
2. A client could create new guest sessions to get more budget, but guest creation has its own limit of 30 per
   15 minutes per address, so that multiplies the budget by at most 30.
3. Budgets live in memory, so a restart resets them. That is fine while there is one instance.
