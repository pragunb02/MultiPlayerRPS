## Problem

The October audit ([AUDIT-2026-10.md](../design/AUDIT-2026-10.md), CC-320) found that every page builds its own
version of the same parts. 64 card rules in 46 CSS modules each set their own border, radius, surface and padding.
Buttons have no link form and no danger look, so links copy the press shadow by hand and Resign or Delete account
look like any other button. About 24 screens show a bare "Loading…" line, four dead ends have four layouts, a
visitor's `/friends` loads forever, selects and textareas are browser defaults, and there are two tab components.
Two tokens are used but never defined and three class names point at nothing. CC-314 wrote the contract; nothing
turned it into components.

## Job to be done

When players move from page to page, they want every button, card, field and empty screen to look and answer the
same way, so the site feels like one premium arcade and not a set of separate forms.

## Appetite

L (up to 2 days of agent time). **Cut line:** the raw-weight lint rule (it needs the header and the match stage,
which other tickets own), then the less used console screens.

## Proposed solution

Build the shared components in `apps/web/src/components/`, each a contract entry with every state, then migrate
the app to them outside the header (CC-324), the match stage and result layout (a later ticket) and `App.jsx`
(CC-322). The APIs are in [CONTRACT.md](../design/CONTRACT.md#the-shared-components-cc-323).

1. **Button**: `primary`, `secondary`, `ghost`, `danger` (and `accent`, the primary on the hero art), sizes `sm`,
   `md`, `lg`, `as="link"` with `to` or `href`, icon-only with a required `label`, and CC-164's states.
2. **Card** with `CardMedia`, `CardHeader`, `CardLink`, `CardBody`, `CardFooter`; variants `surface`, `raised`,
   `accent` (game, brand or gold tone) and `notice` (status tone); `interactive` lifts and glows in CSS (ADR-075's
   simple tier).
3. **PageHeader, Section, Sections**: the page title and titled sections with one rhythm (the owner's rules,
   2026-10-21).
4. **EmptyState, ErrorState, Skeleton** in place of bare loading lines and dead ends.
5. **Field** kinds `text`, `select`, `textarea`, `date`, `copy`, with label, hint, error and character count.
6. **Tabs**: one component in place of the console's and the leaderboard's.
7. **Tokens**: weights, page and section title roles, tap targets, breakpoints, a hover elevation and danger press
   shadows. `--text-base` and `--space-5` replaced. The check refuses unknown `var()` names and other breakpoints.
8. **Focus**: no ring on script-focused headings, destructive confirms keep their backdrop, 24 px targets.
9. `/admin/design` shows every new component in every state, and the owner's section and data patterns.

## Non-goals

- The header and the phone menu (CC-324), route lazy-loading (CC-322), the match stage and the result layout.
- New colours or a light-theme identity pass (audit item 7).
- A two-language copy pattern (audit item 12).

## Rabbit holes

- **Forcing hover in screenshots or on the design page.** The page shows live components; hover, focus and press
  are tried by hand there. Forced-state classes would be a second way to draw a state.
- **A raw-weight lint rule now.** The header and the match stage still hold 46 raw weights in files other tickets
  own. The tokens exist and every other file uses them; the rule comes when those files move.
- **Breakpoints as custom properties.** A media query cannot read `var()`. The tokens name the widths and the check
  compares, which needs no build step.

## Acceptance criteria

- **AC-1** Given each Button look and size, when rendered, then it draws that look and carries `data-cc-variant`,
  and an unknown look fails. Test: `ButtonForms.test.jsx` › "draws each variant and size, and marks its look for the
  one-primary-per-region check (AC-1)"
- **AC-2** Given `as="link"`, when rendered with `to` or `href`, then it is a real link drawn as a button. Test:
  `ButtonForms.test.jsx` › "renders a real router link with as=link and to, drawn as a button (AC-2)" and "renders an
  <a> for an address outside the app, and needs somewhere to go (AC-2)"
- **AC-3** Given an icon-only button, then its label is its name, and without a label it fails. Test:
  `ButtonForms.test.jsx` › "an icon-only button is named by its label, and refuses to render without one (AC-3)"
- **AC-4** Given a slow action on any look, then the button is busy and keeps its width (CC-164). Test:
  `ButtonForms.test.jsx` › "keeps the loading state of CC-164 on every variant: busy, and the label kept for the
  width (AC-4)"
- **AC-5** Given each Card variant, then it has one surface and its parts in order, with art hidden from readers.
  Test: `Card.test.jsx` › "draws every variant with the one card surface, and its parts in order (AC-5)"

  `Card.test.jsx` › "an interactive card lifts on hover and follows its one stretched link from anywhere (AC-6)",

## Threat model

1. **What are we building?** Presentational components and CSS. No route, socket, storage or auth changes.
2. **What can go wrong?** A link button pointing at an outside address; a copy field leaking something private.
3. **What are we doing about it?** `href` is only ever a value the caller already rendered (WhatsApp, the room
   link). The copy field copies only what the page already shows. Inline styles stay blocked by the CSP and lint.
4. **Did we do a good enough job?** The design page shows made-up names only, behind the existing admin allowlist.

## Privacy checklist

- **Data:** none collected. The design page uses made-up names.
- **Retention:** none.
- **Who sees it:** players see the same data as before; the owner sees the design page.
- **Minors (ADR-028):** nothing changes.

## Alternatives considered

  ones measured in CC-321 inject `<style>` that our CSP blocks.
- **Leaving each page its own card and loading styles.** That is the problem the audit found.

## Research (written before any code)

1. **How our code does it today.** The audit counted 64 card rules in 46 modules, about 24 "Loading…" lines with
   three accessibility treatments, four dead-end layouts, two tab components and five breakpoint values. `Button`
   had primary, accent, secondary and ghost, sizes md and lg, and no link form, so links copied the press shadow.
   `Field` styled only `input`. `Modal` closed on every backdrop click. `--text-base` and `--space-5` were never
   defined, and the CC-314 check could not see it.
2. **How others do it.** The W3C Design Tokens Community Group format (draft, 2025) names tokens by role over
   aliases, which our token files follow. The WAI-ARIA Authoring Practices (W3C, 2024) separate navigation links
   with `aria-current="page"` from tab lists that switch panels in place, which is why our tabs are links. WCAG 2.2
   sets 24 by 24 CSS px as the target floor (2.5.8) and asks for a visible focus indicator on keyboard-operable
   controls (2.4.7), not on headings. The open-source design systems we read all ship one button with a link form
   and a danger look, one card with media, header, body and footer slots, and skeletons sized to their content to
   avoid layout shift (Web Vitals CLS guidance, 2024).
3. **What is best for ClassiCade.** Our own small components over tokens: no new dependency (ADR-008), nothing the
   CSP blocks, CSS for hover and lift (ADR-075's simple tier), and one contract the design lens can point at.
