## Why

After a game the only way to play the same person again was a new room and a new invite link. One click to play
again (both must agree) removes that friction and turns single games into a rivalry.

## Scope

- In:
  - `SOCKET_EVENTS.ROOM_REMATCH` (`room:rematch`, `RoomCodePayload → RoomView`).
  - `roomComponent.requestRematch({ code, playerId, now })` and the room fields `rematch { requestedBy, available }`
    (only once finished) and `series { games, wins }`; both in the `RoomView`.
  - Web: `useRoom().rematch()`, `components/Rematch/RematchPanel.jsx` in RoomPage's finished state, a fresh board
    for each game in the room.
- Out: rematch with a different game or options; more than two seats changing their minds in sequence beyond the
  toggle; a "decline" message (declining = not asking, or leaving the room).

## Rules

- Allowed only in a `finished` room, for seated players (`FORBIDDEN` otherwise, `NOT_FOUND` for an unknown room,
  `CONFLICT` when not finished or no longer available).
- Asking again withdraws the request (toggle). Every request refreshes `lastActivityAt`, so the finished-room TTL
  starts again.
- A forfeit ends a game with `available: false` (the leaver is gone). A player leaving a finished room clears all
  requests and sets `available: false`.
- When every seated player has asked: a new game in the same room code — new match id and seed, same options,
  seats reversed, `status: playing`; `result` and `rematch` are cleared, `series` stays. The handler broadcasts the
  new view to the other sockets and acknowledges the requester (the same pattern as moves — no separate
  `ROOM_EVENTS.UPDATED`, which would send the requester the view twice).
- The new game is recorded as its own match when it ends (new match id), so history, XP and leaderboards count it.

## Acceptance criteria

- [x] Rematch needs both players and produces a second recorded match with the seats reversed.
- [x] Declined (withdrawn) and left-opponent cases handled in the server and the UI.
- [x] Back after a rematch does not leave stale history; the URL stays the same (no history entry is added).
- [x] Reload in the middle of a rematch offer shows the same state (the server keeps it).
- [x] Tests cover the change; lint, format, coverage, e2e, audit pass.

## Plan / notes

- Seat order is reversed, as the brief asks. Today's engines (Tic Tac Toe, Chess) choose the starter / White with
  the seeded RNG, not by seat, so the first move does **not** strictly alternate. Making it alternate needs an engine
  contract change (e.g. an optional `starter` hint in `init`) — a follow-up ticket, not done here to keep engines
  untouched.
- UI: "Rematch" → "Waiting for {opponent}…" with "Cancel rematch"; the opponent sees "{name} wants a rematch!" with an
  "Accept rematch" button that pulses three times (no animation under `prefers-reduced-motion`); "Opponent left — no
  rematch this time." with a "New game" link to the lobby; an offline opponent is mentioned; the series score is
  shown from the second game on. The message is a `role="status"` live region.
- The board component is keyed by the game number in the room, so a rematch gets a fresh board (no selection or
  clock state from the last game).

## Verification

- Unit: room state machine for every branch (offer, toggle, start with reversed seats and new match id, series,
  forfeit, leaving, not finished, stranger, unknown room, guest sign-in renaming the series), socket handlers
  (request seen by the opponent, start, second recorded match, left opponent, spectator, malformed payload),
  RematchPanel states through RoomPage.
- Integration: a rematch over real sockets through the composition root stores two matches for the room.
- Browser (`e2e/rematch.spec.js`, desktop + mobile): both accept (with a reload mid-offer, Back/Forward after the
  rematch, series score, two matches in history); the opponent leaves; a request withdrawn.
