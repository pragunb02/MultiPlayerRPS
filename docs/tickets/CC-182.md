## Why

Since CC-101 every room change went to MongoDB three times: the room component read the room, the DAO replaced the
whole document (`replaceOne` of `structuredClone(doc)`, the full move log included), and then read it again to return
it (`persistence/roomDao.js` at the time, lines 120 to 128). The investigation measured mongodb, bson and mongoose at
10 % of CPU samples under load, and the payload of every write grew with the game.

## Scope

In:

1. `persistence/roomChanges.js`: works out a MongoDB update that turns the stored room into the new one by writing
   only what changed. Changed values become `$set` of their path, a list that only grew at the end (the game log, the
   chess move list) becomes `$push` with `$each` of the new items, a field that is gone becomes `$unset`. A list that
   shrank or changed earlier is written whole. An object with a key MongoDB cannot name in a path (a dot, a leading
   dollar sign, an empty key) is written whole. Unchanged parts are skipped by identity first, because a new room
   reuses the unchanged parts of the room it was made from.
2. `roomDao.update({ doc, previous })`: one `findOneAndUpdate` with the same filter as before (`code`, the version that
   was read, not closing), the changes, `$inc: { version: 1 }` and `returnDocument: "after"`. A miss is still told
   apart as `VersionConflict` or `RangeError` by the same `missed` check as before.
3. `roomAccessor.save({ room, previous })` and the room component passes the room it read as `previous`. The
   in-memory double stores the whole room, as before.
4. `scripts/bin/load-moves.mjs`, a local load script in the spirit of the investigation's, measures move latency.

Out: keeping rooms in a process cache to skip the read. The read is the only way to learn the current version without
a cache, and a cache would be wrong as soon as two server processes run (a deploy overlaps two for a moment). Not
needed at today's numbers.

## Acceptance criteria

- [x] A move is 2 round trips (read, then one write that returns the stored room), down from 3
- [x] The write sends only what changed, for a move: `$set` of `lastActivityAt` and the like, `$push` of the log entry
- [x] Optimistic versioning is unchanged: same filter, version counted up by one, same errors
- [x] The CC-101 room DAO contract suite passes on MongoDB and on the in-memory double, with new cases for every kind
      of change (each must read back exactly as if the room had been replaced whole)
- [x] p50 and p95 move latency measured before and after
- [x] Tests cover the change, lint, format, coverage pass
- [ ] Docs: BACKLOG, KNOWN_ISSUES, PROGRESS are updated by the owner when merging (this agent may not edit them)

## Plan / notes

Why `previous` is safe to trust: the write only matches the version that was read, and every write counts the version
up, so the stored document at that version is exactly what was read. If someone else wrote in between, nothing
matches and the change is decided again on their room, as before.

The stored data shape does not change, so a rollback reads every room as it is.

## Verification

Round trips: `roomDao.integration.test.js` listens to the driver's command events and checks that saving a move to a
room with a 300 entry log sends a single `findAndModify` whose update is
`{ $set: { lastActivityAt }, $push: { "game.log": { $each: [entry] } }, $inc: { version: 1 } }`.

Contract: 16 new cases in `testing/roomDaoContract.js` (log entry added, nested value, seat changed in place, seat
removed, list shortened, list grown with an earlier item changed, field removed, field set to undefined, field added,
nested field removed, object turned into a list, empty list filled, whole new game, keys a path cannot name, same
values in new objects, nothing at all), run on MongoDB and on the double. Unit tests for every branch in
`persistence/roomChanges.test.js`.

Load (`PAIRS=100 DURATION_S=90 node scripts/bin/load-moves.mjs`: 100 chess pairs and 100 Rock Paper Scissors pairs,
400 players, about 200 ms thinking time, in-memory MongoDB on the same laptop, so a round trip is far cheaper than on
Render with MongoDB Atlas). Both rows include CC-180, so they show this ticket alone:

| Build               | Moves in 90 s | p50    | p95     | p99     | max      |
| ------------------- | ------------- | ------ | ------- | ------- | -------- |
| before, run 1       | 118 356       | 4.3 ms | 18.1 ms | 30.3 ms | 88.3 ms  |
| before, run 2       | 118 105       | 4.4 ms | 21.8 ms | 33.8 ms | 79.0 ms  |
| after (CC-182), 1   | 119 503       | 2.6 ms | 9.5 ms  | 34.9 ms | 312.9 ms |
| after (CC-182), 2   | 119 667       | 2.3 ms | 7.9 ms  | 29.8 ms | 314.1 ms |
| main, for reference | 41 852        | 279 ms | 981 ms  | 1638 ms | 2005 ms  |

p50 and p95 roughly halve. p99 is unchanged. Both "after" runs had one slow outlier of about 310 ms. It was not
investigated further. Its cause is not known, and the p99 is no worse. With a real network between the server and
MongoDB, the saved round trip (at least a millisecond or two to Atlas, much more if the cluster is in another region
than the Render server) and the smaller payload count for more than on this laptop.
