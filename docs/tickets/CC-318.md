## Problem

The test "gives at most the day's XP from computer games, apart from quest XP, and every game still counts" timed
out at 5 s on `main` at 220b2d8 (job 118657951956), after #145. **Root cause:** the scripted player sends every
event at once, and five quick games take 15 to 25 events in under half a second: drawn rounds are played again, so
the count depends on the match seeds. The per-player event budget (CC-107: a burst of 20, then 10 a second) then
refused a throw or a new game with `RATE_LIMITED`. `playRps` never looked at the answer to a throw. It waited for a
round that could not end until the test timed out. In the CI log the fifth game started and nothing came after it.
Locally, 2 runs in 20 were refused in the same way.

Reproducing it also showed two app bugs, and both showed in the CI log:

1. **The computer acted twice for one moment** (`botDriver.js`). When a room changed while an action was in
   flight, `watch` cancelled the plan's timer, which had already fired, and started a second action next to the
   first. Both read the same sealed throw. The one that came second, after the first had ended the round, was
   refused with "A computer player must play the move it locked in" (or "The game is over" when the round ended
   the game). It then tried again 2 s later, and its retry took over the room's plan entry.
2. **Closing the server did not wait for disconnects to be recorded** (`gateway.js`). A tab that closed just
   before shutdown started `handleSocketGone`, nothing waited for it, and the database closed under it: "failed to
   record disconnect" and "failed to record that the player went offline". The test did the same: it disconnected
   its socket and closed the server straight away.

Under heavy local load (load average above 60) the server's start also took 1.5 to 5 s, which used up most of the
5 s. In CI it took 0.3 s, so it was not the cause there.

## Fix

- `botDriver.js`: a room has at most one action in flight. A change that arrives meanwhile is kept as the newest
  saved room (by `version`) and planned from when the action ends. An action that fails after the room changed is
  not tried again later: the driver plans from the new room at once.
- `gateway.js`: `close` waits for the tabs that already closed to be recorded before it disconnects the rest, so
  the database closes only after that.
- `bots.integration.test.js`: the XP test runs on an injected clock at noon UTC on a fixed day, so the five games
  never span two days of the limit (ADR-025, `utcDayOf`). It gets a larger event budget, because a script is not a
  person. It waits on room and progress events instead of polling. Every throw must be accepted, so a refusal fails
  at once with its reason. At the end the test closes the socket, waits for the server to log the disconnect,
  stops the server and expects no warning or error lines. `updateWhere` is event based for every test in the file.
  No timeout was raised and nothing was skipped, retried or left out of coverage.

**Research.** How our code does it now: `socketAdmission.js` takes one token per event (`roomLimits.js`, CC-107).
`botDriver.js` keeps one plan per room code, but nothing stopped a second action while one was running. The
gateway skips recording only for cuts it makes itself while closing. Sources checked: the Socket.IO server docs on
`disconnect` handlers and `io.close()`, which close connections without waiting for application handlers
(https://socket.io/docs/v4/server-api/#serverclosecallback), and the CC-306 fix for the same kind of timeout
(wait on what the test needs, not on time). Best for ClassiCade: fix the two app bugs where they are, and make
the test as fast as the code under test.

## Acceptance criteria

- **AC-1** Given a computer player whose action is in flight, when the room changes, then it does not start a
  second action, and it plans from the newest room when the first one ends.
- **AC-2** Given an action that fails after the room changed, when it fails, then it is not tried again 2 s later,
  and the driver plans from the new room at once.
- **AC-3** Given a tab that closed just before shutdown, when the server closes, then its rooms are recorded before
  the database closes, with no "failed to record disconnect" line.
- **AC-4** Given five quick games against Rocky, when the XP test runs on any day, at any speed, then it passes
  without a refusal and logs no warning or error.

## Test

- AC-1 and AC-2: two new tests in `domain/bots/botDriver.test.js`. Both fail on the old driver.
- AC-3 and AC-4: the XP test in `bots.integration.test.js`. With the old gateway it failed 3 times in 3 runs with
  "failed to record disconnect". With the fix the whole file passed 6 times in 6 runs, with the XP test at
  1.3 to 3.3 s at a load average above 100. `botDriver.js` and `gateway.js` are fully covered.
