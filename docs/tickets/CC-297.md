The web app (`apps/web`) reads only `GET /api/matches`, on the profile page
(`pages/ProfilePage/ProfilePage.jsx`, `MatchHistory`). It needs, per match: the game, the outcome, the end time,
which players are not you, and their names (with "(computer)" for a computer character). It finds "not you" by
comparing `players[].playerId` with the session's own id. Nothing in the web app reads `GET /api/matches/:matchId`
(`lib/api.js` has `getMatch`, unused by any page). It exists for replays and disputes, so it must still say which
log entry and which winner is which player.

#### 1.1 A gap found in #116 (not in this ticket's files)

`roomComponent.withSeatIds` renames the ids `playersNamedIn` finds. A room stored before #116 has no
`game.players`, so a player who left a finished game and appears in none of the log, the winners, the series or the
requests (for example after an idle abort) would still be named by a raw id inside `game.view` (Tic-Tac-Toe `marks`
keys, RPS `hasChosen` and `score` keys). Rooms last at most 24 hours, so this ends a day after #116 deploys. It is
reported for the #116 review rather than changed here, because `roomComponent.js` is that pull request's file.

**Update 2026-10-20, after #116 merged:** the merged version closed it. `game.players` was replaced by the engine
contract's `playersOf(state)`, and a last pass renames anything shaped like a player id (`models/playerIdShape.js`,
ADR-057.4 and .5). This ticket reuses that last pass for matches, moved into `domain/identity/idShapes.js` so rooms
and matches share it.

**Update 2026-10-20, after #118 (CC-291) merged:** leaderboards now list guests' rows under their server-given
names (ADR-060). Checked again: `GET /api/leaderboards/:boardId` sends `rank`, `displayName` (or "Hidden player"),
`level` and `score` per row, and `you` is `{ listed, rank, score }` or `{ listed: false, reason }`. No player id, so
no change is needed. The crawl test covers every board and the viewer's `you`.

### 2. The threat

1. **An account id dates the account.** "A 4-byte timestamp, representing the ObjectId's creation, measured in
   seconds since the Unix epoch" (https://www.mongodb.com/docs/manual/reference/method/ObjectId/). Anyone who ever
   played an account learns, from their own history, when it was made.
2. **One id in every match links an opponent across matches**, and across people: two players who compare their
   histories learn that they met the same person, even under a guest name that changes. RFC 6973 §5.2.1: "The use
   of persistent or infrequently replaced identifiers at any layer of the stack can facilitate correlation", and
   §6.1: "Allowing for the periodic creation of new or randomized identifiers reduces the possibility that multiple
   protocol interactions or communications can be correlated back to the same individual"
   (https://www.rfc-editor.org/rfc/rfc6973.html).
3. **A handle for later features.** Public profiles (CC-034), friends (CC-052) and challenges (CC-277) will look
   players up. An id read from history must not become a key for any of them (OWASP, below).
4. **What it is not.** Knowing an id does not let anyone act as that player: identity comes from the session only.

### 3. How others do it

1. **OpenID Connect pairwise subject identifiers** (OpenID Connect Core 1.0, §1.2 and §8.1,
   https://openid.net/specs/openid-connect-core-1_0.html): a Pairwise Pseudonymous Identifier "identifies the Entity
   to a Relying Party that cannot be correlated with the Entity's PPID at another Relying Party". The example
   algorithm is "sub = SHA-256 ( sector_identifier || local_account_id || salt )", and "The Subject Identifier value
   MUST NOT be reversible by any party other than the OpenID Provider." It is the same idea as ours: one stable id
   per context, derived on demand from the real id and a secret, nothing stored.
2. **OWASP, Insecure Direct Object Reference Prevention**
   (https://cheatsheetseries.owasp.org/cheatsheets/Insecure_Direct_Object_Reference_Prevention_Cheat_Sheet.html):
   take the current user from the session, "avoid exposing identifiers in URLs and POST bodies if possible", and
   access control checks stay essential whatever the identifiers look like. Our detail route already checks that the
   caller played the match.
3. **CC-253 (ADR-057)** chose a keyed hash per room for room views over a random id stored in each room: nothing to
   migrate, rooms already stored work at once, a rollback leaves nothing behind. The research and the comparison are
   in [CC-253.md](CC-253.md#4-what-is-best-for-classicade). Match records are kept for ever (DATA.md), so storing a
   new field in each would mean migrating every stored match, which "derive on read" avoids.
4. **Lichess and Chess.com** name players in game records by username, a public handle the player chose, and keep
   their internal ids to themselves (general knowledge, high confidence). Our history already shows display names.
   The id adds only the account's creation time and a link that the name does not make for guests.
5. **Our own export** (ADR-048.6) already names everyone in a match as `you`, `player-2` and so on.

### 4. What is best for ClassiCade

What each client needs decides the shape:

| Client need                                                  | Needs an id?                                         | Choice                                                                    |
| ------------------------------------------------------------ | ---------------------------------------------------- | ------------------------------------------------------------------------- |
| The profile list: which player is me, the others' names      | Yes, to tell "me" from the others in a list of seats | A per-match id for every player, and `you`: the viewer's own per-match id |
| The detail: which log entry and which winner is which player | Yes, the log and winners refer to players            | The same per-match id everywhere in the record, as a value and as a key   |
| The export                                                   | No, the file is read by the player                   | Unchanged: `you`, `player-2` (ADR-048.6)                                  |
| The server (blocks, the match pipeline, replays)             | Real ids                                             | Read through methods that never reach a client                            |

Three designs were compared for the list and the detail.

| Question                                            | A. Display names only            | B. Labels `you`, `player-2` as in the export                                                                           | C. Keyed hash of the match and the player, worked out on read (chosen)                    |
| --------------------------------------------------- | -------------------------------- | ---------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| Tells the viewer which seat is theirs               | No: two players can share a name | Yes                                                                                                                    | Yes, with `you`                                                                           |
| Log and winners stay usable                         | No                               | Yes                                                                                                                    | Yes                                                                                       |
| Linkable across matches                             | Through names only               | No, but `player-2` reads as an id that means a seat, and changes with the viewer, so two participants' copies disagree | No: an unrelated id in every match. Both participants see the same ids for the same match |
| Same shape as room views (ADR-057)                  | No                               | No                                                                                                                     | Yes: same length, same field names, `you`                                                 |
| Stored data, migration                              | None                             | None                                                                                                                   | None                                                                                      |
| Later features (CC-034 public match pages, replays) | Not enough                       | Breaks when a third person views                                                                                       | Works for any viewer                                                                      |

**C is best.** It is the room seat id idea applied to matches, so one rule covers both:

1. **Every player in a match view is named by a match player id**: HMAC-SHA-256 of `[matchId, playerId]` under a
   key derived from `SESSION_SECRET` with its own label, "classicade match player ids", the first 16 bytes in
   base64url (22 characters). The label keeps it apart from room seat ids: the same player in the room and in its
   match get unrelated ids, so the history cannot be joined to a room view either.
2. **Both routes rename everyone, the viewer included**, and add `you`. The player's own id may go to them, but it
   is not needed here (the session already has it), and renaming everyone means no special case can leak. Every id
   the match names (players, log entries, winners) is replaced as a value and as a key with `renamePlayer`, the same
   way as room views and the export, so a new kind of log entry cannot leak either.
3. **Field names stay** (`players[].playerId`, `result.winners`, `log[].playerId`), as ADR-057.3 decided for rooms.
   The profile page compares with the match's `you` instead of the session's id.
4. **One keyed id helper.** `domain/rooms/seatIds.js` becomes a thin user of a shared `utils/keyedIds.js`: one HMAC
   recipe, one id shape and one list of labels, each label a separate key. The seat ids it gives do not change (a
   test pins one), so open rooms and blocks are unaffected.
5. **The server keeps the real record.** The block route reads the players of a match through a new
   `matchComponent.playersFor` (participants only, never sent to a client), so `getForPlayer` can become the view.
6. **Nothing is stored and nothing is migrated.** Matches already in MongoDB show the new ids at once. A rollback
   leaves nothing behind. Rotating `SESSION_SECRET` gives every match new ids, which nothing depends on.

Amend ADR-057 rather than a new ADR: it is the same decision ("name players in what a client receives by a keyed id
per context") with a second context, and ADR-057.6 already says later features use "a seat id or an id made for that
purpose".

## Why

A player's own history must not tell them when an opponent's account was made, or let them, or two people comparing
notes, follow one opponent from match to match. Quick match (CC-051) will make the opponents strangers.

- [x] No answer of `GET /api/matches` or `GET /api/matches/:matchId` holds another person's `guest_` or `user_` id,
      for guests, accounts, a guest opponent who signed in since, a computer player and a deleted player's stand-in.
- [x] A crawl of every match-related answer (list, detail, export, finished room view, rematch, `request:updated`,
      `progress:updated`, leaderboards with `you`) finds no `guest_` or `user_` id that is not the viewer's own.
- [x] A player's match id is the same for both participants and on every read, different in every other match,
      different from the room seat id, and not computable without the server's key.
- [x] `you` names the viewer, and the profile page shows the opponents by name as before.
- [x] Blocking from a match still blocks the right person. The export is unchanged.
- [x] Seat ids are unchanged by the shared helper.
- [x] Nothing stored changes. Tests cover the change. `npm run lint`, `npm run format:check`, the touched unit and
      integration tests and the relevant browser specs pass.

## Deployment impact

None to set up. No new env var (the key is derived from `SESSION_SECRET`), no new dependency, no index, no
migration, and no stored data changes: the ids are worked out on every read, so every match already in MongoDB
shows them at once, and the legacy collections are not touched. Seat ids are unchanged (a test pins one), so open
rooms and blocks carry on through the deploy. A rollback leaves nothing behind. During Render's overlap an old
instance still answers with player ids for a few seconds. Rotating `SESSION_SECRET` gives every match new ids, which
nothing stores.
