## Research (written before any code)

Sources were read on 2026-10-18 unless another date is given. "General knowledge" carries a confidence level.

### 1. How our code does it today

1. **The main button is already a character** (CC-221, done). `apps/web/src/pages/PlayPage/PlayPage.jsx` leads with
   `components/PlayComputer` ("Play Rocky", "Play Pip", "Play Queen Vee"), with a Computer badge, a one-tap level
   and the note on how computer games count. It sends `room:play-computer` and `botHandlers.js` seats the character
   at once (about 0.5 s to the first move, CC-221 notes). Below it: "Play a friend" (create a room, `lobby.create`)
   and join by code (`lobby.join`). The characters are in `packages/shared/src/bots.js`.
2. **There is no way to meet a stranger.** Rooms are private: only someone with the code or link can join
   (`roomComponent.joinRoom`). There is no pool, no queue and no public room list. The result screen's
   "New opponent" (`room.new_opponent`) only leaves the room.
3. **No rating yet.** ADR-027 decides Glicko-2 for chess only, but CC-042 is not built, so there is nothing to put a
   rating window on.
4. **No gate yet.** ADR-029 says "Find a person" may become the main button for an hour slot only when 60% of
   searches in that slot find a person within 4 s, and the timeout is the 80th percentile wait, at most 4 s. The flag
   table (CC-228), the nightly job (CC-176) and the telemetry (CC-173 to CC-175) are not built, and EVENTS.md has no
   event for a search.
5. **What a start needs.** Games start only with everyone connected (CC-112, merged in #78). The abuse limits of
   ADR-035 count waiting rooms per player and per network, and ADR-021 caps counted games per pair per day.
6. **No block list** exists (CC-044), so today nothing could keep two players apart.

### 2. How others do it

**Lichess** (source code of lila, https://github.com/lichess-org/lila, `modules/pool`):

1. One pool per time control, 11 of them (`PoolList.scala`), each paired in **waves**: 1+0 every 12 s or at 40
   players, 3+2 every 22 s or at 30, 10+0 every 13 s or at 30, 30+20 every 60 s or at 20.
2. Pairing (`MatchMaking.scala`) is a weighted matching on rating difference. The largest gap allowed depends on the
   lower rating: 130 under 1000, 100 under 1500, then rating / 15 (about 133 at 2000). Each missed wave lowers the
   score by 12, so the window widens the longer someone waits. A player's own rating range is respected.
3. **Blocked pairs are never paired** in the normal path (`blockList(a, b) || blockList(b, a)` is a conflict).
   Players marked for cheating or boosting are paired only with each other.
4. Bots are a separate "Play with the computer" button. Lichess's own engine never sits in a human pool (general
   knowledge, high confidence).

**Chess.com:** "Play" starts a search in the chosen time control, inside a rating range the player can set, which
widens as the wait grows (general knowledge, medium confidence. The support page for this did not resolve). Its bots
are named characters with avatars (Martin, Nelson and others) in a separate "Play Bots" section, always labelled
(general knowledge, high confidence).

**Papergames** (https://papergames.io/en/tic-tac-toe): three separate choices, "Play online with a random player",
"Play with a friend" (a link to send) and "Play vs robot" to "face our bot at any hour". The page says nothing about
how long a search takes or whether bots fill it.

**Bots in empty queues.** Some mobile games fill thin queues with bots that look like people, especially for new
players (general knowledge, medium confidence. No source fetched). That is exactly what ADR-025.1 forbids: every bot
is labelled before and during the match. India's CCPA 2023 dark pattern guidelines list "bait and switch" (cited in
PRODUCT_VISION.md §6.9, "Bots in quick match ... always labelled before the match starts").

**Liquidity.** Lichess's waves assume dozens of players in a pool every few seconds. We expect a handful of people
online at a time for months (GROWTH.md §1.3, §3.5). ADR-029 is our answer: crowd features stay behind numeric
gates, and the honest fallback (a character) is shown until the crowd is there.

### 3. What is best for ClassiCade

1. **Keep "Play <character>" as the main button** for every hour slot until its ADR-029 gate opens. It is what
   CC-221 built, and it is honest at any hour.
2. **Add "Find a person" as the second button**, above "Play a friend". It searches for at most 4 s (the ADR-029
   default, later the gate's measured 80th percentile). The search runs **in parallel with the page**: the character
   button stays usable, and the screen says plainly "Looking for a person… (up to 4 seconds)".
3. **When nobody is found**, say so: "Nobody is free right now." with two buttons, "Play Rocky (computer)" and "Try
   again". The search never seats a computer by itself, and a computer is never shown as a person, so no player is
   fooled (ADR-025.1). Keeping a search running while the player plays the character is a later step, not this
   ticket: it needs a way to offer the match between games and a rule for what happens to the computer game.
4. **One pool per game in server memory.** We run one instance (ADR-005), and a search lasts 4 s, so a restart losing
   the pool costs at most one retry. No new collection. Pair **at once** when two compatible players are waiting
   (no waves, the pool is too small). Rock Paper Scissors and Tic-Tac-Toe use their default options (best of 3).
   Chess uses one pool per quick time control, 3+2 and 10+0 (PRODUCT_VISION.md §6.1).
5. **Chess rating window, when CC-042 exists.** Start at ±150 (between Lichess's 100 and 130 at low ratings and its
   rating / 15 higher up) and widen to ±400 by the end of the 4 s, then to anyone after a "Try again". Provisional
   players ("?") get the wide window from the start. Until CC-042 ships, chess pairs first come first served, and
   the window is a pure function with tests waiting for the rating.
6. **Never pair** a player with themself (another tab), with someone either of them blocked (CC-044, both ways as
   Lichess does), or with someone they already played 10 counted games with today (ADR-021, so a pair cannot farm).
7. **Minors and strangers.** Quick match is the first feature that puts a player with a stranger. Players never talk
   (no chat, emotes off for minors and guests, ADR-028.6), and names already pass the filter (ADR-022). Lichess and
   Chess.com allow children in their pools. **Block and report (CC-044) must ship before "Find a person" goes live**
   (ADR-028.8 asks for them before contact features), so a player can stop meeting someone and report a name.
8. **Measurement for the gate,** without tracking (ADR-034): the server counts, per India hour slot and game,
   searches, searches matched within 4 s and the wait of matched searches in buckets. No player id. This needs a new
   server event in EVENTS.md (`quick_match_searched` with `game_id`, `outcome` `matched | timed_out | cancelled`, `wait_ms`
   rounded) that the owner accepts before it is sent. Until CC-174 exists, the counts can be a log line once a
   minute like the room gauge (ADR-035.6), with no ids.

## Why

A visitor alone can play now (CC-221), but nobody can ever meet a stranger. Without a search, the ADR-029 gate has
nothing to measure and can never open.

## Scope

- In: "Find a person" for every game, a 4 s search, an honest "nobody is free" with the character as the fallback,
  self, block and pair cap checks, counts for the gate.
- In, after CC-042: the chess rating window.
- Out: making "Find a person" the main button (CC-228 flips it per hour slot when the gate opens), staying in the
  queue while playing a character, CC-226 ("ping me when a person is free"), arenas (CC-210).

## Acceptance criteria

- [ ] "Play <character>" stays the main button on every game page.
- [ ] "Find a person" pairs two players searching the same game (and chess time control) and opens the room with

## Plan / notes

### Design

1. `packages/shared`: socket events `match:search { gameId, options }` (ack: searching), `match:cancel`, and the
   server's `match:found { code }` and `match:timed-out`. A `QUICK_MATCH_TIMEOUT_MS = 4000` named rule.
2. `apps/server/src/domain/matchmaking/`: a pure `pairFor(pool, seeker, { now, isBlocked, pairCapReached })`
   returning a partner or nothing, and a small pool component (one map per game key, entries with the player id,
   socket id, joined at, and later the rating). It creates the room through `roomComponent` with both seats, which
   also keeps every room limit in one place.
3. `service/realtime`: handlers that validate payloads, use the identity from the session, take a player out on
   cancel and disconnect, and time out with the injected clock.
4. Web: a `FindPerson` component under `PlayComputer` on `PlayPage`, with the searching and "nobody is free" states.

### Tests

1. Unit, pure: pairing order, self, blocks both ways, pair cap, the chess window and its widening over time (fake
   clock), timeout.
2. Unit, component: two searches pair, a cancel and a disconnect leave the pool, a timed-out search never seats a
   bot.
3. Integration (in-memory MongoDB): two sockets search and both get the same room code with the game started.
4. Browser: two pages search at once and meet. One page alone sees "Nobody is free" within about 4 s, and the
   character button there names the computer.
