## Problem

The owner is adding a lot to the site (more text, toasts, banners, requests, dialogs) and asked on 2026-10-20 that
"we have proper monitoring of all those things" while "we are not increasing the friction". Today the browser
reports nothing. The CC-233 console counts only what gameplay stores (`matches`, `accounts`), so when a guest lands
on a shared link, presses a card that does nothing three times and leaves, nobody ever knows. The catalogue of
what may be counted is written ([analytics/EVENTS.md](../analytics/EVENTS.md), ADR-034), but no code sends it.

## Job to be done

When a player uses the site, the owner wants every page, press, dead or rage click, error, connection change and
page load timing counted anonymously in the player's own browser and sent to our own server, so they can find what
is slow or confusing without tracking anyone.

## Appetite

M (up to 6 agent-hours). **Cut line:** first `page_speed_measured`, then the auth form events (3.3), then
`visit_ended`'s `presses` bucket. Pages, presses, dead and rage clicks, errors, `socket_changed`, `gameplay_started`
and the opt-out are never cut.

## Proposed solution

1. **One event module in `@classicade/shared`**, `packages/shared/src/telemetry/events.js`: every event name of
   EVENTS.md with its fields, each field a closed list or a bucketed number. The client builds events only through
   it, and CC-175's validator reads the same module, so the two can never drift. A name that is not in it throws.
2. **The client**, `apps/web/src/lib/telemetry/`: `track(name, fields)` adds the common fields (`build` from
   `buildStamp`, `route` template from `paths.js`, `device` from the viewport width, `player_kind` from the session),
   queues the event in memory and sends a batch to `POST /api/telemetry` every 10 s or at 20 events, and on
   `pagehide` with `navigator.sendBeacon`. A failed send is dropped, never retried more than once and never stored.
3. **Off switches, checked before anything is queued:** the `cc.telemetry` web storage key (ADR-034.3, the switch
   on the privacy page and the profile's Privacy settings), `navigator.globalPrivacyControl === true`,
   `navigator.doNotTrack === "1"`, the browser test flag (CC-178) and local development. When off, `track` is a
   no-op and nothing records that the player opted out.
4. **Presses.** One capture-phase `pointerup` and `keydown` (Enter, Space) listener on `document`, reading the
   nearest `data-cc-control` (CC-170 stable control ids, 54 files already carry them). `control_pressed`;
   `dead_clicked` (a pressable-looking element with no control, or a control press that changed nothing, sent no
   request and did not navigate within 1 s, measured with a `MutationObserver` window); `rage_clicked` (3 or more
   presses within 700 ms and 30 px, detected in the browser and sent as one event). No text, no coordinates leave.
5. **Pages and visits.** `page_viewed` from the router (landing `entry` and `via` per CC-279), `visit_ended` on
   `pagehide` with the `active_s` and `presses` buckets.
6. **Errors and connection.** `ErrorBoundary.jsx`, `window` `unhandledrejection`, chunk load failures and the stale
   build reload send `client_errored` with the error type only. `lib/api.js` sends `request_failed` with the route
   template. `lib/socket.js` sends `socket_changed`.
7. **Funnel and speed.** `gameplay_started` on the first move of the page load (with CC-220), `page_speed_measured`
   from `PerformanceObserver` (TTFB, FCP, LCP, INP, CLS), `action_waited` from `useAction` (CC-240's client slice).
8. **A hook for CC-313:** `track` accepts the interruption events CC-313 adds, and press events carry `surface` when
   the press landed inside an interruption. CC-313 owns those fields; this ticket only leaves the slot.
9. **Behind the flag** `telemetry_client` (CC-312). Off means `track` is a no-op.

## Non-goals

- Any third-party script or service, session replay, heatmaps by coordinates, or autocapture of text.
- Any id: player, session, device or page load (ADR-034.1). Sequences are worked out in the browser.
- The adult tier (EVENTS.md Q1, not built).
- The privacy page wording itself is CC-173, which must merge first or in the same PR (EVENTS.md section 5).
- Server-side events (`account_created`, the room events): CC-175 and CC-242.

## Rabbit holes

- **Dead click false positives.** Animations, focus rings and the request banner's ticker mutate the DOM without
  being an answer. Elements marked as tickers (RequestBanner already marks its countdown) are ignored, and the
  window watches only the press's own region and the route.
- **Bundle weight.** The client must stay under 4 KB gzipped and load after first paint (`requestIdleCallback`),
  so it never slows the time to first move it measures.
- **Back and forward cache.** `pagehide` with `persisted` is not the end of a visit. Send the batch but not
  `visit_ended`.

- **AC-2** Given `cc.telemetry` set to off, or GPC, or DNT, when the player presses controls and changes pages, then

  `apps/web/src/lib/telemetry/client.test.js` › "sends nothing when opted out, with GPC or with DNT"
- **AC-3** Given 20 queued events, or 10 s passing, or `pagehide`, when the client flushes, then exactly one batch is
  sent (`sendBeacon` on `pagehide`), and a failed send is dropped after one retry. Test:
  `apps/web/src/lib/telemetry/client.test.js` › "batches by count, by time and on pagehide"
- **AC-4** Given any event the client builds, when its payload is checked, then it has only the common fields and its
  own catalogue fields, every value from a closed list or a bucketed number, and no id, text, URL or room code.
  Test: `apps/web/src/lib/telemetry/events.test.js` › "every payload carries only catalogue fields"
- **AC-5** Given three presses within 700 ms and 30 px, when they land, then one `rage_clicked` is sent with the
  control and a `presses` bucket. Test: `apps/web/src/lib/telemetry/clicks.test.js` › "three quick presses are one
  rage click"
- **AC-6** Given a press on a pressable-looking element with no `data-cc-control`, or a control press that changes
  nothing within 1 s, when 1 s passes, then one `dead_clicked` is sent; a ticker's change does not count as an answer.
  Test: `apps/web/src/lib/telemetry/clicks.test.js` › "a press that changes nothing is a dead click"
- **AC-7** Given a render error, an unhandled rejection, a chunk load failure, a failed API call and a dropped socket,
  when each happens, then `client_errored`, `request_failed` or `socket_changed` is sent with the type or code only,
  never a message or stack. Test: `apps/web/src/lib/telemetry/errors.test.js` › "errors carry the type, never the
  message"
- **AC-8** Given the flag `telemetry_client` off, when the app runs, then `track` sends nothing; on, it sends. Test:
  `apps/web/src/lib/telemetry/client.test.js` › `flagPaths("telemetry_client")`
- **AC-9** Given the production build, when its size is measured, then the telemetry chunk is under 4 KB gzipped and
  loads after first paint. Test: `apps/web/src/lib/telemetry/size.test.js` › "the client stays under 4 KB gzipped"

## Instrumentation

Adds every client event of EVENTS.md sections 3.1, 3.2, 3.3 (client rows), 3.4 (`gameplay_started`), 3.5 (client
rows) and 3.6 (`action_waited`), with the common fields `name`, `build`, `route`, `device`, `player_kind`. Counts
tier only, no ids, no free text, no URLs (ADR-034). The flag's success event: a batch accepted by CC-175 (`204`).

## Threat model

1. **What are we building:** a browser module that turns presses, pages, errors and timings into anonymous events.
2. **What can go wrong:** text or ids leak into a field (a control name built from a value, an error message, a
   path with a room code); the client becomes a fingerprint (many fields combined); it slows the page; opt-out is
   ignored.
3. **What we do about it:** every field is a closed list or a bucket from one shared module, checked in tests on
   every payload; routes are templates; errors carry only a constructor name from a list; opt-out and GPC are
   checked before queueing; the client loads after first paint with a size budget.
4. **Good enough?** CC-178's browser check fails on any payload with an id-like value, and CC-175 drops anything the
   catalogue does not allow, so a mistake here is stopped twice.

## Privacy checklist

- **Data:** counts of pages, presses, dead and rage clicks, errors by type, connection changes, timings, about every
  visitor, guest and account, with no id of any kind.
- **Retention:** nothing kept in the browser beyond the in-memory queue. Raw 30 days and totals 13 months are CC-175
  and CC-176.
- **Who sees it:** nobody but the owner's console (CC-177), as totals with `"<5"`.
- **Minors (ADR-028):** the same counts tier as everyone, which carries no id, so nothing about a minor is linked to
  that minor (EVENTS.md section 2). On by default for minors pending EVENTS.md Q4, which ADR-034 keeps on.
- **Defaults:** on, with one switch to turn it off (privacy page and profile), and off with GPC or DNT. The player
  can change it at any time in this browser.

## Alternatives considered

- **PostHog or another hosted SDK:** autocapture collects element text and a distinct id by default, and sends data
  to a third party, against PRODUCT_VISION D15 and ADR-034.1.
- **Plausible (self-hosted):** cookieless and counts-first, but its daily visitor hash still reads IP and
  User-Agent, it needs its own server and ClickHouse (more than the free instance), and it does not do dead clicks.
- **Server logs only:** cannot see dead clicks, rage clicks, page speed or client errors.

## Research (written before any code)

1. **Our code today.** No browser telemetry. 54 files carry `data-cc-control` (CC-170). `buildStamp.js` already
   names each build (CC-290). `useAction` already measures the wait from press to answer for "Sending…" (CC-239).
   Ops telemetry (ADR-055, CC-286) is server-only and goes to Grafana; it never carries product events.
2. **Other products.**
   - PostHog autocapture ([docs](https://posthog.com/docs/product-analytics/autocapture), read 2026-10-20) fires
     `$rageclick` after three clicks each within 30 px and 1 s of the previous, configurable, and ignores steppers
     and next/previous controls; dead clicks are opt-in ("a click that isn't followed by a change to the page").
     We borrow the definitions, not the SDK, since it sends a distinct id and element text by default.
   - Plausible ([data policy](https://plausible.io/data-policy), updated September 2026) sets no cookies and no
     persistent id, and drops query strings; its visitor hash rotates daily but still reads IP and User-Agent. We
     go one step further: no hash at all.
   - Google's HEART framework (Rodden, Hutchinson and Fu, "Measuring the User Experience on a Large Scale:
     User-Centered Metrics for Web Applications", CHI 2010,
     [research.google](https://research.google/pubs/measuring-the-user-experience-on-a-large-scale-user-centered-metrics-for-web-applications/)):
     Happiness, Engagement, Adoption, Retention, Task success, each from Goals to Signals to Metrics. This client
     supplies the Task success and Engagement signals; Retention stays with `matches` (ADR-034).
   - Nielsen Norman Group, "Modal & Nonmodal Dialogs: When (& When Not) to Use Them" (Therese Fessenden, 2017,
     [nngroup.com](https://www.nngroup.com/articles/modal-nonmodal-dialog/)): interrupt only when it is worth its
     cost. That cost is what CC-313 measures through this client.
3. **Best for ClassiCade.** Our own small client, one shared catalogue, everything worked out in the browser and sent
   as anonymous counts: it fits the free instance, ADR-034, minors' rules and the owner's "no friction" ask.

## Build notes (2026-10-20, branch `cc-174-175-telemetry`, with CC-175 and CC-173 in one pull request)

1. **Two parts.** `lib/telemetry/facade.js` is in the first file the page loads: `track` holds events in memory (100
   at most) until the client is loaded, or drops them when the flag is off or counts are switched off, and it counts
   requests for the dead click check. Everything else (`index.js`: the client, presses, page speed, the end of the
   visit) is its own file, loaded by `TelemetryHost.jsx` when the browser is idle after the first paint, and only
   when `telemetry_client` is on: 3.8 KB gzipped today (`size.test.js` prints it), under the 4 KB budget.
2. **Off before anything is held:** the `cc.telemetry` switch (privacy page section 4a and the profile's privacy
   settings), GPC, DNT, `navigator.webdriver` (every browser test) and a laptop's host. A browser that cannot keep web
   storage counts as switched off, because its switch could never work.
3. **The flag's answer** is read with `useFlagState` (a small addition to `useFlag.js`), so "not answered yet" holds the
   landing page view instead of dropping it, and the client keeps running while the answer is asked again for a new
   session. `flagSources.js` reads `useFlagState("…")` too.
4. **Wiring without globals.** The composition root gives the facade to the API client (`onRequest`, `onFailure`), the
   socket client (`onRequest`, `onChange`, `onFirstMove`), the stale build guard (`onFailedLoad`) and the error
   boundary (`onError`). `useAction` reads it from the services, if any.
5. **`action_waited.transport`** is the transport the press actually used, from the request counts before and after;
   a press that sent nothing is not counted. `gameplay_started` is the first `game:move` acknowledged on this page
   load, with the landing's `entry`.
6. **Dead clicks.** A control press is dead when, within 1 s, nothing changed in its region (`data-cc-ticker`
   subtrees ignored), no request went out and the address did not change. A pressable-looking element without a
   control is dead by definition (EVENTS.md 3.2): a pointer cursor on it or just above it, an image, a link or a
   button. Plain text never counts (owner, 2026-10-20). Any request on the page answers a press, which can hide a
   dead click during a busy moment: accepted.
7. **The CC-313 slot.** `watchClicks` takes `surfaceOf(element)`, and `startTelemetry` passes it on. CC-313 fills it.
8. **Test names.** The ACs' tests are in `client.test.js`, `events.test.js`, `clicks.test.js`, `errors.test.js` and
   `size.test.js` as named; `client.test.js` holds the `flagPaths("telemetry_client")` suite (AC-8) with the real host.

## Review fixes (2026-10-21, the coordinator's review of #161)

1. **The switch reaches the server:** the API client sends `X-CC-Counts: off` on every request while the switch is
   off (`countsOff` in `lib/api.js`), so the server records no event of its own about this browser.
2. **A client never starts after its flag went off** while its file was loading: the host reads the flag's latest
   answer when the file arrives.
3. **Error types come from `error.name`,** so DOM errors (`AbortError`, `QuotaExceededError`) and the minified
   `AppRequestError` get their type.

## The first route's budget (2026-10-22, after CC-322's bundle gate, design lead's decision)

Merged with main, usage counts put the first route at 152.96 kB gzip, over CC-322's 150 kB. The design lead set
telemetry's cost to the first route at about 2 kB. It is now 0.9 kB (main 146.61 kB, this branch 147.52 kB):

1. **The small values the first page needs** (player kinds, entries, buckets, error types, socket codes, the longest
   times, `roundMs`, `bucketOf`) live in `packages/shared/src/telemetry/early.js`, apart from the catalogue
   (`events.js`) and the field rules (`fields.js`). The shared package says it has no side effects
   (`"sideEffects": false`), so the bundler leaves out the modules the first page does not use.
2. **A first-route stub** (`TelemetryStub.jsx` with the facade) tells the facade the address and the kind of player,
   and counts each page view. Everything counted early (a render error, the first page view, a failed request) waits
   in the facade with the address it happened at. Once the browser is idle the stub loads the host
   (`TelemetryHost.jsx`), which asks the flag and loads the client. The client turns each address into its screen
   (`routeOf`, given by the host) and makes the fields an event gave as a function (`request_failed`'s endpoint,
   from `endpointOf`). The screens and the API templates no longer load with the first page.

## Review of the reworked #161 (2026-10-22)

1. **The client's budget is 5.5 KB (design lead's decision).** AC-9's test now builds the app as in production and
   measures the real chunk whose entry is `lib/telemetry/index.js`: **4,963 bytes gzipped** (11,480 minified). The
   earlier test left the shared package out, so it measured about 4 KB. Since CC-322 the catalogue (`events.js`,
   about 1.7 KB) and the field rules (`fields.js`, about 0.35 KB) load with the client instead of the first page,
   and the client needs them to check every event before it is sent (ADR-034). Getting back to 4 KB would mean
   dropping that check in the browser, so the budget for this file, which loads only when the browser is idle, is
   5.5 KB.
2. **Early counts wait for the session.** The stub tells the facade the kind of player only once the session has
   answered (anonymous, ready or error), and keeps the last kind while it is asked again. Anything counted before that
   waits and takes the kind the session settles on, so a returning guest's landing page view says `guest`. The page
   view waits too, once per settled address, and the host loads only after the answer.
3. **A failed download never reloads the tab.** The host's and the client's files download through the stale build's
   `quietly` (as Socket.IO's does, CC-333), a failure is caught, and each is tried once more when the browser is idle.
   The host waits for an idle moment with `lib/idle.js`.
