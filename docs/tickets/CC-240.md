## Research (written before any code)

To be written by the builder before any code: how our code does it today, how other products do it (with sources
and dates), and what is best for ClassiCade.

## Why

The owner wants latency recorded now and acted on later from trends (2026-10-18), not as a P0. Today HTTP requests log `durationMs` to Render's short-lived logs, socket events record no timing, and nothing measures what a player waits from press to answer.

## Scope

- In: server timing of every socket event and HTTP route (name, duration, outcome; no identity); the browser's press to answer wait per `data-cc-control`, batched through the first-party telemetry endpoint of CC-175; a daily p50 and p95 per action for the console.
- Out: third-party monitoring; anything that identifies a player; alerts (later).

## Acceptance criteria

- [ ] Every socket event and route has a duration recorded, tested
- [ ] Press to answer waits arrive batched and anonymous, opt out respected (CC-173)
- [ ] Daily p50 and p95 per action are readable by the owner
- [ ] Tests cover the change
- [ ] `npm run lint`, `npm run format:check`, `npm test` pass
- [ ] Docs updated (BACKLOG status, KNOWN_ISSUES, PROGRESS)
