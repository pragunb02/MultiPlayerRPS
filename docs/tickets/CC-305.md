## Research (written before any code)

### 1. How our code does it today

1. Named log lines (ADR-055.1.7) go from pino's second stream into the OpenTelemetry Logs SDK, whose
   `BatchLogRecordProcessor` exports them every `OTEL_METRIC_EXPORT_INTERVAL` (60 s by default)
   (`dependency/telemetry/openTelemetry.js`). A line written just before `process.exit` waits in that batch and is
   lost with the process.
2. `handleFatalErrors` (`server.js`) writes `uncaught exception` or `unhandled promise rejection` and calls
   `proc.exit(1)` at once. Nothing is flushed, so neither line ever reaches Grafana.
3. `handleShutdownSignals` writes `shutting down`, calls `close()`, then writes `shutdown complete` (exit 0) or
   `error during shutdown` (exit 1). A 10 s timer writes `shutdown timed out, forcing exit` and exits 1. None of
   the three last lines is flushed.
4. `index.js` `close()` is `await server.close(); await telemetry.shutdown();`. So when `server.close()` rejects,
   telemetry is never shut down, and `shutting down` and everything since the last export are lost too. When it
   resolves, telemetry is shut down before `shutdown complete` is written, and the stopped SDK drops that line.
5. `telemetry.shutdown()` is already bounded: it races both providers' shutdown against 5 s and runs only once
   (`stopped ??=`). After it, the Logs SDK drops any new record.
6. Other callers of the two handlers (`e2e/app.mjs`, `scripts/bin/load-serve.mjs`, `scripts/bin/load-moves.mjs`)
   run without telemetry.

### 2. How other products do it

1. The OpenTelemetry Logs SDK specification says `ForceFlush` and `Shutdown` "SHOULD complete or abort within some
   timeout", and that `Shutdown` "MUST include the effects of `ForceFlush`"
   (https://opentelemetry.io/docs/specs/otel/logs/sdk/, read 2026-10-20). So the last step before exit is one
   shutdown, which exports what is waiting, with a time limit.
2. Render sends `SIGTERM` and waits 30 s by default before `SIGKILL` (`maxShutdownDelaySeconds`,
   https://render.com/docs/deploys, read 2026-10-20). Our 10 s drain plus a 5 s last flush is 15 s, inside that.

### 3. What is best for ClassiCade

Write the last line first, then flush with a bound, then exit, on every way out. The flush must come after the
last line, so it cannot live in `close()`: anything `close()` does runs before `shutdown complete` or `error during
shutdown` is written. The handlers get the flush injected, so they stay testable and the composition root decides
what is real.

## Root cause

The handlers exited right after their last line, and the only flush was inside `close()`, before the last line,
and skipped when `server.close()` failed.

## Design

1. `handleShutdownSignals({ close, flush, logger, proc, timeoutMs, flushWithinMs })` and
   `handleFatalErrors({ flush, logger, proc, flushWithinMs })` take a required `flush: () => Promise<void>`.
2. One helper, `exitAfterFlush`, is the only way out of each handler: it awaits `flush()` raced against
   `flushWithinMs` (5 s), treats a failed flush like a finished one, then calls `proc.exit(code)`. It runs once, so
   a timeout and a late `close()` cannot both exit, and a line written after the way out started (a late
   `shutdown complete`) is not written.
3. In `handleShutdownSignals` the drain is a `try`/`catch`/`finally`: `shutdown complete` or `error during shutdown`
   is written, the drain timer is cleared in `finally`, then `exitAfterFlush` runs. So a failed close still
   flushes. The timer path writes `shutdown timed out, forcing exit`, then `exitAfterFlush(1)`.
4. `index.js` passes `flush: telemetry.shutdown` to both handlers and `close` closes the server only. The review
   asked for a `try`/`finally` in `index.js`, so that a failed `server.close()` still shuts telemetry down. That
   would shut telemetry down before the handler writes `error during shutdown`, so that line would still be lost.
   The `try`/`finally` lives in the handler instead, after the last line, which covers the failed close and
   delivers its line.
5. `shutdown complete` stays in `NAMED_LINES`, because it is now flushed after it is written.
6. The bound timer is not `unref`ed: after a crash nothing else may hold the process open, and it must still exit
   with code 1, not 0.
7. `e2e/app.mjs` and the two load scripts pass a flush that does nothing, as they run without telemetry.
8. ADR-055 gains a dated amendment: the last line of every way out is flushed, within 5 s more.

## Scope

- In: the two handlers, `index.js`, the three other callers, tests, ADR-055 amendment.
- Out: a crash during start up, before the handlers are wired (it is printed to stdout, as today). Lines held back
  by the 30 a minute cap.

## Acceptance criteria

- [x] With a telemetry exporting into memory, the last named line of each way out reaches the log exporter:
      `uncaught exception`, `unhandled promise rejection`, `shutdown complete`, `error during shutdown`,
      `shutdown timed out, forcing exit`.
- [x] A failed close still flushes, and exits 1.
- [x] A flush that never answers holds the exit for 5 s at most, and a failed flush still exits.
- [x] Tests failed before the fix.
- [x] Docs: this file, ADR-055 amended.

## Verification

1. Failing first, on `main` with only the tests changed (`server.test.js`, new `server.lastLines.test.js`): 13
   failed, 46 passed. On `main` each way out exited before its line reached the exporter, a late close exited a
   second time, and the handlers took no flush.
2. After: those two files, 59 passed. `npx vitest related` on `server.js`, `index.js`, `e2e/app.mjs` and the two
   load scripts, `--maxWorkers=2`: 45 files, 528 tests, all passed but `chessRatings.integration.test.js`, which
   timed out at 5 s under this machine's load (it does the same on `main` here) and passed on rerun.
3. Ran it for real: `apps/server/src/index.js` with telemetry on, pointed at a local OTLP receiver, a throwaway
   in-memory MongoDB and `SESSION_SECRET` made for the run, all on 127.0.0.1 (port 4996), then SIGTERM. On `main`
   the receiver got `server listening`, `telemetry on` and `shutting down` but not `shutdown complete`. After, it
   got all four. Everything was stopped afterwards.
4. ESLint and Prettier on the changed files pass.
