## Problem

The owner asked (2026-10-22): "on all features, on all pages, on all small things, everything should be easy to
understand: what to do, how to do it, and how to play along." There was no checklist for this and no audit of it.
CC-320 audited the look, layout and accessibility, not whether a first-time player understands each screen.

## Fix

A checklist in the design contract, and an audit against it. No app code changes.

- **The checklist.** [CONTRACT.md section 7](../design/CONTRACT.md#7-clarity-cc-348): three questions every screen
  answers, then C1 to C12.
- **The audit.** [CLARITY-AUDIT.md](../design/CLARITY-AUDIT.md):
  - 97 findings: 3 block play, 44 confuse and 50 are polish. Each has evidence and the exact new words.
  - the top 10;
  - eight fix batches that share no files, plus a test batch;
  - six proposed automatic checks;
  - three questions for the owner.

**Research note.** How our code does it today:

- How to play exists as three steps per game (CC-259), shown only at the bottom of the lobby.
- There are no first-time hints.
- Errors pass the server's text through.
- Hinglish already uses "tum" everywhere.

**Sources checked:**

- Nielsen's 10 heuristics, and NN/g on error messages, empty states and icon usability;
- GOV.UK Design System, on buttons and error messages, and the GOV.UK writing guidelines;
- Material Design's empty states;
- Apple HIG, on onboarding and loading;
- Celia Hodent's GDC 2015 onboarding talk and _The Gamer's Brain_.

The audit's checklist section links each one.

**How.**

- **Walk.** The e2e server on loopback only, and an uncommitted Playwright spec run with `--workers=1` on a desktop
  (1280 × 720) and a phone (390 × 844).
- **States.** 152 states, built with `e2e/matchStates.js`, and 281 screenshots pushed to `pr-evidence` under
  `cc-348/`.
- **Code.** A read of the copy in `apps/web/src`, for the states that are hard to reach.

## Acceptance criteria

- **AC-1** Given the contract, when a reviewer quotes clarity, then CONTRACT.md has a numbered section with the three
  questions and the checks the owner listed, each backed by a source.
- **AC-2** Given the audit, when the coordinator plans the fixes, then every finding has the screen, the state, what is
  unclear, evidence (a screenshot on `pr-evidence/cc-348/` or a code reference), a fix in exact words, a severity and
  a batch, and no file is in two batches.
- **AC-3** Given the repo, when this merges, then no app code, `BACKLOG.md`, `PROGRESS.md` or next free line has
  changed.
