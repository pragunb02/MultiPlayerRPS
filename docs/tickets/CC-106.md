## Why

The server trusted exactly one proxy (`trust proxy 1`, hard-coded). If more than one proxy sits in front of it on
Render, `req.ip` is the address of a proxy, not of the player. Every per-address limit (sign-up and login 20 per
15 minutes, guests 30 per 15 minutes, leaderboards 120 a minute) would then be shared by every player behind that
proxy, and at launch real players would get "too many attempts" after a handful of sign-ins.

## Scope

1. In: the trusted hop count as configuration (`TRUST_PROXY_HOPS`, validated, documented). Every limiter keys on the
   client address through one helper. A startup log line with the hop count in effect. The number of
   `X-Forwarded-For` entries (never the addresses) on each access log line, so the real hop count can be read from
   production logs. Tests with multi-hop chains and forged left-most entries.
2. Out: keying on a provider header such as `CF-Connecting-IP` or `True-Client-IP` (Render does not document them for
   web services, and a header is only safe when every request is known to pass the proxy that sets it). Socket
   rate limits (per connection, CC-101 area).

## Acceptance criteria

- [x] `TRUST_PROXY_HOPS` is read and validated in config: a whole number 0 to 5, at least 1 in production, default 1 in
      production and 0 elsewhere. Invalid values stop boot with a clear message.
- [x] The app sets `trust proxy` from it and logs `client addresses read through trusted proxies` once, with
      `trustProxyHops` and no address.
- [x] Auth, guest and leaderboard limiters and the app-wide limit (CC-110) all key on `clientIpKey` (`req.ip`, IPv6
      grouped by /56).
- [x] Tests pin that players behind the same proxy get their own budget, that forged left-most entries cannot change
      the key, and that a too-low hop count makes players share the proxy's budget.
- [x] DEPLOYMENT.md documents the variable, the risks of too low and too high, and how to find the real hop count.
- [x] Tests cover the change. `npm run lint`, `npm run format:check`, `npm run test:coverage` pass.

## Plan / notes

1. Research: Render's docs do not say how many proxies forward a request or which headers they add. Render fronts
   services with Cloudflare for DDoS protection (render.com/docs/ddos-protection), and other public projects on Render
   disagree on whether that is one hop or two. So the hop count cannot be fixed in code with confidence.
2. Default 1 in production because it is the only value that can never be forged: the right-most entry is always
   written by Render's own proxy. A value that is too high would let a script choose its own key and bypass every
   per-address limit, which is worse than sharing a budget.
3. To set the right value without logging addresses, the access log now has `forwardedEntries`. A browser sends no
   `X-Forwarded-For`, so on your own request that count is the number of proxies. DEPLOYMENT.md has the steps.
4. All limiters are now built by `createRateLimit` in `service/http/rateLimits.js`, so the 429 body, the headers and
   the key are the same everywhere.

## Verification

1. Unit tests in `rateLimits.test.js` (two-hop chains, forged entries, hop count too low, IPv6 grouping) and
   `config/index.test.js` (defaults, range, production minimum).
2. App tests in `app.test.js`: hop count from the environment, startup log, app-wide and guest limits keyed on the
   real player behind two proxies.
3. After merge: follow DEPLOYMENT.md "Client addresses and rate limits" to read `forwardedEntries` from one of your
   own requests and set `TRUST_PROXY_HOPS` in Render.
