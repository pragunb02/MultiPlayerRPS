## Problem

While reproducing CC-340 under CPU load, three tests in `apps/server/src/service/realtime` failed now and then, on
main as well. Each one assumed an order of events that a busy runner does not keep.

**Root causes.**

1. **`ratings.test.js` "leaves the computer player out of a game against Queen Vee"** failed with "operation has
   timed out", the 2 s answer limit of `send`. Queen Vee plays White and moves at once (testApp's computers pause
   0 ms), and the test server thinks in process (`inProcessThinking`), on its own event loop. Her Strong level took
   about 350 ms with coverage for that first move on an idle laptop (timed with a temporary log line, three runs:
   342 to 357 ms), and several times that on a loaded runner. When the think started before the `rating:room`
   request was read, the answer waited behind the whole search, past 2 s.
2. **`chess.test.js` "tells the opponent when the offerer withdraws"** expected Alice's next update to show the
   withdrawn offer, and got the offer itself (`state: "open"`, seen in the CC-340 batch logs). The test began to
   listen on Alice's socket only after Bob's request was answered on Bob's socket. Nothing orders the two sockets,
   so Alice's update about the offer could arrive after that and be taken for the withdrawal.
3. **`connections.test.js` "lets a request in flight finish"** timed out at 5 s. It waited 50 ms for its `/slow`
   request to reach the server. On a busy runner closing began first, `closeIdle()` found a connection with no
   request in flight and ended it, as it should, so the answer the test waited for never came.

## Fix

Each test waits for what it needs, never on a clock, and no retry or longer timeout is added:

1. The Queen Vee test plays her easiest level, which thinks in about 2 ms with coverage. Any level is left out of
   the ratings, which is what the test proves.
2. The withdrawal test listens on Alice's socket before Bob offers, sees the open offer, and only then listens for
   the withdrawal, as the decline test beside it already does.
3. The in-flight test waits for the server's `request` event (as "forgets a connection the browser hung up on"
   already does) instead of 50 ms. `trackConnections` counts the request in a listener put first, so it is counted
   by then.

**Research.** How our code does it now: `send` in `testing/socketClients.js` gives every answer 2 s, and
`nextEvent` resolves with the next push of any kind. Socket.IO orders events on one connection only, never across
two clients (<https://socket.io/docs/v4/delivery-guarantees#message-ordering>). Node's `http.Server` emits
`request` once a request's head is parsed (<https://nodejs.org/api/http.html#event-request>), which is the moment
the request is in flight. testApp's thinking runs on the event loop by design (`inProcessThinking.js`), so a test
picks a cheap level unless the search itself is under test (CC-309 did the same for the load harness).

## Reproduction

The three files with coverage, `--maxWorkers=2`, under CPU burners (`node -e 'for(;;){}'`, killed after each
batch):

| Code        | Burners | Runs | Queen Vee | Withdrawn draw | Request in flight |
| ----------- | ------- | ---- | --------- | -------------- | ----------------- |
| main        | 56      | 36   | 6 failed  | 0              | 0                 |
| main        | 8       | 20   | 0         | 0              | 0                 |
| this branch | 8       | 20   | 0         | 0              | 0                 |

The coordinator capped burners at 8 after the first batch, as the machine was shared, and at 8 main no longer
fails. In CC-340's 40 loaded runs of the whole realtime folder the three failed 7, 1 and 1 times. So the last two
are proved by forcing the order each one assumed away, a temporary change not committed:

- Alice's pushes delayed by 100 ms on her client: main's withdrawal test fails, this branch's passes.
- The `/slow` request written 100 ms late: main's in-flight test fails, this branch's passes.

## Acceptance criteria

- **AC-1** Given a slow computer think on the test server, the Queen Vee rating test does not wait behind it.
- **AC-2** Given Alice's pushes arriving late, the withdrawal test still sees the offer, then the withdrawal.
- **AC-3** Given the request reaching the server late, the in-flight test still waits for it before closing.

## Test

The three tests themselves, with the reproduction above: under load, and with each delay forced.
