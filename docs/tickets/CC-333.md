## Problem

Socket.IO's client, about 16.6 kB of gzip (CC-322, finding 3), is in the first download of every page, even home,
which needs no realtime connection to draw. It leaves the first route at 146.9 kB against the 150 kB budget.

## Fix

A small socket facade stays on the first route. It keeps every subscription and request made before Socket.IO is
here, and downloads `socket.io-client` on demand: at once on the pages that need the connection to show anything
(room, challenge, friends), and when the browser is idle after the first paint on every other page.

### Research

**How our code does it today.** `main.jsx` creates the one realtime client, `lib/socket.js`, which imports
`socket.io-client` statically and makes its socket with `autoConnect: false`. Nothing connects until
`SessionProvider` knows who the browser is: after `GET /api/session` answers (or after a guest start, a log in or a
sign up), `adopt` calls `socket.disconnect()` then `socket.connect()`. So on today's site the connection already
starts only after the first render and after one HTTP round trip. Every other part of the app only calls
`socket.on(event, handler)` (with its unsubscribe), `socket.request(event, payload)`, `socket.isConnected()` and
`socket.onEndedByServer(handler)`.

**What on the first route needs the socket, and how soon.** These are all mounted around every page (`App.jsx`,
`Layout.jsx`), so they are on home too:

| Feature                                                    | What it uses                                                                              | Needs it at once?                                                                                                                                                                                                                         |
| ---------------------------------------------------------- | ----------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Presence (rooms): away, not offline, in a seated room      | the server, on `connection` (`handleSocketOnline`)                                        | No. The server marks the player on site when the socket connects, whenever that is.                                                                                                                                                       |
| Site-wide requests, the CC-207 popups (`useSiteRequests`)  | `request:updated` pushes, and `connect` to forget what it knew                            | No. On every connect the server sends the requests of every room the player sits in (`handleSocketOnline`), so a later connect still shows every open request. Answering one is a `request`, which loads the client at once.              |
| Challenge popups and the inbox (`ChallengesProvider`)      | `GET /api/challenges` on mount, again on every `connect`; then `challenge:updated` pushes | No. The list comes over HTTP, and is read again on connect, so a push missed before connecting is made up by that read. Moving a challenge to the inbox is HTTP.                                                                          |
| Session follow, ADR-033 (`SessionProvider`)                | `onEndedByServer`; the other tabs' message is a `BroadcastChannel`, not the socket        | No. The broadcast does not use the socket. A stale or signed out session is refused at the handshake (`connect_error` UNAUTHORIZED), which is still reported, only once the handshake happens.                                            |
| Friends presence and the friends list (`useFriends`)       | `friends:updated`, `friends:presence` pushes                                              | On the friends page, yes: a presence change between the HTTP read and the connect would be missed until the next one, so that page connects at once. Elsewhere friends see the player online from the connect (`friendPushes.tabOpened`). |
| Friend request toasts, progress and achievement toasts     | `friends:request`, `progress:updated`, `achievements:unlocked` pushes                     | No. They follow something the player did (a game, which only happens on the room page) or someone else did, and there is no catch-up for them today either: a push before the connect is never sent.                                      |
| The reconnecting banner (`useConnection`, CC-158)          | `disconnect`, `connect`, `server:restarting`                                              | No. It only reports a drop after a connection.                                                                                                                                                                                            |
| Room page (`useRoom`), challenge page (`useChallenge`)     | `room:join` on `connect`, room and challenge pushes                                       | Yes: nothing of the room shows until it joins, and a challenge page watches a challenge that can be taken any second.                                                                                                                     |
| Lobby "Create room", "Play the computer" (`useCreateRoom`) | `request`                                                                                 | A request loads the client at once. By the time a person presses the button the idle load is long done.                                                                                                                                   |

**What connecting after first paint or when idle changes.** The server can only send to a connected socket, so
nothing that was sent can be lost: the facade attaches every subscription before the socket can connect, in the
order they were made. What changes is only when the connection starts on the pages that wait for idle, which is
already after the session answer today:

- **Reconnect.** Unchanged. Once loaded, Socket.IO's own manager reconnects exactly as before. The facade only adds
  the first download; a failed download is tried again the next time the connection is wanted.
- **CC-207 popups.** Unchanged in content: they are rebuilt from the server's catch-up push on connect. On home a
  popup can appear one idle period later than today (milliseconds after the first paint, at most a second).
- **Stale sessions (CC-234).** Unchanged. A session that may no longer be used is refused at the handshake and
  `onEndedByServer` still fires, because its listeners are attached before the first connect.
- **Pushes with no catch-up** (a friend request toast, a friend coming online) that the server sends in the extra
  moment before the connection are not seen, as they are not seen today in the moment before the session answers.
  The window grows by at most the idle wait on pages other than room, challenge and friends.
- **A tab opened before a deploy** that downloads the client after the deploy gets a missing file. Vite reports it
  as `vite:preloadError`, and `staleBuild.js` reloads the tab once, as for a lazy page (CC-181).

**How others do it.** Philip Walton's _idle until urgent_ pattern (https://philipwalton.com/articles/idle-until-urgent/)
defers non-critical work to `requestIdleCallback` but runs it at once the moment something needs it, which is the
facade's two triggers: idle, or a page or a request that needs the socket now. Socket.IO's own client buffers what
is emitted while it is not connected and sends it on connect
(https://socket.io/docs/v4/client-offline-behavior/#buffered-events), so a facade that also buffers until the
library is here keeps the same contract. `requestIdleCallback` is not in Safari (MDN,
https://developer.mozilla.org/en-US/docs/Web/API/Window/requestIdleCallback#browser_compatibility), so a short
timer stands in there; the `timeout` option bounds the wait on a busy main thread. React's own `React.lazy` and
Vite's dynamic `import()` are what the app already uses for its pages (CC-322).

**Best for ClassiCade.** A facade with the same interface as today's client, so no page or hook changes; the page
table in `routePages.js` says which pages need the socket at once, so the boot code and the router use one list;
and the bundle check fails if Socket.IO comes back to the first route.

## Acceptance criteria

- **AC-1** Given a build, when `node scripts/bin/check-bundle.mjs` runs, then no `socket.io-client`,
  `engine.io-client`, `socket.io-parser`, `engine.io-parser` or `@socket.io/component-emitter` module is on the first
  route, and the check fails if one is.
- **AC-2** Given a subscription, a server-ended listener or a request made before the client downloaded, when it
  downloads, then each is attached or sent, in order, and an unsubscribe made meanwhile is honoured.
- **AC-3** Given a room, challenge or friends page opened directly or by a link, then the client downloads at once;
  on any other page it downloads when the browser is idle after the first render.
- **AC-4** Given the room page of a player with a session, the time to the first socket connect is no slower than
  before.
- **AC-5** Connect, disconnect, reconnect, the session follow and the browser specs for presence, requests,
  challenges, friends, room and restart behave as before.

## Results

**First route** (`npm run build:web`, then `node scripts/bin/check-bundle.mjs`): 146.92 kB gzip before (the
`cc-322-first-route` tip, 05cb1ce4), 134.94 kB after, 11.98 kB less. Socket.IO's own chunk is 12.82 kB of gzip
and downloads on demand. The saving is a little under CC-322's 16.6 kB estimate because about 0.4 kB of shared
module helpers (`rolldown-runtime`) and the small client stay on the first route. The branch already holds `main`
(48f1511e), so this is also the number after #169 merges.

**Time to the first socket connect** on the room page of a player with a session: from navigation start to the
WebSocket's `open`, median of 20 loads (10 when throttled), Chromium headless, against the e2e server on this
machine. The cache was warmed with one load first. The e2e server does not compress, so a throttled load moves
three times the gzip bytes.

| Room page, first socket `open`                  | Before           | After                                |
| ----------------------------------------------- | ---------------- | ------------------------------------ |
| No throttling                                   | 108 ms           | 102 to 115 ms (noise)                |
| Lighthouse mobile throttling (150 ms, 1.6 Mbps) | 3997 ms, 4005 ms | 4035 ms (about 30 ms, 0.8 %, slower) |

Three ways to start the download were measured with throttling: at boot, beside the page's own code (4087 ms,
because it shares the line with that code); after the page's code, while the session is asked (4035 ms, kept);
and, as an experiment only, a `<link rel="modulepreload">` in index.html, the most the browser could do (4042 ms).
The kept order is as fast as the experiment, so the remaining 30 ms is the cost of two more files (Socket.IO's
chunk and the shared helpers), not of when the download starts. On home the socket now connects about 60 ms
later, by design (after the first paint, when idle).

**Browser specs**, `--workers=1`: presence, requests, challenges, friends, invite and host-away (room) on desktop
and mobile; restart and restart-presence on both restart projects; sessions (CC-234, CC-115) and deploy (stale
build) on desktop. All pass. One desktop run lost its server partway through (connection refused on every test
after it); the requests spec passed in full when run again.

**Found while building:** Socket.IO writes to the options object it is given, so a frozen one made every socket
fail at creation. The options are now a fresh object each time, with a test.
