## Research (written before any code)

Sources were read on 2026-10-18 unless another date is given. "General knowledge" carries a confidence level.

### 1. How our code does it today

1. **Head tags.** `packages/shared/src/site.js` (`describePage`) names every page, and
   `apps/server/src/service/http/pageHead.js` writes `og:title`, `og:description`, `og:url`, `og:image` (absolute),
   `og:image:type` `image/png`, `og:image:width` 1200, `og:image:height` 630, `og:image:alt` and the Twitter tags into
   the HTML for every route (ADR-042). The HTML is about 3 KB, so the head is far inside the first 300 KB.
2. **A room's preview** names the game from the address alone and never looks the room up (ADR-042.2): "Join my
   Chess game on ClassiCade". It carries no player name, so today no username of anyone, minor or guest, reaches a
   preview.
3. **Images.** Four PNGs in `apps/web/public/og`, drawn by `apps/web/og/render.mjs` (Vite plus Playwright Chromium,
   committed, no image library in production): `chess.png` 289,218 bytes, `classicade.png` 391,824,
   `rock-paper-scissors.png` 303,838, `tic-tac-toe.png` 297,667. Two of the four are over the ticket's 300 KB.
   `apps/web/og/images.test.js` checks that each game has an image of the right size in pixels, not in bytes.
4. **Caching.** `/og/*.png` are not in `/assets`, so `webApp.js` serves them with `Cache-Control: no-cache` under a
   fixed name. A changed image keeps the same URL.
5. **The share UI.** `apps/web/src/components/ShareRoom/ShareRoom.jsx` shows the room code, the link, "Copy link"
   (`invite.copy`) and, where `navigator.share` exists, "Share…" (`invite.share`). The text is
   `Play <game> with me on ClassiCade — room <code>`, in English. It is shown only while the room is WAITING
   (`RoomPage.jsx`). The result screen has Rematch and New opponent but **no share at all**.
6. **Names.** Guests are `Guest-<suffix>` (`identityComponent.js`). There is no birth year yet (CC-152), so by
   ADR-028.1 every player today counts as a minor.
7. **Cold starts.** On a true cold start Render answers with its own loading page before our process runs (ADR-046),
   so a crawler that arrives then would see no tags.

### 2. How others do it

**WhatsApp's own rules** (https://developers.facebook.com/docs/whatsapp/link-previews):

1. `og:title`, `og:description` and `og:url` in the head, not empty, and the head within the first 300 KB of HTML.
2. `og:image` an absolute URL, **under 600 KB**, at least 300 px wide, aspect ratio at most 4:1. "WhatsApp may relax
   these requirements" but that is not guaranteed.
3. The crawler is a plain GET with User-Agent `WhatsApp/2.x.x.x A|I|N` and the recipient's `Accept-Language`.
4. The page says nothing about caching. The 300 KB in our ticket comes from community reports that large images are
   skipped or shown as a small thumbnail (PRODUCT_VISION.md §6.11, medium confidence). Official is 600 KB, so
   300 KB is a safe margin and smaller is better on slow phones.
5. The preview is fetched by the sender's app when the link is pasted (general knowledge, medium confidence). The
   sender is on our site at that moment, so the server is awake and ADR-046 cold starts rarely hit a share.

**Meta's sharing rules** (https://developers.facebook.com/docs/sharing/webmasters/images/): at least 1200 x 630 for
high resolution screens, about 1.91:1, at most 8 MB. Give `og:image:width` and `og:image:height` so the first share
renders without waiting for the download. **Images are cached by URL: a new image needs a new URL**, and old shares
keep the old one, so old files should stay online.

**Click to chat.** `https://wa.me/?text=<URL-encoded text>` opens WhatsApp with the text and lets the player pick the
chat (general knowledge, high confidence. The WhatsApp FAQ page, faq.whatsapp.com/5913398998672934, did not render
for the fetcher). On Android the app opens directly. On desktop it opens WhatsApp Web.

**Wordle** (https://en.wikipedia.org/wiki/Wordle): the share is **text only**, a header with the puzzle number and
score and an emoji grid that shows the result without the answer. It grew from 90 players on 1 Nov 2021 to more than
300,000 by 2 Jan 2022, and 1.2 million results were shared on Twitter from 1 to 13 Jan 2022. Its own `og:image` is a
fixed 1200 x 630 PNG of 12,215 bytes (curl of nytimes.com/games/wordle, 2026-10-18).

**Lichess** (curl of a live game page, 2026-10-18): every game page has its own `og:title` ("Bullet Chess960 Chess •
bcow vs nauthzz2700"), a description with **both usernames and ratings**, and
`og:image` `https://lichess1.org/game/export/gif/thumbnail/<id>.gif`, a 720 x 840 GIF of the position of 33,004 bytes,
cached for 16 days (`max-age=1382400`). The images come from a separate Rust service, lila-gif
(https://github.com/lichess-org/lila-gif: `GET /image.gif` for a position, `POST /game.gif` for a whole game). The
game page's share menu also offers the GIF, the PGN and a position image (general knowledge, high confidence).

**Chess.com** (curl, 2026-10-18): a game link answers a general preview, "Play Chess Online for Free with Friends &
Family", with a fixed image whose file name carries a content hash (`share-play-og.897c84eb.png`). So a new image
gets a new URL, as Meta advises. In the app, the share sheet offers a link, a GIF and an image of the final position
(general knowledge, medium confidence).

**What this means.** Lichess puts names and a live picture of the game in every preview, which works for an adult
community with public profiles. Wordle shows the result in the text and keeps the image fixed and tiny. Chess.com
keeps previews general and versions the image file name.

### 3. What is best for ClassiCade

1. **Keep previews general, as ADR-042.2 already does.** A preview that never looks up the room cannot leak a name,
   a minor's or anyone's, and needs no server image rendering on the free instance (no image library, no browser in
   production, ADR-042.4). The result goes in the **message text**, Wordle's way, not in the image.
2. **Smaller images, under a new name.** Render the same cards as JPEG from the existing script
   (`page.screenshot({ type: "jpeg", quality })`, Playwright already in the repo, so no new dependency). Target
   **150 KB**, hard limit 300 KB, still 1200 x 630. JPEG rather than WebP because WhatsApp's support for a WebP
   `og:image` is not documented (general knowledge, low confidence that WebP works everywhere). Put a short content
   hash or a version in the file name (`/og/chess.<hash>.jpg`) and keep the old PNGs online for old shares, as Meta
   advises. Change `og:image:type` to `image/jpeg`.
3. **A WhatsApp button** next to Copy link and Share…: a plain link to `https://wa.me/?text=…`. No script from
   WhatsApp, no tracking, works on every phone. The device share sheet stays for other apps.
4. **Share from the result screen too**, which today has no share. The link there is the game's page
   (`/games/<slug>`), not the room: a finished room closes 30 minutes after the game (`rematchWindowMs`), so a room
   link in a group chat would be dead by evening. The game page always opens with Play Rocky (CC-221) and "Play a
   friend".
5. **Names.** Until CC-152 ships, every player is treated as a minor, so **no username appears in the card or the
   text, ever**: the text says "I" and the character's name only ("Maine Rocky ko 2-1 se haraya"). The opponent's
   name never appears, whatever their age, because they did not choose to share. After CC-152, an adult account may
   add its own name by choice (a later decision, not this ticket). ADR-028.7 ("a minor's card shows the avatar and a
   ClassiCade player") is met because the card shows no player at all.
6. **Hinglish text.** Five short lines, drafted by the owner as a native speaker (GROWTH.md §2.7 week 8), kept in one
   module so CC-218's string catalogue can take them later. Drafts for the owner to change:
   1. Invite: "Ek game ho jaaye? ClassiCade pe {game} khelo, link kholo aur seedha khelo:"
   2. Win against a character: "Maine {character} ko {score} se haraya! Tum try karo:"
   3. Win against a person: "Maine {game} jeeta {score} se! Ab tumhari baari:"
   4. Draw or loss: "{game} mein {character} ne mujhe hara diya. Badla loge?"
   5. Line after every text: "Free hai, login nahi chahiye."
7. **No referral reward**, as GROWTH.md §3.8 says. A `ref` parameter is an idea in IDEAS.md, not this ticket.
8. **Counting shares** needs no new event: `control_pressed` with a new control name `invite.whatsapp` and
   `result.whatsapp` is in the counts tier (EVENTS.md §3.2), and it is sent only once telemetry exists (CC-174).

## Why

The share loop is the main free growth channel (GROWTH.md §3.2 rank 2, §3.8). Today two of four images are over the
limit, there is no WhatsApp button, the text is English only and a finished game cannot be shared.

## Scope

- In: JPEG cards under 150 KB with versioned names and a size test in bytes. A WhatsApp button and Hinglish text in
  the waiting room and on the result screen. Text built from the result with no player names.
- Out: per-room or per-result images, per-challenge titles (GROWTH.md §2.4 Part B), the `ref` parameter, the
  string catalogue (CC-218), showing an adult's own name (after CC-152).

## Acceptance criteria

- [x] Every `/og` image is a JPEG of 1200 x 630 under 150 KB, and a test fails at 300 KB or more.
- [x] Image names change when the image changes, and the old PNG names still answer 200.
- [x] `og:image:type` matches the file. Every preview passes WhatsApp's listed rules (a test reads the head).
- [x] A WhatsApp button in the waiting room (room link) and on the result screen (game page link).
- [x] The text never contains a display name, a username or a room code on the result screen (unit test over
      every result shape: win, loss, draw, forfeit, against a character and against a person).
- [x] Every new control has a `data-cc-control` and answers within 100 ms (ADR-038). The copy path of Share result is timed in `share.spec.js`. The two WhatsApp links answer by opening a new tab, and the share sheet is its own answer, so the press tests leave those three out with the reason.
- [x] Tests cover the change. `npm run lint`, `npm run format:check`, `npm test` pass.
- [x] Docs updated: BACKLOG, PROGRESS, ADR-042 amendment (JPEG, versioned names).
- [ ] The owner approves the Hinglish lines (Research §3.6), and they replace or join the English ones. Open in
      ADR-051, so the ticket stays 🟦 until then.

### What was built (2026-10-20)

The owner's Hinglish lines are still open (ADR-051, "Still open"), so this pull request ships short English lines in
one module and keeps the Hinglish drafts above for the owner. Both pull requests of the plan went into one, because
the images and the button change different files and are small.

1. **Images.** `apps/web/og/render.mjs` draws the same cards as JPEG, quality 90, 1200 x 630: 57 to 85 KB each
   (`classicade` 85,155 bytes, `rock-paper-scissors` 69,879, `tic-tac-toe` 59,911, `chess` 57,041). Each name
   carries the first 8 hex characters of the image's SHA-256 (`chess.b756bac7.jpg`), and the script writes the list
   to `packages/shared/src/previewImages.js`. The render is the same byte for byte on a second run, so a run with no
   change to the art changes no name. The four PNGs stay in `apps/web/public/og` and still answer 200
   (`RETIRED_PREVIEW_IMAGES`). `pageHead.js` takes `og:image:type` from the file name (`image/jpeg`).
2. **The site's own address.** Every page the server sends carries
   `<meta name="classicade:site-origin" content="...">`, written from the first `ALLOWED_ORIGINS` entry (ADR-042.3),
   never from the request's Host or X-Forwarded headers. `apps/web/src/app/siteOrigin.js` reads it, and falls back to
   the page's own address only where no server wrote it (the Vite dev server and unit tests). The invite link and
   the result link are built on it.
3. **Text.** `apps/web/src/lib/shareText.js` holds every line. `resultText` takes the game, the outcome, a computer
   character's name or "", the series score as numbers and whether the opponent left, and nothing else.
   `apps/web/src/games/resultShare.js` reads those from the RoomView: the character's name from `BOT_CHARACTERS`,
   never from a seat, and never a seat's name, a player id or the room code.
4. **Buttons.** The waiting room's invite gets "Send on WhatsApp" (`invite.whatsapp`, the room link). The result
   card gets the line it will send, "Send on WhatsApp" (`result.whatsapp`) and "Share result" (`result.share`):
   the device's share sheet where there is one, otherwise a copy of the whole message with a "Result copied" toast.
   Both links point at the game's page. A spectator gets no share. The wa.me link is a plain link in a new tab
   (`noopener noreferrer`), with a green dot and not WhatsApp's logo.
5. **Not in this pull request:** the channel marker (`via=wa`) is CC-279. The Hinglish lines wait for the owner.

### English lines shipped (for the owner to replace)

| When                     | Text                                                                                                                             |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------- |
| Invite (waiting room)    | `Play Chess with me on ClassiCade — room AB2CD3`                                                                                 |
