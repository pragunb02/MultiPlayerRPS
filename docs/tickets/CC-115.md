## Research (written before any code)

### 1. How our code does it today

1. All tabs of one browser share one session cookie (`cc.sid`, HttpOnly). Who the browser is lives only on the
   server.
2. Signing in or signing up (`POST /api/auth/login|signup`, `authRoutes.js` `signIn`) gives the session a new id and
   disconnects the sockets of the old id (`gateway.disconnectSession`). Logging out (`DELETE /api/session`,
   `sessionRoutes.js`) destroys the session, clears the cookie and disconnects its sockets. Starting a guest
   (`POST /api/session/guest`) only creates a session.
3. `SessionProvider.jsx` learns the identity once at start, then only from what its own tab does. Another tab:
   1. had a socket (guest or account): the server cuts it with `"io server disconnect"`, Socket.IO does not
      reconnect after that (see CC-234), and the tab is stuck on its old identity with "Reconnecting".
   2. had no socket (a visitor): nothing tells it anything. It keeps showing "Log in" while the browser is signed in.
4. Result (BUG-20): a tab that is not the one you used is dead or wrong until you reload it. On a room page it keeps a
   board whose moves now fail, or plays on as nobody.
5. Constraint: web storage may hold only allowlisted preferences (`STORAGE_ALLOWLIST` in `e2e/fixtures.js`, CC-103),
   today `cc.sound` alone. Page scripts can read web storage and it outlives the session, so nothing that names the
   player may be written there, and the browser tests fail on anything else.

### 2. How other products do it

1. BroadcastChannel (MDN, https://developer.mozilla.org/en-US/docs/Web/API/Broadcast_Channel_API, read
   2026-10-18): tabs, frames and workers of the same origin (and the same storage partition) post messages to each
   other by channel name. "Baseline: widely available" since March 2022 (Chrome 54, Firefox 38, Safari 15.4). A
   message is not delivered to the object that posted it. Nothing is stored.
2. The `storage` event (MDN, https://developer.mozilla.org/en-US/docs/Web/API/Window/storage_event): fires in the
   other tabs when one tab writes `localStorage`. It is the older way, works in every browser, but needs a write to
   web storage, which outlives the tab and is readable by page scripts.
3. Firebase Authentication (https://firebase.google.com/docs/auth/web/auth-state-persistence, read 2026-10-18): with
   local persistence a sign in "will be detected and synchronized on all tabs", and switching one tab away signs the
   user out "on all other tabs". It stores the tokens in the browser (IndexedDB), which we do not do.
4. Okta Auth JS (https://github.com/okta/okta-auth-js, README, read 2026-10-18): cross tab synchronisation is a
   service (`services.syncStorage: true` by default) that keeps the stored tokens of every tab in step.
5. GitHub: a tab signed out from another tab shows "You signed out in another tab or window. Reload to refresh your
   session." It knows at once, but asks for a reload.
6. Server pushed logout: a realtime connection closed by the server (Socket.IO's `"io server disconnect"`,
   https://socket.io/docs/v4/client-socket-instance/#disconnect) is how a client with a socket learns its session
   ended. It cannot reach a tab without a socket.

### 3. What is best for ClassiCade

1. Two signals, both carrying nothing about who the player is, and one source of truth:
   1. Server disconnect (CC-234): the tab asks `GET /api/session` again. This covers every tab with a socket, even
      in a browser without BroadcastChannel, and also another browser signed out remotely.
   2. A BroadcastChannel named `cc.session`: after this tab signs up, logs in, logs out or starts a guest, it posts
      `"changed"`. Every other tab then asks `GET /api/session`. This covers visitor tabs, which have no socket, and
      tells the others at once instead of after the socket notices.
2. The message is the single word `"changed"`. No id, name or kind, so a tab can never take an identity from
   another tab, only from the server. A forged message from a script on our origin can at most make tabs ask the
   server again.
3. BroadcastChannel over the storage event: it needs no write to web storage (CC-103 stays clean, nothing is left
   behind after the tab closes) and is in every browser we support. A browser without it still gets the server
   disconnect path, which is the documented behaviour of that browser, not a hidden fallback.
4. When the answer is "signed out", the tab becomes a visitor: the header shows Log in and a room page shows the join
   chooser instead of the board. When it is a player, the socket connects again as that player and a room page
   joins again. A tab that already shows that identity with a working socket does nothing.
5. Answers that arrive late are dropped when the tab changed identity meanwhile (the existing counter in
   `SessionProvider`). A tab that receives its own change twice (message and server disconnect) asks twice and
   ends in the same state.

## Why

Players often have the game open in several tabs (a lobby and a room, an invite link). Signing in or out in one of
them must not leave the others dead or showing someone else.

## Scope

- In: `lib/sessionBroadcast.js` (BroadcastChannel, injected through the services), `SessionProvider` posting after
  its own changes and asking the server again on a message or a server disconnect, the socket client's two signals,
  a browser fixture helper for a second tab with the same leak checks.
- Out: tabs of different browsers (that is the server disconnect of CC-234). Showing a reason toast (CC-158).

## Acceptance criteria

- [x] Sign in on tab 1, and tab 2 shows the account without a reload
- [x] Log out on tab 1, and tab 2 leaves any room screen and shows signed out
- [x] Starting a guest on tab 1 shows that guest on tab 2
- [x] The message carries no identity data, and web storage stays empty apart from allowlisted preferences
- [x] Tests cover the change (unit first failing, browser test with two tabs)
- [x] `npm run lint`, `npm run format:check`, `npm run test:coverage` pass

## Plan / notes

1. Decision recorded as ADR-033 in `DECISIONS.md`.
2. ADR-030 (session lifetime and revocation, proposed in CC-116) is unchanged: the server still decides, and the
   browser only asks again sooner.
3. What changed:
   1. `apps/web/src/lib/sessionBroadcast.js`: the channel `cc.session` and its one message `"changed"`. A browser
      without BroadcastChannel gets one that does nothing. Created in `main.jsx` and given to the app as the
      `sessionBroadcast` service.
   2. `apps/web/src/hooks/SessionProvider.jsx`: after this tab's own sign up, log in, log out or new guest it
      announces the change. A message from another tab, or the server ending the socket (CC-234), makes it ask
      `GET /api/session` again. A signal that arrives during this tab's own change waits until that change is done,
      so the tab never flashes signed out while it logs in (the server ends the old socket before the log in answers).
   3. The two signals complement each other. When another tab logs in, this tab's old socket can be ended before the
      browser has the new cookie, so the first answer may be "signed out". The message that follows the log in asks
      again and gets the account.
   4. `e2e/fixtures.js`: `player.openTab()` opens a second tab in the same browser, recorded and checked like the
      first, and the storage check now covers every tab.
4. Found on the way: `RoomPage.alerts.test.jsx` waited for the lazily loaded chess board with the default one
   second, which a busy test run exceeded (it failed three tests locally once these tests were added). The board is
   now loaded before those tests. Needs a ticket on the next board pass (this branch does not edit BACKLOG).
