## Why

The investigation reproduced it in Chromium (`probe/stalechunk.mjs`) and saw it on iPhone: a player has a room open,
a deploy replaces the build, and the board files of the old build are gone. When the opponent joins, the tab asks for
its old `RpsBoard-*.js`, the server answers 404 with the app's HTML, the lazy import rejects, and the only error
boundary (around the whole app) replaces everything with "Something went wrong. Please reload the page.". Since
CC-101 rooms survive a deploy, so this now happens to every player waiting in a room or between games during one.

## Scope

In:

1. `apps/web/src/app/staleBuild.js`, called first in `main.jsx`. It listens for Vite's `vite:preloadError`, which Vite
   fires both when a file a lazy part needs fails to preload (JavaScript or CSS) and when the dynamic import itself
   fails. On the first failure it marks the address with `?reloaded=1` (through `history.replaceState`, so the history
   entry and its state stay) and reloads. Further failures while the reload is under way are swallowed.
2. Loop guard, in memory and in the address, no web storage: the page the reload opens removes the mark at once,
   before the router reads the address, and remembers only in memory that it came from such a reload. A failure in
   the first 30 seconds after that shows the error page instead of reloading again. A failure later on is a newer
   deploy and reloads again.
3. `apps/web/src/games/lazyBoard.js`: the registry's boards use it. While a reload is under way Vite hands back no
   module, and the board keeps showing its loading state instead of the error page. Any other failure still reaches
   the error boundary.
4. Server (`service/http/webApp.js`): a file under `/assets` that is not there answers 404 with the type its extension
   asks for (`text/javascript` for `.js` and `.mjs`, `text/css`, otherwise `text/plain`), a fixed one-line comment as
   the body (the requested path is never repeated, so a crafted URL cannot write script) and `Cache-Control: no-store`,
   so Cloudflare cannot keep serving the 404. Before, it got the app's HTML.

Out:

1. Keeping the previous build's files available for a while after a deploy (named in the board title). Render builds
   each deploy from scratch, so this needs somewhere to keep old files (object storage, or a copy of the previous
   `dist/assets` baked into the image) and a rule for when to drop them. That is a decision for the owner. With the
   reload in place, an old tab already recovers.
2. The other dynamic import, Motion's animation features (`components/Motion`), belongs to the other builder's area.
   The window listener covers it too: its failure also reloads the page.

## Acceptance criteria

- [x] A lazy board file that is gone after a deploy reloads the tab once, and the player lands back in the room
- [x] The error page is never shown on the way, and the URL and Back behave as before
- [x] No reload loop: a second failure right after such a reload shows the error page
- [x] Missing `/assets/*` files answer a typed 404, never the app's HTML, never cached
- [x] Unit tests for every branch, browser test on desktop and mobile
- [ ] Docs: BACKLOG, KNOWN_ISSUES, PROGRESS are updated by the owner when merging (this agent may not edit them)

## Plan / notes

Vite's own advice for this event is a reload. Calling `preventDefault` stops Vite from throwing, and then the import
resolves to nothing, which is why the board loader treats "nothing" as "a reload is under way".

## Verification

1. `e2e/deploy.spec.js`, desktop and mobile. Alice opens a Rock Paper Scissors room, then a deploy is simulated in her
   tab only: until the page loads again, every request for the board file gets what the real server answers for a
   file it no longer has (fetched from `/assets/RpsBoard-from-the-previous-deploy.js`). Vite may ask for the file
   twice (a preload and the import), and the first version of the test failed only the first request, so in CI the
   import got the file and no reload happened. Renaming the file in the shared build would break every other test
   running in parallel. Bob joins. The test checks that Alice sees the board, no alert and no
   "Something went wrong", that the address is the room's without the mark, that the title is the room's, that the
   board file answered 404 with `text/javascript` and then 200 after exactly one page load of `<room>?reloaded=1`,
   that the game plays to the end, and that Back still goes to the lobby. With the listener taken out of `main.jsx`
   the same test fails: the board never shows and React logs "Failed to fetch dynamically imported module".
2. Unit tests: `app/staleBuild.test.js` (reload once keeping address and state, swallow while reloading, remove the
   mark, leave a clean address alone, no loop inside the guard time, reload again after it, stop listening),
   `games/lazyBoard.test.jsx` (module shown, nothing means wait, other failures reach the boundary),
   `service/http/webSecurity.test.js` (typed 404 per extension, `no-store`, path never repeated).
