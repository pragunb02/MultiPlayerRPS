## Why

The 2026-10-17 load investigation found that `replay` in `packages/games/src/chess/chessEngine.js` used 30 % of all
CPU samples and 55 % of busy time, 60 % in the stall windows. Every chess move (`applyMove`) replayed the whole game
from the first move with chess.js, only so that threefold repetition was counted right. The cost grew with the game:
about 20 ms per move at 300 half moves, all of it blocking the event loop, and again on every
`ConcurrentChangeError` retry. In the 10 minute soak, CPU climbed from 26 % to over 85 % at the same load, just
because the chess games got longer.

## Scope

In:

1. The chess state keeps `positions`: the chess.js position keys (`chess.hash()`, the key chess.js itself counts for
   repetition) since the last capture or pawn move, the current position last. No position from before such a move
   can come back, so the list never holds more than about 100 keys (the fifty-move rule ends the game there).
2. `applyMove` loads the board from `state.fen`, plays the move and counts the new key in `positions`. Threefold
   repetition is decided from that list. The fifty-move rule already came from the half move clock in the FEN.
   `validateMove` already used the FEN.
3. Migrate on read, inside the engine: a stored game without `positions` (every chess game running at the moment of
   the deploy) rebuilds the list once from its moves on its next move. The same happens when the list does not fit
   the board (its last key is not the current position, or its length is not the half move clock plus one), which is
   what an older server leaves behind if a deploy is rolled back and then forward again.
4. `scripts/bin/bench-chess.mjs` measures moves per second at different game lengths.

Out: the view (`viewFor`) and the move list are unchanged. Match history keeps replaying from the log
(`replayGame`), which now also runs in linear time instead of quadratic.

## Plan / notes

Why chess.js's hash and not a trimmed FEN: chess.js puts an en passant square into the FEN only when the capture is
legal, but into its hash when a pawn could capture, pinned or not. Using its own key keeps the decision identical to
what the replay decided before. The random game test compares the engine against a chess.js game that keeps its
whole history, ply by ply, over ten seeded games that end by repetition and by the fifty-move rule, with en passant
chances and lost castling rights on the way.

A stored game pays the old replay cost exactly once, on its first move after the deploy.

## Verification

Microbenchmark (`node scripts/bin/bench-chess.mjs`, Apple silicon laptop, Node 24.21), one `validateMove` plus
`applyMove` from the position after N half moves of a seeded random game:

| Half moves played | Before (main)             | After                     |
| ----------------- | ------------------------- | ------------------------- |
| 10                | 1 573 per second, 0.64 ms | 6 132 per second, 0.16 ms |
| 100               | 150 per second, 6.7 ms    | 8 700 per second, 0.11 ms |
| 300               | 49 per second, 20.4 ms    | 5 569 per second, 0.18 ms |

Load (`scripts/bin/load-moves.mjs`, `PAIRS=100 DURATION_S=90`: 100 chess pairs and 100 Rock Paper Scissors pairs, 400
players, about 200 ms thinking time, in-memory MongoDB, production server in its own process):

| Build                           | Moves in 90 s | p50      | p95      | p99       | Move answers over 15 s |
| ------------------------------- | ------------- | -------- | -------- | --------- | ---------------------- |
| main                            | 41 852        | 278.6 ms | 980.6 ms | 1638.0 ms | 257                    |
| CC-180 (room storage unchanged) | 118 356       | 4.3 ms   | 18.1 ms  | 30.3 ms   | none                   |

A second run of the CC-180 row gave 118 105 moves, p50 4.4 ms, p95 21.8 ms, p99 33.8 ms. The CC-182 ticket has the
numbers with both changes.
