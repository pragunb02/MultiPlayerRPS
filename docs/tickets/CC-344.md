## Problem

The owner hears the game sounds while the browser tests run on a laptop. Root cause: Playwright runs the browsers
headless, and headless browsers still play sound through the speakers. Nothing in our configs muted them, and
Playwright has no option of its own to mute a browser.

## Fix

Chromium starts with `--mute-audio` in both browser test configurations, and Firefox with the preference
`media.volume_scale` at `"0.0"`. WebKit has neither, so the fixtures add an init script to every browser context
(each person's browser and Playwright's own page): each audio context's `destination` becomes a gain of 0 in front
of the real speakers. The app still builds and runs its whole sound graph, so the sound settings and a test that
checks a sound was asked for (`controlProbe.js` counts oscillators) work as before. The script runs on every
engine, so it is checked on every pull request, not only on WebKit's runs.

**Research.**

- How our code does it now: `apps/web/src/lib/sound/soundPlayer.js` plays only through Web Audio (CC-103):
  oscillators into one master gain, connected to `context.destination`. No `<audio>` element is used.
- Chromium: `--mute-audio` mutes audio sent to the audio device
  (<https://peter.sh/experiments/chromium-command-line-switches/#mute-audio>).
- Firefox: the preference `media.volume_scale` (see `about:config`) scales all of Firefox's audio output, so
  `"0.0"` is silent. A muted speaker cannot be checked from a test, which is one more reason the init script
  runs on every engine. Playwright passes it with `launchOptions.firefoxUserPrefs`
  (<https://playwright.dev/docs/api/class-browsertype#browser-type-launch-option-firefox-user-prefs>).
- WebKit: Playwright's WebKit has no mute switch. `BaseAudioContext.destination` is a read-only accessor on the
  prototype (<https://webaudio.github.io/web-audio-api/#dom-baseaudiocontext-destination>), so a page script can
  put its own node in front of it.
- Vitest: the web project runs in jsdom, which has no `AudioContext` or `webkitAudioContext`, and every sound test
  passes in a fake context, so nothing plays. A test now says so.

Checked by hand in Chromium, Firefox and WebKit with the init script: `destination` is a `GainNode` at 0, the same
one each time, and the context runs and its clock moves.

## Acceptance criteria

- **AC-1** Given either browser test configuration, then every Chromium project starts with `--mute-audio`.
- **AC-2** Given `E2E_BROWSER=firefox`, then Firefox starts with `media.volume_scale` at `"0.0"`.
- **AC-3** Given any page in a test browser, when the app makes a sound, then its output goes through a gain of 0,
  and the sound graph runs as before.
- **AC-4** Given the web unit tests, then jsdom has no audio context to play through.

## Test

`e2e/testAudio.test.js` checks AC-1 to AC-3: the configs' launch options, and the init script against a fake
audio context. `apps/web/src/lib/sound/soundPlayer.test.js` checks AC-4. The browser tests that touch sound
(`requests.spec.js` "sound switch" on Chromium, Firefox and WebKit, and `match-shell-presses-rps.spec.js`, whose
probe counts sounds, on WebKit) pass.
