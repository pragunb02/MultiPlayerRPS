## Why

Players come on phones, and on an iPhone every browser is WebKit. The browser suite only runs on Chromium (desktop and
Pixel 7), so a page that breaks in Safari or Firefox reaches production unnoticed. The cross-browser investigation
([investigations/2026-10-17-cross-browser-a11y-load.md](../investigations/2026-10-17-cross-browser-a11y-load.md),
section 1) ran the suite on both engines and found that WebKit cannot run it at all without changes to the test
setup, and that the players fixture's error filters only know Chrome's wording.

## Research

### How our code does it today

- `e2e/app.mjs` runs the real server in production configuration on plain `http://localhost:<E2E_PORT>`. Production
  sits behind Render's and Cloudflare's HTTPS, so to get the production `Secure` session cookie the players fixture
  (`e2e/fixtures.js`) sends `X-Forwarded-Proto: https` on every request, and the app trusts one proxy hop.
- Production sends a Content Security Policy with `upgrade-insecure-requests` (`service/http/requestGuards.js`), and
  the session cookie is `Secure` (`service/http/session.js`, `secureCookies: config.isProduction`).
- The fixture fails a test on any console error or warning, page error or failed request. It ignores cancelled
  requests only by Chrome's and Firefox's codes (`ERR_ABORTED`, `NS_BINDING_ABORTED`), and during a planned server
  restart it ignores only Chrome's console wording (`WebSocket connection to '…' failed`).
- `visual.spec.js` walks the page with the Tab key and expects links to be reached.
- `ci.yml` installs Chromium only and runs four projects: `desktop`, `mobile` (Pixel 7), and the two restart projects.
  On main on 2026-10-17 the job took 15.9 minutes for 313 tests.

What the investigation measured (Playwright 1.64.1, Firefox 157, WebKit 26):

1. WebKit applies `upgrade-insecure-requests` to `http://localhost`, so every script, style and API call goes to
   `https://localhost` and fails. Chromium and Firefox treat localhost as already secure and do not upgrade.
2. WebKit refuses to store a `Secure` cookie from `http://localhost`, so nobody stays signed in.
3. With both switched off by scratch flags, WebKit and Firefox passed 69 of 71 tests each. The rest were the fixture's
   wording: WebKit reports a cancelled request as `cancelled`, Firefox words a dropped WebSocket as
   "Firefox can’t establish a connection to the server at ws://…", and WebKit's Tab key skips links (Safari's
   default, the "Press Tab to highlight each item" setting is off).

### How other products and tools do it

- **WebKit and localhost.** WebKit bug 218980, "Treat loopback addresses (127.0.0.0/8, ::1/128, localhost,
  .localhost) as potentially trustworthy URL", is still open (reported 2020-11-16, last changed 2024-10-09). Bug
  231035 "Unable to Set Cookie with Secure on Localhost without HTTPS" was closed as its duplicate, and a 2024-01-25
  comment confirms Gecko and Chromium accept such cookies while WebKit does not (bugs.webkit.org, read 2026-10-18).
  MDN's Set-Cookie page says the `https:` rule "is ignored when the Secure attribute is set by localhost", which is
  true for Chromium and Firefox only. So this will not be fixed for us by waiting.
- **Local HTTPS is the usual answer.** Next.js has `next dev --experimental-https` (since 13.5, 2023) and Vite has
  `@vitejs/plugin-basic-ssl`, both generating a local certificate so development matches production's HTTPS.
  `mkcert` (FiloSottile) does the same with a locally trusted root. Playwright's `webServer` has an
  `ignoreHTTPSErrors` option and browser contexts have `ignoreHTTPSErrors`, for exactly a self-signed test server
  (playwright.dev/docs/test-webserver, read 2026-10-18). Confidence high.
- **Frameworks behind a proxy.** Django's `SECURE_PROXY_SSL_HEADER` and Rails' `config.assume_ssl` trust
  `X-Forwarded-Proto` from the proxy that ends TLS, as our app does with `trust proxy`. That is how our server sees
  HTTPS in production, and it should stay the only way. Confidence high, general knowledge.
- **WebKit Tab key.** In Safari and in Playwright's WebKit, Tab moves only between form controls and Option+Tab
  (Alt+Tab) also reaches links. Playwright's own guidance in its issue tracker is to press `Alt+Tab` on WebKit.
  Confidence medium, general knowledge.

### Options for the two WebKit blockers

| Option                                                                             | For                                                                                                                                                                                                                | Against                                                                                                                                                                                                                                                            |
| ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| A. Test-only HTTPS in front of the e2e app, with a certificate made at start       | Production code and headers stay exactly the same and are what every browser tests. Same shape as production: TLS ends in front of the app, which trusts `X-Forwarded-Proto`. Works the same on all three engines. | Needs `openssl` where the tests run (it is on GitHub's Ubuntu runners and on macOS). Test browsers ignore certificate errors, which is only safe because the certificate is made for this run and never leaves the temp folder. A little more code in the harness. |
| B. A test-only config that drops `upgrade-insecure-requests` and the `Secure` flag | Small change.                                                                                                                                                                                                      | Puts a switch that weakens security headers into production code, where a wrong environment variable could turn it on. The browser suite would stop testing the exact headers production sends, and the fixture's `Secure` cookie check would have to be loosened. |
| C. Run WebKit with a different base URL such as `127.0.0.1`                        | No code.                                                                                                                                                                                                           | Does not help: WebKit treats every loopback address the same (bug 218980).                                                                                                                                                                                         |

### What is best for ClassiCade

1. Option A. `e2e/server.mjs` makes a short-lived self-signed certificate for `localhost` and `127.0.0.1` with
   `openssl` in the run's temp folder, and serves HTTPS on `E2E_PORT`. It passes every decrypted connection straight to
   the app on an internal port, so WebSockets and restarts work without parsing HTTP. The app is unchanged and still
   runs in production configuration. No private key is ever committed.
2. Players' browsers and Playwright's request client set `ignoreHTTPSErrors: true`, test code only. The fixture keeps
   sending `X-Forwarded-Proto: https`, now true, because the connection really is HTTPS, as Render's proxy would say.
3. The fixture's failure filters become browser neutral: a cancelled request is `ERR_ABORTED`, `NS_BINDING_ABORTED`
   or WebKit's `cancelled`. During a planned restart the realtime connection's failure is ignored in each engine's
   wording. Any new WebKit only noise found while running is listed here, not hidden.
4. Keyboard checks press `Alt+Tab` on WebKit, so they test the same journey as Safari users with the default setting
   who use Option+Tab.
5. CI: Firefox desktop and WebKit desktop each get their own job, running the main suite and the restart suite. If
   one run is about as long as today's Chromium job, the jobs run on every PR in parallel and do not add wall time.
   If they are much slower, they run nightly, on dispatch and on PRs that change `apps/web`, `packages/shared` or
   `e2e`. The decision and the measured times are recorded under Verification. They start as non-required checks,
   so a Firefox or WebKit only failure is visible without blocking unrelated merges until they have run green for a
   while. Making them required is the owner's call.
6. Real app bugs that show up on those engines are listed below as findings, the small ones fixed here.

## Scope

- In: `e2e/` harness (server, fixture, config, the Tab key check), CI jobs, this ticket's findings.
- Out: app code, except small bugs found on these engines. Mobile WebKit (iPhone 14) and mobile Firefox, which can
  follow once desktop is green.

## Findings

Found while running the suite on Firefox 157 and WebKit 26 (Playwright 1.64.1) on 2026-10-18.

1. **F-1, app bug, fixed.** The home page crashed (`undefined is not an object (evaluating 'e.games.map')`) when a
   player pressed Back and then Forward quickly on WebKit (`navigation.spec.js` "a redirect is never a step in
   history"). The game list's answer was cut off as the page left. `apps/web/src/lib/api.js` read the unreadable body
   of a 200 as an empty answer `{}`, so `useGames` became "ready" with no games. Any `get*` call could do the same.
   Fix: a success whose body cannot be read is now a `NETWORK` error, with a unit test in `api.test.js`.
2. **F-2, engine quirk, passed on WebKit only.** WebKit logs "Refused to apply a stylesheet because its hash, its
   nonce, or 'unsafe-inline' does not appear in the style-src directive" for every `<select>` under `style-src
'self'`. Reproduced on a page with nothing but a `<select>` and the same policy, so it is WebKit styling its own
   drop-down. The fixture passes that exact text on WebKit only. Chromium and Firefox still fail on it.
3. **F-3, test harness, skipped on WebKit.** `deploy.spec.js` (stale board file after a deploy) fails on WebKit:
   after the reload WebKit never asks for the board file again, because Playwright's routed stand-in answer stays in
   the tab. A plain server that answers 404 and then the file, with no Playwright routing, showed WebKit asking again
   after the reload and loading it, both with `location.replace` and with `replaceState` plus `reload()` as
   `staleBuild.js` does. So Safari players get the recovery. Chromium and Firefox still run the test.
4. **F-4, minor, open.** WebKit warns "The resource …/assets/RpsBoard-….js was preloaded using link preload but not
   used within a few seconds" (also `useMove-….js`). Vite fetches a lazy board's files ahead of time as the board
   starts loading, and on a loaded machine running them takes longer than WebKit's few seconds. It is advice about
   speed, not a failure. Passed on WebKit for the site's own `/assets/*.js` only. Worth a look in the bundle work.
5. **F-5, engine wording, passed on WebKit only.** WebKit reports a request the page starts while reloading as a
   page error "Fetch API cannot load https://localhost:…/api/progress due to access control checks"
   (`navigation.spec.js` "every screen survives a reload"). The app's client already turns it into a failed request.
   Passed only for the site's own address, so a real cross-site refusal still fails.
6. **F-6, not seen.** The investigation's Firefox `JSHandle@object` from React's `onCaughtError` did not show up in
   these runs. It stays open in the investigation, and the Firefox CI job will show it if it comes back. The
   investigation's other two real bugs are already fixed (stale chunks CC-181, "Room not found" CC-204).
7. **F-7, explained by F-8.** Once on CI, Firefox's `page.goto` to a lobby failed with `<unknown error>`
   (`leaderboard.spec.js` "an account who wins climbs the boards"). To rule out the TLS front, its relay no longer
   drops the browser's side when the app closes normally: the pipe ends it after the last bytes, and only a failure
   drops both. A unit test sends an 8 MB answer to a slow reader and checks every byte arrives. The next run showed
   the real cause, F-8.
8. **F-8, real app bug, fixed.** Leaving a page while one of its lazy files is still loading could reload that
   page instead of going where the player was heading, on Firefox and WebKit. Seen on CI in `leaderboard.spec.js`
   "an account who wins climbs the boards" (Firefox once, WebKit once): Riya signs up, lands on `/`, and the test
   goes straight to `/games/rock-paper-scissors`. On WebKit it also failed `owner.spec.js` "a new range from the
   form is a new address" every time. The cross-browser investigation saw the same test log "Unable to preload
   CSS for HeroArt" on iPhone before this change.
   1. Leaving the page cancels the lazy `HeroArt` files. Firefox and WebKit report the cancel to the page, and Vite
      turns it into `vite:preloadError`.
   2. `apps/web/src/app/staleBuild.js` (CC-181) reads every `vite:preloadError` as "a deploy removed this file"
      and calls `location.reload()`. A reload during a navigation replaces that navigation, so the player lands on
      `/?reloaded=1`. WebKit shows it as "Navigation … is interrupted by another navigation to …/?reloaded=1".
   3. Because the handler also calls `preventDefault()`, Vite hands back no module. The boards and the admin page
      load through `lazyBoard()`, which then keeps waiting, but the home page's hero art used a plain `lazy()`, so
      WebKit logged `undefined is not an object (evaluating 'e._result.default')`.
   4. Fix: `staleBuild.js` notes `beforeunload` and no longer reloads a page that is leaving. It still swallows the
      failure, so nothing flashes an error while the next page loads. It recovers again on `pageshow`,
      `pointerdown` or `keydown`, so a page that started to leave and stayed (a link that only started a download)
      still recovers from a later deploy. The hero art now loads through `lazyBoard()` like the boards. Unit tests
      in `staleBuild.test.js`. The two tests above then passed twice on WebKit and Firefox, and on Chromium.

Engine wording now known to the fixture (`e2e/browserNoise.js`, unit tested in `browserNoise.test.js`):

1. A cancelled request: `net::ERR_ABORTED` (Chromium), `NS_BINDING_ABORTED` (Firefox), `cancelled` (WebKit), and
   WebKit's `Provisional navigation canceled.` for a page load another one replaced. A request a test stops on
   purpose with `route.abort()` (`waking-up.spec.js`) is `NS_ERROR_ABORT` in Firefox and `Blocked by Web Inspector`
   in WebKit, which only Playwright causes.
2. The realtime connection down during a planned restart: Chromium's "WebSocket connection to '…/socket.io/…'
   failed", Firefox's "Firefox can’t establish a connection to the server at wss://…/socket.io/…", which Firefox may
   wrap as `[JavaScript Error: "…" {file: … line: …}]`, and "The connection to wss://…/socket.io/… was interrupted
   while the page was loading". WebKit logged nothing extra in the restart suite.
3. A failed request repeated in the console is judged once, by the request: Chromium's "Failed to load resource"
   and Firefox's "Loading failed for the module with source …".
4. Firefox's "Layout was forced before the page was fully loaded" from `debugger eval code`, which is the test's own
   `page.evaluate` measuring the page. The same warning from one of the app's files still fails.
5. Safari's Tab key: `visual.spec.js` presses Alt+Tab on WebKit, as a Safari keyboard user presses Option and Tab.
6. Tests that differ by screen ask `formFactor(testInfo)` (fixtures.js) instead of the project name, so the Firefox
   and WebKit projects get the laptop behaviour (`chess.spec.js`, `match-shell.spec.js`, `visual.spec.js`).

## Plan / notes

As built, following "What is best for ClassiCade":

1. `e2e/tlsFront.js` makes a two-day self-signed certificate for `localhost`, `127.0.0.1` and `::1` with `openssl`
   in the run's temporary control folder (mode 700) and serves HTTPS on `E2E_PORT`, loopback addresses only. Each
   connection is passed byte for byte to the app on `APP_PORT` (`E2E_PORT + 10000`, plain HTTP on 127.0.0.1), so
   WebSockets and restarts need no special handling. It starts on every address or none. Unit tested with real
   sockets and a real certificate (`tlsFront.test.js`).
2. The app (`e2e/app.mjs`) is unchanged apart from its port and `ALLOWED_ORIGINS=https://localhost:<E2E_PORT>`. It
   still runs with `NODE_ENV=production`, the CSP with `upgrade-insecure-requests`, and the `Secure` cookie. Nothing
   in `apps/server` changed.
3. `ignoreHTTPSErrors: true` in the Playwright config, the `players` fixture and the web server check. Test code only.
4. `E2E_BROWSER` (default `chromium`) picks the engine in `playwright.config.js`. Chromium keeps the `desktop` and
   `mobile` projects and their names. Firefox and WebKit run a laptop project and their restart project.
5. CI. Neither new job is required yet: the owner decides when, after a green streak.
   1. The Chromium job keeps its name and stays the required check. With HTTPS in front it took 17.7, 18.1 and
      18.6 minutes, against 16.6 on main. Main has since raised its limit to 30 minutes for the same reason.
   2. New job `e2e-firefox` in `ci.yml`, on every pull request, beside Chromium: 10.3 and 11.5 minutes, all green.
   3. WebKit was measured three ways before choosing:
      1. On GitHub's Linux runners (Playwright's Linux WebKit port, 2 workers), it hit the 20 minute limit after
         about 46 of 161 tests. Chess, fair play and leaderboard tests failed there although they pass on macOS.
      2. On `macos-latest` it got only 1 worker on the 3 core machine and passed 53 tests in 38 minutes. The only
         failures were four of the match-shell "every press answers within 100 ms" tests, at 3 to 6 minutes each.
      3. A whole run on one macOS runner would take over an hour, too slow for every pull request.
   4. So WebKit has its own workflow, `webkit.yml`. It runs on macOS, where Playwright's WebKit is Safari's engine,
      with the restart tests once after part 1. It runs every night, on the "Run workflow" button and on pull
      requests that change `apps/web`, `packages/shared` or `e2e`. Reports are kept even when a run is cut off.
   5. Two parts of 3 workers took about 6 minutes each, but chess and save-progress games that take 4 s on a laptop
      ran past 30 s on the busy three-core machines. It now runs in three parts of 2 workers, with 60 s per test for
      WebKit on CI only. Chromium and Firefox keep Playwright's 30 s.
   6. On CI, WebKit leaves out the 29 match-shell "every press answers within 100 ms" tests (`grepInvert` in
      `playwright.config.js`). The macOS runners answered presses in 101 to 508 ms and each test took 3 to 6
      minutes. It also leaves out `visual.spec.js` "a level-up bursts behind the new badge": the burst comes and
      goes faster than the runner looks for it, and the check missed it in two WebKit runs out of four. All of
      these pass on WebKit on a laptop, and Chromium and Firefox run them on every pull request. Follow-up: run
      them on WebKit when a faster runner or a looser WebKit budget is agreed with the owner.

Trade-off taken: option A adds about 100 lines of harness code and needs `openssl`, against option B's few lines. In
return no production file has a switch that weakens a security header, and every engine tests exactly the headers
production sends.
