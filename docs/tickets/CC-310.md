## Root cause

`apps/server/src/domain/analytics/playerStatuses.test.js`, "cost > works out a slice of 250 players' statuses over
the longest range within the budget", failed on PR #135 (CC-034, public profiles), which does not touch analytics:
run 39398737881, job "Lint, format, audit, unit + integration (coverage gates)", `expected 53.12533099999996 to be
less than 50`. The test (548 ms in total) built 4 slices of 250 players three times each and asserted that the
best of the three runs of the slowest slice took under 50 ms of wall-clock time.

Wall-clock time measures the machine as much as the code. The same slice took 4.7 ms on a laptop (CC-255), and in
CI it ran under V8 coverage on a shared GitHub runner while other test files ran beside it. "Best of 3" only helps
when the machine is busy for part of the test. When it is busy for all of it, every run is slow and the test fails
with no change to the code. The neighbour, "reads the trend, the moves and the North Star from the book within the
budget", has the same weakness (309 ms in total on that run, still under its 50 ms per run, by luck).

What the tests are for is still needed. Review of PR #83 found that the first version of the statuses worked each
status out from scratch about 9 times per player per week, 890 ms for 2,000 players (CC-255). The tests must keep
failing on a regression of that shape.

## Research (written before any code)

1. **Our code today.** `statusRow` walks the days of the read window once per player, with two markers moving
   forwards through the days of play, so its work is days of the window plus days of play. `statusWeeks` reads
   each row's Sunday before each week and the days of the week, `statusMoves` two cells per row, `northStarOn` one.
   None of this depends on how fast the machine is, but the tests could only see it through a timer.
   The repo already solved the same problem once: ADR-041 says "budgets count positions, not milliseconds" for the
   chess bot, and `packages/games/src/bots/chess/search.test.js` "never looks at many more positions than its
   budget allows" counts positions. `chessBot.test.js` says it outright: "Tests do not time moves".
2. **Other projects.**
   1. Google's testing blog, "Flaky Tests at Google and How We Mitigate Them" (John Micco, 2016), and Software
      Engineering at Google (2020, chapter 11 on flaky tests) describe tests that depend on the environment, timing
      included, as a main cause of flakiness, which grows with the load on shared machines.
   2. Benchmark tools such as Vitest's `bench` (tinybench) report times and leave the judgement to a person or a
      tracked trend. They do not fail a build on one slow run.
   3. Counting work instead of time is an established way to pin cost in a unit test: Go's standard library
      tests use `testing.AllocsPerRun` and assert a number of allocations, which is the same on every machine.
3. **What is best for ClassiCade.** ADR-039 and CC-306 already say a slow test is never fixed by a bigger time
   limit, retries or skipping. So the tests count the steps the code takes and compare them with a bound worked
   out from the input: players, days of the window, days of play and weeks. The count is the same on every machine,
   so the test cannot fail on a busy runner, and a slower algorithm always moves it.

## Design

1. Each exported function in `playerStatuses.js` (`statusRows`, `statusWeeks`, `statusMoves`, `northStarOn`)
   takes an optional last argument `{ meter }`. A meter is `{ add(steps) }`. Without one a frozen meter that does
   nothing is used, so the server's calls in `analyticsComponent.js` are unchanged. This is the "explicit option"
   of ENGINEERING.md §3 rule 3 with a default that is part of the documented contract (rule 5).
2. What a step is. `statusRow`: one per day of the read window, one per day of play read, one each time a marker
   moves past a day of play. The walk counts in a local number and tells the meter once per player, so the hot
   loop costs the same without a meter. `statusWeeks`: one per row for the week's last day, plus one per day of
   the week. `statusMoves`: two per row. `northStarOn`: one per row. The file's header comment says that a new
   loop adds its steps to the meter.
3. The bounds, for the same data as before (1,000 players, 400 days, so a 421-day window and 58 weeks):
   1. Each slice of 250 players: at least players times window days (105,250) and at most that plus three steps
      per day of play (136,825). The lower bound proves the meter is wired.
   2. The trend, the moves and the North Star together: at least players times (weeks plus 3) (61,000) and at most
      players times (8 times weeks plus 3) (467,000).
4. A limit of the design: the meter counts the loops that report to it. A new loop that does not would not be
   counted. The header comment and the test comments say so, and a reviewer checks it like any other rule of the
   file.

## Scope

- In: the two cost tests in `playerStatuses.test.js`, the meter in `playerStatuses.js`, and a sweep of every
  other test that asserts elapsed time.
- Out: the tests listed below, whose subject is time itself.

### Other tests that assert elapsed time

The whole repo was searched for `performance.now`, `Date.now() -`, `hrtime`, "within the budget" and
`toBeLessThan(` on a duration. These remain, and a step count does not fit them, because what they check is how
long something takes in real time, not how much work an algorithm does:

| Test                                                                                                                                                 | What it asserts                                                           | Why a count does not fit                                                                                                                       |
| ---------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| `apps/server/src/bots.integration.test.js` "ends its thinking threads well inside the shutdown budget, even mid-think"                               | `running.close()` under 5,000 ms with a worker stuck forever              | It checks that shutdown ends real worker threads instead of waiting out the 30 s think budget. The margin is wide (371 ms on the PR #135 run). |
| `apps/server/src/dependency/thinking/botThinkingClient.test.js` "keeps the event loop answering while a deep chess search runs"                      | a 5 ms timer never waits 60 ms or more, and the searches took over 150 ms | Event loop responsiveness is a time property. A lower bound cannot fail on a slow machine. The 60 ms upper bound is the one to watch.          |
| `apps/server/src/dependency/thinking/botThinkingClient.test.js` "answers closed and ends every thread at shutdown, within its time, even mid-search" | `pool.close()` under 2,000 ms                                             | As for the bots shutdown test.                                                                                                                 |
| `apps/server/src/dependency/telemetry/telemetry.test.js` "stops within its time limit even when the endpoint never answers"                          | `shutdown()` under 1,000 ms with a 50 ms limit                            | The OpenTelemetry SDK's own timers decide it. Fake timers do not reach inside the SDK.                                                         |
| `apps/server/src/service/http/authLockout.test.js` (at least 190 ms) and `loginThrottle.test.js` (at least 4 ms)                                     | lower bounds on a delay that is the behaviour                             | A busy machine only makes them pass more easily.                                                                                               |
| `e2e/computer.spec.js` "Play Rocky"                                                                                                                  | the first move opens within 2,000 ms of the press (CC-221)                | A product promise about what a person waits for, in a real browser.                                                                            |
| `e2e/matchShellPresses.js`, `e2e/restart-presence.spec.js`, `e2e/share.spec.js`                                                                      | every press answers within 100 ms (CC-164)                                | The same, for every control.                                                                                                                   |

They should be watched by CC-301 (flaky test quarantine). If one of them fails on a run that does not touch its
code, it gets its own ticket. A fix there would be deterministic waiting on the event itself, as in CC-306, never a
bigger limit.

## Acceptance criteria

- [x] The two cost tests count steps through a meter and assert a bound from the input size. No timer, no retry,
      nothing skipped.
- [x] Each new test fails against a deliberately quadratic version of the code and passes against the real one.
- [x] The server's calls are unchanged and the file stays at 100 % coverage.
- [x] Every other test that asserts elapsed time is fixed or listed above with the reason.
- [x] `npm run lint` and `npm run format:check` pass on the changed files, and the related tests pass.

## Verification

1. **Fails first, before the meter existed.** With the new tests and the old code, both failed: "expected 0 to be
   greater than or equal to 105250" and "expected 0 to be greater than or equal to 61000".
2. **Fails on a quadratic version.** Two one-line regressions, then reverted. The walk set its older marker back
   to the first day of play on every day of the window (`old = 0;` at the top of the loop), and the trend's inner
   loop started at the book's first day for every week, skipping the days before the week. Every status rule test
   still passed, so the statuses were right, and both cost tests failed: "expected 2273925 to be less than or equal
   to 136825" and "expected 12850000 to be less than or equal to 467000", 17 and 28 times over their bounds.
3. **Passes on the real code.** `npx vitest related apps/server/src/domain/analytics/playerStatuses.js --run`
   `--maxWorkers=2 --project node`: 49 files, 603 tests passed. `playerStatuses.js` with coverage: 100 % of
   statements, branches, functions and lines.
4. `npx eslint apps/server/src/domain/analytics/` and `npx prettier --check` on the same folder pass.
