## Root cause

1. #74 (CC-234, CC-115, merged 2026-10-17 23:51:10 UTC) made `SessionProvider` need a `sessionBroadcast` service,
   so tabs follow a sign-in or sign-out in another tab.
2. #75 (CC-235, merged 23:51:06 UTC, four seconds earlier) added tests in `components/Celebrations` that render
   `SessionProvider` with services built by hand and no `sessionBroadcast`. On `main` with both, 13 tests failed
   with "Cannot read properties of undefined (reading 'onChange')".
3. Each PR was green against a `main` without the other. The two merges came four seconds apart, so neither ran its
   checks on top of the other. Git merged them with no textual conflict, the same kind of break as CC-247 a few
   hours earlier.
4. Production was not affected (tests only).

## Research

1. **How our process did it.** Same as CC-247: GitHub's "loose" required checks, and the coordinator's re-run of
   the fast checks before each merge was not done for two merges in the same few seconds.
2. **GitHub, "Require branches to be up to date before merging"**
   (https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches,
   read 2026-10-18): strict mode makes a PR update and run the checks again after every merge ahead of it. With it
   on, the second of the two merges would have been refused until it was checked on top of the first.
3. **Merge queues**
   (https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue,
   read 2026-10-18): two PRs queued together are checked as `main` + first, then `main` + first + second, so the
   second would have failed in the queue, not on `main`.
4. **Semantic merge conflicts** (Martin Fowler, 4 August 2011,
   https://martinfowler.com/bliki/SemanticConflict.html): a change of contract in one branch and a new caller of the
   old contract in another merge cleanly as text. Here the contract was a React provider's required services.
5. **What else would have helped.** Tests that build services by hand repeat the provider's needs in every file.
   A shared helper that builds a complete fake service set (most tests already use `testing/fakes.js`) means a new
   required service is added in one place. Worth doing when these files are next touched; not a ticket on its own.
6. **Best for ClassiCade.** The strict setting, or a merge queue, is the fix for the class of bug; this ticket only
   made `main` green again. While fast mode lasts (below) the fallback is the coordinator running `main`'s checks
   after every merge.

## Fix

`MatchProgressProvider.test.jsx` and `ResultCelebration.test.jsx` pass `fakeSessionBroadcast()` (PR #79). The 22
tests in `components/Celebrations` pass.

## Lesson (recorded in ADR-039, amended 2026-10-18)

Twice in one day two PRs that were each green broke `main` together (CC-247, CC-257). Rule (owner, 2026-10-18):
branch protection requires a PR to be up to date with `main` for the fast checks, and `strict: true` was set.

Later on 2026-10-18 the owner chose **fast mode** until the feature phase ends (working agreement rule 6, PR #89):
branches need not be up to date to merge, and the coordinator runs `main`'s checks after each merge and fixes a
clash at once. `required_status_checks.strict` then read `false`. Two merges seconds apart, like #74 and #75, can
again break `main`; the coordinator's check after each merge is what catches it now.

## Proposed rule

For CLAUDE.md working agreement rule 4 (added by the docs backfill PR): "A small fix under an hour (one-line hotfix,
test fix) still gets a ticket file with Root cause and a short Research note, written before the PR is merged."
