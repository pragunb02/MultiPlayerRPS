## Root cause

1. #62 (CC-232, merged 2026-10-17 21:32 UTC) changed `createPageTemplate` in `service/http/webApp.js` to take
   `{ head, title, description }` instead of the head string.
2. #64 (CC-233, merged 21:35 UTC, three minutes later) added the owner console route, which called the template
   the old way, with a string. The page rendered "undefined", and `webApp.test.js` ("answer an admin with the
   app…") and `admin.integration.test.js` ("serves the owner the console page") failed on `main`.
3. Each PR was green, but against a `main` that did not have the other one. Branch protection did not require a PR
   to be up to date with `main`, so no check ever ran on the two together before they were both merged. Git
   merged them with no textual conflict: different lines, same contract.
4. Players were not affected: the console is off until `ADMIN_ACCOUNT_IDS` is set.

## Research

1. **How our process did it.** Required checks ran on each PR's merge with the `main` of the moment the check
   started. GitHub's "loose" mode: a later merge ahead of it did not make the check run again.
2. **GitHub, "Require branches to be up to date before merging"**
   (https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches,
   read 2026-10-18). In strict mode "the branch must be up to date with the base branch before merging". In loose
   mode "status checks may fail after you merge your branch if there are incompatible changes with the base
   branch". That is exactly what happened.
3. **Merge queues** (GitHub, "Managing a merge queue",
   https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue,
   read 2026-10-18). The queue builds a temporary branch with the latest `main` plus the PRs ahead in the queue,
   runs the required checks on it (the workflow needs a `merge_group` trigger), and merges first in, first out,
   so `main` is "never broken by incompatible changes", without every author updating their branch by hand. It
   is a branch protection setting. Whether it is offered for a repository owned by a personal account, like this
   one, is not stated on that page and was not checked. The idea is older: Graydon Hoare's "not rocket science
   rule" (2014, bors for Rust): only merge what has passed the tests as it will be after the merge.
4. **Semantic merge conflicts** (Martin Fowler, "SemanticConflict", 4 August 2011,
   https://martinfowler.com/bliki/SemanticConflict.html): changes that "can be safely merged on a textual level
   but cause the program to behave differently". His answers are self-testing code, which finds them, and merging
   more often, which finds them sooner. Our tests found it at once; the gap was that they ran on the wrong
   combination.
5. **Best for ClassiCade.** Strict mode on the fast required checks (lint, format, audit, unit and integration,
   Docker build): they take minutes, so updating a PR after each merge ahead of it is affordable. A merge queue
   would remove the manual updates if the number of builders grows and the setting is available. The browser suite
   is not required (ADR-039 point 5), so it can still break after a merge; the 10th-merge stop catches that.

## Fix

`webApp.js`: the console route passes `{ head, title, description }` (PR #72). The two failing tests pass.

## Lesson (recorded in ADR-039, amended 2026-10-18)

Branch protection was set to require a PR to be up to date with `main` for the fast checks (`strict: true`). Until
it was on, the coordinator re-ran the fast checks against the current `main` before each merge. The same failure
happened again hours later (CC-257) before the setting was turned on.

Later on 2026-10-18 the owner chose **fast mode** until the feature phase ends (working agreement rule 6, PR #89):
branches need not be up to date to merge, and the coordinator runs `main`'s checks after each merge and fixes a
clash at once. `gh api …/branches/main/protection/required_status_checks` then showed `strict: false`. So, for now,
a semantic conflict like this one is caught on `main` after the merge, not before it, as the research above
predicts for loose mode. Strict mode, or a merge queue, is the way back when fast mode ends.

## Proposed rule

For CLAUDE.md working agreement rule 4 (added by the docs backfill PR): "A small fix under an hour (one-line hotfix,
test fix) still gets a ticket file with Root cause and a short Research note, written before the PR is merged."
