Shaped on 2026-10-20 from the owner's request: "the UI must stay great and smooth, with no added friction, backed by
research rather than simple HTML text, with proper contracts and colour coding". Domain:
[Look and feel](../domains/LOOK_AND_FEEL.md). Its partners are [CC-315](CC-315.md) (who may interrupt, and when) and
[CC-316](CC-316.md) (the recurring review that checks both).

## Problem

Every new feature adds its own words, its own pop-up and its own colours. Today the web app has one token file
(`apps/web/src/styles/tokens.css`) but no contract on top of it. Colours are named by hue or by use
(`--color-xp`, `--color-accent`, `--color-game-rps`), not by meaning, so a builder adding "your turn" or "opponent
left" has to pick a colour by taste. There is no `info` colour and no player-identity colour. Thirteen `z-index`
values (1, 3, 5, 10, 15, 20, 30, 40, 50) are written raw in ten CSS modules, so stacking order is whatever the
last builder chose. There are five raw font sizes, three of them in art. Eight places open a dialog (`Seats`,
`FeedbackDialog`, `SoundSettings`, `PassAndPlayShell`, `ConfirmDialog`, `FeedbackInbox`, `PrivacySettings`,
`FairnessLock`), about eleven places show a toast, and seven components act as banners (`RequestBanner`,
`SiteRequests`, `ConnectionBanner`, `TurnBanner`, `StreakAtRisk`, `SaveProgressCard`, `ComputerNote`). Nothing says
when each kind is the right one or how many may share a screen. The shared `Modal` moves focus in and back, but Tab
can leave it for the page behind (no `inert`, no trap). That is a gap against WCAG 2.4.3 focus order. A reviewer has
nothing written to point at, so "this pop-up should be a line of text" stays an opinion.

## Job to be done

When a builder adds anything a player sees, they want one documented set of tokens and component contracts to pick
from, so the screen stays consistent, readable and calm without anyone re-arguing colours and pop-ups in review.

When a player sees a colour or a pop-up, they want it to mean the same thing everywhere, so they can tell at a
glance whose turn it is, what went well and what needs them.

## Appetite

L (up to 2 days of agent time), split into three PRs inside the appetite: (1) tokens and the check, (2) the
component contracts with their tests and the migration of raw values, (3) the living docs page.

**Cut line**, dropped first in this order: the living docs page (part 3) becomes the Markdown contract only; the
badge and card contracts are written but their component tests wait for a follow-up ticket; the DTCG JSON export.
The tokens, the check and the dialog, toast and banner contracts are never cut: CC-315 builds on them.

## Proposed solution

Copy lengths per component (one line per language, Hinglish first where we use it, CC-217): button 3 words, toast
70 characters, banner 90 characters, dialog title 6 words and body 2 sentences, badge 12 characters. CC-316 checks
them in review. The numbers are an open decision below.

A **new pop-up type** is anything that draws over the page or takes the live region and is not one of the
components above: a new portal, a new fixed-position element, a new `role="dialog"`, `role="alertdialog"` or
`aria-live` outside the toast region and the banner. It needs a change to the contract first.

### 3. The check (`scripts/check-css-tokens.mjs`, run by `npm run lint`)

The owner chose stylelint (D4). Until stylelint can pass `npm audit` (see "D4 and ADR-008"), the rules are written in
a stylelint plugin rule's shape over a PostCSS parse (`scripts/design/cssTokens.mjs`) and run by our own script, the
way `scripts/check-comments.mjs` runs the CSS comment check.

1. Refuses in any CSS file except `tokens.css`: a hex, `rgb()`, `hsl()` or named colour; a `z-index` that is not
   `var(--layer-*)`; a `font-size`, `line-height`, `border-radius`, `gap`, `padding` or `margin` written in `px` or
   `rem` (zero, `auto`, percentages, `em`, `ch`, container units and `calc()` over tokens stay allowed). Raw
   timings are left to CC-281's check.
2. Refuses in JSX (an ESLint rule beside `classicade/comment-style`): `createPortal`, `role="dialog"`,
   `role="alertdialog"`, `aria-live` and `position: fixed` classes outside the contract's components
   (`Modal`, `ToastProvider`, the banner components, `CelebrationStage` once CC-099 adds it), with a message that
   points at `docs/design/CONTRACT.md`.
3. Exceptions live in one list in the check, each with a reason (SVG user units in `art/`, the chess board's own
   layers). The list may only shrink: a test fails if it grows without a matching contract change.

### 4. The living docs page: `/admin/design`, inside the owner console

A page in the console (ADR-036) that renders every token as a swatch with its contrast against both backgrounds,
every component in every state from the contract, light and dark side by side, at 390 px and 1280 px. It imports
the real components and the real `tokens.css`, so it cannot drift from the app.

**Why there and not a public `/design` or a static page.** A static docs page (Markdown or a built HTML file) cannot
render our real components in their real states with the CSP the app runs under, so it drifts the day after it is
written. A public `/design` route is more surface for nothing: players never need it, and it would be indexed. The
console already has what this page needs: the allowlist checked on every request, the same 404 as any unknown
address for everyone else, `no-store` and `noindex`, and lazy loading, so nothing reaches the first route's bundle
(150 KB budget, CC-135). The Markdown contract in `docs/design/CONTRACT.md` stays the source of the rules for
agents and reviewers, who read files, not pages. The page shows the components; the file says the rules.

## Non-goals

- No visual redesign. Values do not change except for the new roles.
- No new CSS framework, no Storybook, no Style Dictionary (each a new dependency, ADR-008). stylelint is the owner's
  choice for the check (D4), held back for now by `npm audit` (see "D4 and ADR-008").
- No motion tokens or recipes (CC-281), loading states (CC-282), icons (CC-283) or theme choice (CC-280).
- Not the routing of which notice shows when: that is CC-315.
- Not the layout probe for clipping and overlap: that is CC-154.

## Rabbit holes

- **Migrating every module by hand.** The check lands with the migration of the 13 `z-index` values and 5 font
  sizes in the same PR, and nothing else: the codebase has no raw colours left, so the colour rule is free.
- **Perfect role names.** Names follow Material 3's colour roles shape (role, on-role, role container) and stop
  there. A rename later is one search.
- **A tokens build step.** No build step: `tokens.css` stays hand-written. A DTCG JSON export is a cut-line item.
- **Linting JSX for pop-ups perfectly.** The rule catches the patterns listed. Anything cleverer is caught by the
  design lens in review (CC-316).

### D4 and ADR-008

ADR-008 asks for the latest stable release of any dependency, as few dependencies as possible, built-ins first, and
`npm audit` at 0 high or critical before merge. The owner's answer to D4 is stylelint, as a dev-only dependency, with
`npm audit` kept at 0. The case for it against ADR-008:

1. **It earns its place.** stylelint is the standard CSS linter, maintained, and built on PostCSS, the parser Vite
   already installs. A check on a real CSS parse is sturdier than our own reading of the files.
2. **It never ships.** It is a dev dependency only. It runs in `npm run lint` and never in the server, the web bundle
   or the production image.
3. **One package, not two.** The rules are our own small plugin in this repository, so no third-party plugin is added.
4. **Latest stable.** On 2026-10-20 the latest stable release is **stylelint 17.16.0** (`npm view stylelint
version`, published 2026-10-01). Version 18 is not released.

**What the build found (2026-10-20).** Installing stylelint 17.16.0 makes `npm audit` report **5 high** findings, all
one advisory: [GHSA-vfj7-8cjw-p6xm](https://github.com/advisories/GHSA-vfj7-8cjw-p6xm) (published 2026-09-18), a
denial of service in `braces` through deeply nested patterns. Every `braces` release up to 3.0.3, the latest, is
affected, and there is no fixed version. stylelint reaches it through `micromatch` 4.0.8 (the latest, which needs
`braces`), `fast-glob` and `globby`. Upstream says stylelint 18 drops those for `tinyglobby` and `picomatch`
([stylelint#9559](https://github.com/stylelint/stylelint/issues/9559)). No `overrides` entry can fix it, because no
safe `braces` exists. So "stylelint" and "`npm audit` at 0" cannot both hold today.

**What this build does.** The audit is a required check and a security rule, so it wins until the owner says
otherwise. The check is written as stylelint-shaped rules: each rule walks a PostCSS parse and reports a node and a
message, exactly what a stylelint plugin rule does. PostCSS is the one dependency they use, and it is already
installed by Vite, so `npm audit` stays at 0 and no new package is downloaded. Moving to stylelint once 18 is out is a
small change: add `stylelint` to the dev dependencies, wrap each rule with `stylelint.createPlugin`, point the `lint`
script at `stylelint`. The rules and their tests stay as they are. **The owner decides** whether to keep this until
stylelint 18 ships, or to take stylelint 17 now with the audit finding accepted in writing.

  `--color-bg`, `--color-surface` and its own `-soft`. Test: `apps/web/src/styles/tokens.test.js` › "every role

## Threat model

1. **What are we building?** A CSS and JSX check, token aliases, a contract document, and one console page.
2. **What can go wrong?** The console page could leak that the console exists, or ship in the main bundle. The
   check could be bypassed with an inline style.
3. **What are we doing about it?** The page sits behind the ADR-036 allowlist on the server and the client, answers
   the same 404 as any unknown path, `no-store`, `noindex`, lazy chunk. It shows only test strings and tokens, never
   player data. Inline styles stay blocked by the CSP and the existing `style` lint rule (ADR-012 point 6).
4. **Good enough?** Yes: no new endpoint with data, no new storage. `e2e/owner.spec.js` proves the 404.

## Privacy checklist

- **Data:** none collected or shown. The docs page uses made-up names ("Riya", "Guest-ABCD").
- **Retention:** none.
- **Who sees it:** builders read the contract file in the public repo; only admins see the console page.
- **Minors (ADR-028):** nothing changes for them.
- **Defaults:** not applicable.

## Alternatives considered

- **Storybook** as the living docs: a large dev dependency tree, its own build, and it would not run under our CSP
  without changes. The console page does the same with our own code.
- **Tailwind or another utility framework** to force tokens: a rewrite of every module and against ADR-009.
- **Tokens in DTCG JSON as the source**, generating `tokens.css`: right shape for a multi-platform team, but we have
  one platform and no designer tools to feed. We keep the DTCG names and types in mind so an export is easy later.
- **Only a written guide, no check:** guides drift; the owner asked for contracts.

## Research (written before any code)

### 1. How our code does it today

Read on 2026-10-20 on `main` (a5a801c8). `tokens.css` (170 lines) holds every colour, size, radius, shadow and
duration, light and dark by `prefers-color-scheme`, reduced motion zeroes the durations. A search of every CSS file
outside `tokens.css` finds **no raw hex or `rgb()` colour** (ADR-012 did its job), **13 raw `z-index` values in 10
modules**, **5 raw font sizes** (3 in art, one in the admin charts, the Tic-Tac-Toe mark at `3rem`), 5 raw
`px`/`rem` values among about 765 spacing and radius declarations, and 35 raw timings (CC-281's). Colours are named
by hue or use; there is no `info`, no `you` or `opponent`. The notice side: `lib/notify/categories.js` (CC-208) has
six categories with a place, a priority and a rate limit; `ToastProvider` waits lower toasts while a higher category
holds the screen (`useHold`, used by `RequestBanner`, `SiteRequests`, `ResultCelebration`). The `Modal` portals to
`body`, moves focus in, closes on Escape and returns focus, but does not keep Tab inside. The design lens of the
review (CLAUDE.md "Decision-first tickets" point 4) exists as a name with no checklist.

### 3. What is best for ClassiCade

1. **Keep `tokens.css` as the only source** and add roles as aliases. No build step, no framework, no dependency:
   our CSP, our budget phones and ADR-008 all point the same way.
2. **Contracts as a short table** that a reviewer can quote, with numbers (most per screen, copy length), because
   the owner asked for decisions that can be checked "every now and then", and a number can be checked.
3. **A check in lint** for what a machine can see (raw values, new pop-up patterns) and the design lens (CC-316)
   for what it cannot (is this the right component).
4. **Player colours that are not status colours**, because a loss is not an error (ADR-050) and red and green fail
   for the most common colour vision deficiencies.
5. **The docs page in the console**, for the reasons in section 4.

## Build notes (2026-10-20 and 21)

Built in one pull request, inside the appetite, in the order of the three parts. Where the build differs from the
spec above, and why:

1. **The check runs without stylelint for now** (D4). See "D4 and ADR-008": stylelint 17.16.0 fails `npm audit`
   with no fix. The rules are in a stylelint plugin rule's shape over PostCSS, which Vite already installs and which
   is now a declared dev dependency (8.5.30 to 8.5.31, no new package). The owner decides whether to wait for
   stylelint 18 or accept the finding.
2. **One more layer, `--layer-banner-alert` (20).** The connection strip sat at 20, over the request banner at 10.
   Moving it to `--layer-banner` would change which one is on top, so it keeps 20 under its own name.
3. **The font sizes moved to tokens, none to exceptions** (D7). The SVG text sizes became `--type-svg-*` tokens in
   the drawing's own units and the board's sizes `--type-board-*`, with the same values. The five raw spacing and
   radius values (confetti, the toast's gem, chess coordinates and captured pieces) are the exceptions list, each
   with its reason. A test also fails when an exception no longer lets anything through.
4. **More pop-up components than the ticket named.** The rule found 18 files that already use a portal, a dialog
   role, a live region or `position: fixed`: the dialog, toasts, celebrations, the turn banner, seven announcers
   (hidden lines read out) and the chess promotion picker. Each is listed in the contract with its reason.
5. **The design page shows the theme the device shows**, not light and dark side by side. Side by side needs the
   dark tokens under a class as well as the media query, which is CC-280's theme choice. The page says which theme
   it shows, and the browser test checks both. The card, badge and empty state have no shared component yet, so
   the page shows examples built from tokens (the cut line allowed this).
6. **"Escape closes unless a destructive action is running" is not built.** The `Modal` cannot know what its
   buttons are doing. The contract row says "Escape closes". A follow-up can add it to `ConfirmDialog`.
7. **A spectator** keeps the seat colours and a neutral turn banner, since they are neither "you" nor "opponent".
8. **The ADR is not written.** The coordinator assigns ADR numbers (ADR-068). It amends ADR-009 (the contract and
   its check) and ADR-012 point 1 (tokens by role, layers), with the D4 note.

9. **One token file per role** (coordinator, 2026-10-21, for the owner's premium redesign that builds on this
   ticket). `tokens.css` is now only the entry file. It imports `tokens/palette.css`, `type.css`, `space.css`,
   `elevation.css` (shadows and glows), `layers.css` and `motion.css`, with every declaration moved unchanged. A
   palette, type scale, elevation or glow refresh is then a values-only change in one file, and `tokens.test.js`
   fails when a token sits in another role's file. The check treats every file under `styles/tokens/` as a token
   file.
10. **`--layer-menu` (20)** for the inbox panel that CC-139 merged during this build with a raw `z-index: 20`.
11. **The `Modal` moves the focus itself on every Tab.** On WebKit the browser's own Tab skips buttons, so in a
    dialog of only buttons it left for the address bar (found by the WebKit run of the design page test).
