## Problem

On 2026-10-21 four builders saw these failures on a loaded laptop (load average 8 to 12), and each one passed when
run again alone. In `server.integration.test.js` the `afterAll` hook timed out at 10 s while it stopped the test
database (3 times), and some of its tests timed out at 5 s (once). In `challengeRoutes.test.js` an ordering
assertion failed once.

### Root cause

1. **`server.integration.test.js`: a new database for every test.** Each test started its server on a new
   database (`it-1`, `it-2`, …), so every start created about 30 collections and 80 indexes. mongod syncs every new
   collection and index to disk. Measured one at a time on this Mac, a collection costs 19 ms and an index 10 ms,
   against 0.3 ms for a plain insert and 4.6 ms for a journaled one. That made 1.3 to 1.5 s per server start on a
   quiet machine, and nearly all of every test's time. Under load the server logs showed 4.2 to 4.9 s from
   "database connected" to "server listening", or no "listening" line before the 5 s test timeout. At the end
   mongod held about 737 collections and 1,981 indexes, and its shutdown checkpoint synced every file: the mongod
   log showed "shutdown checkpoint … ran for 6652 milliseconds" and "WiredTiger closed, durationMillis 7106" at
   moderate load. Over 10 s, the hook timed out. `MongoMemoryServer.stop` sends SIGINT and waits up to 10 s itself.
   This is the same root cause for the hook and the test timeouts. The shutdown order of the server (CC-318:
   gateway, background tasks, flags, then the database) was checked and is right; each test closes its server
   before the next starts, and nothing was open when mongod stopped.
2. **The CC-095 daily-limit test slept.** It paused 150 ms after each of its twelve games. The pauses did two
   things. They gave the pipeline time to record a game before the next one (a guess on time), and they let the
   rival's event budget refill (CC-107: a burst of 20, then 10 a second). Without them, the rival's twenty-third
   event is refused.
3. **`challengeRoutes.test.js`: the same millisecond has no order.** The tests ran on the real clock. Two
   challenges made one after another in the same millisecond have the same `createdAt`, and then nothing orders
   them but their random ids. "Refuses a fourth open challenge" got 201: the fourth challenge sorted ahead of an
   older one, so it counted as within the limit of 3 (`brokenLimit` sorts by time, then by id). "Lists the inbox"
   expects newest first; with a tie, the stable sort keeps the older one first. Load did not cause this one: it is
   a millisecond tie, at any load.

## Fix

- `testing/memoryMongo.js` has `empty(dbName)`. It deletes every document of a database and keeps its collections
  and indexes, through one connection of its own, which `stop` closes before it stops mongod.
- `server.integration.test.js` runs every test on one database, `it`, emptied before each test. Only the first
  start creates the collections and indexes. The TTL index test uses a database of its own, so it still proves that
  a start creates the index. A test now takes 10 to 300 ms instead of 1.4 s, and the file takes 7 s instead of 38 s.
- The CC-095 test waits, after each game, for the winner's `progress:updated` push for that game, and has a script's
  event budget (`eventBurstPerPlayer: 1_000`, as in CC-318). No sleep is left in it.
- In `challengeRoutes.test.js` the test clock moves on a millisecond at each reading. The two tests that depend on
  order use it, so challenges made one after another are in the order they were made.

No timeout was raised, nothing was retried or skipped, and no app code changed.

### Research

How our code does it now: `startServer` calls every DAO's `ensureIndexes` on each start (`server.js`), which is
cheap when the indexes exist and costly on a new database. `MongoMemoryServer.stop` sends SIGINT and SIGKILLs after
10 s (`mongodb-memory-server-core/lib/util/utils.js`, `killProcess`). The mongod 8.2 log at shutdown shows the
time in the WiredTiger close checkpoint. Other options checked: the WiredTiger setting `checkpoint_sync=false`
made the stop 0.4 to 1.4 s instead of 4.5 to 5.6 s, but it did not make a start any faster, so it does not fix the
test timeouts. MongoDB's in-memory storage engine is in Enterprise only. A RAM disk for the database path depends
on each laptop. Emptying the collections between tests removes the cost itself: deleting a collection's documents
took 0.14 ms in the same measurement, and the indexes stay. For the challenge tests: the inbox is
newest first by `createdAt` (`challengeComponent.js`), and only an injected clock gives it a defined order.

**Found along the way, not changed here:** in production, two challenges from one player in the same millisecond
can still both count as within the limit. This happens when one reads the list before the other is stored and
then sorts ahead of it by its random id. Then 4 are open, not 3. It needs two requests in the same millisecond,
and the cost is one extra open challenge. It is for the coordinator to ticket.

## Acceptance criteria

- **AC-1** Given a loaded machine, when `server.integration.test.js` runs, then no test times out and the
  `afterAll` hook stops the database well inside 10 s.
- **AC-2** Given challenges made one after another in the same millisecond on the real clock, when the challenge
  route tests run, then their order and limit assertions hold every time.

## Test

Reproduced under load: ambient load from other sessions, plus `node -e 'for(;;){}'` CPU burners, with
`--maxWorkers=2` (no `stress-ng` on this Mac). "Heavy" is four copies of the file at once, as four builders, plus
6 burners.

| Run                                                          | Before                                                                                                                              | After                                                          |
| ------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| `server.integration.test.js`, heavy, load 5 to 16            | 16 of 16 runs failed: 1 to 15 tests timed out at 5 s in each. `afterAll` timed out at 10 s in 5 of 16. mongod stop took 4.5 to 10 s | 24 of 24 passed at load 9 to 23. mongod stop took 1.0 to 1.7 s |
| `server.integration.test.js`, alone, 4 burners, load 6 to 19 | 19 of 20 passed. In the other run one test timed out, after the machine stalled for 12 minutes                                      | (covered by the heavy runs)                                    |
| `challengeRoutes.test.js`, 2 to 4 burners, load 7 to 20      | 3 of 31 failed, all "refuses a fourth open challenge" (201, not 409)                                                                | 40 of 40 passed, plus 24 of 24 in the heavy runs               |

The inbox order assertion did not fail in 31 runs here. It has the same cause as the limit one, and the same fix.
