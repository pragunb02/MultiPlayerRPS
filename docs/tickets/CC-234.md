Built together with CC-115 on one branch, because both are the same gap: the web app never asks again who it is
after the server ends its realtime connection.

## Research (written before any code)

### 1. How our code does it today

1. Server. "Sign out other devices" and a password change (CC-116, PR #57) count the account's session version up
   and call `gateway.disconnectOtherSessions` (`apps/server/src/service/realtime/gateway.js`). It disconnects every
   other socket of the player with `disconnectSockets(true)`. A handshake that was being checked at that moment is
   disconnected as soon as it connects (`socket.disconnect(true)`). Logging out and signing in call
   `gateway.disconnectSession(oldId)`, which does the same for the sockets of one session id. All three send
   Socket.IO's disconnect packet, so the browser sees the reason `"io server disconnect"`. Tests already pin that
   reason: `accountSessions.test.js`, `security.integration.test.js`, `handshakeRaces.test.js`,
   `authRoutes.test.js`, `gateway.test.js`.
2. The ended session is still in the store with its old version. `createSessionCheck` and `createSessionGuard`
   (`apps/server/src/service/http/session.js`) end it on its next `/api` request: the request goes on with an empty
   session, so `GET /api/session` answers `{ authenticated: false }`. A socket handshake with it is refused with
   `UNAUTHORIZED`.
3. Web. `SessionProvider.jsx` asks `GET /api/session` once when the app starts, and changes identity only when this
   tab itself signs up, logs in, logs out or starts a guest. It does not listen to the socket at all.
   `lib/socket.js` passes `disconnect` and `connect_error` through `on`, but nobody subscribes to them for the
   session. `useReconnecting` turns on "Reconnecting" for any drop.
4. Socket.IO client 4.8 does not reconnect after the server's disconnect packet, nor after a handshake refused by
   middleware: both call `destroy()` (`socket.io-client/build/esm/socket.js`, `ondisconnect` and the
   `CONNECT_ERROR` case of `onpacket`). Its own comment on `active` says "the disconnection was initiated by the
   server, you need to manually reconnect".
5. Result (the bug): the signed out device keeps its old screen with "Reconnecting" for ever, a room page keeps the
   board, the header keeps the player's name. Only a reload or a page that calls the API shows the truth.

### 2. How other products do it

1. GitHub: a tab whose session ended in another tab or window shows the banner "You signed out in another tab or
   window. Reload to refresh your session." It tells the player at once, but leaves the reload to them.
2. Firebase Authentication, auth state persistence
   (https://firebase.google.com/docs/auth/web/auth-state-persistence, read 2026-10-18): with the default local
   persistence "any attempt to sign in ... will be detected and synchronized on all tabs", and a sign out in one tab
   signs the user out "on all other tabs". The client follows the change without a reload.
3. OpenID Connect Back-Channel Logout 1.0 (https://openid.net/specs/openid-connect-backchannel-1_0.html, final 2022) ends sessions server to server, and OpenID Connect Session Management 1.0 polls a `check_session_iframe`
   from the client. Both say the client should learn about an ended session without waiting for the next request.
4. OWASP Session Management Cheat Sheet
   (https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html, read 2026-10-18): ending a
   session must happen on the server ("the most relevant and mandatory"), and the client side should follow it, for
   example JavaScript that logs the client out so the user sees the session ended.
5. Socket.IO documentation, client socket instance, "disconnect" reasons
   (https://socket.io/docs/v4/client-socket-instance/#disconnect, the same text is in the 4.8.4 source above):
   after `"io server disconnect"` the client must reconnect by hand, every other reason reconnects by itself.

### 3. What is best for ClassiCade

1. The server already does its part: it ends the session and cuts the socket with a reason the browser can tell
   apart from a network drop. No new server event is needed, and nothing about the session crosses the socket.
2. The web app reacts to exactly the two signals that mean "the server ended this on purpose": a disconnect with
   reason `"io server disconnect"`, and a handshake refused with `UNAUTHORIZED`. It then asks `GET /api/session`
   again, which is the one place that decides who the browser is (identity comes from the session, never from the
   client). A network drop or a server restart is left to Socket.IO's own reconnect, as today.
3. When the answer is "not signed in", the tab becomes a visitor: the header says Log in, and a room page shows the
   join chooser instead of the board. When the answer is a player (for example the same browser signed in again in
   another tab, CC-115), the socket connects again as that player.
4. No polling and no timers: the check happens once per server disconnect, so it costs one request on the rare
   occasion a session is ended.
5. A toast saying why ("You were signed out on this device") would need the server to send a reason first. Out of
   scope here, noted for the presence work (CC-158).

## Why

A lost phone or a shared computer is signed out from elsewhere (CC-116). Its socket is cut at once, but its screen
still shows the account until someone reloads it. Whoever looks at it believes it is still signed in, and a player
in a room sees a board that no longer answers.

## Scope

- In: `SessionProvider` asks the session again after the server ends the socket or refuses its handshake, and
  reconnects the socket for whoever the session is then. Socket client exposes these two signals.
- Out: a server sent reason and toast (CC-158). Ending other devices' sessions in the store at once (CC-116 out of
  scope).

## Acceptance criteria

- [x] "Sign out other devices" on A, and B shows signed out without a reload, on the home page and in a room
- [x] A password change on A does the same for B
- [x] A network drop or server restart does not ask the session again
- [x] Tests cover the change (unit first failing, browser test with two browsers)
- [x] `npm run lint`, `npm run format:check`, `npm run test:coverage` pass

## Plan / notes

1. Shared design with CC-115 and ADR-033. No server change: the gateway already ends the sockets with the reason
   the browser needs, and the tests from CC-116 pin it.
2. `apps/web/src/lib/socket.js` `onEndedByServer(handler)`: called for a disconnect with `"io server disconnect"`
   and for a handshake refused with `UNAUTHORIZED`. Network drops, restarts, this tab's own disconnect and other
   refusals are not reported.
3. `SessionProvider.jsx`: on that signal it asks `GET /api/session` and takes the answer. The socket is connected
   again even when the answer is the same player, because Socket.IO will not do it after a server disconnect.
4. A handshake made with an old cookie during the five second renewal grace of CC-116 can be refused while HTTP
   still passes. The tab then connects again, and stops as soon as the browser has the new cookie. Accepted: it needs
   a handshake already on its way during a password change of the same browser.
