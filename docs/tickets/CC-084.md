## Why

The owner asked for unit tests of every branch and browser tests of every scenario on every screen — including
history: Back, Forward, Back-Back-Forward, reload.

## Scope

- **Every branch** in `apps/server`, `apps/web`, `packages`: 92.9 % → 99.4 % branches, 96.9 % → 100 % lines and
  functions (967 tests). Gates raised to 100 % lines/functions, 99 % branches.
- **Browser history** (`e2e/navigation.spec.js`): browsing chains, reload of every screen, redirects never in history,
  404 → back; rooms: create → Back → Forward → reload, join by code → Back → Forward, leave, forfeit, finish → Play
  again → Back; account: log in from a lobby and Back never showing the form, log in ↔ sign up chains keeping `next`,
  log out on the profile and Back showing no account data, guest sign-up from a room through Back/Forward.
- **Every screen state** (`e2e/screens.spec.js`): home (guest in one click, catalog links), lobby (join enabled only
  for a full code, unknown code, per-game options), room (already started → offer a new game, everyone left → gone,
  names/connection/turn for both, logout in a waiting room), profile (match in history after a game; guest vs account
  prompts), sign-up (checks on blur, Enter submits only when valid).
- 84 browser tests (42 × desktop and mobile), stable over 5 consecutive runs.

## Found and fixed

- **Back re-entered a room you had left** (and re-seated you, or showed a forfeited game as if joinable): leaving now
  replaces the history entry.
- **CC-085 — logging out inside a waiting room, then Back,** seated a fresh guest against the account that had just
  left. Signing out now gives up seats in rooms that haven't started (running games keep the seat). One hook,
  `onIdentityChanged`, covers sign-in (seats follow a guest to the account, CC-083) and sign-out.
- **Stale first session answer:** a slow "who am I?" reply could arrive after a room link had already started a guest
  session and disconnect the new socket. It is ignored once the identity changed.
- **Corrupt stored password hash** (`scrypt$…` with bad parameters) made login answer 500 and let a stored value pick
  scrypt's memory size. Parameters are validated; a corrupt hash simply doesn't match.
- **"Load more" on the profile failed silently** (unhandled rejection): it now says so and offers a retry.
- A latecomer to a started game is offered "Start a new <game> game".
- Dead code removed: an unreachable "room is full" guard, an unreachable chess click guard, two unreachable fallbacks.

## Branches deliberately not covered

- `persistence/accountDao.js:62` — `err.keyPattern ?? {}`: MongoDB ≥ 4.2 always sends `keyPattern`; the fallback keeps
  an older server answering 409 instead of crashing.
- `persistence/progressDao.js:70` (2) — retry and give-up after concurrent first inserts for the same player; only
  reachable by a timing race (the concurrency test hits it by chance).
- `persistence/progressDao.js:29` — default when no document exists; reachable only from that race.
- The merged report shows `packages/shared/src/progression.js` below 100 % because the web project also loads it; the
  node project alone reports 100 %.
