## Research (written before any code)

Sources were read on 2026-10-20.

### 1. How our code does it today

1. `docs/PROGRESS.md` holds one dated changelog line per change, newest first, under `## Changelog`, in the format
   `- YYYY-MM-DD — <ticket IDs> — what changed` (CLAUDE.md workflow rule 5). Every pull request that finishes work
   adds its line at the same place, the top of that list.
2. `docs/BACKLOG.md` holds the board. Finishing a ticket changes its row's Status cell to ✅ and adds `done in #PR`
   to its Links cell. The tables are aligned by Prettier (`npm run format:check` covers Markdown), so changing one
   cell can re-pad every row of that table.
3. The "next free" lines (top of BACKLOG.md, DECISIONS.md and PROGRESS.md's Status table) are bumped by whoever
   adds a ticket or an ADR.
4. The gap. With up to five builders at once (workflow rule 9), every pull request edits the same top line of the
   changelog and often the same table, so two pull requests that change unrelated code still conflict in git.
   Builders were told not to touch these files, so the coordinator copies each builder's line and board mark by
   hand in a "Docs sync" pull request (for example the 2026-10-20 sync line naming eleven merged pull requests).
   That is slow, easy to get wrong, and the line is written by someone who did not do the work.

### 3. What is best for ClassiCade

1. **One fragment per ticket, `docs/changes/CC-###.md`.** The ticket ID is unique and permanent, so two pull
   requests never add the same file and never conflict. Front matter holds what the script needs: `ticket` (must
   match the file name), `date`, `type` (the board's types), `status` (the board status after this pull request:
   `todo`, `in-progress`, `blocked`, `done`), `adrs` (a list, each `ADR-###` with an optional ` (amended)`), and
   an optional `pr`. The body is the changelog text, and optionally one Markdown table row for the board, used for
   a ticket that has no row yet or whose title changed.
2. **The collector** (`scripts/bin/collect-changes.mjs`, logic in `scripts/changes/collectChanges.mjs`) folds every
   fragment into the changelog in the existing format, newest first, sets each ticket's Status cell, adds its ADRs
   and `done in #PR` to the Links cell and links the ID to `tickets/CC-###.md` when that file exists, appends a new
   row given in a fragment to the last board table, formats both files with Prettier and deletes the fragments it
   folded. Running it again changes nothing: a line already in the changelog is not added twice and a mark already
   on the board is not repeated. `--check` validates and folds in memory without writing.
3. **The CI guard** (`changes` job in `ci.yml`, pull requests only) runs `--check --base HEAD^1` on GitHub's merge
   commit, whose first parent is `main`. It fails on a malformed fragment, and on a pull request that adds, changes
   or removes a changelog entry in PROGRESS.md, **unless** each added entry is the line made from a fragment that
   this same pull request deletes, and nothing is removed or changed. That is exactly what the collector's own pull
   request contains, so the collector is exempt by what it changes, not by a branch name or label anyone could set.
   This is towncrier's idea (skip the check when the branch rewrites the news file), made exact.
4. **Folding: the coordinator runs the script, no bot.** A workflow on `main` that opens a bot pull request (as
   CC-300 and changesets/action do) needs a job with `contents: write` and `pull-requests: write`, the repository
   setting, and a person to close and reopen every bot pull request to get CI (`GITHUB_TOKEN` rule). Images must
   be made in CI's pinned container, so CC-300 had no choice. A fold is plain text a laptop makes the same way,
   the coordinator already opens a docs pull request after a batch of merges, and fragments waiting a day hurt
   nothing (they never conflict, the changelog only lags). So: one command, no new token with write access, no
   new workflow. Revisit if the coordinator forgets often.
5. **ID allocation.** The coordinator gives each builder its ticket and ADR numbers at dispatch and bumps the next
   free lines itself. Builders never edit those lines, so two builders can never take the same number or conflict on
   the line.
6. **PR numbers.** A builder does not know the number before opening the pull request. The collector fills it from
   git when `pr` is missing: the first-parent commit on `main` that added the fragment is `Merge pull request #N`.
   With no such commit (not merged yet, or squashed) the line has no number, which the format allows.

## Why

Every parallel pull request conflicts on the changelog and the board, and the coordinator copies lines by hand.

## Scope

- In: fragment format, `scripts/changes/collectChanges.mjs` and its tests, `scripts/bin/collect-changes.mjs`, the
  `changes` job in `ci.yml` and its workflow tests, `docs/changes/README.md`, this ticket's fragment, CLAUDE.md
  (ID allocation, workflow rules 3 and 5), BACKLOG.md's workflow list, the ticket template, ADR-068.
- Out: one file per ADR (CC-295), the merge queue (CC-298), the stage counters (still the coordinator's, CC-137),
  folding the existing changelog into fragments.
