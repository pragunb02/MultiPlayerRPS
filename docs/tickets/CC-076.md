## Why

Guests (CC-013) cover casual play; accounts give players a permanent identity across devices and the basis for
ratings, friends and payments. The legacy auth was hardened in place (CC-009/010) but lives in the code being replaced.

## Scope

- In:
  - **Hashing** (`utils/passwordHasher`): Node's built-in scrypt (no native dependency — npm 11 blocks native builds),
    N = 2^15, r = 8, p = 1 (~32 MiB, sized for the hosting tier); self-describing hashes so parameters can be raised;
    transparent rehash at the next successful login; constant-time comparison; dummy verification for unknown emails.
  - **Models**: username (3–20 `[A-Za-z0-9_]`, unique case-insensitively, casing kept), email (trimmed, lower-cased,
    ≤ 254), password (8–128, never trimmed or logged).
  - **Persistence**: `accounts` collection (unique `email`, unique `usernameKey`); in-memory double; shared DAO contract.
  - **Data/domain**: account accessor (duplicates → ConflictError naming the field); account component (signup, login
    returning the same `Identity` model guests use: `user_<id>`, display name = username).
  - **Service**: `POST /api/auth/signup`, `POST /api/auth/login` — strict payloads; per-IP limit (20 / 15 min) and per-email
    limit on _failed_ logins (5 / 15 min, across IPs); new session id on sign-in and the old session's sockets disconnected.
    Logout = `DELETE /api/session`, "me" = `GET /api/session`.
- Out: email verification + password reset (CC-033), guest → account progress merge (CC-032), social login (CC-058),
  legacy user migration (CC-078), CSRF tokens (CC-030).

## Decisions / trade-offs

- **Signup reveals that an email is taken** (409 "That email can't be used"). Avoiding it needs email verification
  (CC-033); login, the main attack surface, does not leak (same message and same timing).
- scrypt over bcrypt/argon2: built in, memory-hard, no 72-byte limit, no native build.

## Acceptance criteria

- [x] Passwords stored only as scrypt hashes; never logged
- [x] Login failures indistinguishable by message and timing
- [x] Rate limits per IP and per targeted email
- [x] Sign-in rotates the session and cuts off sockets of the previous session
- [x] Users and guests share one identity model end to end (HTTP + sockets)
- [x] Tests, lint, format, coverage, audit pass; ran for real

## Verification

- 627 tests (5 consecutive green runs), incl. MongoDB integration with production-strength scrypt.
- Live: signup → login → `GET /api/session` as the user; failed logins for a real vs unknown email both averaged 44 ms;
  stored hash `scrypt$32768$8$1$…`; unique indexes on `email` and `usernameKey`; no password or email in any log line.
