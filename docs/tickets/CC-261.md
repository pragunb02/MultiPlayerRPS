## Problem

Sign-up and password change accepted any password of 8 to 128 characters that is not only spaces
(`models/credentials.js` `parsePassword`), including "password1" and passwords from public breaches (SEC-24, found
in the CC-116 research, #87).

## Fix

After the length rules, refuse a new password that is on a bundled list of common passwords or in Have I Been
Pwned's Pwned Passwords, with one plain message at the field, and let it through after the local check when the
remote service fails.

**Research note.**

1. **Our code today.** `parsePassword` checks length and blank only. `accountComponent.signup` and
   `changePassword` hash whatever passes. There is no outbound HTTP client in the server yet, and the CSP's
   `connect-src` is `'self'`.
2. **Sources.** NIST SP 800-63B section 5.1.1.2 asks verifiers to compare a new password against values known to
   be commonly used, expected or compromised, and to say why it was refused. Have I Been Pwned's API v3 documents
   the range API (`GET https://api.pwnedpasswords.com/range/{first 5 hex of SHA-1}`, no key) and the
   `Add-Padding: true` header, which pads each answer with fake suffixes of count 0. HIBP's privacy page says only
   the 5 character prefix reaches it, it keeps web server logs for up to 31 days, and nothing identifying is stored.
   Other products: GitHub checks new passwords against HIBP's list (GitHub blog, "New password security checks",
   2018), and Django's `CommonPasswordValidator` refuses a bundled list of about 20,000 common passwords. SecLists
   (MIT) publishes `Passwords/Common-Credentials/10k-most-common.txt`.
3. **Best for ClassiCade.** Both, local first: the list costs no network and catches the obvious ones even when HIBP
   is down, and the range API catches the rest without sending anything that names a person. Fail open, because a
   sign-up should not depend on a service we do not run, and count the outcome so an outage shows.

## The words

"That password is too easy to guess. Choose a different one." Checked against the other auth messages, which use
the same voice and say what to do: "That is not your current password", "Choose a password different from your
current one", "Passwords are 8–128 characters". It names neither the list nor the service, and is the same for
both, so it says nothing about where the password was found. The web app already shows a field error from the
server under its field (`SignupPage.jsx`, `AccountSettings.jsx`), so no web code changes.

Not behind a flag (a security fix), so the guardrail compares before against after instead of on against off.

## Acceptance criteria

- **AC-1** Given a sign-up whose password is on the common list in any capitals, when it is sent, then it answers
  400 at `details.field` "password" with the plain message, creates no account, and does not ask HIBP.
- **AC-2** Given a sign-up whose password's SHA-1 suffix is in the range HIBP answers with a count above 0, when it
  is sent, then it is refused the same way. Only the 5 character prefix is in the request, with `Add-Padding: true`.
- **AC-3** Given a password change whose new password is common or breached, when the current password is right,
  then it answers 400 at "newPassword" and changes nothing. With a wrong current password the check is not run.
- **AC-4** Given HIBP fails or takes more than 1.5 s, when a password that is not on the list is sent, then sign-up
  or change goes on, and `accounts.password_checks` counts `unavailable`. Every check counts exactly one of
  `clear`, `common`, `breached` or `unavailable`, with nothing about the player.
- **AC-5** Given any test, unit, integration or browser, when it runs, then it never reaches the network: the fetch
  is injected, and only `index.js` passes the real one.
- **AC-6** Given the privacy page, when it is read, then it names Have I Been Pwned among the services and says
  that only the first 5 characters of a hash are sent, from the server.
