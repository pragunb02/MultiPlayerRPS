## Research (written before any code)

### 1. How our code does it today (origin/main at `c35daaa`, read on 2026-10-18)

`apps/web/src/pages/LegalPages/PrivacyPage.jsx` was written from the server of 2026-10-16 (CC-046). Rooms in MongoDB
(CC-101), the network hash (CC-107), the login throttle (CC-117), the 90-day session limit (CC-116) and backups
(CC-108) came after it. `docs/DATA.md` (CC-241) is the inventory checked against the code, and its findings say
what is wrong on the page.

| Finding | The page says                                                                  | DATA.md (and the code)                                                                                                                                  |
| ------- | ------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| F1      | "Open game rooms live only in the server's memory"                             | `rooms` in MongoDB, 30 minutes to 24 hours after the last activity, then a `closed_rooms` record (code, game, reason, time) for 24 hours                |
| F2      | "We do not record your IP address with your games"; per-IP counts never stored | every room stores a keyed hash of the host's address. After CC-249 its key is random, made each day and forgotten after it                              |
| F3      | the server "counts recent requests per IP address for a few minutes"           | the login throttle also remembers which addresses signed in to each email, up to 10, for 30 days. After CC-250 it keeps only keyed hashes of both       |
| F4      | "Two services run the site"                                                    | nightly encrypted backups through GitHub Actions to an S3-compatible bucket the owner chooses, kept 30 days (ADR-044)                                   |
| F8      | "Sessions end 30 days after your last visit"                                   | also 90 days after signing in for accounts, and at a password change or "sign out other devices" (ADR-030). Guests have no 90-day limit                 |
| F9      | "Server logs record which page was asked for and how it went"                  | player ids, socket ids, room codes, match ids and account events too. No addresses or emails from the app. Render keeps logs 7 days (Hobby) or 14 (Pro) |

Analytics: the page says "no analytics services". ADR-034 decided that telemetry, when built (CC-173 to CC-178),
is anonymous counts only, first party, with an opt out. Nothing of it is built, and EVENTS.md is still Proposed.

The only test of the page (`legal.test.jsx`) checks the title, the draft note, the contact link and `cc.sound`. No
test ties the page to DATA.md, so the two drifted without anyone noticing.

### 2. How others do it (sources fetched 2026-10-18)

1. **UK ICO, the right to be informed**: a privacy notice says what is collected, why, who receives it, and "Say
   how long you will keep the personal data for. If you don't have a specific retention period then you need to tell
   people the criteria you use to decide"
   (https://ico.org.uk/for-organisations/uk-gdpr-guidance-and-resources/individual-rights/the-right-to-be-informed/what-privacy-information-should-we-provide/).
   So each store gets its period, not "until they are left or idle".
2. **Lichess** (https://lichess.org/privacy) names each kind of data with its retention, including connection data,
   and names its processors. We follow the same shape already, only the facts are out of date.
3. **Plausible** says exactly what it keeps instead of an address ("a daily changing identifier", salts "rotated and
   deleted every 24 hours", https://plausible.io/data-policy). That is the honest way to describe a hash: say it is
   kept, what it is made from, and why it cannot be turned back.
4. **DPDP Act section 5** asks a notice to say what personal data is processed and for what purpose, in plain
   language. ADR-028 keeps the lawyer's review before launch, and the page keeps its draft note until then.

### 3. What is best for ClassiCade

1. Correct the six sentences and add what is missing: rooms (with how long), the room's network hash, the login
   throttle, backups as a third handler (GitHub Actions and the owner's storage bucket), the 90-day limit and the
   other ways a session ends, and what logs hold.
2. Analytics: say only what is true on `main`. No analytics service or third-party analytics. If ClassiCade ever
   counts how the site is used, it is first party anonymous counts with an opt out, and this page changes before it
   starts (ADR-034, CC-173). The page does not describe any counting as built.
3. **A test that reads DATA.md.** Each fact the page states is written once as a pair: a sentence that must be in
   DATA.md and the wording that must be on the page. If DATA.md changes a period, the test fails until the page
   changes too. Old sentences that were wrong are checked to be gone. Normal unit test, no new dependency
   (`node:fs`, as `og/images.test.js` does).
4. DATA.md is updated in the same pull request for CC-249 and CC-250, so the two never disagree.
5. `LEGAL_TEXT_DATE` moves to 18 October 2026, because the page says readers can compare the date.

## Why

The privacy page is what players read. Today it says rooms live only in memory and that no address is kept with
games, which is not true since CC-101 and CC-107. A wrong privacy page is a trust and legal problem (CC-241 F1 to
F4, F8, F9).
