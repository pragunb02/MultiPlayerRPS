## Why

Players of the legacy app have accounts in the `users` collection (bcrypt hashes). When production switches to the new
stack (CC-029) they must still be able to log in with the email and password they know.

## Scope

- In:
  - **Lazy migration at login** — no batch job, no writes to legacy data. A login whose email has no account falls back
    to the legacy `users` collection (read-only DAO with no write methods). If the bcrypt hash matches, an account is
    created with the same email, the password re-hashed to scrypt, and the first free username valid under today's rules
    (`"Sam Lee!"` → `Sam_Lee`, then `Sam_Lee_2`, …). Later logins use the new account only.
  - **Signup refuses an email that belongs to a legacy player** ("That email can't be used", same as a taken email), so
    nobody can claim it first.
  - Unknown emails still get the dummy scrypt verify; every failure gets the same generic answer.
  - Two parallel first logins of the same player end on the same account (the email conflict is resolved by re-reading).
- Out:
  - **Legacy XP/levels are not imported**: they were writable by the client (SEC-01), so they can't be trusted.
  - Removing the legacy `users` collection (after CC-029, once migration traffic has died down).

## Acceptance criteria

- [x] Legacy player logs in with the old password; account created with a scrypt hash and a valid unique username
- [x] Wrong legacy password: generic 401, nothing created
- [x] Legacy documents are never written (integration test compares them before and after)
- [x] Signup with a legacy email is refused
- [x] Tests cover the change
- [x] `npm run lint`, `npm run format:check`, `npm test` pass
- [x] Docs updated (BACKLOG status, PROGRESS, ARCHITECTURE)

## Plan / notes

- Layers: `persistence/legacyUserDao` (read-only, case-insensitive email, regex-escaped) → `data/legacyUserAccessor`
  (empty list when absent) → `domain/accounts/accountComponent`. Username cleaning is a pure model
  (`models/legacyUsername`), bcrypt verification a utility (`utils/legacyPassword`, accepts only `$2a/$2b/$2y` hashes,
  never throws). `bcryptjs` is pure JS (no native build on Render).
- Timing: a legacy email with a wrong password costs a bcrypt compare instead of a scrypt verify. This can reveal that
  an email belonged to a legacy player — the signup form already reveals that an email is in use, so nothing new leaks.
