## Problem

A player can end every other session at once ("Sign out other devices", CC-116), but cannot see where they are
signed in, or end one lost phone without signing out the laptop too. CC-116's research named this gap G4: lichess
and GitHub both list sessions and end them one at a time.

## Fix

Under "Devices" on the profile's Account section, a list of the account's signed-in devices, each with a coarse
browser and system ("Chrome on Android"), the day it signed in and the day it was last seen (India days), "This
device" on the current one, and a Sign out button on every other one. Signing one out deletes only that session at
once and cuts its live sockets. The decisions are below and in ADR-081.

### Research (2026-10-21, before code)

**How our code does it today.**

1. Sessions are express-session 1.19 over connect-mongo 6 in `player_sessions`, stored as objects
   (`stringify: false`), rolling for 30 days, with `touchAfter` one hour, so an unchanged session's `expires` is
   rewritten at most once an hour (`persistence/sessionStore.js`). An account's session holds `identity`,
   `sessionVersion` and `signedInAt` (CC-116, `service/http/session.js`).
2. "Sign out other devices" counts the account's `sessionVersion` up and leaves the other sessions in the store:
   they are refused on their next request (ADR-030). So the store holds sessions that can no longer be used, and a
   list must not show them.
3. The only lookup by player is `sessionDao.deleteByPlayer` (account deletion, CC-035), with no index on the
   identity.
4. `gateway.disconnectSession(sessionId)` already cuts every socket opened with one session (used by logout).
5. CC-326: an answer to a request sent before a session id was renewed must not set the old id again
   (`createRenewedSessionRelease`). Reading express-session's `res.end` shows it starts `store.set` (an insert or
   update) for a changed session before it writes the headers, and only a touch (an update that never inserts)
   for an unchanged one. So a request of a device that is being signed out, still on its way, would put that
   session back in the store if it had changed the session. This design never changes an account's session after
   it has its device (below), so that cannot happen, and nothing in CC-326 changes.

**How others do it** (read 2026-10-21).

1. GitHub, "Viewing and managing your sessions"
   (https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/viewing-and-managing-your-sessions):
   a list of web sessions with the device, an approximate location and the last activity, and "Revoke session" on
   each. The current one is marked.
2. lichess (`lila`, the security page, `app/controllers/Account.scala`, as read for CC-116): up to 50 open sessions,
   each with a browser and system and a place, each closable alone, the current one marked.
3. Google Account, "Your devices" (https://support.google.com/accounts/answer/3067630): device name, place and
   last activity, with "Sign out" per device.
4. OWASP Session Management Cheat Sheet: offer users a way to "remotely terminate sessions"; session ids never go
   anywhere but the cookie.
5. User agent parsing. `ua-parser-js` 2.x is licensed AGPL 3.0 (1.x was MIT), and `bowser` is MIT but a whole
   parser for two words. Chrome's User-Agent Reduction (https://www.chromium.org/updates/ua-reduction/) freezes
   the system version and device model but keeps the platform name and the browser, which is all we show.

**What is best for ClassiCade.** The GitHub and lichess shape, without the place: a place needs the IP address and
a lookup database, and showing where a player was is personal data we do not want to keep (ADR-034 spirit). A
browser and a system from a closed list, read by about twenty lines of our own and no new dependency. The random
device id is the only handle the browser gets. The session id never leaves the server (OWASP).

## Acceptance criteria

- **AC-1** Given an account signed in on a laptop and a phone, when the laptop asks for its devices, then it gets
  both, each with a browser, a system, a sign-in day and a last-seen day, the laptop marked as this device, and the
  answer holds no session id and no player id.
- **AC-2** Given the same, when the laptop signs the phone out by its device id, then the phone's next request is a
  visitor's, its socket is cut at once, and the laptop stays signed in.
- **AC-3** Given another account's device id, when a player tries to sign it out, then the answer is 404 and that
  device stays signed in.
- **AC-4** Given the list, when a player tries to sign out the device they are using, then it is refused (400) and
  they stay signed in.
- **AC-5** Given "Sign out other devices" was used, when the list is read, then the devices it signed out are gone
  from it.
- **AC-6** Given a guest or a visitor, when they ask for devices, then they get 403 or 401.
- **AC-7** Given the profile page, when a player presses Sign out on a device, then the row goes, a status says so,
  and the focus moves to the next device's button (or the status when none is left). The list is a list, and each
  button is named after its device.

## Residual risks

1. A socket handshake that read the session just before it was deleted can still finish connecting. It is cut on
   its next reconnect, and every HTTP request of that browser is already a visitor's.
2. A session signed in before this change has no device until its next request, so it is listed only from then.
   Such a session is harmless until it is used, and "Sign out other devices" ends it either way.
3. The last-seen day comes from the store's expiry, which is rewritten at most once an hour, so a device seen just
   after midnight in India can show the day before.
