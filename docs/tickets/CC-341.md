# CC-341 — A friend request sent while the recipient is between pages never shows its toast

## Problem

A friend request sent while its recipient's browser is between pages or reconnecting never shows the "wants to be
your friend" toast on any page. The request still waits on the friends page.

### Root cause

The toast (`FriendRequestToasts.jsx`) comes only from the `friends:request` push. The server sends that push once,
to the player's channel, when the request rings (`friendComponent.ring`, `friendPushes.js`). Socket.IO delivers to
the sockets in a room at that moment only and keeps nothing for one that connects later, so a tab without a socket
in the channel at that moment (a page load, a reconnect) never hears of it, and nothing asks again when it
connects. Found by CC-339, where the browser test sent the request in that gap.

## Fix

When a player's socket connects, the server sends that socket each request that rang in the last 15 minutes, still
waits and was never sent to a tab of that browser (its session), so the toast shows on the next page and a reload
shows no second one. The web app is unchanged.

### Research

How our code does it now, for every push that shows something on any page:

- **Room invites and rematch requests** (`request:updated`, CC-207): `handleSocketOnline` in `roomHandlers.js`
  sends each connecting socket the open requests of every room the player sits in. Covered.
- **Challenge popups** (`challenge:updated`, CC-139): `ChallengesProvider` reads `GET /api/challenges` again on
  every `connect`, and the popups come from that list, so a challenge made while the tab was offline shows. "Later"
  is kept by the server, so a reload does not bring a dismissed one back. Covered.
- **Friend requests** (`friends:request`, CC-052): nothing on connect. This ticket.
- The "can't play right now" toast for a declined challenge and the gamification toasts are about something that
  just happened in this tab's own game or challenge, and the inbox or profile shows the result; they are left as
  they are.

Why the server and not `GET /api/friends`: the friends view lists every waiting request, also ones the server
chose not to announce. A minor's request in their quiet hours (CC-052 rule 3) is never announced, and a request
cancelled and sent again rings only once every 15 minutes (ADR-031.1, `ringAgainAfterMs`). A toast built from the
view would break both. So the server, which knows when each request last rang (`notifiedAt`), sends again only what
it announced: still waiting, rung in the last 15 minutes (the same 15 minutes as the ring rule, so it never tells a
player about a request more often than ringing does), not rung in the player's quiet hours and not in them now, and
from nobody on either side of a block with them. This is the pattern `handleSocketOnline` already uses for room
requests, and what Socket.IO's documentation leaves to the application: delivery is at most once by default, and
its connection state recovery only restores a short drop of the same socket, never a page load
(socket.io/docs/v4/delivery-guarantees, socket.io/docs/v4/connection-state-recovery).

Who already heard a ring is kept on the server, per browser session, not in the browser: the app keeps nothing in
web storage but allowlisted preferences (ADR-018, the browser tests check it), and the session is what a reload
keeps. When a ring goes out, the sessions with a tab in the player's channel are noted as having heard it, and a
session sent it again on connect is noted too. A ring is the request and when it rang (`ringAt`, now in the push),
so a request cancelled and sent again after 15 minutes rings again. The notes live in the server's memory for the
same 15 minutes, so they stay small; after a restart a browser may get one ring of those minutes a second time,
which is a toast, not a wrong state. A tab that connects at the very moment of a ring can get the push and its copy
at once: the toasts already show the same message only once within 3 seconds (`ToastProvider`, CC-208).

## Acceptance criteria

- **AC-1** Given a player whose socket is not connected when a friend request to them rings, when their tab
  connects within 15 minutes, then they see the "wants to be your friend" toast.
- **AC-2** Given a browser already showed that toast (or it was closed), when the page reloads or another page
  opens, then it does not show again.
- **AC-3** A request rung in the recipient's quiet hours, answered, cancelled, from someone on either side of a
  block, or rung over 15 minutes ago is not sent again, and a guest is sent nothing.

## Test

Each failed before the fix:

- `friendComponent.test.js` ("friendComponent: missed rings (CC-341)"): `ringAt`, and AC-3.
- `friendPushes.test.js` ("a request whose ring a browser may have missed"): sent to the connecting tab only, once
  per browser, never to a browser that heard it, again after a new ring, and the notes forgotten after 15 minutes.
- `friendRoutes.test.js` "tells a browser that had no connection as the request rang, once it connects": over real
  sockets (it timed out with the call in `gateway.js` taken out).
- `e2e/friends.spec.js` "a friend request sent while the other's page has no connection yet still shows its toast,
  once" (AC-1, AC-2): Arjun's new page is held off the realtime server with `routeWebSocket` until Riya's request
  has rung, then connects and shows the toast; after Close, a reload and the friends page show none. Before the fix
  it failed 2 of 2 at the toast; after it the friends spec passed 40 of 40 at `--repeat-each=10`.
- `Friends.test.jsx` "shows one toast when the ring and its copy for a tab that just connected both arrive" guards
  the moment both arrive; it passed before too, because of the toasts' own limit.
