## Research (written before any code)

1. **How our code does it today.** `.github/workflows/ci.yml` starts on `pull_request` and on `push` to `main`.
   Branch protection on `main` (classic, no rulesets) requires no checks during the feature phase (CLAUDE.md
   workflow rule 7); before that it required eight checks with branches up to date (ADR-039, amended 2026-10-18).
   The up-to-date rule made every open PR rebase and rerun after each merge. Without it, two green PRs broke `main`
   together twice in one day (CC-247, CC-257). Four jobs are written for pull requests only: `changes` (CC-299),
   `render-blueprint` (CC-294), `visual-scope` and `visual` (CC-155, CC-300). CodeQL runs from GitHub's default
   setup, not from a workflow file here. WebKit (`webkit.yml`) is advisory. `visual-refresh.yml` runs on the push
   to `main` after a merge. The changelog collector reads the PR number from `Merge pull request #N` subjects.
   The check names, from main's check runs on 2026-10-20: `Lint, format, audit, unit + integration (coverage
gates)`, `Docker image builds and serves (docker compose)`, `Browser persona tests (desktop + mobile)`, `Browser
persona tests (firefox desktop)`, `Backup round trip (mongodump, age, mongorestore)`, `Workflow files
(actionlint)`, `Changelog fragments`, `render.yaml matches Render's schema`, `Visual baselines (advisory)`, and
   CodeQL's `Analyze (actions)` and `Analyze (javascript-typescript)`.
2. **How GitHub's merge queue works** (read 2026-10-20):
   - "Managing a merge queue", docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue:
     workflows **must** use the `merge_group` event or the required checks never report; the queue builds on
     temporary `gh-readonly-queue/{base}` branches; settings are merge method, build concurrency (1 to 100), only
     merge non-failing PRs, status check timeout, minimum and maximum group size (1 to 100) and the wait time for
     the minimum. A failing PR leaves the queue and the groups behind it are rebuilt.
   - "Events that trigger workflows", docs.github.com/en/actions/writing-workflows/choosing-when-your-workflow-runs/events-that-trigger-workflows:
     `merge_group` has one activity type, `checks_requested`. `GITHUB_SHA` and `GITHUB_REF` are the merge group's.
   - "Using conditions to control job execution", docs.github.com/en/actions/using-jobs/using-conditions-to-control-job-execution:
     "A job that is skipped will report its status as Success. It will not prevent a pull request from merging,
     even if it is a required check." So a pull-request-only job is safe in the queue.
   - "Customizing your advanced setup for code scanning", docs.github.com/en/code-security/code-scanning/creating-an-advanced-setup-for-code-scanning/customizing-your-advanced-setup-for-code-scanning:
     with a merge queue, code scanning needs `merge_group` as a trigger. That is about workflow files. The default
     setup pages say nothing about merge queues, so we cannot add the trigger and do not rely on it.
   - `gh pr merge` manual, cli.github.com/manual/gh_pr_merge: on a branch with a merge queue, no strategy is
     needed; if checks have not passed, auto-merge is turned on, and if they have, the PR is added to the queue.
     `--admin` bypasses the queue.
   - Other products: GitLab merge trains (docs.gitlab.com/ci/pipelines/merge_trains) and Bors (the Rust project's
     merge bot, after Graydon Hoare's "not rocket science rule", 2014) do the
     same thing: test the exact commit that will land, then land it.
3. **Best for ClassiCade.** One owner, up to five builders, free runners (20 jobs at once, one CI run takes about
   15). Merge commits, so the collector keeps working. Build concurrency 2 and groups of up to 5. A 30 minute
   timeout, three times a normal run. The seven ci.yml checks required, CodeQL by the code scanning rule.

## Why

Green PRs that break `main` together, without making every PR rebase after every merge.

## Scope

- In: `merge_group` on ci.yml with the per-job behaviour written down and pinned, owner steps in DEPLOYMENT.md
  (UI and `gh api`), the coordinator's merge command in CLAUDE.md, ADR-074.
- Out: turning the queue on (the owner's step), a CodeQL advanced setup workflow, requiring WebKit.

## Plan / notes

The event table is in ci.yml's header. `changes` in the queue compares with `HEAD^1`, which on a queue commit is
the queue's base (main, or the PR ahead), so it checks exactly this PR's change, as on a PR's merge commit.
