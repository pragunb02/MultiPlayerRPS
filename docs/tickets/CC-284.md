## Research (written before any code)

1. **Our code today.** Feedback is visual and sound only. Sounds come from pure functions over two room views
   (ADR-018 point 3), play only after a user gesture, and follow `cc.sound` (mute, volume, six categories, CC-208).
   Nothing vibrates.
2. **Others.** MDN Vibration API (read 2026-10-19): `navigator.vibrate(pattern)`, "limited availability", feature
   detect, works without haptics, stop with `vibrate(0)` when the page is hidden. It works in Chrome on Android and
   not in Safari on iOS, and Chrome ignores it before the person has interacted with the page (general knowledge,
   high confidence). StatCounter (September 2026): Android is 93.9 % of mobile use in India. Game feel literature
   (Swink 2008; "Juice it or lose it", GDC Europe 2012) counts touch feedback with sound and motion as the response
   to the player's own action.
3. **Best for ClassiCade.** Three short patterns (at most 30 ms for your turn and a placed move, a 2 by 40 ms pulse
   for a win), worked out by the same pure functions that pick sounds, played through an injected `haptics` service
   with a fake for tests, only after a gesture, never when the tab is hidden, and with a switch next to sound
   (stored inside `cc.sound`, so no new storage key). Never for losses, never repeated, never as the only signal.

## Why

Most of our players hold an Android phone; a tiny touch response makes a move feel placed, at no download cost.

## Scope

- In: the service, the three patterns, the switch, tests.
- Out: iOS (no API), patterns for notifications outside a match.

## Acceptance criteria

- [ ] Nothing vibrates before a tap, with the switch off, or in a hidden tab (unit tests with a fake).
- [ ] `cc.sound` keeps one key; the storage allowlist checker follows the new field.
- [ ] Tests cover the change; `npm run lint`, `npm run format:check`, `npm test` pass.
- [ ] Docs updated (BACKLOG, PROGRESS, ADR-018 amendment).
