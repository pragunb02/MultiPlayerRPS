## Research (written before any code)

### 1. How our code does it today

1. A game ends inside `roomComponent.change`: the room is saved as finished (one atomic MongoDB write, ADR-017),
   then `room.gameFinished` is emitted on an in-process `EventEmitter`.
2. `connectMatchPipeline` (`apps/server/src/server.js`) reacts with background tasks nested four deep: record the
   match, then (follow a guest who signed in, judge fair play, apply progression), then gamification, then
   leaderboards in a `finally`. `utils/backgroundTasks.js` runs each once and, on failure, logs
   "background task failed" at error level. Nothing retries.
3. So a database blip while recording loses the match for good (BUG-16): no history entry, no XP, no quests, no
   board. A crash or a deploy that kills the process between "match recorded" and "progression applied" loses the
   XP the same way. Shutdown drains running tasks (SIGTERM), but a crash or a forced exit does not.
4. Every step can already run twice safely, which is the hard half of the job:
   1. `matchAccessor.record` is keyed by `matchId` (unique index) and returns the stored match when it exists.
   2. `playerTransferComponent.follow` rewrites a match only while the guest is still in it.
   3. `matchComponent.judge` keeps the first verdict (`judgeOnce`).
   4. `progressionComponent.applyMatch` uses `applyMatchOnce` per player and match (CC-017, exactly once, tested
      under concurrency), and only announces an award it applied.
   5. Gamification applies a match once per player (`applyToStatsOnce`, `applyToQuestDayOnce`, quest bonuses
      keyed `quest:<day>:<id>`).
   6. Leaderboard writes only raise totals or add once per key.
5. One gap: the leaderboard step is fed the `updates` progression returned. Run again after progression already
   applied, progression returns no updates, so a retried leaderboard step would silently do nothing. It must read
   what it needs from the stored match and progress instead.
6. The finished room itself stays in MongoDB as `finished` until its rematch window ends, so after a crash the
   finished game is still on disk for a while.

### 2. How others do it

1. **Transactional outbox** (Chris Richardson, microservices.io, "Pattern: Transactional outbox", read
   2026-10-18): write the message to an outbox in the same database, in the same local transaction as the business
   change, and let a relay deliver it later. "Messages are guaranteed to be sent if and only if the database
   transaction commits." For a document database the outbox may be a field on the record that changed. The relay
   (a polling publisher, or log tailing) may deliver a message twice, for example after crashing before it marked
   it sent, so consumers must be idempotent.
2. **Idempotent consumer** (microservices.io, "Pattern: Idempotent Consumer", read 2026-10-18): "Make a consumer
   idempotent by having it record the IDs of processed messages in the database", in a separate table or inside the
   entities it changes. Our steps already do the second: progression stores the match ids it applied.
3. **Retries with backoff** (Marc Brooker, Amazon Builders' Library, "Timeouts, retries and backoff with jitter",
   now at builder.aws.com, read 2026-10-18): retry transient failures with exponentially growing waits, cap them,
   limit the number of attempts and hand persistent failures to a higher level, retry in one place only, add jitter
   so clients that failed together do not retry together, and "APIs with side effects aren't safe to retry unless
   they provide idempotency".
4. **MongoDB TTL indexes** (MongoDB manual, "TTL Indexes", read 2026-10-18): a single field date index with
   `expireAfterSeconds` deletes old documents in the background, about once a minute, not at the exact moment.
5. **Atlas M0 limits** (MongoDB Atlas, "Atlas M0 (Free Cluster) Limits", read 2026-10-18): 100 operations a
   second, 500 connections, 0.5 GB of data, a three node replica set, and maintenance that Atlas schedules by
   itself. A short primary change during maintenance is exactly the blip BUG-16 describes.

### 3. What is best for ClassiCade

1. **The outbox is a collection, `pending_matches`, one document per finished game**, keyed by `matchId`
   (unique). It holds the match to record and the names of the steps already done, the attempts, the time of the
   next attempt, the last error and a status (`pending`, `done`, `failed`).
2. **How a finished game gets into it.** A real transactional outbox writes the entry in the same transaction as
   the room. Our room DAO deliberately uses single document writes (the in-memory test database is a standalone
   server, and `roomDao.close` already documents the "two collections cannot change at once here" choice), and a
   transaction on every finished game is more than one instance needs. Instead the finished room is the outbox
   until its entry exists, which is the "outbox as a field on the record" variant:
   1. Right after the room is saved as finished, the pipeline adds the entry (insert if absent). A failure there is
      retried in this process like any step.
   2. At startup, before anything can close or change a room, every stored finished room adds its game's entry
      (insert if absent, so games already handled change nothing). That covers a crash between saving the room and
      adding the entry. A finished room lives for its rematch window, and the process restarts within seconds on
      Render, so the room is still there to read.
3. **Flat named steps, in one list:** record match, judge (follow a guest who signed in, then fair play),
   apply progression, apply gamification, apply leaderboards. Each step reads what it needs from storage, so an
   entry can resume at any step. Each declares the steps it needs: gamification and leaderboards both need
   progression, but not each other, so a failing gamification step does not hold back the boards (as today).
4. **Exactly once comes from the steps, not the delivery.** The outbox delivers at least once (a step may run again
   after a crash or a retry). Every step already changes nothing the second time, so XP and the rest arrive once.
   The leaderboard step is changed to read the stored match and progress, so it is safe to repeat too.
5. **Retry with backoff:** an attempt that fails waits `2 s × 2^(attempt − 1)`, capped at 5 minutes, up to 10
   attempts (about 13 minutes in all, longer than an Atlas primary change). No jitter: there is one instance and a
   handful of entries, so there is no crowd to spread out, and fixed delays are easier to read in the logs. After
   the last attempt the entry is marked `failed` and kept, and the server logs "match pipeline failed" at error
   level with the match id, the step and the error. That is the alert line for CC-049. Each failed attempt before
   that logs "match pipeline step failed" at warn level with the next attempt time.
6. **Who runs it:** the pipeline runs a new entry at once, housekeeping looks for due entries every 5 seconds, and
   startup runs whatever is due. One instance runs it, so a set in memory stops the same entry from running twice
   at once in this process. A second instance (CC-061) would need a lease in the entry.
7. **Retention:** a done entry stays two days (a TTL index on `expiresAt`), longer than any room lives, so the
   startup check never runs a finished game twice. A failed entry has no `expiresAt` and stays until someone looks
   at it.
8. **Cost on M0:** about five extra small writes per finished game, and one indexed query every 5 seconds. Both are
   far below 100 operations a second.

## Why

A finished game is the only thing that earns a player anything. A database blip or a crash must never lose it.

## Scope

- In: `pending_matches` (DAO, accessor), a match outbox component in the domain with the retry policy, the steps
  wired in `server.js`, housekeeping and startup runs, the leaderboard step reading stored data, logs for the
  alert, ADR-033, DEPLOYMENT.md notes.
- Out: the alert itself in a monitoring tool (CC-049), an owner screen to retry failed entries, horizontal scaling
  (CC-061), the quest bonus path (`connectLeaderboardBonuses`), which stays a background task.

## Acceptance criteria

- [ ] A crash between recording a match and awarding XP: after a restart the XP arrives, exactly once
- [ ] A step that keeps failing is retried with growing waits, then marked failed and logged at error level
- [ ] A step that failed does not block steps that do not need it
- [ ] Tests cover the change, each fix with a test that failed first
- [ ] `npm run lint`, `npm run format:check`, `npm test` and `npm run test:coverage` pass
