## Research (written before any code)

### 1. How our code does it today

1. **No way to hear from players.** The only contact is the privacy contact on the privacy page (ADR-023). There is
   no form, no inbox and no free text from players anywhere: DATA.md "Not stored anywhere" item 5 says display names
   are the only text a player chooses.
2. **Patterns to reuse.**
   1. Layers and a new store: CC-044 blocks (`persistence/blockDao.js`, `data/blockAccessor.js`,
      `domain/blocks/blockComponent.js`, `service/http/blockRoutes.js`), with a DAO contract run against MongoDB and
      an in-memory double (`testing/blockDaoContract.js`).
   2. Abuse limits: `service/http/rateLimits.js` `createRateLimit`, one limit per player and one per address, the
      player's own limit first (ADR-035, ADR-053).
   3. CSRF: every non-GET `/api` request passes `createCsrfGuard` (ADR-010): a foreign `Origin` gets 403 and a body
      that is not JSON gets 415. A new route inherits it by being under `/api`.
   4. Owner console: `createAdminAccess` (ADR-036). `requireAdmin` answers the same 404 as any unknown address,
      `Cache-Control: no-store` and `X-Robots-Tag: noindex, nofollow`. The web console lives at `/admin` and its code
      loads only for an admin (`pages/AdminPage/AdminRoute.jsx`).
   5. Expiry: `account_deletions` uses a TTL index (`persistence/accountDeletionDao.js`).
   6. Copy: CC-217 writes every shared text as a Hinglish line first and a short English line under it, all in one
      file (`lib/shareText.js`) so the string catalogue (CC-218) can take them over (ADR-051).
   7. Age: `packages/shared/src/ages.js`. Unknown age is a minor (ADR-028.1). Guests have no age. Only an account
      whose birth year makes it surely 18 is an adult (ADR-048.8). `accountComponent.adultsAmong` answers it.
3. **Gaps.** There is no app build or version the page knows (nothing in `vite.config.js`), and the session does not
   carry the age group (the page reads it from `GET /api/account`).

### 2. How others do it (read 2026-10-20)

1. **Sentry User Feedback widget** (https://docs.sentry.io/platforms/javascript/user-feedback/configuration/): a
   button that opens a small form with a required description and optional name and email (`isEmailRequired`
   defaults to false), and an optional screenshot. When the app has already told Sentry who the user is, their name
   and email are sent even when the fields are hidden. That last point is what we must not copy: nothing the player
   did not type should leave with the message.
2. **Small web games.** Lichess has no form at all: feedback goes to a public forum
   (https://lichess.org/forum/lichess-feedback), which would need moderation we do not have and would publish
   minors' words. Sentry's widget (above) is the common shape for small apps: one menu entry, a short form, and context
   the player does not have to type.
3. **What to attach.** Bug trackers ask for the page, the version and the device first (Mozilla's bug writing
   guidelines, https://bugzilla.mozilla.org/page.cgi?id=bug-writing.html: "the build", "the platform"). A coarse
   class (phone, tablet, desktop) answers "is it a phone layout bug" without a user agent string, which is a
   fingerprinting surface (https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/User-Agent).
4. **Privacy.** GDPR Article 5(1)(c) data minimisation and 5(1)(e) storage limitation
   (https://gdpr-info.eu/art-5-gdpr/). India's DPDP Act 2023 section 9 needs verifiable parental consent before
   processing a child's personal data and bars tracking and behavioural monitoring of children
   (https://www.meity.gov.in/data-protection-framework). Our ADR-028.1 counts
   unknown age as a child.
5. **Abuse.** OWASP API4:2023 Unrestricted Resource Consumption
   (https://owasp.org/API-Security/editions/2023/en/0xa4-unrestricted-resource-consumption/): limit requests per
   client and the size of each, and cap what one client can make the server store. An open text form on a free
   database tier (Atlas M0, 512 MB) also needs a cap for the whole site, so many addresses together cannot fill it.
6. **Expiry.** MongoDB TTL indexes (https://www.mongodb.com/docs/manual/core/index-ttl/): a monitor deletes expired
   documents every 60 seconds, not to the second, on a single date field. A changed period is applied with `collMod`
   (Mongoose `syncIndexes` drops and rebuilds the index), and documents without the date never expire.

### 3. What is best for ClassiCade

1. **One entry, two places.** "Feedback" in the footer of every page, and in the header menu, which is one tap from
   the top of every page on a phone (CC-259). The footer alone is below the fold on a phone during a game.
2. **A short dialog.** Type (Bug, Idea, Other), a message of 1 to 1000 characters with a live count, Send, then a
   thank-you. Hinglish line first and English under it, as CC-217 does, all copy in one file.
3. **"Email me back" only for adults.** A reply email is a child's contact detail when the age is unknown, and
   ADR-028.1 says unknown is a minor. So the field shows only to an account whose birth year makes it an adult, and the
   server refuses a reply email from anyone else. Everyone else still sends feedback, just without a reply address.
   **Owner decision:** keep this, or show the field to everyone (one line, `REPLY_EMAIL_FOR` in
   `feedbackComponent.js`) after the lawyer's review of DPDP consent.
4. **Context the page attaches, and why each field is kept** (data minimisation):

   | Field    | Value                                                         | Why we need it                                                    | Why it is safe                                                                                      |
   | -------- | ------------------------------------------------------------- | ----------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
   | `page`   | the route pattern, e.g. `/games/chess/rooms/:code`            | which screen the bug is on                                        | no query, no hash, every room code, name or id replaced by its placeholder, checked again on server |
   | `build`  | the web build, e.g. `0.1.0+3f9c2ab`                           | whether a bug is already fixed in a newer deploy (stale tabs)     | the same for every player of that deploy                                                            |
   | `device` | `phone`, `tablet` or `desktop`                                | layout bugs are mostly phone bugs                                 | three values, no user agent, no screen size                                                         |
   | `kind`   | `visitor`, `guest` or `account`, from the session, not client | guest only flows (save progress) differ from account ones         | three values, no player id                                                                          |

   **Not stored:** player id, session id, IP address or its hash, user agent, screen size, language, time zone,
   referrer. The feedback cannot be joined back to a player by us. The only personal data is what the player types,
   and the reply email if an adult gives one.

5. **Data rules (ADR-059).** A new collection `feedback`, kept 180 days from `createdAt` by a TTL index: long enough to
   see a theme across two release cycles and to reply, short enough that nobody's words sit for ever. Statuses
   `new`, `read`, `done`, set by the owner. Because no player id is stored, deletion and export by player id
   (ADR-048.2) cannot find a player's feedback and do not take part. The only identifying field is the reply email,
   so account deletion also deletes feedback whose reply email is the account's own email, and the data export lists
   them. Anything else (a request from someone who wrote their name in the message) goes through the privacy
   contact, and the owner can find it in the inbox.
6. **Abuse limits (ADR-035 style), checked in this order:**
   1. per session: 5 feedback items an hour (a session means a guest or an account),
   2. per address: 20 an hour (a school or carrier address, and visitors without a session),
   3. the whole site: 300 a day, so 180 days hold at most 54,000 items of at most about 2 KB (about 110 MB, well
      inside a free 512 MB tier, and never close to it in practice).
      The body is at most 2 KB of JSON (`express.json` already caps 100 KB for the whole API). Counts live in memory,
      like every other limit (a restart forgets them).
7. **Plain text only.** The message is stored as typed, after removing control characters other than new lines and
   tabs and turning `\r\n` into `\n`. The console shows it as React text in a `pre-wrap` paragraph, never as HTML,
   and a test sends `<img src=x onerror=alert(1)>` and checks the page shows the characters and makes no element.
8. **The owner's inbox.** A Feedback tab in the console at `/admin/feedback`: newest first, filters for type and
   status in the address, 50 at a time with "Older", and Mark new, read and done on each item. Non-admins get the
   console's 404 for the page and the API.

## Why

The owner is sharing ClassiCade with friends and needs to hear what breaks and what they want, from inside the
app, without them writing to the owner privately and without anything that tracks them.

## Scope

- In: the dialog on every page, `POST /api/feedback`, the `feedback` collection with TTL, the console inbox with
  `GET /api/admin/feedback` and `PATCH /api/admin/feedback/:feedbackId`, the limits, the build stamp, DATA.md, the
  privacy page, deletion and export of feedback with the account's own reply email, ADR-059.
- Out: screenshots, attachments, replying from the console (the owner uses their own email), notifications to the
  owner, feedback analytics.

## Acceptance criteria

- [x] A "Feedback" entry in the footer of every page and in the header menu, reachable on a 390×844 phone.
- [x] Dialog: type, message (required, at most 1000, live count), "Email me back" for adults only, Send,
      thank-you. Hinglish and English.
- [x] Context: route pattern without query or ids, build, device class, player kind from the session. No player id,
      IP or user agent stored.
- [x] Server: route, component, accessor, DAO, `feedback` with `createdAt`, `status`, a 180 day TTL index. Strict
      validation, unknown fields refused, CSRF policy, limits per session, per address and for the site, each tested.
- [x] Console: list newest first, type and status filters, mark new, read or done, everything shown as text,
      non-admins get the same 404.
- [x] DATA.md, the privacy page, deletion and export.
- [x] Tests cover the change, and failed first.
- [x] `npm run lint`, `npm run format:check`, `npm test`, coverage, the new browser spec.

## Plan / notes

### Data

`feedback` (new, `persistence/feedbackDao.js`): `feedbackId` (random UUID, unique, the only id any client sees),
`type`, `message`, `replyEmail` (only when given), `page`, `build`, `device`, `kind`, `status`, `createdAt`,
`updatedAt`. Indexes: unique `feedbackId`, TTL on `createdAt` (180 days), `{ createdAt: -1, feedbackId: -1 }` for the
newest first list. Legacy collections are not touched.

### Extending

Types, statuses, device classes and limits are lists in `packages/shared/src/feedback.js`, read by the server's
validation, the dialog and the console. A new type is one line there and one line of copy. A new context field is a
line in the server's `CONTEXT_FIELDS` validator table, the DAO schema and the page's context builder.

### Open questions for the owner

1. The reply email for adults only (Research 3.3).
2. 180 days, or another period (one constant, `FEEDBACK_KEEP_DAYS`).
3. The limits (5 an hour per session, 20 per address, 300 a day for the site).
