## Problem

Main's CI run on df8710f (#175 merged) failed once: `scripts/load/swarm.test.mjs` › "createSwarm against the real
server" › "records each kind of call by name" hit "Test timed out in 5000ms". The next runs on main passed.

**Root cause.** The test was not waiting for a name. Every expected name had come, and the test hung in
`swarm.stop()`. `stop` sets `stopping`, closes every socket and waits for every player's loop. A loop that had just
had an answer went straight on to its next call without looking at `stopping`: the friend's `room:join` after
`room:create`, the host's `room:leave` after the friend's, a computer player's next `room:play-computer` after its
`room:leave`. Socket.IO's client keeps an emit on a closed socket in its send buffer, and an ack still in the buffer
is not cleared on disconnect (`_clearAcks` in `socket.io-client` 4.8.4 skips buffered packets), so that call waited
the whole `waitMs`, 30 s in these tests. The test stops as soon as the last name comes, so it hung whenever that last
name was one followed at once by another call, here `room:leave`, which usually came just before `room:answer` and
sometimes just after. CC-309 had fixed the same hang for a player still arriving, not for one between two calls.

Two more things made the run slower and less certain, without being the hang:

- **A computer reply could go untimed.** The test server's computers act at once (`delayMs: () => 0`, in-memory
  storage), so the computer's `room:updated` often came in the same read as the answer to the player's move, and
  the client handled it first. The swarm then looked at the newest view, saw its own turn again, and did not time
  the reply. Counted with a temporary log line on 10 loaded runs: chess replies were missed in 25 of 41 chances, tic-tac-toe in 9 of 33. Each missed reply put its name off to a later move, with no bound on how many.
- **The friends who rematched played Rock Paper Scissors**, where drawn rounds are replayed, so the match before
  `room:request` and `room:answer` had no bound: after n rounds it is still going with probability
  (n² + n + 1) / 3ⁿ, about 1 % at 8 rounds.

Not the cause: the CC-322 and CC-333 changes are in the web app only, CC-260's scrypt cost does not reach this test
(guests do not hash, and testApp's hasher is fast), and CC-318's one action per room changes no timing here. No
server code waits on a real clock in this path (testApp's computers pause 0 ms).

## Research

- **How our code does it now.** `scripts/load/swarm.mjs` `call()` emits with `socket.timeout(waitMs).emitWithAck`.
  `stop()` closes the sockets, which rejects acks already sent, but a call made after the close is buffered and only
  its timeout ends it. `playGame` decided whether to time a computer reply from `player.view`, the newest view, which
  may already hold the reply.
- **Socket.IO.** `socket.io-client` 4.8.4 `build/esm-debug/socket.js`: `emit` pushes to `sendBuffer` when not
  connected, and `_clearAcks` (called on close) skips acks whose packet is still buffered; the client docs describe
  the send buffer ("the events are buffered until reconnection",
  <https://socket.io/docs/v4/client-offline-behavior/>). With `reconnection: false` the buffer is never flushed.
- **Vitest.** The test context's `signal` is aborted when the test times out
  (<https://vitest.dev/guide/test-context#signal>), so the test can say what it was waiting for.
- **What is best for ClassiCade.** Fix the harness, not the test's limits: a stopping swarm makes no new call, the
  reply is decided from the answer to the move (the game just after it), and the test's plans each reach their names
  in a bounded number of moves. No retry and no longer timeout.

## Fix

- `call()` returns at once once the swarm is stopping, so `stop` never waits on a closed socket.
- A computer reply is timed when the answer to the move shows the computer to move, whether or not the reply has
  already arrived.
- The test's rematching friends play chess and resign at their first move (`chessOwnMoves: 0`), the Rock Paper
  Scissors friends leave after one game (their names all come in the first round), and a time-out prints what the
  test was doing, the missing names and the failures.

## Reproduction

The swarm file plus `apps/server/src/service/realtime`, with coverage, `--maxWorkers=2`, under 56 `node -e
'for(;;){}'` burners on a 14-core Mac (four burners per core, killed after each batch), 20 runs each:

| Code            | "records each kind of call by name" failed                                          |
| --------------- | ----------------------------------------------------------------------------------- |
| main (c6383bcd) | 4 of 20 (20 %), each "timed out" with no name missing and no failure, then the hook |
| this branch     | 0 of 20, in 0.73 to 1.05 s                                                          |

The test alone under 16 burners passed 20 of 20 on main, in 0.8 to 1.9 s, so it takes coverage and a busy machine.
With main's `swarm.mjs` and this branch's test, the test failed on the first of six runs with
`timed out stopping the swarms: missing [], failures []`.

Under the same load, other tests in `apps/server/src/service/realtime` failed now and then on both main and this
branch, untouched here: `ratings.test.js` "leaves the computer player out of a game against Queen Vee" (4 of 20
before, 3 of 20 after, "operation has timed out" from a Socket.IO ack), and once each `chess.test.js` "tells the
opponent when the offerer withdraws" and `connections.test.js` "lets a request in flight finish". They are left
to the coordinator for their own tickets.

## Acceptance criteria

- **AC-1** Given a swarm that stops between two calls, when `stop` is called, then it resolves at once and the next
  call is never sent.
- **AC-2** Given a computer reply that reaches the player before the answer to their move, then the reply is timed.
- **AC-3** Given CPU load as above, "records each kind of call by name" passes 20 of 20 runs, with no retry and no
  longer timeout.

## Test

`scripts/load/swarm.test.mjs`: "resolves at once when it stops between two calls, and sends nothing after" (AC-1)
and "times the reply when it overtakes the answer to the move" (AC-2). Both failed on main's `swarm.mjs` (the first
timed out after 5 s, the second recorded no reply) and pass with the fix. AC-3 is the reproduction above.
