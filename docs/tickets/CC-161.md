## Research (written before any code)

### 1. How our code does it today

Server:

- `apps/server/src/domain/rooms/roomComponent.js` `nextSeries(series, outcome)` runs in `finish`: `games + 1`, and
  `wins[id] + 1` for each winner. The room stores `series: { games, wins }` (`data/roomAccessor.js`), the view copies
  it (`viewFor`), and `@classicade/shared` `events.js` documents it on the RoomView.
- What is **not** stored: the order of results, draws (only implied by `games − sum(wins)`), how each game ended
  (checkmate, forfeit, timeout), and which match each game was. So "one dot per game, with the reason on hover"
  (MATCH_EXPERIENCE.md §2 item 2) cannot be drawn from today's data.
- A forfeit (a player left during play) counts as a game won by the other player, and ends the rematch
  (`rematch.available = false`).
- A rematch reverses the seats (`[...room.seats].reverse()`), so seat order cannot be used to say who is "left" in a
  score. The score must be keyed by player id from the viewer's side.
- `transferPlayer` renames the player inside `series` with `renamePlayer` (`packages/games`), so a guest who signs
  in during the rematch window keeps their wins (ADR-014, test "keeps a guest's series wins").
- Rooms live for the rematch window (30 minutes after a game, `roomLifetimes.js`), so a series is short and lives
  only in its room. Matches are recorded separately, through the outbox (ADR-047), with `roomCode`.

Open PR #67 (read 2026-10-18) changes three things that touch the series:

- Games are numbered on the server (`game.number`, from 1); `gameNumber(room)` on the web reads it.
- A game with no first move in 60 s is **aborted**: it finishes with `result: ABORTED`, records nothing, and does
  not call `nextSeries`, so it never counts in the series. The next game still gets the next number, so game
  numbers and series entries can differ by the aborted games.
- Rematch is a room request (`room.requests`), and the RematchPanel reads the last rematch request.

Web:

- `SeriesScore` in `components/Rematch/RematchPanel.jsx` prints "Series after N games: You 2 – 1 Bob", only when
  the room is finished **and** `series.games >= 2`. It is inside the result, under the rematch button, below the
  fold on a phone. Never while playing. This is finding **A4 (P0)**: "Hidden until two games are done, shown only
  after a game, below the fold. Never visible while playing."
- RPS has its own in-game score line in `RpsBoard.jsx` ("Best of 3 · You 0 – Rocky 0 · first to 2 wins", CC-254).
  That is rounds inside one game, a different thing from the series of games in the room. Both will sit in the
  match bar.
- The board is keyed by `gameNumber(view)`, so a rematch mounts a fresh board.

### 2. How others do it (read 2026-10-18)

- **lichess crosstable** (`modules/game/src/main/Crosstable.scala`, commit `cd2656d`): the history is a list of
  `Result(gameId, winnerId: Option[UserId])` in order, oldest first, capped at `maxGames = 20`; a draw is a result
  with no winner. Scores are kept times ten so a draw adds a half (`showScore` prints "2½"). Besides the all-time
  crosstable there is a `Matchup`: the score of the current run of games between the two players. The web shows
  the results as a strip of boxes, each linking to its game, the current game highlighted
  (`ui/lib/css/component/_crosstable.scss`: `povs`, `.current`, `.loss` dimmed). It is hidden on narrow
  layouts (`_layout.scss`: `.crosstable { display: none }` in the squeezed two column layout).
- **lichess mobile** shows no series in the game screen; the result dialog carries Rematch and New opponent.
- **Board Game Arena** guidelines: essential information such as the score must not live only on the player
  panels, and panels stay small on a phone (at most a quarter of the screen for four players).
- **chess.com, papergames.io, casual mobile games**: no primary source on a series display was reachable today.
  We claim nothing about them.

What to take: an ordered, capped list of per-game results with the winner (or none for a draw) and the reason; the
score computed from it; the current game marked; a compact strip that can hide its detail when space is short.

### 3. What is best for ClassiCade, and why

1. **Store the history in the room, on the server.** The room is the authority for the live series (ADR-000), it
   already holds `series`, and it is written with optimistic versioning on every finish. Deriving the strip from
   `matches` would lag behind the outbox (ADR-047) and mix rooms that reuse a code. Proposed shape, an addition to
   ADR-015 point 7:

   ```js
   series: {
     games: 3,                                  // kept, as today
     wins: { user_a: 2, guest_b: 0 },           // kept, as today
     history: [                                 // new, oldest first, at most 20 entries
       { number: 1, winners: ["user_a"], reason: "checkmate", endedAt: 1760000000000 },
       { number: 2, winners: [], reason: "stalemate", endedAt: 1760000300000 },   // a draw
       { number: 3, winners: ["user_a"], reason: "forfeit", endedAt: 1760000600000 },
     ],
   }
   ```

   `games` and `wins` stay, so old clients, `gameNumber` before #67 and the transfer keep working. `history` is
   appended in `finish` beside `nextSeries`; aborted games (from #67) add nothing; `renamePlayer` already renames
   ids in nested arrays, values and keys, so the transfer needs no new code. `number` is the game's own number, so
   it can skip one after an aborted game; the strip shows "Game 3" as the server numbers it. No match id in the view: the view must not hand out ids the player cannot use.

2. **Old rooms**: a room stored before this has `games` and `wins` but no `history`. The view sends
   `history: []` and the strip shows the score without dots until the next game (no made-up order). Rooms live at
   most 30 minutes after a game, so this lasts one deploy.
3. **The scoreboard is a pure function on the web** (`seriesBoard(room)`): from the viewer's side (you first when
   seated; for a spectator, the seat order of the first game), the two scores, the dots (win, loss, draw, from the
   viewer's side, each with a text label such as "Game 2: draw by stalemate"), the current game number, and what
   changed since the previous view (for the bump). It reuses each game's `reasonPhrase` (CC-162), so the words match
   the result headline.
4. **Always visible** in the shell's match bar (CC-157): from the first game, not from the second: "You 0 – 0 Bob ·
   Game 1". When there is no space (CC-172, a short phone), the dots collapse to the last five and "+N", but the
   numbers stay. Draws show as half dots; the score counts wins only, as today (no "½" for casual players), so
   "You 2 – 1 Bob" means wins.
5. **Meaning never only in colour or shape** (ADR-012 point 3, Discord and BGA guidance): each dot has a text
   label, the strip is a list (`<ol aria-label="Games in this series">`), the score is text. The bump on a change is a
   CSS `transform` keyframe of about 300 ms, off with reduced motion, and the change is announced politely once
   ("Series: You 2, Bob 1"), never on every render.
6. **Scope stays the room.** A head-to-head across rooms and days (lichess's all-time crosstable) needs accounts and
   a query over `matches`. It is a separate idea for phase 2 (friends, ADR-028), not part of this ticket.

## Why

Players in a WhatsApp group play "best of" runs against each other. The series is the reason to press Rematch, and
today it is invisible until the second game is over and then below the fold (A4, P0).

## Scope

- In: `series.history` on the server (append on finish, cap 20, aborted games skipped, transfer, old rooms); the
  RoomView and its JSDoc in `@classicade/shared`; `seriesBoard` on the web; the scoreboard in the match bar slot;
  the series change in the result card; `SeriesScore` removed from `RematchPanel`.
- Out: head-to-head across rooms; ratings (CC-042); turn timers in the match bar (CC-165); the RPS in-game score line
  moving into the match bar (CC-166).

## Acceptance criteria

- [ ] The score shows from the first game, while playing and after it, at 1280×720 and 390×844 without scrolling.
- [ ] One dot per finished game, in order, from the viewer's side, with a text label for each.
- [ ] Aborted games add no dot; forfeits do, with the reason.
- [ ] A guest who signs in during the rematch window keeps their dots.
- [ ] Rooms stored without `history` load and show the score.
- [ ] Reduced motion: no bump, same text; the change is announced once.
- [ ] Tests cover the change
- [ ] `npm run lint`, `npm run format:check`, `npm test` pass
- [ ] Docs updated (BACKLOG status, ADR-015 amendment, DATA.md room fields, PROGRESS)

  semantics, announcement once, reduced motion).
- Browser: extend `e2e/rematch.spec.js` (it already plays a rematch): both players see "Game 2" and the first dot in
  the match bar while the second game is on. The fold check in `match-shell.spec.js` adds the match bar's score to
  every playing and finished state.
- Order: after #67 and CC-157, before CC-172 (see CC-157 "Order of PRs").
- Risks: a second write path into `series` (keep it in `finish` only); seat reversal bugs in the viewer side (test
  it); the match bar is crowded on a 360 px phone (CC-172 decides what collapses).

### Owner decisions

1. Store the series history in the room document, capped at the last 20 games (recommended), rather than deriving it
   from recorded matches. This amends ADR-015 point 7 and adds a field to DATA.md.
2. The score counts wins only, draws are half dots without a "½" in the numbers (recommended for casual players), or
   lichess style scores with halves.
3. Show the score from game 1 ("You 0 – 0 Bob"), not from game 2 as today (recommended: the empty score is the
   invitation to a best of three).
4. For Rock Paper Scissors the series counts matches (each a best of 3 rounds), and the round score stays a second,
   smaller line in the match bar (recommended), or the series counts rounds.
5. A head-to-head across rooms is out of scope here; open it as a new ticket for phase 2 if wanted.
