## Owner's rule (2026-10-18, binding)

Faster only by running in parallel. Nothing checks less and no code is loosened: no fewer or weaker assertions, no
skipped flows, games, devices or browsers, no test-only switches in production code, no jumping a game into a
state instead of playing to it, no loosened timeouts, retries, leak, console or CSP checks, and no fake clocks or
shorter game timings unless the owner approves first. The first plan in this ticket (short timers for the browser
tests, or Playwright's clock) is dropped.

## Research (written before any code)

### How our code does it today

- `ci.yml` job `e2e`, "Browser persona tests (desktop + mobile)", runs `npm run test:e2e` on one `ubuntu-latest`
  machine (4 CPUs, 16 GB for public repositories, docs.github.com "GitHub-hosted runners", read 2026-10-18).
  Playwright starts its default 50 % of the CPUs, 2 workers. `e2e/playwright.config.js` has `fullyParallel: true`
  and four projects: `desktop`, `mobile` (Pixel 7) and the two restart projects, which depend on the others and
  run last, one at a time, because they stop the server.
- `e2e-firefox`, "Browser persona tests (firefox desktop)", does the same with `E2E_BROWSER=firefox`, 2 workers.
  WebKit has its own workflow, `webkit.yml`, already split into 3 parts with `--shard` on macOS (CC-184).
- Setup is short. In CI run 39085728868 (the #65 merge on `main`, 2026-10-18) the Chromium job spent 2 s on
  checkout, 6 s on `npm ci` (setup-node already caches `~/.npm`), 19 s installing Chromium with its system
  packages, then about 4 s building the web app and starting the server (the build takes 0.6 s with Vite), and
  21.4 minutes on the tests. So almost all of the time is tests.

The longest single tests are the chess clock (60 s) and the match-shell press states (23 to 41 s each). Every one
of them is already its own `test()`, so `fullyParallel` can spread them; none of them is a long chain that could
be cut into cases without either repeating its flow or sharing state. So the floor for any one machine is about
60 s of tests, and the rest is a question of how many machines and workers share the 2400 s.

The queue matters too: in run 39088342536 (`main`, 2026-10-18) the Chromium job started 9 minutes after the
Firefox job, waiting for a free runner, because several builders' pull requests were running at once.

### How Playwright shards

- `--shard=x/y` runs part x of y. With `fullyParallel: true` it splits by test, otherwise by file. It balances by
  **number of tests**, not by time: in the code (`filterForShard`, Playwright 1.64.1) the tests, in project and
  file order, are cut into y contiguous runs of equal count. Statically skipped tests are not counted
  (playwright.dev/docs/test-sharding, read 2026-10-18). There is an undocumented `PWTEST_SHARD_WEIGHTS`, but it
  only changes the counts, it is internal (the `PWTEST_` prefix is Playwright's own test switch) and still not
  about time.
- Simulated with our measured times, equal-count shards are badly uneven, because match-shell's 30 s tests sit
  together: 4 shards of 2 workers give 495, 146, 478 and 118 s; 5 shards give 275, 307, 141, 418 and 94 s. The
  slowest part, not the average, sets the wall time.
- Each shard writes a **blob report** (`reporter: "blob"`, results and attachments such as traces). A last job
  downloads them all and runs `npx playwright merge-reports --reporter html ./all-blob-reports`. The docs' GitHub
  Actions example is a matrix `shardIndex: [1, 2, 3, 4]` with `fail-fast: false`, one `blob-report-<n>` artifact
  per shard uploaded `if: !cancelled()`, and a `merge-reports` job with `needs:` on the matrix
  (playwright.dev/docs/test-sharding, read 2026-10-18). Blob file names must differ; `PLAYWRIGHT_BLOB_OUTPUT_NAME`
  sets one.
- Playwright also runs any list of files or a `--test-list` file, so a shard can just as well be "these files".
- Workers: Playwright's CI page recommends 1 worker on CI "to prioritize stability and reproducibility", and more
  only on a powerful machine (playwright.dev/docs/ci, read 2026-10-18). Ours already run 2, and the press tests
  time 100 ms answers in the browser, so a crowded machine can fail them. Workers have to be measured, not guessed.
- Caching browsers: the same page says "Caching browser binaries is not recommended", since restoring takes about
  as long as downloading and the system packages cannot be cached. We measured 19 s for Chromium with its
  packages.

### GitHub Actions matrix jobs

- `strategy.matrix` makes one job per value, at most 256 per run, `fail-fast: false` keeps the others running when
  one fails, `max-parallel` caps them (docs.github.com "Running variations of jobs in a workflow", read
  2026-10-18).
- A matrix job's check is named after its `name:` with the values filled in, so each part is its own check. A job
  that `needs:` the matrix and checks `needs.<job>.result` gives one stable check name that branch protection can
  require.
- Limits: the Free plan runs **20 jobs at once** across the account, 5 of them macOS; Pro runs 40
  (docs.github.com "Actions limits", read 2026-10-18). Today a pull request uses 6 jobs. Every extra part is one
  more runner per pull request, and with six builders the queue, not the tests, can become the wait. So the number
  of parts should be the smallest that reaches the target.

### How other projects split long end-to-end suites

- **Cypress Cloud** estimates each spec file's time from earlier runs and hands files out one by one to whichever
  machine is free, "in a way that minimizes overall test run time" (docs.cypress.io, "Parallelization", read
  2026-10-18). Balancing by time, with the file as the unit.
- **CircleCI** `circleci tests split --split-by=timings` cuts the files by the timings of the last run, "the most
  accurate split" (circleci.com/docs, "Test splitting and parallelism", read 2026-10-18).
- **Knapsack Pro** (Ruby, JS) does the same from stored timings, with a queue mode in which machines pull the next
  file (knapsackpro.com, general knowledge, confidence medium). GitLab's `parallel:` gives each job
  `CI_NODE_INDEX` and `CI_NODE_TOTAL` for such tools (docs.gitlab.com, general knowledge, confidence high).
- **Playwright's own repository** runs its tests as a GitHub matrix with `--shard` and merges blob reports
  (github.com/microsoft/playwright `.github/workflows`, general knowledge, confidence medium).

The common thread: big suites are split by **measured duration**, files are the unit, and a file that is too long
for one machine is split into smaller files. The timing services need an account or a stored timing artifact; a
plan committed in the repository, rebuilt from the per-file times each run prints, gives the same result for a
suite of our size with nothing to sign up for.

### What is best for ClassiCade

1. **A committed, duration-balanced plan**, `e2e/shards.js`: a list of parts, each a list of spec files. The
   config runs only part `E2E_SHARD` when that is set (`testMatch`), and every file otherwise, so a laptop still
   runs everything. A test in `scripts/workflows.test.mjs` pins it: every spec except the restart file is in
   exactly one part, and each CI matrix lists exactly the plan's parts. A new spec file fails that test until it is
   given a part.
2. **match-shell's press tests get one file per game** (`match-shell-presses-<game>.spec.js`), using one shared
   helper. Same tests, same names, same assertions, same states played to for real; only the file they live in
   changes, so each can go to its own machine. A guard test checks every game has its file.
3. **Chromium desktop + mobile as a matrix of parts**, each with blob reports, plus a **restart job** running
   `restart desktop` and `restart mobile` with `--no-deps --workers=1`, still one test at a time, on its own server.
   A last job, which keeps the name "Browser persona tests (desktop + mobile)", merges the reports into one HTML
   report, prints a per-file time table and fails unless every part and the restart job passed **and** the merged
   report holds exactly the tests `--list` counts, so a test can neither be dropped nor run twice.
4. **Firefox the same way**, with its own merged check keeping the name "Browser persona tests (firefox desktop)".
5. **Workers measured on CI** at 2, 3 and 4 per machine, keeping the fastest that passes three runs in a row.
   Fewer parts with more workers is better for the 20-job queue, if the 100 ms checks hold.
6. **Caching.** npm's download cache is already on (setup-node). Playwright's browsers get an `actions/cache`
   keyed on the Playwright version, with only the system packages installed on a hit, measured against the plain
   install. The web build takes under a second, so caching it would cost more than it saves and would add a way
   to test a stale bundle; it stays a fresh build in each job.
7. Not done: fake clocks or shorter rematch and chess timings (the owner's rule), test retries, fewer devices.
   WebKit (`webkit.yml`) is already 3 parts on macOS, which has only 5 runners for the whole account; it stays as
   it is.

## Why

The browser job took about 22 minutes on `main` (run 39085728868), Firefox 14. Every pull request waits on them,
so they slow all work, and the owner made the browser tests a non-required check until this ticket lands
(ADR-039).

## Plan / notes

As built, following "What is best for ClassiCade":

1. `e2e/shards.js` holds the plan: four parts, each a list of whole spec files with its measured seconds, and
   `RESTARTS`, the pattern of the restart files (`restart.spec.js`, `restart-presence.spec.js` since CC-207).
   `playwright.config.js` sets `testMatch` from `E2E_SHARD`; without it every file runs, as before.
2. `e2e/matchShellPresses.js` holds the press machinery from `match-shell.spec.js`, unchanged, and
   `pressEveryStateOf(gameId)`. `match-shell-presses-{rps,tictactoe,chess}.spec.js` call it. `match-shell.spec.js`
   keeps the header and footer presses and the layout checks. The moved code differs from `main`'s only in the loop
   over games becoming that function (checked with a diff after merging `main`).
3. `ci.yml`: `e2e-parts` (matrix part 1 to 4, 3 workers), `e2e-restarts` (`--no-deps --workers=1`), and `e2e`
   (needs both, keeps the name). The same for Firefox with 2 workers. Blob reports per part, one day; failure traces
   per part, 14 days; the merged HTML report, 14 days.
4. `e2e/reportSummary.js` and `e2e/report-summary.mjs`: the merge job compares the merged JSON report with
   `playwright test --list --reporter=json` by test ID and project, fails on a test that did not run, is not on the
   list or ran twice, and writes a table of each file's seconds per project to the job page.
5. `.github/actions/browser-tests-setup`: Node and npm's cache, the MongoDB binary, `npm ci`, and the Playwright
   browser from a cache keyed on the Playwright version (`~/.cache/ms-playwright`), then `playwright install
--with-deps`, which only installs the system packages on a hit.
6. `ci.yml` concurrency: pull request runs are cancelled by a newer push. Each commit on `main` has its own group
   (`ci-${{ github.event_name == 'pull_request' && github.ref || github.sha }}`), so no run on `main` is cancelled
   or replaced (coordinator and PR #88 review, 2026-10-18). With one group per branch, `cancel-in-progress: false`
   alone still let a newer waiting run replace an older one. Pinned in `scripts/workflows.test.mjs`.
7. Workers, measured on CI: Chromium parts at 2 workers took 5.6 to 6.6 minutes of tests before CC-207 doubled the
   press states; at 3 workers, after CC-207, 6.0 to 6.8 minutes with every press check passing. Firefox at 3
   workers failed one 100 ms check (203 ms, chess `request-asked-of-me`), so Firefox stays at 2.
8. Found on the way, not caused here: `matchStates.js` "Rocky never won a game" failed once on Chromium desktop
   (RPS `computer finished`, run 39091677381): the visitor plays rematches with Rock until Rocky wins one, at most 12. Needs a ticket (the coordinator allocates IDs while several builders add them).
