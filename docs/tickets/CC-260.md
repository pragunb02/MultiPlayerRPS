# CC-260 — Password hashing below OWASP's minimum: scrypt to N=2^15, r=8, p=3, rehash at login

## Problem

New password hashes used scrypt N=2^15, r=8, p=1 (`utils/passwordHasher.js`), below OWASP's minimum (SEC-23,
found in the CC-116 research, #87). Root cause: the default was sized for memory only when CC-076 chose it, and p
was left at 1.

## Fix

Raise the default to OWASP's alternative minimum, N=2^15, r=8, p=3, keep verifying old hashes with their stored
parameters, and make the rehash after a successful login best effort, so a failed save never fails the login.

**Research note.**

1. **Our code today.** Each hash stores its own parameters (`scrypt$N$r$p$salt$hash`), `verify` reads them back,
   and `needsRehash` already asked for a new hash when p or r differ or N is lower. `login` already rehashed, but
   awaited the save without a catch, so a database error there failed a login whose password was right. The dummy
   hash for unknown emails is made from the same `params` as real hashes.
2. **Sources.** The OWASP Password Storage Cheat Sheet (scrypt section, read 2026-10-21) gives a minimum of N=2^17,
   r=8, p=1, or N=2^16, r=8, p=2, or N=2^15, r=8, p=3, or N=2^14, r=8, p=5, or N=2^13, r=8, p=10, which all cost the
   same CPU, with memory 128 × N × r. Node's `crypto.scrypt` documentation: `maxmem` must be above about
   128 × N × r, and p does not change memory. Django's `check_password` upgrades a hash with an outdated hasher
   or work factor at the next successful login (docs, "Password management in Django", password upgrading), the
   pattern we already had.
3. **Best for ClassiCade.** N=2^15 keeps memory at 32 MiB per hash on Render's 512 MB instance. N=2^17 would need
   128 MiB per hash, too much when a few logins arrive at once. p=3 meets the minimum by spending time instead.

## Decisions

Made by the coordinator, who has design authority for security tickets, and recorded in ADR-080.

| Question                         | Options                                    | Recommended default                      | Owner answer                                     | Default applies on |
| -------------------------------- | ------------------------------------------ | ---------------------------------------- | ------------------------------------------------ | ------------------ |
| Which OWASP parameters?          | N=2^17 p=1 · N=2^16 p=2 · N=2^15 p=3       | N=2^15, r=8, p=3 (32 MiB per hash)       | Coordinator, 2026-10-21: N=2^15, r=8, p=3        | 2026-10-21         |
| What if the new cost is too slow | Stop and report · pick a cheaper set       | Stop and report above about 300 ms       | Coordinator, 2026-10-21: stop and report         | 2026-10-21         |
| What if saving the rehash fails  | Fail the login · keep the login and log it | Keep the login, log it, retry next login | Coordinator, 2026-10-21: best effort, never fail | 2026-10-21         |

## Measurements

`createPasswordHasher({ params }).hash` and `.verify` on the owner's laptop (Apple M4 Pro, Node 24.21.0), 30 runs
each after one warm up, twice:

| Parameters             | Hash median   | Hash p95   | Verify median | Memory per hash |
| ---------------------- | ------------- | ---------- | ------------- | --------------- |
| N=2^15, r=8, p=1 (old) | 40 to 43 ms   | 42 to 45   | 39 to 44 ms   | 32 MiB          |
| N=2^15, r=8, p=3 (new) | 126 to 128 ms | 130 to 145 | 123 to 128 ms | 32 MiB          |

Well under the 300 ms stop line. Render's shared CPU will be slower than this laptop. The login p75 guardrail below
watches that.

## Acceptance criteria

- **AC-1** Given a new account or a password change, when the hash is stored, then it is `scrypt$32768$8$3$…`.
- **AC-2** Given an account whose hash has N=2^15, r=8, p=1, when the player logs in with the right password, then
  the login succeeds and the hash is replaced by one with p=3.
- **AC-3** Given an outdated hash, when saving the new hash fails, then the login still succeeds and the failure is
  logged as "saving the upgraded password hash failed", without the email.
- **AC-4** Given an email with no account, when someone logs in with it, then the dummy check runs scrypt with
  N=2^15, r=8, p=3, the same work as a real account's check.
- **AC-5** Given a hash made with the old production parameters, when it is checked with the new hasher, then the
  right password still verifies.

## Test

Each failed before the fix:

1. AC-1: `passwordHasher.test.js` "uses OWASP's alternative parameters in production" (was `…$8$1$`), and the
   production-strength checks in `server.integration.test.js` and `security.integration.test.js`.
2. AC-2: `passwordHasher.test.js` "asks for a rehash of a hash made with the old production parameters", and
   `accountComponent.test.js` "upgrades a hash with a weaker p".
3. AC-3: `accountComponent.test.js` "still signs in when saving the upgraded hash fails" (the login rejected) and
   `authRoutes.test.js` "still logs the player in when saving an upgraded hash fails, and logs the failure".
4. AC-4: `passwordHasher.dummy.test.js` records the parameters of every scrypt run (p was 1).
5. AC-5: `passwordHasher.test.js` "still verifies a hash made with the old production parameters" (passes before
   and after, it pins that old hashes keep working).
