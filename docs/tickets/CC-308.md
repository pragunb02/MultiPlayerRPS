## Why

CC-289 measured two hot spots in the computer players (docs/tickets/CC-289.md, "Hot spots"):

- **H1.** A chess search runs on the event loop (`packages/games/src/bots/chess/chessBot.js:20-21`, called from
  `apps/server/src/domain/bots/thinkingQueue.js:35-40`). It is about a third of the busy CPU, and on Render Free
  (0.1 CPU) it stalls every player on the server for 0.3 to 1.5 s.
- **H2.** One computer thinks at a time on the whole server, and the server then rests as long as it thought.
  Computer replies collapse under load: p50 0.8 s at 250 players and 27 s at 1 600 on Standard. Rock Paper Scissors
  and Tic-Tac-Toe replies, which take microseconds, wait behind chess searches.

People wait for the server while a computer thinks for someone else. That breaks NFR-3 (a move answered within
150 ms) on every plan with computer games.

## Research (written before any code)

Written 2026-10-20. Every web source was read on that date.

### 1. How our code does it today

1. **Where a move is chosen.** `botDriver.perform` (`domain/bots/botDriver.js:138`) calls
   `thinking.think(() => botTurns.moveFor(room, playerId))`. `botTurns.choose` builds the bot's turn from the room:
   `engine.viewFor(state, seat)` (ADR-040: only its own seat's view), the bot level from the character's level
   pick, `history: []`, and a random number generator seeded from `sha256(game.seed:log.length:botId)` as a 32-bit
   number. So a turn is fully described by plain data: the game, the bot id, the level, the seed and the view.
2. **The queue.** `thinkingQueue.js` runs one piece of synchronous work at a time on the whole server, then rests
   as long as it took (`REST_PER_THINKING_MS = 1`). This is ADR-025's amendment point 3 ("computer players use at
   most half of the event loop", BUG-33). The work runs on the event loop.
3. **What costs what.** Chess levels search by a position budget (ADR-041): Club 20 000 positions, Strong 60 000.
   Beginner scores every move one ply deep. Every chess level first replays the game's move list on its own board.
   Tic-Tac-Toe's Unbeatable level is a memoised solve of at most 5 478 positions, Rock Paper Scissors is a few
   lines. Measured on this laptop (Apple M4 Pro, one core, `node`, 10 Strong searches after 20 random plies): 156 to
   232 ms each, and a 5 ms timer was held up by up to **236 ms** (the whole search). At 0.1 CPU that is about ten
   times longer.
4. **Sealed moves.** Rock Paper Scissors computer throws are chosen inside `botTurns.settle` when the round opens
   and sealed (ADR-025 point 6, CC-225). `settle` runs synchronously inside the room's save, so it cannot wait for
   a thread. Those throws are microseconds and stay where they are.
5. **Ordering per room today.** The driver keeps one plan per room code, keyed by the moment (`matchId:log
length:playerId`). After thinking it reads the room again (`stillPlanned`) and drops the move when the moment
   passed (the person resigned, left or a rematch started). With one global line no two thinks of one room ever
   overlap. That second property is implicit and must become explicit once thinks run in parallel.
6. **Shutdown.** `close()` stops the driver, closes sockets, drains background work and closes the database
   (`server.js`). CC-305 gives the whole shutdown 10 s for the drain plus 5 s for the last telemetry flush, inside
   the 30 s Render waits after SIGTERM.
7. **Telemetry.** ADR-055 allowlists every metric, attribute and log line in `telemetrySchema.js`. The service
   layer gets plain functions (`utils/operationsMetrics.js`). `game` (catalogue id) is an allowed attribute and log
   field already. No id of any kind may leave.
8. **Parallelism on Render's sizes.** `os.availableParallelism()` in `node:24-alpine` (our runtime image) under
   Docker on this laptop (14 cores): `--cpus=0.1` gives 1, `--cpus=0.5` 1, `--cpus=1` 1, `--cpus=2.5` 2. So
   Node 24's libuv reads the container's CPU quota and rounds down, and `os.cpus().length` (14) would be wrong.

### 2. How others do it

1. **Node.js worker threads** (https://nodejs.org/api/worker_threads.html): "Workers (threads) are useful for
   performing CPU-intensive JavaScript operations." The docs advise "In practice, use a pool of Workers for these
   kinds of tasks. Otherwise, the overhead of creating Workers would likely exceed their benefit."
   `worker.terminate()` will "Stop all JavaScript execution in the worker thread as soon as possible" and returns
   a promise for the exit code. An uncaught exception emits `'error'` and "the worker is terminated"; `'exit'` "is
   the final event emitted by any `Worker` instance". `resourceLimits` (`maxOldGenerationSizeMb`,
   `maxYoungGenerationSizeMb`, `codeRangeSizeMb`, `stackSizeMb`) end a worker that passes them.
2. **Node.js guide "Don't block the event loop"**
   (https://nodejs.org/en/learn/asynchronous-work/dont-block-the-event-loop): partitioning (yielding every few
   steps) "uses only the Event Loop, and you won't benefit from multiple cores"; "the Event Loop should orchestrate
   client requests, not fulfill them itself. For a complicated task, move the work off of the Event Loop onto a
   Worker Pool." The cost is "communication costs": objects are serialised to the worker and back. On sizing: "If
   you have 4 logical cores and 5 Workers, one of these Workers cannot make progress."
3. **`os.availableParallelism()`** (https://nodejs.org/api/os.html): "Returns an estimate of the default amount of
   parallelism a program should use. Always returns a value greater than zero", and "`os.cpus().length` should not
   be used to calculate the amount of parallelism available to an application."
4. **Piscina** (https://github.com/piscinajs/piscina), the common Node pool: "A fast, efficient Node.js Worker
   Thread Pool implementation". Defaults `minThreads` = `availableParallelism()`, `maxThreads` = 1.5 times that.
   Cancelling is an `AbortSignal` per task ("If the task is already running, the corresponding Worker thread will
   be stopped"); it lists no task timeout option and does not describe replacing a crashed worker. `maxQueue` is
   unbounded by default, and its queue is one global FIFO. Needs Node 24, one optional native addon
   (`@napi-rs/nice`).
5. **Lichess** sends engine analysis to separate worker machines through queues (fishnet,
   https://github.com/lichess-org/fishnet: "Distributed Stockfish analysis for lichess.org"), with a "user queue"
   for jobs a person waits for and a "system queue" for the rest. The web server never runs the engine itself.

### 3. What is best for ClassiCade

1. **Worker threads, our own small pool, no new dependency (ADR-008).** Piscina would give us threads, but not the
   three things we need most: a fair line per room with one pending think each, a hard time budget per think with
   the worker replaced, and a safe answer for the room when that happens. We would write those on top of it
   anyway, and the pool itself is about a hundred lines on `node:worker_threads`. A child process per think, or a
   second machine like fishnet, costs more memory and start-up than a 512 MB plan can spare.
2. **What crosses to the worker is the turn as plain data** (`{ gameId, botId, difficulty, seed, view }`), and the
   worker answers the raw move. The worker builds the same seeded generator from the seed and calls the same
   `chooseMove`. Both the worker and the in-process path call one pure function in `@classicade/games`
   (`createBotThinker`), so identical input gives identical moves by construction, and a parity test proves it on
   many positions of every game and level. Bots stay pure and see only their seat's view (ADR-040). Replays and
   restarts keep their moves.
3. **Pool size from config:** `max(1, availableParallelism() - 1)`, capped at 4. That leaves a core for the event
   loop and gives one worker on every Render size up to Pro (research 1.8). No env var: the number comes from the
   machine, and a test can pass another.
4. **Only levels that think hard go to the pool.** A level says so in its definition (`cost: "heavy"`, default
   `"light"`): all three chess levels, because each replays the game's moves first. Rock Paper Scissors and
   Tic-Tac-Toe levels answer at once on the event loop, as today, so they never wait behind a chess search (H2's
   suggestion). The sealed throws of point 1.4 are light and stay in `settle`.
5. **Fair queue per room.** Each room has at most one think waiting and one running. A newer think for a room
   replaces its waiting one (the old one's moment has passed, and the driver drops it as gone). Rooms are served in
   the order they asked, so with one pending each no room can crowd out the others. A room's next think starts only
   when its last one finished, so moves of one room are never chosen out of order, and the driver's existing check
   still drops a result that arrives after the room moved on.
6. **The rest after each think goes.** It protected the event loop from work that ran on it. Off the loop, the
   operating system shares the CPU between the worker and the event loop by itself, and a Render container's CPU
   quota is shared by every thread of the process. With one worker on one core the event loop still gets at least
   half of the CPU when both are busy, which keeps ADR-025's guarantee without idling a free core.
7. **Hard budget and failure.** Each heavy think gets 10 s of wall time once it starts (a Strong search takes about
   0.2 s on a full core and 2 to 3 s on 0.1 CPU). On timeout, a crash, or a worker that exits, the worker is
   terminated and replaced, and the room gets the bot's cheapest level (`levels[0]`, "easiest first" in the bot
   contract) chosen on the event loop from the same view and seed. That is still a legal, fair, pure move from the
   bot's own seat (ADR-040 points 2 and 4, the engine checks it). ADR-025 is about identity, rewards and fairness of
   sealed throws, none of which this touches: the fallback is never a sealed throw, and it gives no XP of its own.
   A strategy that throws keeps today's behaviour (the driver tries again, then logs `computer player failed`).
   A room is never left waiting on a think: every think ends in a move, an error the driver already handles, or,
   at shutdown, a `GoneError`.
8. **Telemetry.** A histogram `bots.thinking.duration` (ms, from the ask to the answer, waiting included) with
   `game` and `outcome` (`ok`, `timeout`, `crashed`, `failed`), and two named warning lines,
   `computer player ran out of time to think` and `computer player's thinking crashed`, with the `game` field only.
   No room code, player id or bot id.
9. **Memory.** Each worker gets `resourceLimits.maxOldGenerationSizeMb = 64`, so a runaway search ends that worker
   (counted as a crash) instead of the 512 MB process.
10. **Shutdown.** `close()` stops the queue (every waiting think ends as gone) and terminates the workers, raced
    against 2 s, before the sockets close. That is well inside CC-305's 10 s drain.
