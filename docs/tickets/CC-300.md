## Research (written before any code)

Sources were read on 2026-10-20.

### 1. How our code does it today

1. `e2e/baselines.visual.js` compares 14 screens and states at two sizes and two themes with the 64 PNGs in
   `e2e/visual-baselines/`, only inside `mcr.microsoft.com/playwright:v1.64.1-noble` (CC-155, ADR-056).
2. `ci.yml` job `visual`, "Visual baselines (advisory)", runs on pull requests only. It checks out GitHub's merge of
   the pull request into the newest `main` and compares with the baselines in that merge, which are `main`'s unless
   the pull request changed them. Any difference fails the job.
3. The only ways to make new images are `npm run test:visual:update` (Docker on a laptop) and
   `visual-update.yml`, a `workflow_dispatch` run on the ticket branch that renders with a read-only token and
   commits from a second job. Both put the images on a ticket branch. Nothing ever makes them for `main`.
4. The gap. Pull request A changes the home card and makes its images. Pull request B changes the room and makes
   its images, from a `main` without A. Both merge. Now `main` has A's home images, but B's room images were drawn
   without A's change (or the other way round), so `main`'s baselines no longer match `main`'s screens, and every
   open pull request's merge with `main` fails the visual check, including pull requests that changed only docs.
   Each builder then makes images that are not about their change. This is the state after #121, #123 and #124
   (merged within 15 minutes of each other on 2026-10-20).
5. The CodeQL lesson of #104 (`docs/tickets/CC-155.md`, plan item 7): the first `visual-update.yml` ran on `main`
   with the branch as an input. CodeQL flagged it high (cache poisoning): unreviewed code would have run in `main`'s
   cache scope, where every branch reads caches from. It now runs on the branch itself.

### 3. What is best for ClassiCade

1. **Refresh on `main` after each merge, as a pull request, never a push.** `main` deploys to production and only
   reviewed changes reach it. The images are proposed in one pull request, `visual-baselines/refresh`, rebuilt from
   the newest `main` each time and force pushed to that branch only. Each update adds a comment listing the images.
   A person reviews them in the Files tab and merges. Auto-accept on `main` (Chromatic's option) is not taken: a
   bad merge would then silently become the new truth.
2. **Least privilege, the #104 lesson kept.** The run is started only by a push to `main` (or by hand, refused unless
   on `main`), so the code that runs is `main`'s own merged commit, which already runs with `main`'s cache scope in
   ci.yml. No ref is an input and nothing else is checked out. `render` has `contents: read` and no stored
   credentials. `propose` has `contents: write` and `pull-requests: write` and runs no project code, no npm, no
   cache: it copies PNGs, refuses any other path or a removed image, and pushes one fixed branch.
3. **Which merges start it.** The brief named `apps/web`, `packages/shared` and `e2e`. The screens are also drawn from
   the server (`apps/server` serves the pages and their data, such as quest and achievement names), the engines
   (`packages/games`, the boards' states), and the installed versions (`package.json`, `package-lock.json`, which
   pin React, Vite and Playwright). A narrower list would let a server change make `main` stale with no refresh
   started. So the list is `apps/**`, `packages/**`, `e2e/**`, `package.json`, `package-lock.json`. A run that finds
   nothing changed costs one runner for about 3 minutes and opens nothing.
4. **The pull request check reports and does not wrongly fail.** The simplest correct rule: _a pull request that
   changes none of the files above cannot change a screen_. So when its comparison fails, the difference is `main`'s,
   and the merge that caused it has already started the refresh (same list). The check then passes with the notice
   "baselines on main are stale; a refresh PR is pending" and a link to that pull request when it is open. A pull
   request that does change those files still fails on a difference, because the difference may be its own. Its
   summary says so, and names the open refresh pull request when there is one, since then `main` is stale too.
   Any doubt (the merge commit missing, the list of files not readable) counts as changing the screens, so a doubt
   never hides a difference. Not chosen: comparing each failing image with the refresh pull request's images
   (exact, but it needs the bot branch's images and a second comparison step, much more code for a rarer case), and
   skipping the comparison on such pull requests (it would hide that `main` is stale).
5. **Pull requests no longer need to make their images.** A pull request that changes the look may still run
   `Visual baselines (update)` on its branch to show the new images to its reviewers, which is clearer for a big
   change. If it does not, the refresh after its merge proposes them.

## Why

One UI merge made every open pull request's visual check fail, and every builder then had to make images that were
not about their change. With several builders merging in a row this repeats after each merge.

## Acceptance criteria

- [x] On a push to `main` that changes the screens' files, the refresh renders in the pinned image and, if an image
      changed, opens or updates `visual-baselines/refresh` with only the changed PNGs and a comment listing them
- [x] Nothing pushes to `main`. Render is read-only, the writing job runs no project code, no other ref is checked out
- [x] One refresh at a time (`concurrency: visual-refresh`, not cancelled in progress)
- [x] A pull request that changes no screen file passes with "baselines on main are stale; a refresh PR is pending"
- [x] Tests pin the triggers, permissions, concurrency, "never pushes to main" and run the verdict script
- [x] actionlint passes
- [ ] First run on `main` after merge opens the refresh pull request (needs the owner's setting, below)

## Plan / notes

### The refresh workflow, `visual-refresh.yml`

1. `on: push` to `main` with the paths above and the workflow file itself, so merging this pull request runs it the
   first time. `workflow_dispatch` for a rerun by hand. Both jobs have `if: github.ref == 'refs/heads/main'`.
2. `render`: the pinned Playwright image, `npm ci`, `--update-snapshots=changed`, uploads `e2e/visual-baselines/`.
   A test failing for another reason fails the job, so a half set is never proposed.
3. `propose`: checks out the same commit, replaces `e2e/visual-baselines` with the artifact, and with bash:
   1. No change: writes so in the summary, closes an open refresh pull request as out of date, ends.
   2. Refuses any changed path but `e2e/visual-baselines/<name>.png`, and any removed image.
   3. Commits as `github-actions[bot]` (`CC-300: refresh the visual baselines for main at <sha>`), force pushes
      `HEAD:refs/heads/visual-baselines/refresh` after checking the branch name, opens the pull request if none is
      open, and comments the list of new and changed images with a link to the run.

### The pull request check

1. `visual-scope` (plain runner, `contents: read`, `pull-requests: read`, no stored credentials) checks out the merge
   commit with `fetch-depth: 2`, diffs it against its first parent (`main` now) and outputs `screens=true|false`,
   plus the open refresh pull request's URL for the message.
2. `visual` needs it. The comparison has `continue-on-error`, the images are kept when it failed, and a last
   `Verdict` step passes, passes with the notice, or fails, as in research item 4.

### What the owner must do

1. Settings, Actions, General, Workflow permissions: tick "Allow GitHub Actions to create and approve pull
   requests". Without it the first run pushes the branch and fails at `gh pr create`. After ticking it, rerun the
   failed job, or run "Visual baselines (refresh)" from the Actions tab on `main`.
2. CI does not start on the bot pull request by itself (`GITHUB_TOKEN` rule). Close and reopen it to run CI while
   reviewing, which matters once required checks are back. A GitHub App token would remove this step; not done here
   because it adds a secret.
3. Never push to `visual-baselines/refresh` by hand: the next refresh replaces it.
