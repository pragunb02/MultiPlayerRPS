## Research (written before any code)

Sources were read on 2026-10-19 unless another date is given. "General knowledge" carries a confidence level, as in
the rest of `docs/`.

### 1. How our code does it today

1. **There is no local play.** Every game is a server room (`apps/server/src/domain/rooms/roomComponent.js`). The
   lobby (`apps/web/src/pages/PlayPage/PlayPage.jsx`) offers three ways in, all through the socket: play the
   computer, create a room, join a room by code. Two people on one phone today would need two browsers.
2. **The engines are pure and already browser safe.** `packages/games` has no I/O, no timers, no `Math.random` and
   no `Date.now` (lint enforced). Each engine is `init`, `validateMove`, `applyMove`, `getOutcome`, `viewFor` and
   `activePlayers`, with optional `deadline` and `expire` (chess clocks) and `requestTypes` and `acceptRequest`
   (chess draw offers). The only dependency besides `@classicade/shared` is `chess.js`, which the web chess board
   already loads. The web app does not depend on `@classicade/games` yet.
3. **`viewFor(state, viewer)` already hides what a viewer may not see.** For Rock Paper Scissors it gives the
   viewer their own pending choice and only `hasChosen` for the other player. Tic-Tac-Toe and chess hide nothing.
4. **The game shell (CC-157, ADR-049)** is `MatchShell`: the request banner, the match bar, the stage with the
   game's `Board` from `GAME_VIEWS`, the action bar, the result card and the side column with the seats. Its slots
   are tied to a server room: Rematch and New opponent, the claim the win card, presence chips, "Save your progress"
   for a guest's win, and the room code in the page title.
5. **Boards take a RoomView and `onMove`.** `RpsBoard`, `TicTacToeBoard` and `ChessBoard` read `room.you`,
   `room.seats`, `room.status` and `room.game` (`view`, `activePlayers`, `outcome`, `number`). They do not care
   where the RoomView came from, so a RoomView built in the browser from an engine works for them unchanged.
6. **Rewards are server only.** XP, quests, streaks, achievements and boards are paid from the match outbox
   (ADR-047) after the fair play verdict (ADR-021). Nothing in the web app can award anything, so a game that never
   reaches the server cannot count.

### 2. How other products do it

**Chess.com, "Play in Person"** (formerly "Pass & Play"), help article dated 9 February 2026
(https://support.chess.com/en/articles/8583716-how-do-i-play-in-person-against-a-friend-on-the-app). "lets you
and a friend take turns on the same device, just like using a real board." At setup the player chooses "whether
the board flips after each move". On Android, "When Auto Flip is on, the board will automatically rotate after
each move", and with it off "you can still flip the board manually by tapping 'Options' > 'Flip Board.'" The
timer can be any live time control or "None". The article does not say whether these games are rated (general
knowledge, high confidence: they are not, they cannot be, nobody's identity is checked).

**Lichess mobile, "Over the board"** (source code, lichess-org/mobile on GitHub,
`lib/src/model/over_the_board/over_the_board_preferences.dart` and `translation/source/mobile.xml`):

1. Display settings "Flip pieces and opponent info after move" and "Use symmetric pieces", plus blindfold mode.
2. Defaults: `flipPiecesAfterMove: false`, `symmetricPieces: false`, time control `unlimited` (a 5+3 clock is the
   default when a clock is chosen).
3. The game runs in the app itself (`over_the_board_game_controller.dart`, `over_the_board_clock.dart`) and is kept
   in local storage on the device (`over_the_board_game_storage.dart`), not sent to a server. It is never rated.

So both big chess products let the board **stay** by default or by choice, and offer flipping as an option. Lichess
flips the pieces, not the board, for players sitting across a table with a tablet flat between them.

**boardgame.io** (open source game framework, `docs/documentation/multiplayer.md` and `secret-state.md` in
boardgameio/boardgame.io on GitHub): "The game master can run completely on the browser. This is useful to set up
pass-and-play multiplayer". Hidden information is handled by `playerView`, which "returns a version of `G` that is
stripped of any information that should be hidden from that specific player". This is exactly our `viewFor`, and
running the engine in the browser is the framework's own recipe for pass and play.

**Hidden choices on one device.** Card and strategy games with a hot seat mode (Heroes of Might and Magic, which
"allows up to 8 players to play locally on the same computer", https://en.wikipedia.org/wiki/Hotseat_(multiplayer_mode);
Civilization; the Ticket to Ride and Catan apps) cover the screen between turns with a "next player" screen that
names who should take the device, and show nothing private until that player presses a button (general knowledge,
medium confidence: the vendors' help pages did not resolve for the fetcher). The screen exists because a turn's
private part (a hand of cards, a secret choice) must never be on screen while the device changes hands.

**Ludo King** (https://en.wikipedia.org/wiki/Ludo_King, already in SOCIAL_AND_SHARING.md §4): local play for up to
six people on one device is a main reason the game spread through Indian families in 2020. That is Meena's
household (PRODUCT_VISION.md, GROWTH.md: "Children on the same phone use pass and play and receive nothing").

### 3. What is best for ClassiCade

1. **Fully in the browser, with the pure engines, no server room.** The engines already decide every rule and run
   in the browser (point 1.2). A local session controller calls them exactly as the room component does:
   `validateMove`, then `applyMove`, then `getOutcome`, and `viewFor` for the player holding the phone. There is
   nothing to authorise: both players are at the same phone, so there is nobody to cheat against. No room is
   created, no socket event is sent, no API is called for any move.
2. **Fair play and rewards.** Server-authoritative play (ENGINEERING.md) exists so a result can be trusted. A local
   game cannot be trusted (one person can play both sides), so it must never count: **no XP, no quests, no
   streaks, no achievements, no leaderboards, no match history** (ADR-021: a reward is paid only from a recorded
   match with a verdict, and these are never recorded). Because the server never learns of a local game, this holds
   by construction, not by a flag a client could flip. The result card says "Not counted" in words, so nobody
   expects XP. No bot is involved, so ADR-025 does not apply, and the ADR-025 caps are untouched.
3. **Privacy.** Names are typed on the phone and kept only in the page's memory (React state). They are never sent,
   never put in the URL, never stored in web storage or cookies, and they are gone when the tab closes. Empty names
   become "Player 1" and "Player 2". That suits children on a family phone (ADR-028, ADR-048: nothing about a minor
   is collected) and keeps ADR-051 point 7 true: pass and play creates no account link between the players. A name
   is at most 20 characters and the two must differ, so the screens never confuse who is who.
4. **Rock Paper Scissors: a "pass the phone" screen.** It covers the board whenever the player who must choose
   changes, names who takes the phone next ("Pass the phone to Ben"), asks the other to look away, and shows the
   board only after a press of "I'm Ben, show my turn". While the screen is up the board is not in the page at all,
   so a choice is never in the DOM for the wrong person. Once both have chosen the screen shows the round's result
   to both, then covers again before the next choice. Which games need it is a field in the client game registry
   (`passAndPlay.handOver`), not a check on the game id (ADR-049, open/closed).
5. **Tic-Tac-Toe: no hand-over screen.** Nothing is secret, and both players watch the same grid, as on paper. The
   match bar names whose turn it is.
6. **Chess: the board stays, White at the bottom, with the existing Flip board button.** Lichess's default is no
   flip, and chess.com makes auto flip a choice. On a phone held between two people sitting side by side, or handed
   across, a board that turns after every move is disorienting and hides what just happened. Rotating the pieces
   for players face to face (lichess) needs a tablet flat on a table and new piece art, which we do not have. So the
   board stays, either player can flip it by hand, and the match bar says "Asha (White) to move". Clocks use the
   lobby's own time controls through the engine's `deadline` and `expire`, run by a browser timer. An untimed game
   (lichess's default) would need a new time control in the engine and the server lobby, so it goes in IDEAS.md,
   not in this ticket (working agreement rule 1).
7. **Chess actions.** Resign stays as it is. A draw offer on one phone is agreed in person: the shell asks the
   other player in its confirm dialog, worded from the game's own request texts ("Asha offers a draw. Ben, do you
   accept?"), and accepting runs the engine's `acceptRequest`. No game id is named.
8. **Inside the game shell.** The frame of `MatchShell` (match bar, stage, result card, action bar, side column,
   announcer) becomes a `MatchFrame` that both the room's shell and the pass and play shell fill, so the layout,
   styles and slots stay one (ADR-049). The pass and play shell leaves out what only a room has: the request banner,
   claim the win, presence chips, Rematch and New opponent, "Save your progress" and the XP pop. At the end it
   offers "Play again" (same names, a fresh game, colours or the first player drawn again by the engine) and
   "Back to the lobby".
9. **Entry from each lobby.** A "Pass and play" panel in every game's lobby (`/games/:slug`) links to
   `/games/:slug/pass-and-play`, the setup form (two names, the game's options) and then the game. A game whose
   registry entry has no engine loader shows no panel.
10. **Engines load on demand.** `@classicade/games` gets one export per engine (`@classicade/games/rps` and so on),
    so the Rock Paper Scissors page does not download chess.js, as the boards already do (`lazyBoard.js`).
11. **Leaving.** Leaving mid game asks first ("The game is not saved"), and Back from the game goes to the lobby.
    Nothing is kept, so a reload starts again at the setup form.

## Why

Meena's family has one phone and no graph (PRODUCT_VISION.md personas, SOCIAL_AND_SHARING.md §1 point 13). Pass
and play lets two people play any of our games on it today, with nothing to sign up for and nothing stored.

## Scope

- In: a pass and play entry in each lobby, a setup form with local names, a local session controller over the pure
  engines, the RPS hand-over screen, chess with a fixed board and manual flip, "Not counted" results, Play again,
  unit tests, a no network test, browser tests at 390×844 and 1280×720.
- Out: untimed chess (IDEAS.md), rotated pieces for face to face play, more than two players (Ludo, later),
  keeping a local game across a reload, any reward or history.

## Acceptance criteria

- [x] Each lobby has a Pass and play entry that opens the setup form for that game
- [x] Names are typed locally, default to "Player 1" and "Player 2", and are never sent or stored
- [x] RPS covers the board with a pass the phone screen whenever the chooser changes
- [x] Chess keeps the board still with a manual flip, and its clocks run from the engine
- [x] Results say "Not counted". No XP, quests, streaks, achievements, boards or history
- [x] No socket event or API call happens during a game (unit test and browser test)
- [x] Unit tests for the local session controller, browser tests of a whole game of each game at 390×844 and 1280×720
- [x] `npm run lint`, `npm run format:check`, `npm test` pass
- [x] Docs updated (BACKLOG status, PROGRESS, IDEAS)
