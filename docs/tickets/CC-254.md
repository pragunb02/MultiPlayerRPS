## Owner's report (2026-10-18)

Playing Rock Paper Scissors, best of 3, against Rocky, the screen shows "🔒 Rocky has locked in a throw. Lock
1db7…834". "How we keep it fair" shows a 64 character lock, `{"choice":"paper"}:e47030e0…` as "Throw and key shown
after the round", the lock sent with the throw, and "Lock checked ✓". The owner asks why players see lock ids and
keys, how a player could understand them, and whether players need them at all: "I am not able to be sure. I am able
to guess."

## Research (written before any code)

### 1. How our code does it today

1. `apps/web/src/games/rps/FairnessLock.jsx` (CC-225, merged in #61) shows, above the hands, "🔒 Rocky has locked
   in a throw. Lock `7f3a…c21`" (the first 4 and last 3 hex digits, `shortLock` in `lib/sealCheck.js`). After the
   round it shows "Rocky threw Rock. Lock checked ✓", or in red "The lock does not match this throw.", "This browser
   could not check the lock." or "This browser did not see the lock before this round, so it cannot check it.".
2. "How we keep it fair" opens a dialog with one long paragraph ("a code made from Rocky's throw and a secret key …
   your browser makes the code again from them") and, once a round is over, the whole proof as a list: the 64
   character lock, the raw JSON text of the throw joined to the 64 character salt, the lock sent with the reveal,
   and the result. All of it is open as soon as the dialog opens.
3. The check itself is right and stays as it is: `useSealChecks` remembers the first lock this browser saw for each
   game, player and turn, `checkSeal` hashes `text:salt` with Web Crypto, and `sealVerdict` says "matched" only when
   the remembered lock is the reveal's lock, the revealed throw is the one in the round's result, and the hash fits
   (CC-138 note 5, fixed in #61).
4. The status under the hands says "Rocky has locked in", a third wording for the same fact.
5. The score line is "You 0 — Rocky 0 Best of 3" with a hidden "Score:" in front. It never says how many wins end
   the match, and the engine replays a drawn round without counting it (`rpsEngine.js`: "Drawn rounds are replayed
   and do not count towards the match"), which the screen never says. After a draw the heading goes from "Round 2" to
   "Round 3" while the score stays the same, so a player can think the draw was lost, or that "Round 4" in a best of
   3 is a bug.

The gap: the main screen shows proof material (a hash fragment) that only a technical reader can use, the dialog
leads with that material instead of the idea, and the series rules are never written down. The player is asked to
trust a code they cannot read, which is the opposite of what the lock is for.

### 2. How others do it (sources fetched 2026-10-18 unless stated)

1. **Provably fair casinos.** Stake's and BC.Game's fairness pages (https://stake.com/provably-fair/overview,
   https://bc.game/help/provably-fair) refused the connection from this network on 2026-10-18 (the sites appear
   to be blocked from here), so this point is from the pattern as widely known, not checked today: the game screen
   shows only the result, and a "Fairness" or "Verify" link opens a panel with the server seed hash, client seed and
   nonce, plus a calculator. The hashes are kept off the play screen and are there for the few who want them. We
   keep the idea (proof one step away) and leave out the vocabulary (seeds, nonces), which our players do not need.
2. **Lichess.** The fair play page (https://lichess.org/page/fair-play) and FAQ (https://lichess.org/faq) state the
   rules in plain sentences ("We prohibit the use of any external assistance used whilst a game you are involved in
   is ongoing") and say nothing about how detection works. Players get the promise and the consequence (rating
   refunds), not the mechanism.
3. **Chess.com.** The fair play policy (https://www.chess.com/legal/fair-play) uses short bullet rules and one
   promise, "We can detect if you are using any of these programs", without technical detail. Both chess sites show
   that ordinary players are told what fairness means for them, in their words, and never shown the machinery.
4. **Commitment schemes, the everyday picture.** The standard explanation of commit and reveal is a sealed envelope
   or a locked box: "think of a sender as putting a message in a locked box, and giving the box to a receiver", and
   people "commit to a decision or give an answer in a sealed envelope, which is then opened later"
   (https://en.wikipedia.org/wiki/Commitment_scheme). That picture needs no maths and is exactly what the check
   proves, so the explanation uses it.
5. **Progressive disclosure.** Show the core first and move specialised material behind one control, and keep it to
   two levels (Jakob Nielsen, https://www.nngroup.com/articles/progressive-disclosure/, 3 Dec 2006). For us: level 1
   is the main screen line, level 2 the dialog, and the raw proof sits collapsed inside it.

### 3. Plain language and accessibility guidance

1. **WCAG 2.2 SC 3.1.5 Reading Level (AAA)**: when text needs more than lower secondary reading ability (more than
   nine years of school), offer a simpler version. Short, common words and short sentences help most
   (https://www.w3.org/WAI/WCAG22/Understanding/reading-level.html).
2. **WCAG 2.2 SC 3.1.3 Unusual Words (AAA)**: jargon needs a way to find its meaning, and content written for
   non-specialists should meet this even when only AA is claimed
   (https://www.w3.org/WAI/WCAG22/Understanding/unusual-words.html). "Lock", "key" and "SHA-256" are jargon here, so
   the proof section names each part in words ("Secret key, shown after the round").
3. **GOV.UK style guide**: "All content on GOV.UK should be written in plain English", "use language your audience
   will understand", and technical terms are fine when needed but explained the first time
   (https://guidance.publishing.service.gov.uk/writing-to-gov-uk-standards/style-guides/a-to-z-style-guide/).
4. **GOV.UK Design System, Details component**: use it "to make a page easier to scan when it contains information
   that only some users will need", never to hide what most users need, with short descriptive summary text
   (https://design-system.service.gov.uk/components/details/). That is exactly the proof: most players need the
   verdict, a few want the numbers.
5. **MDN, `<details>`**: the summary is focusable without `tabindex`, toggles with click, Enter or Space, and screen
   readers announce expanded and collapsed by themselves, so no script or ARIA is needed
   (https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/details).

### 4. What is best for ClassiCade's players

Our players are casual, mostly on phones, in India, and many are not technical. India had about 806 million
internet users in January 2025 (55.3% of people, up 49 million in a year, DataReportal, 25 Feb 2025,
https://datareportal.com/reports/digital-2025-india), so most new players are new to the internet as well. English
is often a second language (GROWTH.md keeps Hindi pages for later). For them:

1. **The main screen says what it means for them, not how it works.** Before the throw: "Rocky has chosen. It's
   locked, so Rocky can't change it after you pick." After the round: "✓ Fair: Rocky's choice didn't change".
   A mismatch is a clear warning in words: "⚠ Warning: Rocky's choice changed after it was locked. This round may
   not be fair." No hashes or keys on the main screen at all, not even the short code: a fragment of a hash gives a
   player nothing to compare with, so it can only make them guess.
2. **"How we keep it fair" explains the idea in three steps, with a sealed envelope.** Then a collapsed
   "Show the proof (for the curious)" holds the lock, the throw, the key and the text to hash, each with a label in
   words, and a line saying anyone can check it with any SHA-256 tool. The proof is a native `<details>`, so it
   works with a keyboard and a screen reader without script.
3. **The meaning of the check does not change.** The verdicts are the same five (`checking`, `matched`,
   `mismatched`, `unchecked`, `unseen`) from `sealVerdict`, and the remembered lock logic from #61 is untouched.
   Only their words change. "Fair" is said only for `matched`.
4. **The series is unmistakable.** "Best of 3 · You 0 – Rocky 0 · first to 2 wins", with you always first, and
   after a drawn round: "Draw. It doesn't count, so you play the round again."
5. **One word per idea.** "Chosen" and "locked" on the main screen, "lock", "choice" and "key" in the proof. The
   status under the hands says "Rocky has chosen" like it does for a person.

## Why

Players cannot use a hash fragment, so the lock that should make them sure only makes them guess. The fix keeps the
proof for the few who want it and tells everyone else, in their words, what it means.

## Plan / notes

1. Words live in one frozen table in `FairnessLock.jsx`, one entry per verdict, so the main line and the proof can
   never disagree.
2. The proof uses `<details>` and `<summary>`. The Modal focuses the first button inside it, which stays "Got it",
   so opening the dialog never opens the proof.
3. Before any round is over the proof shows the current lock and says the key comes after the round.
4. Found while building (fixed here, same ticket): the shared `Modal` ran its focus effect again whenever the caller
   passed a new `onClose`, which most callers do on every render. Each room update behind an open dialog moved the
   keyboard focus back to the first button, so a keyboard player on the proof was thrown back to "Got it" (the
   browser test caught it when Rocky's next lock arrived). The Modal now reads `onClose` through `useEffectEvent`,
   and runs the focus effect only when it opens. The Modal also scrolls inside itself when it is taller than the
   screen, so "Got it" stays reachable with the proof open on a phone.
5. `shortLock` is gone: nothing shows a short lock any more.
6. Review of #77: the heading counted draws ("Round 4" in a best of 3 after two draws) while the line under it said
   "play the round again". The heading now counts only rounds someone won, so a draw keeps the number. Tested in
   `boards.test.jsx`.
