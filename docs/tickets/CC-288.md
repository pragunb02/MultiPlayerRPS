## Root cause

### 1. "Docker image builds and serves (docker compose)": `mongo` exits with code 1

The job printed no MongoDB log, so the first change prints `docker compose logs mongo` on failure. The log on the
next failing run (job 118281122059):

```
mongo-1  | {"t":{"$date":"2026-10-19T20:19:01.289+00:00"},"s":"F","c":"CONTROL","id":12257600,"ctx":"main","msg":"MongoDB cannot start: Linux kernel versions 6.19 and newer has a known incompatibility with this version of MongoDB. See https://jira.mongodb.org/browse/SERVER-121912 for more information."}
```

1. The image did not change. Every Docker job of 2026-10-19, passing or failing, pulled the same `mongo:8` layers
   (`f2b4ef06ff01` … `d90d7952f291`, digest `sha256:0e900a33…`, MongoDB 8.3.13). The suspects "the floating tag moved"
   and "a stale volume" are ruled out: the volume is created fresh in each job (`Volume … Created` in the log).
2. The runner changed. Of 21 Docker jobs that day, every one on runner image `ubuntu-24.04` **20261018.339.1** failed
   and every one on **20261012.334.1** passed. The runner image notes differ in the kernel: `6.17.0-1022-azure` before,
   `7.0.0-1017-azure` after (`/proc/version_signature`: upstream **7.0.14**). GitHub rolls a runner image out over a
   few days, so the job failed now and then in the morning and most of the time by the evening.
3. Why MongoDB refuses that kernel: kernels 6.19 to 7.0.13 changed rseq behaviour that MongoDB 8's TCMalloc relies
   on, so 8.0 and later crash on them (SERVER-121912). MongoDB added a startup check that exits instead. Kernel 7.0.14
   restored the old behaviour and MongoDB exempts 7.0.14 and later (SERVER-125742, in 8.0.30 and 8.3.9), but the check
   reads `uname -r`, which Ubuntu keeps at `7.0.0`, so the fixed Ubuntu kernel is still refused (SERVER-136848, open).
   8.2 has neither the crash on this kernel nor the check.

### 2. "Lint, format, audit, unit + integration": web unit tests fail at random

Not shared module state: Vitest runs each file in its own module graph, and shuffled runs (`--sequence.shuffle`)
passed every time. The failing tests act or assert the moment the page shows something, but what they depend on
happens in a `useEffect`. React runs effects in a separate task after it changes the page (through `setImmediate` in
Node). Testing Library's `findBy…` resolves as soon as the page changes, so on a busy CI runner the test runs in the
gap before the effects:

1. `SessionProvider.test.jsx` (CC-115 "tells nobody when nothing changed", CC-234 "asks the server again…"): the
   probe copied the session value in a `useEffect`. The page said "ready" or "anonymous" while the copy still held the
   value from before, so the test called `ensurePlayer` as a visitor (a guest start and an announcement) or read the
   old identity. CI job 118212320040 shows it directly: the page read "anonymous" and `session.identity` was Riya.
2. `RoomPage.test.jsx` (CC-086): the chooser focuses its heading in an effect, and the test checked focus as soon as
   the heading showed.
3. `saveProgress.test.jsx` (CC-097): the header link shows as soon as the guest is known, and the progress listener
   starts in an effect. The test pushed progress in the gap, nobody heard it, and the late load answered 0 XP.

Making the gap long shows every such test. `apps/web/src/testing/slowEffects.js` delays React's effects by
`CC_SLOW_EFFECTS_MS`. On `main`, 5 ms failed 7 tests and 25 ms failed 13, among them all four tests that failed on CI.

Three of the gaps are real, if rare, in a browser too, because the work read a value that an effect had not yet
updated:

1. `useAction` kept the newest work function in an effect: a press in the gap ran the work from the render before
   ("Load more" loaded the first page again).
2. `useRoom` copied the seat in an effect: an effect from before a press on Leave could give the page its old seat
   back, and leaving the page then reported the player away.
3. `useHold` (CC-208) started holding rewards in an effect: a reward in the gap covered the question.

The `TypeError`s in the logs (`reading 'guest_…'`, `reading 'then'`) were in tests that passed. They came from test
fakes: `fakeApi().getMatches` answered nothing, and the claimed win in a chess test had a Ludo view. They are fixed so
the logs only show real failures.

## Research (written before any code)

1. **Our code today.** `docker-compose.yml` used `mongo:8`. Dependabot watches docker-compose weekly. The repo pins
   tools by exact version (`rhysd/actionlint:1.7.12`) and checks downloads by SHA-256 (`backup-tools`), but no image by
   digest yet. The web tests use Testing Library's `findBy…` and `waitFor`, and ENGINEERING.md §4 rule 4 says to poll
   for a condition, never to sleep.
2. **Others.** MongoDB's own tickets (SERVER-121912, SERVER-125742, SERVER-136848, read 2026-10-20) describe the
   kernel issue and the open Ubuntu version bug, and SERVER-136848 names 8.2 and 7.0 as starting normally on the same
   host. Docker's guidance pins images by digest for reproducible builds (docs.docker.com, "Image digests"). React's
   docs ("useLayoutEffect", react.dev) say a layout effect runs before the browser repaints, and React's "latest ref"
   pattern updates refs in a layout effect so event handlers never see a stale value. Testing Library's docs
   ("Async methods") say to wait for the thing the test needs, not for something that comes before it.
3. **Best for ClassiCade.**
   1. Pin `mongo:8.2.12` by tag and by multi-platform digest. A probe on 8 runners (both kernels) ran `mongo:8`
      (8.3.13) and 8.0.34: both exit with the message above on 7.0.14. 8.2.12 and 7.0.45 took 100,000 inserts and stayed
      up over a minute on both kernels. 8.2 stays on the 8.x line our integration tests use (mongodb-memory-server
      8.2.6). 7.0 would also work but is older. Dependabot ignores 8.3 and later until SERVER-136848 is fixed, so it
      cannot propose the broken versions. Not chosen: setting `GLIBC_TUNABLES` (the image already sets
      `glibc.pthread.rseq=0`, and SERVER-121885 reports it does not help), or loosening the healthcheck.
   2. Tests wait for what they depend on: the focus, the listener (through something drawn in the same step), the
      button that can act (`findUsableButton`), the session drawn (`SessionStatus`). The three app hooks set their
      refs in a layout effect, which closes the gap for real players too. No retries and no longer timeouts.
   3. Keep `CC_SLOW_EFFECTS_MS` as an opt-in knob, so the next flaky effect test can be reproduced on a laptop.
