## Problem

The players fixture failed a test because Chromium logged
`request failed: https://localhost:4997/assets/art-Ne-3T1sF.css net::ERR_TOO_MANY_RETRIES` (main at 3be99e6, run
39447225362, "Browser persona tests (desktop + mobile, part 2 of 4)", `pass-and-play.spec.js:110` on desktop). A scan
of the last 300 failed CI runs found it in 13 of them since 2026-10-18, on `main` and on pull requests, in a
different test each time. The URL was always a stylesheet (`art-*.css`, `index-*.css`, `Button-*.css`; today the
first two are the ones the page's `<head>` links), never a script, an image or an API call.

**Root cause: the test certificate, not the server.** The e2e server's certificate is self-signed and made for each
run (`e2e/tlsFront.js`, CC-184), so no browser trusts it, and the tests set `ignoreHTTPSErrors`. In Chromium that
does not stop the certificate error. Every new connection still fails the handshake with
`ERR_CERT_AUTHORITY_INVALID`, the browser is asked, says go on, and the request starts again with the certificate
allowed (`HttpNetworkTransaction::RestartIgnoringLastError`). Chromium allows 32 such restarts per request
(`kMaxRestarts`) and then gives up with `ERR_TOO_MANY_RETRIES` (`net/http/http_network_transaction.cc`, lines 127
and 476). Connection attempts are shared by every request waiting for the same server, and a certificate error on
one attempt fails all the requests waiting on it (`HttpStreamPool::AttemptManager::NotifySingleRequestJobOfFailure`).
So the page's first stylesheet, the first request to wait for a connection, is restarted again for each new
connection opened while it waits. On a laptop that is up to 5 times. On a busy runner it passed 32: in the failed test's trace the
stylesheet failed after 44 ms, while the page's other first requests waited about 40 ms for their answers.

The evidence, from Chromium's own network log (`--log-net-log`) of the real suite:

| Run                                                                                       | Requests | Restarted after the certificate error | Most restarts of one request |
| ----------------------------------------------------------------------------------------- | -------- | ------------------------------------- | ---------------------------- |
| Laptop, pass-and-play, sessions, guest, 3 times each, before the fix                      | 3,657    | 686 (19%)                             | 5, `art-Ne-3T1sF.css`        |
| Laptop, pass-and-play 30 times under 16 busy threads, before the fix                      | 4,590    | 808 (18%)                             | 5, `art-Ne-3T1sF.css`        |
| Linux (CI's Playwright image, 4 CPUs), CI part 2, before the fix                          | 6,406    | 1,971 (31%)                           | 4, `art-Ne-3T1sF.css`        |
| Laptop, the same three files 3 times each, with the fix                                   | 3,657    | 0                                     | 0                            |
| Linux (CI's Playwright image, 4 CPUs), pass-and-play and guest 3 times each, with the fix | 2,073    | 0                                     | 0                            |

In every run before the fix the requests restarted most were the `<head>` stylesheets, the same files that failed
in CI. No request in any run was retried for a broken reused connection (`HTTP_TRANSACTION_RESTART_AFTER_ERROR`: 0),
which is Chromium's only other way to reach `ERR_TOO_MANY_RETRIES` (50 retries on a reused connection).

**Ruled out, with evidence:**

- _Keep-alive or HTTP/2 GOAWAY race._ The browser and the e2e server speak HTTP/1.1 (`tls.createServer` offers no
  ALPN, and the trace's requests are all `HTTP/1.1`), so there is no GOAWAY. The app keeps Node's defaults
  (`keepAliveTimeout` 5 s, `headersTimeout` 60 s; `apps/server/src/server.js` sets neither), and the failed request
  came 70 ms after a fresh browser context opened its first connection, far inside both. A loopback client that
  opened 280 TLS connections, idled 0 ms to 6 s and then asked for the stylesheet got an answer on every one.
- _Rate limits._ `createApiRateLimit` is mounted on `/api` only (`apps/server/src/service/http/app.js`), and the
  static files are served before any limiter. A 429 would also be an answer, and the request got none.
- _Static handler and old builds._ `express.static` serves `/assets` with no special closing; ADR-045 (keeping the
  previous build's files) is still open and not built; a missing file gets a 404 of its own type (CC-181), which is
  an answer, not a failure. The file was in the build.
- _Restarts._ The restart specs run in their own projects after all others (`playwright.config.js`,
  `restartProjects`) and in their own CI job, so nothing restarted the server during these tests.
- _Production._ Players reach Render's edge, which presents a publicly trusted certificate (Google Trust Services,
  `CN=onrender.com`) over HTTP/2. A trusted certificate never causes the restart, so players are not affected and
  the production server does not change.

## Fix

Chromium in the browser tests starts with `--ignore-certificate-errors`, so it accepts the run's certificate during
the handshake, no certificate error happens and nothing restarts. It is set once in `e2e/tlsFront.js`
(`CHROMIUM_ACCEPTS_TEST_CERTIFICATE`) and used by both configs (`playwright.config.js` for Chromium runs only, and
`playwright.visual.config.js`). It trusts no more than `ignoreHTTPSErrors` already did, and only test browsers get
it. No retry, no longer timeout, nothing added to `browserNoise.js`.

Research: Chromium's `net/http/http_network_transaction.cc` (main, read 2026-10-20) for the two limits and
`net/http/http_stream_pool_attempt_manager.cc` for how one attempt's certificate error reaches every waiting request;
Chromium commit 17f0315e11 (2026-03-18), which made the 50-retry case return `ERR_TOO_MANY_RETRIES`; the network log
of our own runs for the counts above. Firefox and WebKit accept the certificate without restarting and never showed
the error, so they are unchanged. The other way, trusting only this certificate with
`--ignore-certificate-errors-spki-list`, needs the certificate before Playwright reads its config, but `server.mjs`
makes it after; that is a bigger change for no gain over `ignoreHTTPSErrors`, which accepts any certificate anyway.

## Acceptance criteria

- **AC-1** Given the browser suite on Chromium, when it loads pages over the e2e server's HTTPS, then no request is
  restarted after a certificate error, so no stylesheet can fail with `net::ERR_TOO_MANY_RETRIES`.
- **AC-2** Given both Playwright configs, when a project is added or changed, then a unit test fails if a Chromium
  project starts without the switch.

## Test

- `e2e/tlsFront.test.js`, "the test browsers": every project of both configs starts Chromium with the switch. It
  fails without the change to the configs.
- The network-log counts above, before and after (a local harness, not committed: `--log-net-log` per worker and a
  script that counts `URL_REQUEST_DELEGATE_SSL_CERTIFICATE_ERROR` per request). The hard failure needs a loaded CI
  runner and did not happen locally in about 25,000 requests, so the proof is that the restarts it counts are gone.
- The full suite on CI.
