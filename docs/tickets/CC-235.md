## Research (written before any code)

### 1. How our code does it today

The failure. CI run 39073239696 (2026-10-17, `main` after #61): `[desktop] fairPlay.spec.js:5` "an instant forfeit
gives no XP and no win, and says the game didn't count" failed on
`expect(alice.page.locator("p", { hasText: "This game didn't count: it ended too soon" })).toBeVisible()`. The steps
before it passed: Alice saw "You won", and the toast with the same words was visible. The same test passed on
mobile in the same run. Locally it passed 60 of 60 (`--repeat-each=30`, desktop and mobile) and 120 of 120 with 20
workers: it only shows on a loaded CI machine.

What the server sends, and in which order.

1. Bob leaves. `roomComponent.leaveRoom` saves the finished room and emits `ROOM_EVENTS.GAME_FINISHED`
   (`apps/server/src/domain/rooms/roomComponent.js`, `change`). The leave handler then broadcasts `room:updated`
   (`apps/server/src/service/realtime/roomHandlers.js`, `ROOM_LEAVE`).
2. `GAME_FINISHED` starts the match pipeline in background tasks (`connectMatchPipeline` in
   `apps/server/src/server.js`): record the match, follow guests, judge fair play (CC-095), apply progression.
   Progression emits `PROGRESSION_EVENTS.UPDATED`, and the gateway sends `progress:updated` to every tab of the
   player (`apps/server/src/service/realtime/gateway.js`) with `{ source, key, matchId, xpGained, leveledUp,
progress, counted, notCountedReason, botXpLeft? }`. `botXpLeft` is new in #61 (CC-138, ADR-025). #61 also added
   `unrankedXp`, the part of the XP from games against a computer, which the leaderboards leave out. It is stored
   with the progress but taken out before the progress is sent (`describe` in `progressionComponent.js`), so it
   never reaches the web app and plays no part in this bug.
3. Usually `room:updated` leaves first, but the two are independent. Nothing promises an order, and with the
   in-memory MongoDB of the browser tests the pipeline takes only a few milliseconds.

What the web app does with them.

1. `useRoom` (`apps/web/src/hooks/useRoom.js`) puts the finished view into state. React renders the room page later,
   in its own task, and only then mounts `ResultCelebration`
   (`apps/web/src/components/Celebrations/ResultCelebration.jsx`, inside `{finished && ...}` in
   `apps/web/src/pages/RoomPage/RoomPage.jsx`).
2. `ResultCelebration` subscribes to `progress:updated` in a `useEffect`. An effect runs after the render is on
   screen, again in a later task. So it listens only from some time after the finished view arrived.
3. Socket.IO calls the listeners that exist when an event arrives, and keeps nothing for listeners added later.
4. So when `progress:updated` arrives in the gap between `room:updated` and the effect (or before `room:updated`), the
   result never hears it: no XP pop for a counted game, no "didn't count" line for an uncounted one. Two websocket
   frames that arrive together are handled as two tasks back to back, before React's render task, which is exactly
   what a busy CI machine does.
5. `ProgressToasts` and `SaveProgressProvider` are mounted for the life of the app, so they are always listening.
   That is why the toast was there and the line under the banner was not.

The same gap hides the XP pop after a counted game, and it would also lose the update if the result section were
mounted again (for example after a rejoin), because the update lives only in the component's own state.

The room view has no match id (`roomComponent.viewFor`). The update has one. Without it the client cannot tell
which game an update belongs to. That matters after a rematch in the same room, where an update from the last game
must not show under the next game's result.

### 2. How others do it

1. React says an effect runs after the browser has painted the update, so a subscription in an effect starts later
   than the render that showed the component (react.dev, "useEffect" caveats and "Synchronizing with Effects", read
   2026-10-18). Data that must not be missed is kept in a store that subscribes early, and components read it while
   rendering ("You Might Not Need an Effect", and `useSyncExternalStore`, react.dev, read 2026-10-18).
2. Socket.IO listeners are plain event emitter listeners. An event with no listener is gone (socket.io docs,
   "Listening to events", v4, read 2026-10-18). Products that push results keep the last value per subject, the
   way TanStack Query keeps a cache per query key and Apollo Client per id, so a screen that mounts late reads the
   value that already came.
3. Chess.com and Lichess show the rating change in the game result. Both send it with, or keyed to, that game, and
   the result panel reads it whenever it appears (behaviour seen 2026-10-18).

### 3. What is best for ClassiCade

1. Keep the last match update per match, for the life of the app, in a provider mounted next to `ProgressToasts`
   (`MatchProgressProvider`). It listens from the first render of the app, long before any game.
2. The finished room view says which match it shows: `game.matchId`. The id is not secret. Only the players of a
   match can read its record (`GET /api/matches/:matchId`), and a spectator already sees the whole result.
3. `ResultCelebration` reads the update for `room.game.matchId` while rendering. It has no subscription and no
   state of its own, so the order of `room:updated` and `progress:updated` no longer matters, and nor does mounting
   again.
4. The kept updates belong to whoever is signed in. When the identity changes (sign in, sign out) they are dropped,
   so a new person in the same tab never sees someone else's XP. Only the last few matches are kept, so memory
   stays small. Quest pushes (`source: "quest"`) are not match updates and are not kept.
5. The test is not changed. The bug is in the app, and the browser test found it.

## Why

A player whose game didn't count sometimes saw no reason under the result, and a player who earned XP sometimes saw
no XP rise out of the banner. It depends on timing, so it fails CI now and then (CC-164 asks every result to answer
visibly).

## Scope

- In: `game.matchId` in the room view, a provider that keeps the last match update per match, `ResultCelebration`
  reading from it, unit tests that fail first, browser test proof.
- Out: the toasts (they already listen all the time), any change to the browser test.

## Plan / notes

1. Server: `roomComponent.viewFor` adds `game.matchId` (the id the match is recorded under, and the one in
   `progress:updated`). The `RoomView` typedef in `packages/shared/src/events.js` says so. Stored rooms always had
   `game.matchId`, so rooms that survive a restart get it too.
2. Web: `components/Celebrations/MatchProgressProvider.jsx` listens to `progress:updated` from the start of the app
   (mounted in `App.jsx` around the toasts and routes) and keeps the last update of each of the last
   `KEPT_MATCHES` (10) matches, for the signed-in identity only. `keepMatchUpdate` in `matchProgressContext.js` is
   the pure rule: only `source: "match"`, the same match replaces its earlier update, oldest out first.
3. `ResultCelebration` reads `useMatchProgress(room.game.matchId)` while rendering. It has no subscription and no
   state. XP pop and the "didn't count" line come from that update.
4. No browser test changed. The race was in the app.
