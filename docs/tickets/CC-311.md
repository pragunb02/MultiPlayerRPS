The first ticket written from the new full template, so it doubles as its worked example.

## Problem

A builder takes a ticket whose copy, default or privacy choice is still open, guesses, and the owner changes the
answer in review. The PR is rebuilt, its reviews run again, and builders waiting on the same files wait longer.
Meanwhile the owner gets those questions one at a time, from several tickets, through the day. The owner's
research brief of 2026-10-20 asked for the questions to come first and all together.

## Job to be done

When the coordinator dispatches a ticket, the owner wants to answer every open question once, in one list, so they
can steer the product without being interrupted all day and builders build each thing once.

## Appetite

M (up to 6 agent-hours). **Cut line:** the CI check's per-row date logic goes first (keep only "has a row and an
AC"), then the lite template.

## Proposed solution

1. Rewrite `docs/tickets/TEMPLATE.md` in the order of ADR-072 point 1 and add `TEMPLATE-lite.md`.
2. Short rules in CLAUDE.md (the decision gate, the owner list, the shaping interview, spec review, appetite, files
   touched, flags), the detail in a new `docs/PROCESS.md`, the list in a new `docs/DECISIONS-PENDING.md`.
3. The PR template gets a table of acceptance criteria, each with its test and evidence.
4. `scripts/tickets/checkTickets.mjs` (pure, tested) and `scripts/bin/check-tickets.mjs`, run in the
   `Changelog fragments` job.

## Non-goals

- Rewriting older tickets to the new template. They keep their emoji statuses and are not checked.
- The flag system itself (CC-312).
- Slimming CLAUDE.md (CC-302). This adds about 20 lines and moves the detail to PROCESS.md.
- Checking that an answer is good. Spec review does that.

## Rabbit holes

- Parsing every Markdown table form. The check reads pipe tables only, which is all Prettier writes.
- Time zones for the default day. The check uses the UTC day, written down in the script.

## Acceptance criteria

- **AC-1** Given a ticket at Ready with every decision answered and one AC, when the gate runs, then it passes.
  Test: `scripts/tickets/checkTickets.test.mjs` › "passes a Ready ticket whose decisions are answered and which has
  a criterion"
- **AC-2** Given a ticket at Ready with a decision unanswered before its default day, when the gate runs, then it
  fails and names the row and day. Test: › "fails an unanswered decision whose default day has not come"
- **AC-3** Given an unanswered decision on or after its default day, when the gate runs, then it passes. Test: ›
  "passes an unanswered decision on and after its default day"
- **AC-4** Given a row with an empty or placeholder question, options or default, when the gate runs, then it fails.
  Test: › "fails a row whose question, options or default is empty or still the template's placeholder"
- **AC-5** Given a ticket at Ready or later with no AC id, when the gate runs, then it fails. Test: › "applies the
  gate at every status from Ready on"
- **AC-6** Given a ticket in Shaping or Spec review, or an older ticket with an emoji status, when the gate runs,
  then nothing is checked. Test: › "checks nothing before Ready, nor an older ticket"
- **AC-7** Given a pull request, when CI runs, then the `Changelog fragments` job runs the gate on every ticket file.
  Test: the job's log on this PR ("150 ticket file(s) pass the decision gate").
- **AC-8** Given a builder opening a PR, when they fill the template, then it asks for each AC with its test and
  evidence. Test: by hand, `.github/pull_request_template.md`.

## Instrumentation

None. No player-facing events. The coordinator counts the two metrics from PR history.

## Threat model

1. What are we building: a docs process and a CI script that reads Markdown in the repository.
2. What can go wrong: a crafted ticket file makes the script slow or run something. It reads text only, with
   bounded regular expressions, runs no command and needs no secret or write token.
3. What we do: the job keeps `persist-credentials: false` and read-only `contents`.
4. Good enough: yes, nothing new reaches production or players.

## Privacy checklist

- **Retention:** not applicable.
- **Who sees it:** the repository is public, so owner answers are public. No names or personal data go in them.
- **Minors (ADR-028):** not applicable.
- **Defaults:** not applicable.

## Alternatives considered

- **GitHub issue forms** with required fields. Not chosen: tickets live in the repo with the code (ADR-068), and an
  issue form cannot check a default day.
- **One ticket template for everything.** Not chosen: one-line fixes would carry twenty empty sections.
- **A new CI job.** Not chosen: a new check name to require, for a step that takes a second.

## Pre-mortem

| Risk                                                                      | Mitigation                                                                                          |
| ------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| The gate fails every PR because one ticket's default day is in the future | Only tickets at Ready or later are checked. A ticket should not be Ready before its days have come. |
| Coordinators skip the full template and use lite for everything           | PROCESS.md: a choice for the owner, a new screen, data or a flag means full. Spec review checks it. |
| DECISIONS-PENDING.md goes stale                                           | The coordinator adds rows at Spec review and removes them on an answer, as part of dispatch.        |

## Research (written before any code)

1. **Our code today.** `docs/tickets/TEMPLATE.md` had Research, Why, Scope, a checklist of acceptance criteria and
   notes, with no appetite, no owner decisions, no metric and no rollout. CLAUDE.md working agreement rules 4 and 8
   require research first and reviews before merge, but nothing required decisions before build. CC-299's
   `Changelog fragments` job already checks docs on every PR, with its logic tested in `scripts/changes/`.
2. **Other products and methods.**
   - Basecamp, _Shape Up_ (Ryan Singer, 2019, basecamp.com/shapeup): appetite instead of estimates, a fixed time
     with variable scope, rabbit holes and no-gos written before the bet.
   - Amazon's working backwards and Google design docs (Malte Ubl, "Design Docs at Google", 2020,
     industrialempathy.com): goals and non-goals, alternatives considered, decided before code.
   - Gherkin, Given/When/Then (Cucumber docs, cucumber.io/docs/gherkin): acceptance criteria that map to tests.
   - Gary Klein, "Performing a Project Premortem", Harvard Business Review, September 2007: name how it failed
     before starting.
   - Adam Shostack's four questions (Threat Modeling Manifesto, 2020, threatmodelingmanifesto.org).
   - Feature flags with removal dates (Martin Fowler, Pete Hodgson, "Feature Toggles", 2017, martinfowler.com):
     release toggles are short-lived and need a removal plan.
   - Jobs to be done, the job story form (Alan Klement, "Replacing the User Story with the Job Story", 2013).
3. **Best for ClassiCade.** A solo owner and up to five agent builders: the scarce thing is the owner's attention,
   so questions are batched with recommended defaults and a day after which work goes on. The check is text only
   and runs in an existing job, so it adds no required check name. Older tickets are left as they are.
