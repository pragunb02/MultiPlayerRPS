## Why

"Play a bot: pick game + difficulty, play instantly" is a Stage 1 journey (PRD §2, FR-AI-1..4), and quick match
will fall back to a bot (FR-AI-5). Before a bot can sit in a room we need the strategies themselves: pure,
deterministic, tested to play only legal moves, with difficulty levels players understand.

This branch delivers the **strategies only**, in `packages/games/src/bots/`. Seating bots in rooms waits for
CC-101 (durable rooms), which is rewriting the room component and DAOs right now (planned wiring below).

## The contract

```js
bot.chooseMove({ view, botId, rng, difficulty, history }); // → a raw move, exactly as a client would send it
```

- `view` is `engine.viewFor(state, botId)`: what a person in that seat sees. **The full state is not passed**,
  see the ADR below.
- `rng` is the only randomness (seeded mulberry32 from `rng.js`). Same turn and same RNG sequence, same move.
- `difficulty` is one of `bot.levels[].id`. An unknown id throws `RangeError` (no silent fallback to some level).
- `history` is the bot's final views of earlier games against the same opponent in the room (rematches), oldest
  first, `[]` for the first game. The pattern reader uses it, the others ignore it.
- `bot.levels` is `[{ id, name, description }]`, easiest first: `id` is stable for the API and database, `name`
  and `description` are what players read on the picker.
- Bots only get called when the engine lists them in `activePlayers`, and never mutate their input.
- The move goes through `engine.validateMove` like anyone else's, so a buggy bot cannot break a game.

Levels:

| Game                | Level ids                      | Names players see             |
| ------------------- | ------------------------------ | ----------------------------- |
| Rock Paper Scissors | `random`, `pattern`            | Random, Pattern reader        |
| Tic-Tac-Toe         | `easy`, `medium`, `unbeatable` | Easy, Medium, Unbeatable      |
| Chess               | `beginner`, `club`, `strong`   | Beginner, Club player, Strong |

## Bot contract kit

`describeBotContract(bot, { engine, options, games, maxMoves, seed?, timeoutMs? }, { describe, it })` registers:

1. belongs to its engine and names its levels for players;
2. refuses a difficulty it does not have (must throw `RangeError`);
3. plays only legal moves, never throws and finishes every game, at every level: each level plays a rematch
   series against the easiest level (mostly random for every bot here, so this is also a fuzz over many unusual
   positions), seats swapped every game, history passed in, every move checked by the engine's `validateMove`,
   views and history deep-frozen (a bot that changes them throws), moves must be plain objects;
4. makes the same moves from the same seed (two games per level, optionally only their first `replayMoves` moves,
   which keeps the chess check quick).

`checkBotContract` returns the violations instead; `botContract.test.js` proves each check catches a broken bot.

## Rock Paper Scissors bots

- **Random**: uniform choice.
- **Pattern reader**: reads the opponent's choices from the resolved rounds of this game and of the earlier games
  in `history` (never the pending choice, which the view does not contain). It scores each choice by how often
  the opponent picked it overall plus twice how often it followed the opponent's last choice (a first-order
  Markov habit), predicts the highest (ties broken by `rng`) and throws what beats it. One move in five it picks
  at random instead, so it cannot be steered and stays beatable.

Measured (200 seeded best-of-5 matches each): Pattern reader beats always-rock 198 times, a rock-paper-scissors
cycle 176 times. Random wins 100 against each.

## ADR-0xx (proposed): bots are pure strategies that see only their seat's view

- **Context:** FR-AI-1 asks for a server-side bot that implements `chooseMove(state)`. ENGINEERING.md lists bots
  under `apps/server/src/domain/bots/`. Some states hold secrets: in Rock Paper Scissors the state has the
  opponent's pending choice.
- **Decision:**
  1. A bot's decision is a pure function in `packages/games` (next to the engines it plays, sharing their purity
     lint rules), `chooseMove({ view, botId, rng, difficulty, history })`. The server will own when and where a
     bot plays (domain layer), not how it decides.
  2. Bots get `engine.viewFor(state, botId)`, never the state. A bot can then not cheat even by accident, and the
     contract is identical to what a human client gets. Everything the bots need is in the views today (the chess
     view has the move list, which gives repetition history).
  3. One bot per game with named levels, rather than one bot per level: levels of one game share code (chess
     levels are one search with different limits) and the picker lists `bot.levels`.
  4. The bot answers with a raw client move that the engine validates. No trusted path for bots.
  5. Determinism comes from the injected RNG and, for chess, from position budgets instead of clocks (CC-040).
- **Consequences:** bots are unit-testable with no server, replayable from a seed, and fair by construction. A
  future bot that needs hidden information legitimately (none planned) would need a contract change. The
  ENGINEERING.md extension point table should say "`packages/games/src/bots/<game>/` implementing `Bot`, register
  in `BOTS`" once this is accepted.

## Planned wiring (after CC-101 merges)

1. **Identity:** a bot seat gets a player id from a reserved, non-user namespace (e.g. `bot:<game>:<level>:<n>`)
   and a display name like "Pattern reader (bot)". It never collides with user or guest ids, and the identity kind
   is a new `IDENTITY_KINDS.BOT` in `@classicade/shared`.
2. **Starting:** "Play a bot" on the lobby → a room with the player and a bot seat, created by `roomComponent`
   with `{ bot: { level } }` validated against `bot.levels` (unknown level → `ValidationError`).
3. **Moving:** a `botComponent` (domain) subscribes to room updates. When a bot id is in
   `engine.activePlayers(state)`, it calls `BOTS[game].chooseMove({ view: engine.viewFor(state, botId), botId,
rng, difficulty, history })` and submits the move through the same `roomComponent.move` path as a person.
   The RNG is seeded from the match seed plus the move number, so a match replays exactly. A short human-like
   delay (a few hundred ms, longer for chess) is scheduled by the server through the injected clock, never inside
   the strategy.
4. **Chess time:** Strong searches about 200 ms on this machine (CC-040). On the server it should run off the
   event loop (a `worker_threads` pool of one or two workers) so a bot move never delays other rooms' sockets.
5. **History:** the room's `series` already knows the earlier games, the bot component passes their final views.
6. **Results:** bot games are recorded as matches with the bot's id, excluded from leaderboards and ratings, and
   give reduced XP (to be decided with CC-042).
7. **Draw offers:** chess bots never resign, offer or accept draws in this version, moving declines an offer.
