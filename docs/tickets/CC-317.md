## Problem

`e2e/accessibility.spec.js:227`, "page changes › Back focuses the heading and keeps the place the browser scrolled
back to", failed on mobile on `main` at a5a801c (run 39425319752, job 118636302430,
`expect(heading).toBeFocused()` at line 242, "Received: inactive"). PR #148 did not touch navigation.

**Root cause: the test went Back before the app had drawn the privacy page.** It waited only for the URL. A
`<Link>` press calls `history.pushState` straight away, so the URL is `/privacy` at once, but React Router's
`BrowserRouter` hands the new location to React inside `startTransition`
(`node_modules/react-router/dist/development/lib/dom/lib.js`, `BrowserRouter`). A transition render can yield to
the browser, and a newer transition replaces it. On the busy runner `page.goBack()` came 6 ms after the click, the
popstate's update (`/`) replaced the pending `/privacy` one, and `/privacy` was never committed. The trace shows it:
the DOM snapshots taken at `/privacy`, after the click and after `toHaveURL`, are still the home page, scrolled to
1906 px. To `PageAnnouncer` the path never changed (`/` before and after), so it rightly did nothing and focus
stayed on the tapped footer link.

The app is right here. If the privacy page never showed, the player never left the home page, and moving focus to
its heading would take focus away from the link they pressed (CC-183 rule: never take focus from a player). No
toast or CC-207 popup was involved: the failure needs nothing but the lost page.

## Fix

The test waits for the real sign that the privacy page is on screen, its focused heading, before going Back. No
sleep, no retry, no longer timeout.

Research: `PageAnnouncer.jsx` (CC-183) acts on a committed change of `pathname`; React Router 8.4's `BrowserRouter`
wraps every history update in `React.startTransition` unless `useTransitions={false}`; React's docs say a
transition is interruptible and a later one supersedes it ("Transitions are interruptible", react.dev
`startTransition`). Turning transitions off for the whole app to suit a test would change how every page with a
lazy board loads, so the test changes, not the app. The test above it ("focus moves to the new page's heading")
already waits for the Chess heading before Back.

## Acceptance criteria

- **AC-1** Given a phone whose main thread is slow while the privacy link is tapped, when the test runs 40 times,
  then it passes 40 times, and still checks that Back focuses the home heading without a jump to the top.

## Test

`npx playwright test e2e/accessibility.spec.js -g "Back focuses" --project=mobile --repeat-each=40 --workers=1`
(E2E_PORT=4995), with a local harness that was not committed: CDP `Emulation.setCPUThrottlingRate` 30x from just
before the tap until Back returns, to stand in for the loaded runner.

| Run                       | Before the fix                                  | After the fix |
| ------------------------- | ----------------------------------------------- | ------------- |
| Plain, laptop             | 40 passed                                       | 40 passed     |
| CPU 30x from tap to Back  | 40 failed, all "Received: inactive" at the line | 40 passed     |
| CPU 100x from tap to Back | 10 of 10 failed                                 | —             |

The plain run never lost the race on a laptop, which is why it showed only in CI.
