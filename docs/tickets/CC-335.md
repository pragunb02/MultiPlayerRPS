## Problem

CC-319's Chromium network logs (`--log-net-log`) showed 186 requests ending in `ERR_WS_UPGRADE`, about 5% of the
requests, the same count before and after its certificate fix. No test failed. We read it as about 5% of WebSocket
connections failing their upgrade.

**Root cause: none of them failed. `ERR_WS_UPGRADE` is how Chromium logs a successful upgrade.** Chromium's
`net/base/net_error_list.h` says: "When a WebSocket handshake is done successfully and the connection has been
upgraded, the URLRequest is cancelled with this error code" (`NET_ERROR(WS_UPGRADE, -173)`). The only place that uses
it is `WebSocketStreamRequestImpl`'s destructor in `net/websockets/websocket_stream.cc`, and only when
`ws_upgrade_success_` is set (both read on main, 2026-10-21). After the 101 the connection belongs to the WebSocket
and no longer to the HTTP request, so the HTTP request is closed with this code. A refused upgrade ends another way
(`ReportFailure`, for example `ERR_INVALID_RESPONSE`). So the 186 is not 5% of the WebSockets: it is every one of
them, and 5% of all requests. The count did not change with CC-319 because the same tests open the same number of
sockets.

**Evidence.** Chromium's network log of our own runs, with the same harness as CC-319 (a local config, not committed,
that adds `--log-net-log` and `--net-log-capture-mode=Everything` per worker, and a script that groups the log by
request):

| Run (laptop, desktop and mobile projects)                   | Requests | WebSocket handshakes | Answered 101 | Ended `ERR_WS_UPGRADE` | Ended any other way                        |
| ----------------------------------------------------------- | -------- | -------------------- | ------------ | ---------------------- | ------------------------------------------ |
| pass-and-play, sessions, guest, desktop only, once each     | 693      | 31                   | 31           | 31 (4.5% of requests)  | 0                                          |
| pass-and-play, sessions, guest, 3 times each (CC-319's set) | 4,100    | 186                  | 186          | 186 (4.5% of requests) | 0                                          |
| `realtime-upgrade.spec.js` (this ticket), desktop           | 37       | 3                    | 2            | 2                      | 1, the refused one: `ERR_INVALID_RESPONSE` |

The second row gives exactly CC-319's 186. In each socket's log the 101 comes first, then the `CANCELLED` event with
`net_error -173`, then the socket's frames in both directions on the same source, ending with the browser's close
frame (145 at teardown, where the browser closed without waiting for the server's reply, and 41 with the reply).
No socket had any other error.

**The four suspects, each ruled out:**

- _The e2e TLS front proxying upgrades._ Every handshake through it was answered `101 Switching Protocols` (186 of 186) and then carried frames both ways. `e2e/tlsFront.js` copies bytes and reads no request, so it cannot answer
  an upgrade itself.
- _Socket.IO's polling-to-websocket upgrade racing a navigation or a close._ There is no such upgrade: the web app
  connects with `transports: ["websocket"]` (`apps/web/src/lib/socket.js`). The logs have no
  `transport=polling` request at all, and every handshake URL is `EIO=4&transport=websocket` with no `sid`.
- _The server refusing the upgrade._ No handshake got anything but a 101, and the app's log (warn level, as the e2e
  app runs) had no `socket refused` line in any run. A refusal looks different: `realtime-upgrade.spec.js` makes
  one with the real origin check (a page on `https://127.0.0.1:4997`, not an allowed origin), Engine.IO answers
  `400 Bad Request` with the body `Forbidden` before any 101 and Chromium ends the request with `ERR_INVALID_RESPONSE`, not `ERR_WS_UPGRADE`.
  The session check and the socket caps refuse after the 101, with a Socket.IO `connect_error`, so they never show
  as an upgrade failure; CSP allows `'self'` for `connect-src`, and a CSP block would be a console error.
- _Connections cut at test teardown._ Teardown closes come after the upgrade, so they cannot change how the
  upgrade's request ended. They are clean closes (the browser sends a close frame) and no engine reports them: a
  reload and `player.leave()` gave no problem in Chromium, Firefox or WebKit.

**Production is not affected.** The marker comes from the browser, for every WebSocket that upgraded, behind
Render's edge as here. Nothing in the server or the Render setup changes.

## Fix

Nothing in the app was broken, so the app does not change. What was missing is a test that shows the browser
tests do catch a real upgrade failure, so nobody silences `ERR_WS_UPGRADE` or the console's WebSocket wording to
make the logs look clean. `e2e/realtime-upgrade.spec.js`:

1. The app's own realtime connection upgrades (the server speaks on it), a reload opens a second one that upgrades
   too, and the reload's close and the person leaving leave the players check clean.
2. A refused upgrade, by the server's real origin check, is recorded by the players check exactly once, in each
   engine's words: Chromium "Error during WebSocket handshake: Unexpected response code: 400", Firefox "Firefox
   can’t establish a connection to the server at wss://…/socket.io/…", WebKit "There was a bad response from the
   server." Outside a declared restart that fails the test. The test takes the recorded problem with the new
   `player.takeProblems()` (for tests of the check itself only), so its own provoked failure is not reported twice.

No retries, no longer timeouts, nothing added to `browserNoise.js`.

Research: Chromium `net/base/net_error_list.h` and `net/websockets/websocket_stream.cc` (main, read 2026-10-21) for
what `ERR_WS_UPGRADE` means and how a refused upgrade is reported; Engine.IO 6.6.11 `build/server.js`
(`handleUpgrade`, `verify`, `abortUpgrade`) for how our server refuses an upgrade (400 before the 101); Playwright
1.64's `websocket`, `socketerror` and `close` events, checked in all three engines with a probe spec (not
committed). Side note, not ours to fix: a client that asks for Engine.IO 3 on the WebSocket transport is refused
after the 101 (Engine.IO checks the protocol version in `handshake`, after `ws` has upgraded), so it sees "Invalid
frame header". Our client always sends `EIO=4`.

Left as is, with a reason: while a test has declared a restart (`player.expectRestart()`), any failed realtime
connection is let pass, a refused one too. Chromium's wording would let a refusal through ("Unexpected response
code"), but Firefox uses the same words for both, and no run showed a refusal during a restart.

## Acceptance criteria

- **AC-1** Given a Chromium network log of the browser tests, when its WebSocket requests are counted, then each one
  that ended in `ERR_WS_UPGRADE` had been answered 101 (186 of 186), and the ticket records that this is Chromium's
  success marker.
- **AC-2** Given a browser test whose realtime upgrade is refused by the server, when the players check runs, then
  it records the failure, in Chromium, Firefox and WebKit.
- **AC-3** Given a page reload or a person leaving with the realtime connection open, when the players check runs,
  then it records nothing.

## Test

- `e2e/realtime-upgrade.spec.js`, both tests, passed on desktop and mobile Chromium, Firefox and WebKit.
- It fails when the check is weakened: with the fixture letting every realtime console failure pass (not only
  during a restart), "a refused upgrade fails the players check" failed with "the refused upgrade was reported".
- The network-log counts above (AC-1).
