## Problem

`main` went red at 631dceb: `e2e/user.spec.js:161` "signs out the other devices from one browser, which stays
signed in" failed on mobile because the laptop, which pressed the button, was signed out too. Root cause, a real
app bug from CC-116 that #164 did not touch: sessions are rolling (`rolling: true`), so every answer re-issues the
cookie its request came with. The profile page asks for about a dozen things at once and the button can be pressed
before they are all answered. An answer the server writes after `keepOnlyThisSession` has renewed the id sets the
old id again, over the new one from the 204. The old id is already destroyed, so the next request (the test's
reload) goes on as a visitor. The CC-116 grace window only kept such requests from being signed out on the server;
it did nothing about the cookie they hand back.

Evidence from CI's trace (run 39537709093): the 204 set `cc.sid=s:8xh6HU…`, the answers to `/api/account`,
`/api/progress` and `/api/challenges` that came in after it set `cc.sid=s:mW-gtyt…` (the old id) again, and the
reload sent `mW-gtyt…`, getting `authenticated: false` and the "Log in" profile in the screenshot. Not the profile
page, the header, the challenges provider or the test: the test waited on the real signal (the status message),
and the browser really was signed out.

## Fix

`createRenewedSessionRelease` in `service/http/session.js`, mounted straight after the session middleware: when an
answer's headers are written for a session id that is being renewed (`renewals.isRenewing`, the same 5 s window
CC-116 already keeps), it lets go of `req.session`, so express-session sets no cookie and does not save or touch
the destroyed session. Research: express-session 1.19 decides the cookie in an `on-headers` listener
(`shouldSetCookie`: with `rolling` it sets the cookie whenever `req.session` is there, and does nothing when it is
not); `on-headers` wraps `res.writeHead`, and a wrapper added later runs first, so ours runs before it. The express-session README (`resave`, `saveUninitialized`) warns of the same kind of race, "a client makes two parallel requests … and changes made to the session in one request may get overwritten", and leaves it to the app. No new dependency.

## Acceptance criteria

- **AC-1** Given a request of this browser that was sent before "sign out other devices" and is answered after it,
  when its answer arrives, then it sets no cookie, this browser stays signed in under its new id, and the old id
  still answers `authenticated: false`.

## Test

- `accountSessions.test.js` "keeps this device signed in when a request it sent before is answered after it": holds
  `GET /api/account` in the account read while sign out others answers. Fails without the fix (`setsCookie` true).
- `session.test.js` "createRenewedSessionRelease (CC-326)": unit tests of the release.
- The browser test, unchanged: `--repeat-each=30 --workers=1` passed 30/30 before and after (it needs a busy
  server, as on CI). Under load, `--repeat-each=120 --workers=8`: 10 failed of 120 before (5 of 60 in a first run),
  0 of 120 after (and 0 of 60), always at line 179. 6× CPU slowdown in the laptop's browser did not reproduce it:
  the late answers come from a busy server, not a slow page.
