## Research (written before any code)

Sources were read on 2026-10-18 unless another date is given. "General knowledge" carries a confidence level.

### 1. How our code does it today

1. **No email is ever sent.** There is no mail code, no provider and no mail setting in
   `apps/server/src/config/index.js`. Emails are collected at sign-up and never verified.
2. **Accounts.** `apps/server/src/domain/accounts/accountComponent.js`: `signup`, `login` (same answer and the same
   work for an unknown email and a wrong password), `changePassword` (needs the current password) and
   `signOutOtherDevices`. Both of the last two call `accountAccessor.bumpSessionVersion`, which ends every other
   session (ADR-030.4 and .5). ADR-030.5 already says "password reset will too".
3. **Routes.** `apps/server/src/service/http/authRoutes.js`: `POST /auth/signup`, `/auth/login`, `/auth/password`,
   `/auth/sign-out-others`, with `perIp` (20 per 15 minutes), `signupPerIp` (10 an hour) and the failed login
   throttle (ADR-035.5).
4. **Legacy players.** A login that finds no account reads the frozen legacy `users` collection (CC-078) and creates
   an account from it. The legacy DAO cannot write. A legacy player who forgot their old password has no way in
   today.
5. **Messages that promise a reset.** ADR-037.5 (pending PR #69, CC-238) shows "If it's yours, log in or reset your
   password". SEC-17 (sign-up says an email is taken) stays open "until CC-033 sends email" (ADR-035, ADR-037).
6. **What is already right for a reset page.** Helmet's default `Referrer-Policy: no-referrer` is on for every
   answer (`service/http/app.js`). The site's public address is the first `ALLOWED_ORIGINS` entry, never the Host
   header (ADR-042.3). The request log writes the path without the query string and redacts `token` and `email`
   (DATA.md, server logs).
7. **No domain.** Production is `nocapgaming.onrender.com`. Mail cannot be sent from an onrender.com address
   (GROWTH.md §2.6), so CC-033 waits for the brand domain (CC-123).
8. **Render free blocks SMTP.** "Free web services can't send outbound network traffic on ports 25, 465, or 587"
   (https://render.com/docs/free). So the provider must be reached over its **HTTPS API**, not SMTP.

**OWASP Forgot Password Cheat Sheet**
(https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html):

1. "Return a consistent message for both existent and non-existent accounts", with uniform timing (do the slow part
   in the background).
2. Rate limit per account and address, so nobody can flood an inbox.
3. Tokens "randomly generated using a cryptographically safe algorithm", long enough against guessing, tied to one
   user, stored safely, "single use and expire after an appropriate period".
4. URL tokens are "the simplest". Build the link from a fixed, trusted address, never the Host header. Send
   `Referrer-Policy: no-referrer` on the reset page. Rate limit token guesses.
5. "Do not make a change to the account until a valid token is presented." Do not lock accounts because of reset
   requests.
6. Ask for the new password under the normal password rules, offer or force signing out every session, and "Don't
   automatically log the user in".
7. Email the player that the password was changed, never including it.

**Email authentication.** Gmail's sender rules (https://support.google.com/a/answer/81126): every sender needs SPF
or DKIM, TLS, valid DNS and a spam rate under 0.3%. Above 5,000 a day, SPF and DKIM and DMARC, with the From domain
aligned. Resend recommends a **subdomain** for sending, to keep its reputation apart from the main domain
(https://resend.com/docs/dashboard/domains/introduction). SPF, DKIM and DMARC are DNS records the owner adds at the
registrar (GROWTH.md §2.6).

**India, DPDP Act and Rules** (Rules notified 14 Nov 2025, text at https://www.dpdpa.com/dpdparules.html and per
rule pages):

1. Rules 3 (notice), 5 to 16 apply **18 months after publication**, about mid May 2027 (Rule 1). They apply to us
   before any marketing at all, because we already hold emails.
2. **Rule 3, notice:** say what we collect, why, and how to withdraw. The privacy page must name the email provider
   as a processor and say a reset email is sent to the address given.
3. **Rule 7, breach:** tell affected players "without delay" and the Board within 72 hours. An email provider holds
   addresses, so it is part of that plan.
4. **Rule 10, children:** verifiable parental consent before processing a child's data. Unknown age counts as a
   minor (ADR-028.1). A reset email goes only to the address the account holder gave, for the service they asked for
   (getting back in), and carries no marketing. Whether that needs consent for a minor's account goes to the
   lawyer's review (ADR-028.9).
5. **Rule 14(3):** publish how grievances are handled, answered within at most 90 days.
6. **Cross-border.** Resend sends from servers outside India. The Act allows transfers except to countries the
   government restricts (general knowledge, medium confidence). The privacy page says where mail is processed.
7. **ADR-032.4:** transactional email such as a password reset is **exempt** from the postal address rule that holds
   back marketing and recap email. A reset email is not marketing, so CAN-SPAM's address and unsubscribe rules do not
   apply to it (GROWTH.md §5.9).

### 3. What is best for ClassiCade

1. **Provider: Resend, free tier**, called over HTTPS with `fetch` (no SDK, no new dependency, ADR-008). Behind a
   small `mailer` port in the dependency layer, with a fake for tests, so moving to Brevo, Mailjet or SES later is one
   adapter. 100 a day is far above what password resets need for a launch cohort of 100 to 300 players
   (GROWTH.md §1.3).
2. **Sending domain: a subdomain of the brand domain**, for example `mail.<domain>`, From
   `ClassiCade <no-reply@mail.<domain>>`. SPF and DKIM as Resend lists them, DMARC on the main domain starting at
   `p=none` with reports to the owner, moving to `quarantine` after two clean weeks. No reply address that nobody
   reads: the email says where to get help.
3. **The flow.**
   1. `POST /api/auth/reset-request { email }` always answers **202** with "If an account uses that email, we've
      sent a link. It works for 30 minutes." The lookup, the token and the send happen in a background task
      (`utils/backgroundTasks.js`), so the answer time is the same for every email.
   2. The token is 32 random bytes (`crypto.randomBytes`), sent once in the link, stored only as its SHA-256 hash in
      a new `password_resets` collection with the account id, `createdAt` and `expiresAt`. A TTL index removes it. A
      new request replaces the old token. **Lifetime 30 minutes, single use.**
   3. The link is `https://<site>/reset-password#<token>`, built from the configured site address. The token is in
      the fragment, so it never reaches a server log, a proxy or a `Referer`. The page reads it and posts it in the
      body.
   4. `POST /api/auth/reset { token, newPassword }` checks the hash, the expiry and the password rules (the same
      `parsePassword` as sign-up), writes the new scrypt hash and **bumps the session version** in one write, which
      signs out every device (ADR-030.5). It does **not** sign the player in: the page sends them to `/login`. The
      token is deleted in the same step.
   5. A second email says "Your ClassiCade password was changed. If this wasn't you, reset it again" with the link to
      the reset page.
4. **Legacy players.** A reset for an email that is only in the legacy `users` collection creates the account from
   that row (the same path as `loginLegacyUser`, CC-078) with the new password, without ever writing to `users`. The
   ADR-037 case twins rule applies.
5. **Limits** (named rules, as ADR-035): 3 reset emails per email address an hour and 10 a day, 10 requests per
   network address an hour, 10 wrong tokens per address in 15 minutes, and a **daily budget of 80 sends** so the
   provider's 100 a day is never hit by an attack (above it, the request still answers 202 and logs
   `mail budget reached` at warn level). No limit ever locks an account.
6. **Data.** DATA.md gains `password_resets` (account id and a token hash, 30 minutes) and the provider as a
   processor holding the address and the message for its log retention (30 days on Resend free). Logs keep only the
   account id and an outcome, never the email or token. The privacy page changes in the same PR (DATA.md rule).
7. **SEC-17 after this ticket.** With email working, sign-up with a taken email can answer like a new sign-up and
   send the owner of the address "someone tried to sign up with your email". That closes SEC-17 and is the "uniform
   response after email ships" of CC-118. It is the last PR of this ticket, so it can be reviewed on its own.

## Why

A player who forgets their password loses their account, their level and their history. Legacy players who forgot
the old password cannot get in at all. SEC-17 cannot be closed without email.

## Scope

- In: the mailer port and Resend adapter, reset request, reset page, the changed password email, legacy players,
  limits, DATA.md and privacy page, the ADR for the provider, the SEC-17 sign-up change (last PR).
- In (added 2026-10-18 from the CC-116 and CC-117 research, #87): a "your password was changed" and a "your other
  devices were signed out" email for every password change and every "Sign out other devices", not only for a
  reset; and a reset that works for a player the failed login throttle (ADR-035.5) is holding back, because the
  reset is OWASP's way out of a lockout.
- Out: email verification at sign-up as its own flow, recap or marketing email (ADR-032.4, needs the postal address),
  inbound mail, email change, account deletion (CC-035).

## Acceptance criteria

- [ ] The request answers the same status, body and about the same time for an account email, a legacy email and an
      unknown email (test with the fake mailer and a fake clock).
- [ ] A token works once, within 30 minutes, and only its hash is stored. A newer request voids the older token.
- [ ] A reset signs out every session (ADR-030), does not sign in, and sends the changed password email.
- [ ] A password change and "Sign out other devices" each send their email ("password changed" or "signed out
      elsewhere"), with no token or session detail in it.
- [ ] A player blocked by the failed login throttle for their email and address can still request a reset and set a
      new password, and the new password then signs in from that address.
- [ ] A legacy only email can be reset, creating its account, without any write to `users`.
- [ ] The link is built from the configured site address, the token is in the fragment, the page sends
      `no-referrer`, and no log line contains the token or the email.
- [ ] Every limit is a named rule with a test, and none locks the account.
- [ ] The boot fails in production without `RESEND_API_KEY` and `MAIL_FROM`. Locally and in tests a fake mailer
      writes to the log.
- [ ] Tests cover the change. `npm run lint`, `npm run format:check`, `npm test` pass.
- [ ] Docs updated: ADR, DATA.md, privacy page, DEPLOYMENT.md (env vars, DNS), KNOWN_ISSUES (SEC-17), BACKLOG,
      PROGRESS.
