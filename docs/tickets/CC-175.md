## Problem

CC-174's client needs somewhere to send its batches. Without a strict door, anyone can post anything: a script can
fill the free Atlas cluster (512 MB, shared with every game record), forge presses to skew the owner's dashboard, or
smuggle text and ids into fields that the catalogue says must be closed lists. The owner's monitoring of new text,
toasts and dialogs (CC-313) is only as true as what this endpoint lets in.

## Job to be done

When a browser sends a batch of events, the owner wants only well-formed, anonymous, catalogue events kept for 30
days, and everything else dropped and counted, so the dashboard can be trusted and the database stays small.

## Appetite

M (up to 6 agent-hours). **Cut line:** first the bot User-Agent filter, then the daily cap's console line (keep the
cap itself), then the owner purge endpoint. The validator, limits, opt-out headers, admin drop and the TTL are never
cut.

## Proposed solution

1. **The route.** `POST /api/telemetry`, `Content-Type: application/json` or `text/plain` (what `sendBeacon` sends),
   body `{ build, events: [ { name, route, device, player_kind, ...fields } ] }`. Always answers `204` with no body,
   whatever it kept, so it reveals nothing and the client never retries on a rejection.
2. **Drop before reading:** `Sec-GPC: 1` or `DNT: 1` drops the whole batch (EVENTS.md 1.6). A session in
   `ADMIN_ACCOUNT_IDS` drops it (EVENTS.md 1.7). The flag `telemetry_ingest` off drops it.
3. **The validator** reads `packages/shared/src/telemetry/events.js` (CC-174): each event's name must be known, every
   field must be allowed for it, every value from its closed list or a bucket, no other key. An invalid event is
   dropped on its own; the rest of the batch is kept.
4. **Limits** (ADR-035 style, named rules in `domain/telemetry/telemetryLimits.js`): body at most 8 KB, at most 30
   events a batch, at most 30 batches per 10 minutes per rate-limit key (the CC-110 limiter), and a daily cap of
   100 000 stored events. Above the cap, events are dropped and counted.
5. **Storage** (as reviewed 2026-10-21, below). `telemetry_counts` collection, one counter per tuple of catalogue fields and India hour, with `tier: "counts"`
   and `received_at` truncated to the hour. TTL index 30 days. No id, no address, no User-Agent, no cookie.
6. **Counting what was dropped.** An ops counter `telemetry.dropped` with `reason` (`opted_out`, `admin`, `invalid`,
   `rate_limited`, `cap`, `bot`, `flag_off`) goes to Grafana with the other ADR-055 metrics. No product data goes
   there, only the reason.
7. **Server-side events** (`account_created`, `login_succeeded`, `login_failed`, `session_ended`, `guest_started`,
   `server_errored`) are written by their components through the same validator, never through HTTP.
8. **Owner purge.** `DELETE /api/admin/telemetry?before=YYYY-MM-DD` (ADR-036 allowlist and 404) deletes raw events,
   for a rollback or a mistake found in a field.

## Non-goals

- Aggregation (CC-176) and the dashboard (CC-177).
- Any id, hash or address, even for rate limiting beyond the existing keyed limiter, which stores nothing.
- Authentication of the sender. Telemetry is anonymous by design; forgery is limited, not prevented.
- Room events (EVENTS.md 3.4): CC-242 stores those, CC-176 counts them.

## Rabbit holes

- **Atlas storage.** At 100 000 events a day and about 200 bytes each, 30 days is about 600 MB before compression,
  over the free 512 MB. The documents are small and WiredTiger compresses them, but the cap and the TTL must be
  measured on a copy before the ramp passes 10 %. If the estimate is off, the cap goes down, not the TTL up.
- **`sendBeacon` and CSRF.** The route takes `text/plain`, so the existing CSRF rule (CC-030) needs an explicit,
  narrow exception for this one route, which changes no state a player owns.
- **Clock skew.** The server's hour is the only time stored. The client sends no timestamp.

## Instrumentation

Stores the events CC-174 sends and the server-side events listed above, counts tier only. Adds the ops counter
`telemetry.dropped` by `reason` (ADR-055, no player data). The flag's success event: a batch with at least one
stored event.

## Threat model

1. **What are we building:** a public, unauthenticated endpoint that writes to the shared database.
2. **What can go wrong:** storage exhaustion; forged events skewing the dashboard; text or ids smuggled into fields;
   XSS later when values are shown in the console; the endpoint used to learn who is an admin.
3. **What we do about it:** size, count, rate and daily caps; closed lists for every value, so nothing free-form is
   stored; the console renders values as text; always `204`, so the answer never says what was kept or why.
4. **Good enough?** Forgery within the limits stays possible and is accepted: the dashboard is for the owner's
   judgement, never for anything that pays out or ranks players. Revisit if any number is ever shown to players.

## Privacy checklist

- **Data:** anonymous events (catalogue fields only), about every visitor, guest and account.
- **Retention:** 30 days by TTL index; the owner can purge earlier.
- **Who sees it:** nobody directly; CC-176 totals and CC-177 shows them to the owner.
- **Minors (ADR-028):** no difference, since no event carries any id; GPC and DNT are honoured for everyone.
- **Defaults:** opt-out headers win over the flag and the client; the User-Agent and address are read in memory for
  the bot filter and the limiter and never stored or logged.

## Alternatives considered

- **Store into a hosted analytics product:** third party, against D15.
- **Write straight into daily totals with `$inc` and keep no raw events:** smaller, but any mistake in a rollup is
  permanent and new questions (CC-313's) cannot be asked of the last 30 days.
- **Reject the whole batch on any error:** one bad field from an old build would lose every event of that build.

## Research (written before any code)

1. **Our code today.** No ingestion route. The CC-110 limiter and ADR-035's keyed network hash exist and store no
   address. The console reads `matches` only (ADR-036.4). ADR-055 sends ops metrics to Grafana and scrubs ids; this
   ticket adds one counter there and keeps every product event in our own database.
2. **Other products.** Plausible ([data policy](https://plausible.io/data-policy), updated September 2026) never
   stores raw IP or User-Agent and discards query strings except campaign parameters; we keep that rule and store
   no hash either. PostHog's ingestion accepts any property and relies on project settings to drop data; we take the
   opposite, allowlist-only stance, because our catalogue is small and closed. Google's HEART paper (Rodden et al.,
   CHI 2010) warns that signals must map to a goal before they are collected; the catalogue is that mapping, and the
   validator enforces it.
3. **Best for ClassiCade.** An allowlist validator shared with the client, small hard limits sized to the free
   cluster, and an answer that never says what was kept.

## Build notes (2026-10-20, branch `cc-174-175-telemetry`, with CC-174 in one pull request)

1. **One pull request with CC-174.** The route without its client, or the client without its route, would be dead
   code, so both ship together, behind their own flags, both off.
2. **The India hour.** `received_at` is the start of the India hour, which starts at half past in UTC, so an hour
   never straddles two India days for the nightly totals (CC-176). `_id` is a random UUID, because an ObjectId holds
   the second it was made.
3. **Defence in depth.** The catalogue check, then the Mongoose schema with `strict: "throw"` on the same field list,
   so a key the catalogue does not have can never be written even by a mistake in the validator.
4. **Drop order and units.** GPC or DNT, an admin, a known bot, the flag off, then 30 batches per 10 minutes per
   network (`clientIpKey`, the CC-110 limiter, which keeps no address), then the body size (read first, as text,
   before the JSON parser), the event count, each event, the daily cap. `telemetry.dropped` counts one per batch for
   the whole-batch reasons and one per event for `invalid` and `cap` (DEPLOYMENT.md).
5. **The daily cap** is counted in the process, read from the database once per India day and at boot, and counted
   before each write so two batches cannot both take the last places. A second instance (CC-061) would share it in
   the database.
6. **Server events.** `guest_started`, `account_created` (`from_guest`), `login_succeeded` (`from_guest`),
   `login_failed` (`reason`), `session_ended` (`logout`, `password_changed`, `signed_out_elsewhere`) and
   `server_errored` (the API template and the code) go through `createServerEvents`, after the answer, with the same
   GPC, DNT, admin and flag rules. Not built, and refused by the catalogue: `login_succeeded.method` and `waited`
   (the login does not report a legacy move or a slow down yet), `account_created`'s two buckets (in the catalogue,
   not sent: they need a read of the guest's matches) and `session_ended`'s `expired_90_days` (the session guard).
7. **Seams for CC-176 and CC-177.** `telemetryAccessor.list({ from, to, limit })` reads a range oldest first for the
   nightly totals. The purge is the only admin route; the dashboard is CC-177's.
8. **Test names.** Each AC's test has the name in Acceptance criteria. AC-7's suite is
   `flagPaths("telemetry_ingest")` in `telemetryRoutes.test.js`.

## Review fixes (2026-10-21, the coordinator's review of #161)

1. **Counters, not events.** The coordinator, as design and privacy lead, decided that no single event is stored:
   one batch written in one insert with one hour put a visit's events next to each other, against "cannot be linked
   to each other". Each event is added to an hourly counter (`telemetry_counts`, one per tuple of catalogue fields and
   India hour, `$inc` on upsert, a random `_id`). The order and the batch disappear, storage shrinks and CC-176's
   rollup reads counters. AC-5's test now checks counters, and a new DAO test checks that nothing per event, in order
   or per batch is stored. Points 5 and 8 of the proposed solution read "counters" for "events".
2. **The switch reaches the server.** While the privacy switch is off the web app sends `X-CC-Counts: off` on every
   request, and the server records no event of its own (new guest, sign-up, logins, sessions, errors), as for GPC and
   DNT. The header is never stored or logged.
3. **Batch limit per session.** 600 batches per 10 minutes per session, per network for a visitor: ten times the
   client's one every 10 seconds, so long sessions and shared mobile networks keep their counts.
4. **Per-network day.** One network may have at most 2 000 events counted per India day (a fiftieth of the site's
   100 000), counted in memory like CC-110; the rest are dropped as `rate_limited`.
