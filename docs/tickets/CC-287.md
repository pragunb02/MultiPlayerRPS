## Root cause

`apps/server/src/server.js` calls `server.listen(port)` with no host, so Node binds every interface. On Render that
is required (the public web service), but a developer running `npm run dev:server` or `npm start` on a laptop also
exposes the server, its session cookie and the dev database behind it to the local network. Docker Compose already
publishes only on 127.0.0.1.

## Plan

1. Add `HOST` to config: default `127.0.0.1`, validated, documented in `.env.example` and DEPLOYMENT.md.
2. **Before merge, the owner sets `HOST=0.0.0.0` in Render** (otherwise production stops answering). The PR's
   Deployment impact lists it as an env var to set first.
3. Docker: the container sets `HOST=0.0.0.0` inside the image only, since its published port stays 127.0.0.1.
4. Tests: the default is loopback; the configured host is used; the e2e server stays on loopback.

## Research

Written 2026-10-20, before any code.

### 1. How our code does it today

1. `apps/server/src/server.js` (`listen`) calls `server.listen(port, callback)`. There is no host argument, and
   `apps/server/src/config/index.js` has no host setting.
2. `apps/server/src/index.js` logs `server listening` with the port only, so the log never says which address.
3. The `Dockerfile` sets `NODE_ENV`, `PORT` and `WEB_DIST_DIR`. `docker-compose.yml` publishes the app as
   `127.0.0.1:4000:4000` and MongoDB as `127.0.0.1:27017:27017`, so compose is already limited to this machine.
4. `e2e/app.mjs` builds its config with `loadConfig` and no host, so the browser test app also listens on every
   interface today. `e2e/tlsFront.js` (the HTTPS front) already listens on `127.0.0.1` and `::1` only.
5. `apps/server/src/testing/testApp.js` and `service/realtime/connections.test.js` already call
   `server.listen(0, "127.0.0.1")`. The integration tests that call `startServer` inherit the no-host bind.
6. Measured on `main` with `npm start` (see Verification): `lsof -nP -iTCP -sTCP:LISTEN` shows `*:4000`, every
   interface, IPv4 and IPv6.

### 2. How it works elsewhere (sources read 2026-10-20)

1. **Node `server.listen(port, host)`** (nodejs.org/api/net.html, docs for v26.12.0): "If `host` is omitted, the
   server will accept connections on the unspecified IPv6 address (`::`) when IPv6 is available, or the unspecified
   IPv4 address (`0.0.0.0`) otherwise." And: "listening to the unspecified IPv6 address (`::`) may cause the
   `net.Server` to also listen on the unspecified IPv4 address (`0.0.0.0`)" unless `ipv6Only: true` (default
   `false`). So our current call is a dual stack wildcard bind. `127.0.0.1` binds IPv4 loopback only, `::1` IPv6
   loopback only, and a hostname such as `localhost` is looked up first and Node binds the first address it gets.
2. **Render** (render.com/docs/web-services, no page date, footer 2026): "Every Render web service must bind to a
   port on host 0.0.0.0 to serve HTTP requests." Render recommends binding to the port in the `PORT` environment
   variable (default 10000). If Render cannot detect a bound port the deploy fails. So production needs
   `HOST=0.0.0.0` (or `::`, which also covers IPv4). Our health check means a failing deploy is not promoted, but
   it would still stop every later deploy from going live.
3. **The twelve-factor app** (12factor.net/config and 12factor.net/port-binding, read 2026-10-20): config that
   differs between deploys is stored in environment variables, "easy to change between deploys without changing
   any code", and the app "exports HTTP as a service by binding to a port". The bind address is exactly such
   per-deploy config: loopback on a laptop, all interfaces on the platform.
4. **Other Node servers:** Fastify (fastify.dev/docs/latest/Reference/Server, read 2026-10-20) listens on
   `localhost` when no host is given and advises `0.0.0.0` inside containers. Vite's dev server
   (vite.dev/config/server-options) defaults `server.host` to `localhost` and needs `--host 0.0.0.0` to be seen on
   the network. Express's `app.listen` passes straight to Node's `http.Server.listen`, so it has Node's wildcard
   default, which is what we inherited.
5. **Docker** (docs.docker.com/engine/network/port-publishing, read 2026-10-20): without a host address, Docker
   publishes a port on every host address (`0.0.0.0` and `[::]`). A process inside a container that binds
   `127.0.0.1` cannot be reached through a published port at all, so the image must bind all interfaces inside the
   container and let the publish (ours is `127.0.0.1:4000:4000`) be the boundary.

### 3. What is best for ClassiCade

1. `HOST` in the validated config, default `127.0.0.1`, like Fastify and Vite. A laptop is private unless someone
   asks otherwise. `127.0.0.1` rather than `localhost`, because `localhost` can resolve to `::1` first on some
   machines and the IPv4 tools and the e2e front connect to `127.0.0.1`.
2. Accept only an IPv4 or IPv6 address (`net.isIP`) or a hostname made of DNS labels. Anything else, an empty value
   included, fails the boot with the other config errors (ENGINEERING.md: no silent fallbacks). No production
   specific rule: the default is the documented contract, and Render is set by the owner before merge.
3. The startup log says the bound address and port, so a wrong bind is visible in the first log line.
4. The Docker image sets `HOST=0.0.0.0`, because the bind inside the container must accept the published port, and
   compose keeps that port on `127.0.0.1`.
5. The e2e app and the test servers stay on loopback. A test checks that the config the e2e app uses resolves to
   `127.0.0.1`.
6. Order on Render: the owner sets `HOST=0.0.0.0` in Render → Environment first. The current server ignores it, so
   the redeploy it causes changes nothing. Then the PR merges and the new server reads it.
