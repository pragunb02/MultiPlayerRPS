## Why

A draw offer showed up as a line of text in the chess side panel and a rematch request as text under the result.
Players missed both, the asker never learned that the answer was no, and a player in another tab had no idea it was
their move.

## Scope

- In: a popup (Accept, Decline, Hide) for a chess draw offer and for a rematch request in any game, a waiting card
  with Cancel for a draw offer (the rematch panel already shows "Waiting for…" with Cancel), toasts that tell the
  other side about a decline or a withdrawal, a chime for each, the tab title "Your turn! · ClassiCade" with a badged
  favicon while it is your move in a background tab.
- Server, kept small: chess actions `decline-draw` and `withdraw-draw` with `drawAnswer` in the chess view, and the
  socket event `room:rematch-decline` with `rematch.declinedBy` in the RoomView.
- Out (follow-ups): takebacks (the engine would need to undo moves and clocks, which is not simple, so it needs its
  own ticket), a limit on how often one player may offer a draw, and showing the waiting card on phones without
  scrolling up (it sits above the board).

## Acceptance criteria

- [x] The player asked gets a popup with Accept and Decline, announced (the question is a `role="alert"`). Focus
      stays where the player has it, so keyboard chess goes on; Escape inside the popup hides it. The popup sits in
      the page above the board and never covers a square, on phones too. (Changed while integrating: it first took
      focus and floated at the bottom of the screen, over a phone's bottom ranks.)
- [x] Chess draw offers are answered only in the popup. The side panel keeps "Offer draw", disabled while an offer
      stands.
- [x] The "declined" message goes away when the rematch starts.
- [x] The asker sees "Waiting for <name>…" with Cancel. Declines and withdrawals are shown to the other side.
- [x] The popup has no backdrop, so the board stays usable. Hide (or Escape inside it) puts it away. It closes by
      itself when the request ends (answered, withdrawn, opponent left, game over) and comes back the same after a
      reload.
- [x] Background tab: the title alternates every second and the favicon gets a badge until the tab is visible or it
      stops being your move.
- [x] Unit, socket and browser tests for all of the above.

## ADR-019 (accepted 2026-10-17, recorded in DECISIONS.md): requests between players are derived from the RoomView

Context. Draw offers and rematch requests already live in server state (the chess engine's `drawOfferBy`, the room's
`rematch.requestedBy`). Popups could be driven by new push events, but those are lost on a reload and would duplicate
state the view already carries.

Decision.

1. A request is a plain object (`RoomRequest` in `games/roomUpdates.js`) computed from the current RoomView: who
   asked, the texts, and what Accept, Decline and Cancel do (a game move, or the rematch events). Games add their own
   requests and notices through the client game registry (`requests`, `notices`), so the room page never names a
   game.
2. How a request ended is part of the state: `drawAnswer` ("declined" or "withdrawn") in the chess view and
   `rematch.declinedBy` in the RoomView. Notices are worked out by comparing the view before and after an update,
   so they follow every kind of update and nobody is told about their own answer.
3. Moving instead of answering still declines a draw offer, as before, and now says so to the offerer.

Consequences. A reload shows the same popup with no chime. Rooms and chess games stored before this change (rooms
live in MongoDB since CC-101) have no `declinedBy` or `drawAnswer`. The server's views read that as nobody, and so
does the client. Declining runs through the room component's versioned `change({ decide })` like every other room
change, and answers GONE once the rematch window has ended.
