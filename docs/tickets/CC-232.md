## Why

Production runs on Render's free plan (ADR-005). The instance sleeps after 15 minutes without traffic and takes
about a minute to wake. ADR-005 accepted that some first visits still wait, on the condition that the wait says what
is happening. Today a visitor sees a blank white page until the app's JavaScript has downloaded and run (the
investigation of 17 October measured 7.2 s on slow 3G before anything paints), and then plain "Loading…" text
while the session check is outstanding.

## Research

### How our code does it today

1. `apps/web/index.html` has an empty `<div id="root"></div>`. Nothing paints until `main.jsx` runs, because the
   page is rendered only in the browser. The investigation
   ([2026-10-17-cross-browser-a11y-load.md](../investigations/2026-10-17-cross-browser-a11y-load.md) §4) measured
   first paint at 0.1 s unthrottled, 1.2 s on 4G, 2.5 s on 3G and 7.2 s on slow 3G, for a 122 KB (gzip) main chunk.
2. The server (`apps/server/src/service/http/webApp.js`) sends that same `index.html` for every page, with only the
   head tags changed (CC-047). The body passes through untouched, so anything we put in the body reaches every page.
3. The server only starts listening after MongoDB is connected (`server.js`, `connectDatabase` then `listen`). So
   while the instance wakes, nothing of ours can answer at all.
4. After the app renders, `SessionProvider` asks `/api/session`. While that is outstanding the header hides the
   sign-in links, the home page's Play button says "Checking whether you are signed in", and the profile and room
   pages say "Loading…". Nothing says that the server may be slow, or why.
5. The CSP (`requestGuards.js`) is `script-src 'self'`, `style-src 'self'`: no inline script, no inline style, no
   `style` attribute. Vite already puts a `<link rel="stylesheet">` for the built CSS in the head, so that CSS is
   loaded before the body paints. That is the one place a pre-JavaScript screen can get its look from.
6. `global.css` turns every animation off with `!important` under reduced motion (ADR-012 rule 4).

### What the browser shows while Render wakes (what we can and cannot control)

1. Render's documentation for free web services (render.com/docs/free, read 18 October 2026) says the service
   "spins back up whenever it next receives an HTTP request or new WebSocket connection", "This process takes about
   one minute", and "Render displays a loading page to connecting browsers while a service is spinning up."
2. So on a true cold start the first thing a visitor sees is **Render's own page, not ours**. Our HTML does not
   exist yet: the process that would send it is still starting. Render's documentation offers no setting to change
   or brand that page, and its changelog (read the same day) has no entry about one. We cannot style it, translate
   it, or put our words on it. Confidence: high for "it is Render's page", medium for "it cannot be customised" (no
   documented option found).
3. API requests that arrive while it wakes wait until the process answers (the same is true of Fly.io's proxy:
   "When a request arrives and no Machine is running, Fly Proxy starts a stopped Machine and routes the request to
   it", docs.fly.io/launch/autostop-autostart, read 18 October 2026). That is the case our in-app screen covers: a
   tab that has the page but whose `/api/session` call is held while the server starts, for example after a deploy
   or a restart, or a reload just as the instance went to sleep.
4. What would put our own screen in front of a cold start, and why this ticket does not do it:
   1. **Serve the web app from a static host** (Render static sites are served from a CDN and do not sleep). The
      HTML and the loading screen would then always be instant, and only the API would wake. This splits the single
      deploy of ADR-002 into two, needs cross-origin or proxy work for cookies and the socket, and is a hosting
      decision. It belongs with CC-028 (always-on hosting) and needs an ADR.
   2. **A service worker** that caches the app shell, so a repeat visitor's browser shows our screen without asking
      the server. That is a caching layer with real risks (stale builds after a deploy, see CC-181), and a new
      decision. Not in scope.
   3. **Cache the HTML at the edge** (Cloudflare in front of Render). The investigation found the edge does not cache
      even hashed assets (`cf-cache-status: DYNAMIC`), and we do not control Render's Cloudflare. Not possible today.
   4. The uptime monitor (CC-049) already keeps the instance awake most of the time, which removes most cold starts.

### How other products handle long first loads

1. **Gmail and Google Docs** (general knowledge, high confidence) put a loading screen straight into the HTML the
   server sends: a logo and a progress bar that paint before the main script runs, removed by the app when it
   starts. Our case is the same pattern without the script part, because React clears the root on its first render.
2. **React's own documentation** (react.dev/reference/react-dom/client/createRoot, read 18 October 2026): "The first
   time you call `root.render`, React will clear all the existing HTML content inside the React root before
   rendering the React component into it." So markup placed inside `#root` disappears exactly when the app's first
   render is committed, with no code of ours.
3. **Streamlit Community Cloud** (docs.streamlit.io, read 18 October 2026) shows a sleeping page that says what
   happened in plain words: "This app has gone to sleep due to inactivity", with a button to wake it. It tells the
   visitor why they wait. Hugging Face Spaces and Glitch (general knowledge, medium confidence) do the same with
   "Building" and "Waking up" pages.
4. **Nielsen Norman Group, "Progress Indicators Make a Slow System Less Insufferable"** (nngroup.com, 26 October
   2014): no indicator is needed under about 1 second (a loop that short only distracts), a looped
   animation fits 2 to 10 seconds, waits over 10 seconds need more than a loop, static "Loading…" text should be
   avoided because it does not show the system is still working, and the text should explain why the user waits.
5. **Delayed spinners** (general knowledge, high confidence): design systems and React's Suspense guidance hold a
   loading indicator back for a few hundred milliseconds, so a fast answer never flashes one. A CSS
   `animation-delay` does this without any script.

### What is best for ClassiCade

1. **A static screen inside `#root` in `index.html`**, styled only by the built CSS file that is already in the
   head. It paints as soon as the HTML and CSS arrive, before any JavaScript, and React removes it on its first
   render. No client code, nothing to fail, nothing for the CSP to block.
2. **Shown only after 0.6 s**, with a CSS animation delay that also hides it from screen readers until then
   (`visibility`). A warm visit renders in well under that, so the screen never flashes. With reduced motion the
   same delay still applies (one step, no movement), because otherwise `global.css` would show it at once.
3. **Honest words for each wait.** Before the app runs, the wait is the download: "Waking up the arcade… Getting the
   games ready." In the app, the wait is the server: "Waking up the arcade… Free servers take a moment to wake up."
   After 10 seconds a second line appears in both (NN/g): "Still waking up. This can take up to a minute, and the
   page carries on by itself." When the app starts after the page's line appeared, the app's copy shows its line at
   once (`wake-waited-long`), so it does not vanish for another 10 s. After 90 s, half a minute past the slowest
   wake, the page's screen adds "Still nothing after all this time? Reload the page", a plain link (`href=""`) that
   needs no script. By then the app's main script most likely failed to load (a dropped connection, a blocker, a
   throw before the first render), and only a reload helps.
4. **The same look in the app**, as one component (`WakingUp`) that the layout shows while the session check is
   outstanding, with the same delay. It reuses the same CSS classes as the static screen, so there is one drawing.
5. **Arcade style per ADR-012**, CSS only: a cabinet whose screen powers on (a bright line that opens into the
   screen, as old monitors did), marquee lights, and "Insert coin" blinking. Only `transform` and `opacity` move.
   ADR-012 says nothing loops forever: the blink runs 40 times (about a minute, the longest cold start) and then
   stays lit. With reduced motion nothing moves and the text says everything.
6. **Crawlers read the page, not the loading screen.** Crawlers and preview bots that run no scripts read the body
   text as what the page is about. So the static screen starts with the page's own title (an `h1`) and description,
   which the server writes in for each page, the same text as its head tags (CC-047, `createPageTemplate` fills the
   tags marked `data-server-body`, and refuses a build without exactly one of each). People see them as a small
   header above the cabinet. The `<noscript>` line moved after `#root`, so it is not the first text either.
7. **Accessible**: `role="status"` with the words as text, the drawing `aria-hidden`, and a `<noscript>` line for
   browsers without JavaScript, so they are not told to wait forever.
8. **Not done here**: retrying a failed session check on its own (it lives in `SessionProvider`, which the security
   batch #57 is changing), a static host or service worker (above), and the shared Render page (not ours).

## Scope

- In: the static screen in `index.html`, its CSS, the in-app `WakingUp` while the session check waits, unit and
  browser tests.
- Out: Render's own wake page, static hosting, service workers, automatic retry of a failed session check.

## Acceptance criteria

- [x] The screen is in the HTML the server sends and needs no JavaScript or inline style
- [x] It appears only after a short delay, so a warm visit never flashes it
- [x] It goes as soon as the app renders
- [x] While `/api/session` is slow, the app shows the same screen until it answers
- [x] Reduced motion: nothing moves, the delay still applies, the words are all there
- [x] `role="status"` and text, drawing hidden from screen readers
- [x] Tests cover the change (unit for the component, browser tests that delay the server and a warm-load check)
- [x] `npm run lint`, `npm run format:check`, `npm test` pass
