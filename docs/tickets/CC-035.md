## Research (written before any code)

### 1. How our code does it today

1. There is no way to delete an account or to get a copy of one's data. The privacy page (section 7) tells the
   player to ask the owner through a GitHub issue. `accounts` rows are kept for ever (DATA.md, `accounts`).
2. What a deletion has to cover, store by store, from [DATA.md](../DATA.md) at `61b3bb2`:

   | Store                       | Holds for the account                                                                              | Today                               |
   | --------------------------- | -------------------------------------------------------------------------------------------------- | ----------------------------------- |
   | `accounts`                  | username, email, scrypt hash, created, session version                                             | kept for ever                       |
   | `users` (legacy, read only) | username, email, bcrypt hash, legacy level                                                         | read only on purpose (CC-078)       |
   | `player_sessions`           | identity (id, display name) of every signed-in browser                                             | 30 day TTL, logout                  |
   | `rooms`                     | seats, host id, moves with times, result, rematch, series                                          | 30 minutes to 24 hours              |
   | `matches`                   | the player's id and name in `players`, the log, the result and `credit`. Shared with the opponent. | for ever                            |
   | `player_progress`           | XP and totals, and guest markers with `mergedInto: <account>`                                      | for ever                            |
   | `player_stats`              | results, streaks, the last day played                                                              | for ever                            |
   | `player_achievements`       | one row per unlock                                                                                 | for ever                            |
   | `player_quests`             | quest days                                                                                         | 8 day TTL                           |
   | `leaderboard_entries`       | username, level and score, public                                                                  | all time for ever, weekly 28 days   |
   | `player_transfers`          | guest id to account id and username                                                                | for ever                            |
   | server memory               | login throttle (email and addresses), rate limit counts                                            | up to 30 days, lost on every deploy |
   | server logs (Render)        | player ids, never emails                                                                           | 7 or 14 days                        |
   | backups                     | everything above                                                                                   | 30 days                             |

3. **Finding F6 and F7** of CC-241 (DATA.md says "Where this file and the privacy page disagree"): the privacy page
   says rooms "live only in the server's memory" (they are in MongoDB since CC-101) and does not mention the 30 day
   backups, the login throttle's addresses, or that guest data is kept for ever. This ticket rewrites sections 2, 6
   and 7 of the page, so it fixes the parts it touches: backups and how long deleted data stays in them, and the
   rooms line.
4. Signing in already re-checks every account session on each request (CC-116). `sessionVersionOf` throws
   `NotFoundError` for an account that is gone and the session guard turns that into "signed out". So deleting the
   `accounts` row signs out every browser on its next request without any new code. The rows in `player_sessions`
   would stay until their TTL, still holding the username, so deletion removes them too.
5. A guest's move to an account (ADR-014) already shows the pattern to copy: every component that stores data by
   player id exposes `transferPlayer`, and `playerTransferComponent` runs them in order, records progress and
   resumes after a crash. Deletion can be built the same way: each component exposes `erasePlayer`, one component
   runs them in order, and a record lets housekeeping finish a deletion that stopped half way.
6. **The legacy row.** A legacy player's account is created at their first login from the `users` row with the
   same email (CC-078). If deletion only removes the `accounts` row, the next login with the old password finds no
   account, finds the legacy row and creates the account again. The legacy DAO must stay read only. So the server
   needs its own note that a legacy row was closed.
7. **Games still running.** A player can be seated in a room when they delete. If the room keeps their id, a game
   that ends later is recorded under it and the match pipeline writes progress, stats and even a leaderboard row
   with their username again, after the erasure.

### 2. The law and how other products do it

Sources fetched on 2026-10-18 unless a date is given.

**India, the DPDP Act 2023 and the DPDP Rules 2025.**

1. Section 12(3) of the Act: on a request, the Data Fiduciary "shall erase her personal data unless retention of the
   same is necessary for the specified purpose or for compliance with any law" (https://www.dpdpa.com/dpdpa2023/chapter-3/section12.html).
   Section 8(7) also asks for erasure when consent is withdrawn or the purpose is served.
2. The Rules were notified on 14 November 2025 (https://en.wikipedia.org/wiki/Digital_Personal_Data_Protection_Rules,_2025).
   The Data Protection Board parts applied at once, consent managers from 13 November 2026, and everything else,
   including the rights and the erasure rules, from **13 May 2027** (https://en.wikipedia.org/wiki/Digital_Personal_Data_Protection_Act,_2023).
3. Rule 14: a fiduciary must publish how a person can make a rights request, and answer grievances "within a
   reasonable period not exceeding ninety days" (https://www.dpdpa.com/dpdparules/rule14.html).
4. Rule 8(1) and (2): erase data when the purpose is served, and for the classes in the Third Schedule (large
   e-commerce, online gaming and social media intermediaries) after three years without use, with **48 hours'
   notice** first. Rule 8(3): keep "personal data, associated traffic data and other logs" of processing "for a
   minimum period of one year" for the purposes of the Seventh Schedule (https://www.dpdpa.com/dpdparules/rule8.html).
   **Rule 8(3) conflicts with our 7 to 14 day Render logs from 13 May 2027.** That is a question for the lawyer's
   review (PRODUCT_VISION.md §6.10), not for this ticket: our logs hold ids, not names or emails.
5. The Act has no data portability right. Export is a GDPR and good practice item, and it also answers the
   Section 11 right to a summary of the data processed.

**GDPR, the reference pattern.**

1. Article 17: erase "without undue delay" when consent is withdrawn or the data are no longer needed. 17(2): when
   the data were made public, take reasonable steps to tell others. 17(3): exceptions for legal claims, legal
   obligations and some archiving (https://gdpr-info.eu/art-17-gdpr/). Our public data is the leaderboard row, and
   only we publish it, so removing the row is enough.
2. Article 20: data the person provided, "in a structured, commonly used and machine-readable format", and 20(4):
   it "shall not adversely affect the rights and freedoms of others" (https://gdpr-info.eu/art-20-gdpr/). So an
   export holds the player's own data and the game records they took part in, but not the opponents' player ids.

**App stores, the practical bar.**

1. Apple, guideline 5.1.1(v): deletion must be possible inside the app, deactivation alone is not enough, it may
   confirm intent and identity, it must not be "unnecessarily difficult", no email or phone call to support, and
   if it is not immediate the person is told how long it takes
   (https://developer.apple.com/support/offering-account-deletion-in-your-app/).
2. Google Play: an in-app path and a web link, delete the data linked to the account, and say in the privacy policy
   what is kept and why (https://support.google.com/googleplay/android-developer/answer/13327111).

**Games.**

1. Lichess: requests by email, and it may "proceed with their complete and irreversible anonymization" instead of
   deleting. Games are kept for the history and statistics of everyone else (https://lichess.org/privacy).
   Lichess also offers a personal data download page while signed in.
2. Supercell: deletion is asked through in-game support, identity may be checked first, unused accounts are
   de-identified over time, and data is kept where there is "a business need, such as for legal compliance, dispute
   resolution" (https://supercell.com/en/privacy-policy/).
3. Epic and Chess.com refused automated reading on 2026-10-18 (403 and 404). From memory, not checked today: Epic
   deletes after a waiting period of about two weeks, and Chess.com closes the account first and keeps games in
   opponents' histories. **The owner should check these two before quoting them.**
4. What they share: identity is checked again (a password, an emailed code, a receipt) before deleting, and the
   opponent's copy of a shared game is kept, with the person removed or anonymised.

### 3. What is best for ClassiCade

1. **Immediate deletion, no grace period.** A grace period protects players from a mistake or from someone using
   their unlocked phone. We ask for the password again and show exactly what goes, which covers both. A grace period
   would need a way to tell the player it is ending (we have no confirmed email, CC-033) and would keep everything
   for 7 to 30 more days. Owner to confirm.
2. **Re-authentication.** The password again, in the same form as the deletion. Wrong passwords count against the
   same per-account limit as a password change (5 in 15 minutes), so a borrowed signed-in browser cannot guess it.
3. **Delete or anonymise, store by store.** Deleted: the account, its sessions, progress (and the guest markers that
   point at it), stats, achievements, quests, leaderboard rows, guest transfer records. Matches: a match nobody else
   played (against a computer character, or a game whose other seats were the same player) is deleted. A match with
   another person stays in their history, with the deleted player's id replaced by a new random id for each match and
   the name "Deleted player". A new id per match means the anonymous matches cannot be put back together into one
   person's history.
4. **Rooms.** Every room the player sits in is handed to that same kind of anonymous seat first, then the seat leaves:
   a running game is forfeited (the opponent gets the win and the match is recorded with "Deleted player"), a
   waiting seat is given up, a finished room loses its rematch. An anonymous seat earns nothing: no progress, stats,
   quests or board rows are written for it. Without this, a game that ends later would write the player's data back.
5. **The legacy row stays untouched, and is closed.** The server stores the legacy row's MongoDB id (not its email)
   in a new `legacy_closures` collection. A login whose email only matches a closed legacy row fails with the usual
   "Invalid email or password". Signing up with that email works again and makes a new, empty account, since it no
   longer claims the old one. The legacy document itself keeps its data, as it does today for every migrated player,
   until the owner removes the legacy collection (DATA.md, `users`). Owner to confirm.
6. **Finishing for sure.** An `account_deletions` record, written first, holds the player id, when it was asked and
   when to sweep again. Housekeeping sweeps every record again 5 minutes later. That finishes a deletion the server
   could not complete (a crash or a deploy) and removes anything a game that was finishing at that very moment
   wrote. The record is removed by a TTL index after 30 days. It names an id that leads nowhere any more, and it is
   what an owner restoring a backup uses to delete those accounts again (runbook).
7. **Backups.** Deleted data stays in the encrypted nightly backups for up to 30 days and then ages out. The privacy
   page says so. A restore brings deleted accounts back, so the runbook keeps `account_deletions` and
   `legacy_closures` from the live database and sweeps again after a restore.
8. **Export.** A JSON file of the player's own data, by `POST /api/account/export` with the password (the export holds
   the email, which no client sees today). Matches name the player as "you" and other people by their display name
   only, never their ids. At most 3 exports an hour per account.
9. **Not in scope:** deleting guest data (a guest has no password, CC-098 removes old guest data), deleting or
   exporting the legacy row's own data (read only), Render's logs (ids only, 7 to 14 days) and the in-memory login
   throttle (lost on the next deploy, at most 30 days).

## Why

FR-ACC-7. A player must be able to leave and take their data with them, without writing to the owner. Required by
the app stores, expected under the DPDP Act from 13 May 2027 and the GDPR, and promised by our privacy page.

## Scope

- In: deletion with the password, export with the password, the legacy closure, the 5 minute sweep, the privacy
  page, DATA.md, the backup runbook, tests at every level.
- Out: grace period, emailed confirmation (CC-033), guest data (CC-098), deleting the legacy collection.

## Acceptance criteria

- [x] `POST /api/account/delete` with the password removes or anonymises every store in DATA.md for that account,
      ends every session and socket of it, and answers 204.
- [x] A shared match stays in the opponent's history with "Deleted player".
- [x] A deleted legacy player cannot log in through the legacy row again, and can sign up afresh.
- [x] `POST /api/account/export` with the password downloads the player's own data as JSON, at most 3 an hour.
- [x] The privacy page and DATA.md say what is deleted, what is anonymised, and the 30 days in backups.
- [x] Unit, MongoDB integration and browser tests.
- [x] `npm run lint`, `npm run format:check`, `npm run test:coverage` pass.

## Plan / notes

Decision record: ADR-047 (accepted by default, owner may change).

1. **Server, five layers.**
   1. Persistence: `accountDao.deleteById`, `matchDao.deleteForPlayer`, `progressDao.deleteByPlayer` (with the guest
      markers), `leaderboardDao.listByPlayer` and `deleteByPlayer`, `playerTransferDao.listByTo` and `deleteByTo`,
      `questDao.listByPlayer`, `legacyUserDao` now also answers the row's `legacyId`, a new `accountDeletionDao`
      (`account_deletions` with a 30 day TTL, `legacy_closures`) and a new `sessionDao` (deletes
      `player_sessions` by `session.identity.id`). Every one has a contract run against MongoDB and its double.
   2. Data: the matching accessor methods, `createAccountDeletionAccessor`, `createSessionAccessor`.
   3. Domain: `erasePlayer` and `exportPlayer` on matches, progression, gamification, leaderboards and guest
      transfers. `roomComponent.erasePlayer` hands each seat to a stand-in who leaves. `accountComponent` gains
      `confirmPassword` and `close` (closes the legacy row, deletes the account), and refuses a login through a
      closed legacy row with the usual answer. `playerDataComponent` runs `deleteAccount`, `exportFor` and the
      housekeeping `sweepDue`. `models/deletedPlayer.js`: the stand-in, and `earnsNothing`, which progression,
      gamification and fair play judging now use instead of only skipping computer characters.
   4. Service: `POST /api/account/export` and `POST /api/account/delete`, both `{ password }` only. Wrong passwords
      count 5 per 15 minutes per account for both together. Exports 3 an hour per account. Deletion destroys this
      session, clears the cookie and disconnects every socket of the account (`gateway.disconnectPlayer`).
   5. Composition root: participants in the order rooms, sessions, matches, progress, gamification, leaderboards,
      guest transfers. Housekeeping sweeps deletions every minute.
2. **Web.** A "Your data and privacy" section on the profile of an account: "Download my data" (password, a JSON
   file saved through the injected `download` service) and "Delete my account" (password, then a question that says
   what goes and what stays, Escape or "Keep my account" cancels). After deletion the profile says so and the
   browser is signed out like a logout.
3. **Docs.** ADR-047, DATA.md (new rows and sections only, at the coordinator's request, because CC-248 rewrites the
   rest), the privacy page (one new section, nothing else reworded, same reason), the backup runbook (deleting again
   after a restore).
4. **Left for CC-248** (it is rewriting the privacy page and DATA.md now): the sentence in section 7 of the privacy
   page "Until a delete button exists, ask the owner" is no longer true; the date at the top; and the "Deleted by"
   cells of the existing DATA.md rows. The exact wording needed is in the PR body under "Privacy page".
5. **Found along the way:** under full parallel load on this machine, integration tests that start the real server
   can take more than 5 seconds. Not caused here (the server starts in about 2 seconds alone, the deletion DAO adds
   its two indexes in parallel). CI is the judge.
