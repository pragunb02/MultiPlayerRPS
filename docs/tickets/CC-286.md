## Why

Logs live only in Render (7 to 14 days, hard to search) and there are no metrics dashboards or alerts beyond the
uptime check. The owner asked (2026-10-20) whether Grafana could carry metrics and logs.

## Research (written before any code)

Written 2026-10-20. Every web source was read on that date. Measurements were made on that date on the owner's
machine, with the scripts kept outside the repository (they are described below so they can be repeated).

### 1. How our code does it today

1. **Logs.** `apps/server/src/utils/logger.js` builds one pino 10 logger that writes JSON lines to stdout. Render
   collects them and keeps them 7 days on Hobby, 14 on Pro (DATA.md, Server logs). Redaction is by key (`password`,
   `token`, `sessionId`, `email`, `secret`, cookie and authorization headers). A value inside a message or an error
   string is not caught (DATA.md finding F10, CC-241). The lines hold pseudonymous data on purpose: player ids,
   socket ids, room codes, match ids, account events (DATA.md, Server logs, point 1.2).
2. **HTTP timing.** `service/http/requestLogger.js` writes one `request completed` line per request with method,
   path (no query), status, `durationMs` and the error code. The path is the raw path, so it can hold a room code.
   There is no route template and no aggregate.
3. **Socket timing.** None. Every client event goes through one function, `registerHandlers` in
   `service/realtime/acknowledgements.js`, which already knows the event name, the outcome (`ok`, a typed error
   code, or `socket handler failed`) and the rate-limit refusal. It is the natural place for a timer.
4. **Gauges and alert lines.** The composition root (`apps/server/src/server.js`) logs `room gauge` every minute
   (rooms per game and status, open total, connections; ADR-035) and `match pipeline failed` with `alert: true`
   when an outbox record gives up after 10 attempts (ADR-047). Nothing reads either line; CC-049 lists both as
   alerts still to build.
5. **Uptime.** A GitHub Actions schedule every 10 minutes, incidents as issues (ADR-043). It sees "down", not
   "slow" or "failing for some players".
6. **Event-loop lag and memory.** Not measured. The instance has 0.1 CPU and 512 MB (Render compute plans,
   https://render.com/docs/compute-plans), so both matter most on this plan.
7. **The rules that bind this ticket.** ADR-034: product analytics stay first party, anonymous counts only. The
   privacy page (section 5) names three processors (Render, Atlas, GitHub) and says "no third party analytics". The
   DATA.md rule: anything stored somewhere new updates DATA.md and the privacy page in the same pull request. CC-252
   owns the log retention decision (DPDP rules, one year from 13 May 2027). CC-240 wants server timing of every
   socket event and route, with no identity, for trends.

### 2. OpenTelemetry for Node 24

1. **Status of the signals.** Traces and metrics are stable in OpenTelemetry JavaScript, logs are "Development"
   (https://opentelemetry.io/docs/languages/js/). Every active or maintenance LTS of Node is supported, so Node 24
   is. Versions installed for the measurements: `@opentelemetry/sdk-node` 0.223.0, `sdk-metrics` 2.12.0,
   `auto-instrumentations-node` 0.81.2, `instrumentation-http` 0.223.0, `instrumentation-express` 0.71.1,
   `instrumentation-socket.io` 0.70.0, `instrumentation-pino` 0.69.0, `instrumentation-runtime-node` 0.36.1
   (npm, 2026-10-20).
2. **ES modules need a loader hook.** Our server is ESM (`"type": "module"`). Auto-instrumentation of ESM needs
   `node --experimental-loader=@opentelemetry/instrumentation/hook.mjs --import ./telemetry.js`; the docs call ESM
   support "ongoing" and the flag experimental
   (https://github.com/open-telemetry/opentelemetry-js/blob/main/doc/esm-support.md). That changes Render's start
   command, and it monkey-patches `http`, `express`, `socket.io` and `pino` at load time.
3. **Metrics without auto-instrumentation.** `@opentelemetry/api` + `sdk-metrics` + an OTLP exporter let our own
   code create histograms, counters and gauges. No loader hook, no patching. The SDK has an attribute allowlist per
   instrument (`createAllowListAttributesProcessor` in a View) and an `InMemoryMetricExporter` for tests (both
   exported by `sdk-metrics` 2.12.0, read in its `index.d.ts`). The minimal set (API, sdk-metrics, sdk-logs,
   resources, the two OTLP/HTTP exporters) installs 12 `@opentelemetry` packages and no other dependency, 28 MB on
   disk, `npm audit` 0 vulnerabilities (measured 2026-10-20).
4. **Logs: the pino bridge.** `@opentelemetry/instrumentation-pino` does two things: it adds `trace_id` and
   `span_id` to log lines when a span is active, and it adds a destination that sends every record to the Logs SDK
   (`disableLogSending`, `disableLogCorrelation` options; pino `>=5.14 <11`, so pino 10 is covered)
   (https://github.com/open-telemetry/opentelemetry-js-contrib/tree/main/packages/instrumentation-pino). It needs
   the loader hook above, and it sends **every** line with all its fields: player ids, socket ids and room codes
   included. Our logger already takes a `destination` (tests pass an in-memory stream), so the same result without
   patching is a second pino destination of our own that keeps only allowlisted lines and fields and hands them to
   the Logs SDK.
5. **What auto-instrumentation would export about players** (read in the installed source on 2026-10-20):
   1. `instrumentation-http` puts on every server span `client.address` (from `X-Forwarded-For`, the player's
      real IP behind Render), `network.peer.address`, `user_agent.original`, `url.path` (room codes) and `url.query`
      (`build/src/utils.js`, `getIncomingRequestAttributes`). Its metrics keep only method, scheme, route, status
      and error type.
   2. `instrumentation-socket.io` puts `messaging.socket.io.rooms` on every emit span: the list of Socket.IO rooms
      the emit goes to (`build/src/socket.io.js`). Our gateway joins each socket to `session:<sessionId>`,
      `player:<playerId>` and `room:<code>` (`gateway.js` line 174, `roomHandlers.js`). So the default
      instrumentation would ship **the session id**, a secret that signs a player in, plus player ids and room
      codes, to the vendor on every broadcast.
   3. The default resource detectors add `host.name`, `process.command_args`, `process.owner` and similar.
      This is the concrete reason the ADR uses allowlists and our own instruments, not the defaults plus a denylist.
6. **Cost on a 512 MB, 0.1 CPU instance.** Measured 2026-10-20 with a small Express 5 + Socket.IO 4.8 + pino 10
   app (one route, one acknowledged socket event, one log line each, logs to `/dev/null`), exporting to a local
   OTLP sink: 20 000 HTTP requests from 10 connections, then 5 000 socket events one after the other, memory read
   after a forced GC. Two settings, Node 24.21 in both:
   1. **Linux container with Render free's limits** (`docker run --cpus 0.1 --memory 512m node:24-slim`). The load
      generator shares the 0.1 CPU, so absolute numbers are pessimistic; compare the rows.

      | Mode                                                                  | RSS idle | RSS after load | JS heap after | Peak HTTP rate | CPU per HTTP request |
      | --------------------------------------------------------------------- | -------- | -------------- | ------------- | -------------- | -------------------- |
      | No telemetry                                                          | 59-70 MB | 67-74 MB       | 12 MB         | 351-357 /s     | 196-200 µs           |
      | Our own metrics only (no hook, no patching)                           | 74 MB    | 78 MB          | 15 MB         | 286 /s         | 250 µs               |
      | http + express + socket.io + pino + runtime instrumentations, metrics | 93 MB    | 95 MB          | 19 MB         | 101 /s         | 825 µs               |
      | The same plus logs                                                    | 94 MB    | 98 MB          | 21 MB         | 102 /s         | 834 µs               |
      | The same plus traces (100 % sampled)                                  | 87 MB    | 100 MB         | 21 MB         | 93 /s          | 907 µs               |
      | `getNodeAutoInstrumentations()` (every instrumentation), all signals  | 80 MB    | 107 MB         | 28 MB         | 153 /s         | 559 µs               |

   2. **macOS, unthrottled** (best of two runs): no telemetry 77 MB idle, 43 µs a request; our own metrics 82 MB,
      44 µs; the loader hook alone (nothing instrumented) 98 MB and half the peak HTTP rate (20 000 to 10 000 a
      second); the five instrumentations about 115 MB idle and 90 to 98 µs a request; every instrumentation 122 MB
      and 108 to 163 µs. macOS reported about 300 MB resident after the burst for every instrumented mode while the
      JS heap stayed under 37 MB; Linux did not show it (rows above), so it is read as the macOS allocator keeping
      freed pages, not a leak.

   Findings: memory is not the problem on Linux: auto-instrumentation adds about 25 to 35 MB, our own metrics
   about 5 to 15 MB. **CPU is.** On 0.1 CPU the instrumented server answered about a third as many requests as the
   plain one (93 to 153 a second against about 350), with three to four times the CPU per request. Our own metrics
   cost about a fifth of the peak rate in the same setting, and nothing measurable unthrottled. Our real load is
   far below either peak today, but the instance has no CPU to spare when a burst or a slow chess move comes.

### 3. Export: straight to Grafana Cloud, or through a Collector

1. Grafana Cloud takes OTLP over HTTP at `https://otlp-gateway-<region>.grafana.net/otlp`; the SDK adds
   `/v1/metrics`, `/v1/logs`, `/v1/traces`. Authentication is a token from the stack's OpenTelemetry tile, passed in
   `OTEL_EXPORTER_OTLP_HEADERS` as `Authorization=Basic <base64 of instance id:token>`. `OTEL_SERVICE_NAME` is
   required (https://grafana.com/docs/grafana-cloud/send-data/otlp/send-data-otlp/).
2. Grafana recommends a Collector (Grafana Alloy) in production for reliable transport, sampling, redaction and
   routing, and describes direct export "where a Collector can't be deployed" (same page).
3. **We cannot run a Collector for free.** Render's free plan has only web services (plus free Postgres and Key
   Value); "Other service types don't support Free instances", there is no private network on free, and one
   instance only (https://render.com/docs/free). A Collector as a second free web service would be public and
   would sleep. A sidecar in our container would share our 512 MB.
4. **So: direct export, with the Collector's jobs done in process.** Redaction is the allowlist and scrubber in the
   app (section 6). Sampling is not needed for metrics. Transport: the periodic metric reader retries a failed
   push; a lost minute of metrics is acceptable. On shutdown the server flushes once (Render sends SIGTERM and
   waits). A Collector becomes worth it with paid hosting or a second instance (CC-028, CC-061).

### 4. Grafana Cloud free tier

1. **Limits** (https://grafana.com/pricing/, 2026-10-20): metrics 10 000 active series a month, logs 50 GB a month,
   traces 50 GB a month, profiles 50 GB a month, **14 days retention** for each, 3 active Grafana users a month,
   3 incident (IRM) users, 100 000 synthetic API checks a month. "No credit card required", "No charges ever".
   Dashboards and folders are hard-limited at 1 000 each per free stack
   (https://grafana.com/docs/grafana-cloud/cost-management-and-billing/understand-your-invoice/usage-limits/).
2. **When the limits are hit.** None of the public pages read says what a free stack does past its limits. The
   usage limits page says over-rate spans are discarded as "rate limited"; dashboards past the cap cannot be saved.
   With no card on file and "no charges ever", going over cannot bill us; we assume data past the limit is
   refused. **Owner check:** the stack's usage page after the first week. The design stays far under the limits
   (ADR-054 point 2: about 2 000 series, well under 1 GB of logs a month).
3. **Region.** Grafana Cloud has India regions (AWS `ap-south-1`, GCP `asia-south1`), plus Singapore and US West
   (AWS `us-west-2`, near Render's Oregon). A stack's region cannot be changed later; a new stack is needed
   (https://grafana.com/docs/grafana-cloud/security-and-account-management/regional-availability/). Whether a free
   account may pick any region is not stated there; the owner sees it at sign-up.
4. **Terms.** Grafana Labs may suspend or end access "for any reason or for no reason at all" and "rename or remove
   inactive accounts"; governing law is Ireland for customers outside the Americas
   (https://grafana.com/legal/terms/). A free stack is a convenience we can lose without notice, so nothing may
   depend on it: Render's logs stay the record, and the uptime monitor (ADR-043) stays.
5. **Alerting.** Grafana-managed alert rules with an email contact point are part of every stack; the pricing page
   lists no separate alerting limit for free.

### 5. Self-hosted Grafana OSS later

1. **What it takes.** Grafana itself wants 512 MB and 1 core at the minimum, 2 cores and 2 to 4 GB for a small
   production setup, with SQLite or PostgreSQL for its own data
   (https://grafana.com/docs/grafana/latest/setup-grafana/installation/). Loki only documents sizing for its
   distributed mode (38 cores at the smallest tier, https://grafana.com/docs/loki/latest/setup/size/); monolithic
   mode on one machine is the small-site option. Grafana's all-in-one image `grafana/otel-lgtm` (Collector,
   Prometheus, Tempo, Loki, Pyroscope, Grafana) is "intended for development, demo, and testing" and its script
   gives it 2 GB (https://github.com/grafana/docker-otel-lgtm).
2. **Minimum hosting.** One small VM with about 2 vCPU, 4 GB and 40 GB of disk running Grafana, Prometheus (or
   Mimir monolithic), Loki monolithic and, if wanted, Tempo, with a Collector in front that also does redaction and
   tail sampling. Options checked 2026-10-20:
   1. Oracle Cloud Always Free Ampere A1: 2 OCPU and 12 GB in total, 200 GB block storage, free, but idle
      instances can be reclaimed (95th percentile CPU, network and memory under 20 % for 7 days) and capacity in a
      home region is not guaranteed
      (https://docs.oracle.com/en-us/iaas/Content/FreeTier/freetier_topic-Always_Free_Resources.htm).
   2. A small paid VM (Hetzner in Singapore or Europe, or similar) at a few euros a month. Hetzner's pages did not
      show prices to the fetch on 2026-10-20, so the owner checks the price when the time comes.
   3. A Render background worker or private service: not free on Render (above), and 512 MB on Starter is too small
      for the stack.
3. **The real cost is operations**, not money: upgrades, disk, backups of the metrics, and its own uptime. With one
   owner and no players yet, that is not worth it now. The move later is cheap if the app only speaks OTLP and the
   endpoint is an env var: point `OTEL_EXPORTER_OTLP_ENDPOINT` at the self-hosted Collector and import the same
   dashboard JSON.

### 6. Privacy: making sure nothing personal leaves

1. **How other products do it.** OpenTelemetry's guidance: "the best way to prevent the collection of sensitive
   data is not to collect data that might be sensitive", review what instrumentation libraries emit, and scrub the
   rest in the Collector, whose redaction processor "deletes attributes that aren't on an allowed list"; it also
   warns that hashing small predictable ids is not anonymization
   (https://opentelemetry.io/docs/security/handling-sensitive-data/). Sentry scrubs by default with a list of
   sensitive words (password, secret, token, card-like values), plus "Additional Sensitive Fields" and "Safe
   Fields" exempt from scrubbing: a denylist model
   (https://docs.sentry.io/security-legal-pii/scrubbing/server-side-scrubbing/). Grafana's direct export page names
   redaction as a Collector job, which we do not have (section 3). The lesson: a denylist misses new fields (our
   F10 is that lesson), so we do the allowed-list redaction in the app, and do not send ids hashed either.
2. **What that means for us** (the ADR's points 1, 2 and 7):
   1. **Our own instruments only.** No auto-instrumentation, no default resource detectors, so no attribute
      appears that we did not write.
   2. **Allowlist by key and by value.** Each instrument has a fixed list of attribute keys (a View with
      `createAllowListAttributesProcessor`). Every value comes from a closed set: the route template (Express's
      matched route, `unmatched` otherwise, never the raw path), the socket event name from `SOCKET_EVENTS`, the
      outcome from the shared error codes, the game id from the catalogue, the room status, the outbox step name.
   3. **A scrubbing step before export** (a wrapper around the exporter): every data point and log record is
      checked again, key in the allowlist and value matching its rule. Anything else is replaced by `other` and
      counted in a `telemetry.scrubbed` counter, so a mistake shows on the dashboard instead of leaving.
   4. **Logs: only named lines.** The log destination forwards only lines whose message is on a list (the alert
      lines and warnings and errors from the server's own code), with only allowlisted fields. Error class and
      error code go; the error message and stack do not (F10: a MongoDB duplicate key message holds an email). The
      full line stays in Render as today.
   5. **The test.** An in-memory exporter is wired into the integration suites that already drive sign-up,
      login, legacy login, guests, rooms, every game, the outbox and their failures. The test then (a) checks
      every exported key against the allowlist and every value against its rule, and (b) plants canaries (a known
      email, an IP in `X-Forwarded-For`, a player id, a session cookie, a room code) and asserts none of them
      appears anywhere in the serialized export. It fails closed: a new attribute fails the test until it is added
      to the allowlist on purpose. This is also the test CC-252 asks for on the log side.
3. **India's DPDP Act.** Section 16 lets the government restrict transfers to notified countries; none are notified
   in the material we hold, so transfer abroad is allowed by default (Act section 16,
   https://www.dpdpa.com/dpdpa2023/chapter-4/section16.html). A processor may be used "only under a valid
   contract", and the fiduciary stays responsible for security and for erasure by the processor (sections 8(2),
   8(5), 8(7), https://www.dpdpa.com/dpdpa2023/chapter-2/section8.html). The DPDP Rules (as read in CC-241 F9) ask
   for one year of logs from 13 May 2027. What follows for us:
   1. If what we send holds no player id, room code, IP, email, cookie or session, it is not personal data, and
      Grafana Labs is not a processor of personal data at all. That is the main reason for the allowlist: it keeps
      the foreign vendor out of DPDP scope instead of needing a processing contract, erasure on deletion (CC-035)
      and breach duties for it.
   2. Grafana's 14 days does not meet the one-year log rule, and it is not meant to. The record of who did what
      stays in Render's logs; the retention decision stays in CC-252, with the lawyer.
   3. We still name Grafana Labs on the privacy page, for honesty and because the page lists every service.
      (This is a reading of public texts for a small project, not legal advice. ADR-028's lawyer review covers it.)

### 7. Alternatives, one line each (pricing pages read 2026-10-20)

1. **Better Stack**: free tier has logs 3 GB a month kept 3 days, 10 uptime monitors; too short to see trends
   (https://betterstack.com/pricing).
2. **Axiom**: free Personal plan, 500 GB a month of ingest compute and 30 days retention, OpenTelemetry listed;
   strong for logs, but dashboards and alerting are weaker than Grafana's and the same scrubbing work applies
   (https://axiom.co/pricing). The best runner-up, and the endpoint swap is one env var.
3. **Highlight.io**: the pricing page now redirects to LaunchDarkly, which bought it; not a standalone free product
   to build on (https://www.highlight.io/pricing, 308 to launchdarkly.com).
4. **Sentry** for errors: free Developer plan, 5 000 errors a month, 1 user, 30 days
   (https://sentry.io/pricing/). Good at stacks, but stacks are exactly what may hold an email (F10) and its SDK
   collects request data by default; error rate and error class in Grafana cover us for now. Revisit with CC-049's
   error tracking if stacks are needed, with `sendDefaultPii` off and server-side scrubbing.
5. **Self-hosted Grafana OSS now**: no free host that fits (section 5); later.
6. **Render's own metrics and log streams**: Render's dashboard shows CPU and memory, and log streams forward the
   raw lines to a syslog endpoint (not checked on the free plan), but that ships every field, ids included, and
   gives no per-route or per-event latency and no alerts on our lines.

### 8. What is best for ClassiCade

Metrics and a short list of log lines, from our own instruments, straight to a Grafana Cloud free stack, with an
allowlist, a scrubber and a test that fail closed. No auto-instrumentation and no traces for now: on 0.1 CPU they cut
the peak request rate to about a third, they need an experimental loader flag, and their default attributes carry
the session id and IPs. The same socket and route
timer feeds CC-240's first-party trend later. Proposed as **ADR-054** in [DECISIONS.md](../DECISIONS.md), status
"Proposed — owner to decide". Nothing is sent until the owner accepts it and sets the env vars.

## Verification

Measurements (section 2.6) were made with throwaway scripts outside the repository: an Express 5 + Socket.IO 4.8 +
pino 10 app, `autocannon` 8 for HTTP, `socket.io-client` for acknowledged events, a local HTTP sink on port 4318
standing in for the OTLP endpoint, and `process.memoryUsage()` after a forced GC. Exports reaching the sink were
checked (4 metric pushes in a run with a 1 s interval). The container run with Render's limits is table 2.6.1
(`docker run --cpus 0.1 --memory 512m -v <scripts>:/bench node:24-slim`, about 40 minutes for nine runs). Not
measured: a real Grafana Cloud endpoint (no account yet; the first smoke test in the code pull request checks that
the stack accepts OTLP/HTTP with protobuf and that the series count matches the budget).
