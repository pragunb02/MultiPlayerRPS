## Research (written after the work, 2026-10-18)

This section was written after the work, on 2026-10-18. PR #57 was started, and merged at 20:42:28 UTC on
2026-10-17, before the "research before code" rule (working agreement rule 4, ADR-039, PR #59, merged 13 seconds
later). It records what the research would have said, checks what we built against it, and lists the gaps. It
changes no code.

### 1. How our code did it before (`git show 370c614`, `main` just before #57)

1. `service/http/session.js`: express-session with connect-mongo, cookie `cc.sid`, `httpOnly`, `sameSite: "lax"`,
   `secure` in production, rolling 30 days (`SESSION_TTL_SECONDS`, CC-096). No absolute lifetime.
2. `establishSession` regenerated the session id on every sign-in (no fixation). `destroySession` ended the one
   session of the browser that logged out.
3. Nothing could end a session on another device. No password change. No session version on the account.
4. A stolen cookie stayed valid for as long as it was used at least once every 30 days.

### 2. How others do it (sources read 2026-10-18)

1. OWASP Session Management Cheat Sheet
   (https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html):
   1. "The session ID must be renewed or regenerated by the web application after any privilege level change",
      and it names password changes among them. The old id "must be destroyed".
   2. Applications should "provide user features to remotely terminate sessions manually".
   3. Both an idle timeout and an absolute timeout. Its example ranges (15 to 30 minutes idle for low risk apps, 4
      to 8 hours absolute for an office worker) are written for work applications, and it says the absolute
      timeout "depends on how long a user usually uses the application".
   4. It recommends the `__Host-` cookie prefix for the session id (`Secure`, no `Domain`, `Path=/`).
2. OWASP Authentication Cheat Sheet
   (https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html): a password change needs
   "Current password verification". It also says to "Block common and previously breached passwords", for example
   with Pwned Passwords.
3. OWASP Password Storage Cheat Sheet
   (https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html): scrypt with at least
   N=2^17, r=8, p=1, or an equal setting such as N=2^15, r=8, p=3.
4. lichess (open source, `app/controllers/Account.scala` in lichess-org/lila, `master` read 2026-10-18): a password
   change runs behind a hashing rate limit, checks the new password against breach data, then
   `closeAllSessionsOf(me)` and gives the current browser a new session. "Sign out all" (`signout("all")`) does
   the same without a password. The security page lists up to 50 open sessions with their place, and each can be
   closed alone.
5. GitHub ("Viewing and managing your sessions",
   https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/viewing-and-managing-your-sessions):
   a list of web sessions by device, each with "Revoke session". "Sudo mode"
   (https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/sudo-mode) asks for the
   password again before high impact actions (changing email, deleting the account, tokens) and lasts two hours.
   Revoking a session is not on that list. GitHub's docs do not say how long a web session lasts or what a
   password change does to other sessions.
6. Session limits: neither lichess nor GitHub documents a cap on how many sessions an account may have. Both list
   them instead.

### 3. Does what we built match?

1. Matches: current password required for a change; this browser gets a new id after a password change or "sign
   out other devices" (the review fix); every other session is refused on its next request or handshake and its
   sockets are cut; an absolute 90 day end for accounts. That is the same shape as lichess, done with a version
   number instead of deleting sessions (ADR-030 says why).
2. Accepted differences: the idle timeout is 30 days and the absolute one 90 days, far above OWASP's office
   examples. A free game with no payments and no personal data beyond an email stays signed in like lichess and
   GitHub do; the trade-off is in ADR-030. "Sign out other devices" asks for no password, the same as lichess and
   GitHub. Someone with a stolen cookie could use it to sign the owner out, but cannot change the password, and
   the owner's password change ends the stolen session.
3. Gaps (findings, not fixed here):
   1. **G1. scrypt cost below the OWASP minimum.** `utils/passwordHasher.js` uses N=2^15, r=8, p=1, and OWASP's
      least setting at N=2^15 is p=3. Each hash records its own settings, so they can be raised and old hashes
      upgraded at the next login. Suggested ticket: security, P1, "Raise scrypt to OWASP's minimum (N=2^15 r=8 p=3
      or N=2^17 p=1), rehash at login; measure the time and memory per login on the Render instance first, and keep
      `verifyAgainstDummy` the same cost".
   2. **G2. No check against breached or common passwords** at sign-up and password change (OWASP Authentication
      and Credential Stuffing; lichess does it). Suggested ticket: security, P1, "Refuse breached passwords at
      sign-up and password change (Pwned Passwords range API with k-anonymity, or a bundled list of the most common
      passwords if no outside call is wanted), with a clear message on the password field".
   3. **G3. No email when the password changes or other devices are signed out.** Needs email (CC-033). Suggested:
      add "your password was changed" and "your other devices were signed out" emails to CC-033's scope.
   4. **G4. No list of sessions with one-by-one sign out.** Both lichess and GitHub have it; OWASP's minimum
      ("remotely terminate sessions") is met by "sign out other devices". Already out of scope above. Suggested
      ticket: security, P3, "List signed-in devices (approximate place, last seen) and sign out one".
   5. **G5. The session cookie has no `__Host-` prefix.** Renaming it signs every player out once, so it needs a
      deployment note. Suggested ticket: security, P3, "Rename `cc.sid` to `__Host-cc.sid` in production".

## Why

SEC-15: a player could not change their password, and could not end a session on a lost phone or a shared
computer. A stolen session cookie stayed valid for as long as it was used, because sessions roll for 30 days after
the last visit (CC-096).

## Scope

In:

1. `sessionVersion` on each account (MongoDB `accounts`, default 0). Accounts stored before this change have no
   field and read as 0.
2. Every signed-in session stores the version it was made at and the moment of signing in (`sessionVersion`,
   `signedInAt`). `createSessionCheck` (`service/http/session.js`) answers whether a session may still be used. It
   runs on every `/api` request (after the app-wide rate limit, so a flood costs no database reads) and on every
   socket handshake. A session that may no longer be used is replaced by an empty one, so the request goes on as a
   visitor (`GET /api/session` answers `authenticated: false`) and its sockets are disconnected. A refused socket
   handshake answers `UNAUTHORIZED` with "You were signed out on this device, please log in again".
3. `POST /api/auth/password` with `{ currentPassword, newPassword }`: JSON only, same Origin rules (ADR-010), the
   20 per 15 minutes per address limit of the other account routes, and at most 5 wrong current passwords per
   account in 15 minutes. Answers 204. Wrong current password is a 400 on `currentPassword`. A new password that
   breaks the rules, or equals the current one, is a 400 on `newPassword`. Guests get 403, visitors 401. The new
   hash and the new version are written in one update.
4. `POST /api/auth/sign-out-others` (no body or `{}`): counts the version up. Answers 204.
5. Both keep this browser signed in under a new session id with the new version, so a copy of its old cookie
   stops working too. This browser's sockets move to the new id and stay connected. Every other socket of the
   account is disconnected (`gateway.disconnectOtherSessions`), and so is a handshake of the account that was
   being checked at that moment. A password change starts the 90 days again (the password was given), signing out
   other devices does not.
6. A 90 day absolute lifetime for signed-in sessions, on top of the 30 day rolling cookie. Sessions made before
   this change are stamped the first time they are seen, so their 90 days start then.
7. Web: an "Account" section on the profile of a signed-in player with "Change password" (current and new
   password fields, errors on the right field) and "Sign out other devices". Both say when they are done. Built
   with the existing `Button` (`busy`) and `Field`, because `useAction` is not on `main` yet (PR #53).

Out:

1. Password reset by email, which also counts the version up (CC-033).
2. A list of signed-in devices with names. Needs a session index per account.
3. Deleting the other sessions from the store at once. They are refused on their next request and the store's TTL
   removes them.
4. Refreshing the screen of a device that was signed out from elsewhere. Its socket is cut at once, but the page
   keeps its old view until it reloads or makes a request. Tracked as CC-234.

Decided by the owner on 2026-10-17: guests are exempt from the 90 day lifetime. The ADR below is ADR-030.

## ADR-030 (accepted, recorded in DECISIONS.md): session lifetime and revocation

Recorded as ADR-030 in DECISIONS.md on 2026-10-18.

**Context.** Sessions live in MongoDB (`player_sessions`, connect-mongo) and roll for 30 days after the last visit.
Nothing could end a session except logging out on that device.

**Decision.**

1. Each account has a `sessionVersion`. A session stores the version it was made at. A session whose version is not
   the account's current one is ended on its next request or connection. Changing the password, "sign out other
   devices" and later the password reset (CC-033) count the version up. The session that asked takes the new
   version and stays.
2. The check reads one field of one account by its id on every request and handshake of a signed-in player. That
   is a primary key read of a few bytes. Guests are not checked.
3. A signed-in session ends 90 days after signing in, however often it is used. That bounds a stolen cookie to
   three months, and asks for the password about four times a year.
4. Guest sessions have no absolute end. A guest has no password to sign in with again, so ending the session would
   lose their progress. Their rolling 30 days stay.
5. Sessions and accounts from before this change count as version 0, and their 90 days start when first seen.

**Alternatives.** Deleting every session of an account from the store (needs an index on the session data in
connect-mongo's collection and misses sessions that are being written at that moment). Short lived tokens with
refresh (a new client protocol, for no gain on a same-origin app).

**Consequences.** One small read per signed-in request. A request of the same browser that is on its way while
the version moves on carries the old id and version. For five seconds such a request still passes
(`createSessionRenewals`), so the browser that asked to stay is not signed out by its own other tab. The old id is
destroyed in the store at the same moment, so it cannot be used after that.

## Review fixes (PR #57 review, 2026-10-18)

1. The session that asked kept its id, so a stolen copy of exactly that cookie stayed valid. It now gets a new
   id (fix above). Tests: `accountSessions.test.js` "gives this device a new session id",
   `security.integration.test.js`.
2. A handshake checked just before the version moved on had not joined the player's channel yet and stayed
   connected. The gateway now remembers, per player, how often other devices were signed out and which session
   stayed, and disconnects such a socket as soon as it connects. Test: `handshakeRaces.test.js` "is disconnected
   when the player signs out their other devices during the check".
3. A request of the same browser between the version change and the session save signed out the browser that asked
   to stay. The id is marked as renewing before the version changes, and the guard lets it pass for five seconds.
   Test: `accountSessions.test.js` "keeps a request of this browser that was on its way during the change signed
   in".

## Acceptance criteria

- [x] Password change keeps this session, signs out the others, old password refused, new password works.
- [x] Sign out other devices does the same without changing the password.
- [x] Version checked on every request and socket handshake, including a device that makes no request first.
- [x] 90 day absolute lifetime for accounts, none for guests.
- [x] Wrong current password limited per account. JSON and Origin rules as the other account routes.
- [x] Profile page section with feedback.
- [x] Unit, integration (MongoDB through the real server) and browser tests.
