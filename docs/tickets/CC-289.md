## Why

ADR-005 waits for triggers before paying for hosting, and every trigger needs a number. Nobody knows how many
players the free Render instance (0.1 CPU, 512 MB) carries at once, how many moves a second it answers inside the
150 ms of NFR-3, or what gives way first. Without that, the owner cannot tell when each scaling step is due or what it
costs. This ticket measures it on a local production build under the free plan's limits, never on production, and
turns the numbers into a scale plan.

## Research (written before any code)

Written 2026-10-20. Every web source was read on that date unless another date is given.

### 1. How our code does it today

1. **The load script that exists.** `scripts/bin/load-moves.mjs` (CC-182, raised limits added in CC-107, PR #57)
   starts an in-memory MongoDB and the server in production mode in a child process, then plays chess and Rock
   Paper Scissors pairs of guests for a fixed time and prints one line with p50, p95, p99 and max of the move round
   trip. Its limits are raised in code, through `startServer({ limits, rooms })`, because every player shares one
   address. Gaps: one fixed load (no ramp), no CPU or memory cap (it runs at the full speed of the laptop), no
   Tic-Tac-Toe and no computer games, no event-loop lag, CPU, memory or MongoDB numbers, and no stop rule. It also
   still calls `SOCKET_EVENTS.ROOM_REMATCH`, which no longer exists since rematch became a room request (CC-159), so
   its rematches are sent as an `undefined` event and refused. It is left as it is (this ticket only adds files) and
   the new harness replaces it.
2. **What one move costs.** `game:move` goes through `registerHandlers` (`service/realtime/acknowledgements.js`,
   the event budget of ADR-035 point 3), `roomHandlers.js` `GAME_MOVE`, `roomComponent.makeMove`, which runs
   `change`: one `findOne` of the room (`roomDao.get`), the engine, then one `findOneAndUpdate` that writes only the
   changed fields and returns the room (CC-182). After that `broadcastRoom` calls `io.in(room).fetchSockets()` and
   builds one personalised view per socket (`stampedView`). So a move is two MongoDB operations and two view
   builds. A move that ends a game adds the outbox record and its five steps (ADR-047): the match, the verdict,
   progress, gamification and leaderboards, each a few reads and writes.
3. **Background work, whatever the load.** `server.js` runs `expireDue` every second (`listDue`, an indexed query),
   the match pipeline every 5 seconds, and every minute the room sweep, `botDriver.resume`,
   `matchPipeline.addFinishedRooms`, the transfer and deletion sweeps and the room gauge. Two of the minute jobs
   (`listFinishedGames` and `botDriver.resume`) read every open room with `roomDao.list()`, so their cost grows with
   the number of rooms.
4. **Computer players.** `domain/bots/thinkingQueue.js` lets one computer player think at a time on the whole
   server and then rests as long as the thinking took. Chess levels search by a position budget, not by time
   (`packages/games/src/bots/chess/chessBot.js`: club 20 000 positions, strong 60 000). On 0.1 CPU a search that
   takes 250 ms on a full core takes about ten times longer and holds the event loop for all of it, which is a
   likely hot spot to measure.
5. **Hard caps already in the code (ADR-035).** 2 000 open rooms on the server, 30 open rooms and 30 sockets per
   address, 5 sockets per session, 3 waiting rooms per player, one event budget per player (bursts of 20, 10 a
   second), 300 `/api` requests a minute per session or address, and the guest sign-in limit. A load test from one
   machine hits the per-address limits at once, so they must be raised for the test only (section 4).
6. **Mongo.** One MongoDB connection pool per process (the driver default, 100 connections at most). Sessions are in
   MongoDB too (`player_sessions`, connect-mongo), so each guest sign-in writes a session.
7. **Socket.IO transport.** The web app connects with `transports: ["websocket"]` (`apps/web/src/lib/socket.js`
   line 16), never long polling. That matters for scaling out (section 2.3).

### 2. How others do it

#### 2.1 Tools for load testing a Socket.IO server

| Tool                                | What it does well                                                                                                                                                                                                                                                                                     | What stops us                                                                                                                                                                                                                                                                                                           |
| ----------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Artillery with its Socket.IO engine | Scenarios in YAML, `emit` with `acknowledge`, a `socketio.response_time` histogram from emit to answer, `think` steps and ramps (https://www.artillery.io/docs/reference/engines/socketio).                                                                                                           | "The `extraHeaders` option only works if the default `polling` transport is used" (same page). Our session is a cookie sent on the handshake and our app is WebSocket only, so the test would use a transport production never uses. Game logic (whose turn, legal chess moves, rematch) needs custom JavaScript hooks. |
| k6 with `k6/websockets`             | Ramping stages and thresholds such as `p(95)<200` with a failing exit code (https://grafana.com/docs/k6/latest/testing-guides/api-load-testing/), cookies and headers on the WebSocket (https://grafana.com/docs/k6/latest/javascript-api/k6-websockets/).                                            | Plain WebSocket only. The docs do not mention Socket.IO, so the Engine.IO and Socket.IO framing (handshake, pings, `42[...]` packets, ack ids) would have to be written by hand, and chess.js does not run in k6's JavaScript runtime as is.                                                                            |
| A custom `socket.io-client` swarm   | The Socket.IO docs recommend it for anything beyond simple emits: "you cannot easily test server-to-client events" with Artillery, and their example creates many clients from one Node script (https://github.com/socketio/socket.io-website/blob/main/docs/categories/06-Advanced/load-testing.md). | One Node process may itself become the bottleneck, so its own event-loop lag must be measured and reported.                                                                                                                                                                                                             |

The k6 guide also says load tests "should add sleep time" because it "better simulates the traffic patterns of
human users", and that pass or fail criteria should be written as thresholds (same k6 page).

#### 2.2 Realistic players

There are no real players to copy yet (PRODUCT_VISION.md: no counted result on production on 2026-10-17), so the
model is written down as assumptions, each one a setting of the harness:

1. **Think time.** A person needs time to choose. Rock Paper Scissors: 1 to 4 s a throw. Tic-Tac-Toe: 1 to 3 s a
   mark. Chess on the default `blitz-5+0` (`packages/shared/src/chess.js`): 300 s for a game of about 40 moves each
   is about 7 s a move, so 2 to 10 s with an average near 5 s. Each think is drawn at random between its bounds, as
   k6 advises, so players never move in step.
2. **Game length.** Rock Paper Scissors best of 3 (two or three rounds). Tic-Tac-Toe 5 to 9 marks. Chess is played
   with random legal moves, which never end a game in a human length, so each chess player resigns after a random
   20 to 60 of their own moves, which keeps games close to human length and every resignation is a real game end.
3. **Between games.** 2 to 5 s on the result, then a rematch 60 % of the time (both players ask, the second asking
   accepts, CC-159). Otherwise both leave and the pair opens a new room, as friends sharing a link would.
4. **Mix of games.** Rock Paper Scissors 40 %, Tic-Tac-Toe 30 %, chess 30 %. Rock Paper Scissors and Tic-Tac-Toe
   are the short, casual games of the drop-in searcher, the primary persona (PRODUCT_VISION.md, persona 3).
5. **Computer games.** 40 % of players play a computer character, because "There is always someone to play. A
   ClassiCade character is always ready" (PRODUCT_VISION.md, loop 2) and a solo visitor needs one. Chess.com's bots
   played about 120 million games in January 2023 (PRODUCT_VISION.md, citing
   https://en.wikipedia.org/wiki/Mittens_(chess)). Levels are drawn evenly from each character's levels.
6. **Sign in.** Every player is a new guest (`POST /api/session/guest`), as a first visit is. Accounts are left out,
   because sign-up runs scrypt and is limited to 10 an hour per address (ADR-035), which is not a playing load.

#### 2.3 Scaling Socket.IO past one server

1. The Socket.IO docs name two things to solve with several servers: load balancing and passing messages between
   servers (https://github.com/socketio/socket.io-website/blob/main/docs/categories/02-Server/using-multiple-nodes.md).
2. **Sticky sessions** are needed because of HTTP long polling. The same page lists "disabling HTTP long-polling" as
   one of the ways around it. Our web app already connects with WebSocket only (section 1.7), so a load balancer
   without session affinity works. That matters because Render's scaling page describes instance counts behind one load balancer and no
   session affinity (https://render.com/docs/scaling).
3. **The Redis adapter** (`@socket.io/redis-adapter`) passes room broadcasts to the other servers over Redis Pub/Sub.
   It "does not store data in Redis", and requests that ask every server, such as `fetchSockets()`, wait for all
   servers up to `requestsTimeout`, 5 000 ms by default. The sharded variant for Redis 7 is recommended for new
   projects (https://github.com/socketio/socket.io-website/blob/main/docs/categories/05-Adapters/adapter-redis.md).
   For us that means every `broadcastRoom` on a move (`io.in(room).fetchSockets()`) becomes a round trip to every
   other server. It should be changed before a second server, so the move path uses `io.to(room).emit` per viewer
   seat channel instead.
4. **Our own state in one process** that a second server breaks: login counts and the daily network keys (ADR-035,
   amended), the bot driver's plans and the thinking queue, the match pipeline's in-memory claim (ADR-047 says a
   second instance needs a lease), and the timers of the room component. CC-061 owns all of them.

#### 2.5 Render instance sizes and prices

From https://render.com/pricing (compute table and workspace plans):

| Instance | Price a month | CPU                             | RAM    |
| -------- | ------------- | ------------------------------- | ------ |
| Free     | $0            | "less than 1 CPU" (0.1, CC-286) | 512 MB |
| Starter  | $7            | 0.5                             | 512 MB |
| Standard | $25           | 1                               | 2 GB   |
| Pro      | $85           | 2                               | 4 GB   |
| Pro Plus | $175          | 4                               | 8 GB   |

1. Workspace plans: Hobby $0 a month plus compute, Pro $25 a month plus compute. Bandwidth: 5 GB a month on Hobby,
   25 GB on Pro, then $0.15 a GB.
2. Free instances sleep after 15 minutes and have 750 instance hours a month (https://render.com/docs/free).
3. Manual scaling to a fixed number of instances "is available for all Render workspaces", autoscaling only on Pro
   workspaces, and each instance is billed in full (https://render.com/docs/scaling).
4. Render Key Value (Redis compatible) for the adapter: Free 25 MB and 50 connections, Starter $10 a month with 256
   MB and 250 connections (same pricing page).
5. The docker flags model these sizes: `--cpus=0.1 --memory=512m` (Free), `--cpus=0.5 --memory=512m` (Starter),
   `--cpus=1 --memory=2g` (Standard). `--cpus` sets a CFS quota like Render's container limit. Render's network,
   disk and neighbours are not modelled.

### 3. What is best for ClassiCade

1. **A custom swarm in Node with `socket.io-client`**, because only it sends the session cookie on a WebSocket-only
   connection as the browser does, plays real games with real rules (chess.js for legal moves), and hears
   `room:updated` from the server (what a player actually waits for when the opponent or a computer moves). Same
   dependencies as the old script, so nothing new is installed.
2. **The server in Docker, built from our own `Dockerfile`**, so the test runs the production image (`NODE_ENV=production`,
   the built web app) with `--cpus` and `--memory` like Render. MongoDB in a second container pinned exactly as
   CC-288 pins it (`mongo:8.2.12@sha256:e0ce8c35…`), on a private Docker network, published to `127.0.0.1` only.
   MongoDB gets no CPU limit, because Atlas runs it elsewhere, and its operations a second are compared with M0's
   100 and Flex's 500 instead.
3. **Measured inside the server** with a small probe that the harness starts beside the server in the same process
   (event-loop delay from `perf_hooks.monitorEventLoopDelay`, CPU from `process.cpuUsage`, memory from
   `process.memoryUsage`), printed to stdout once a second. Docker's own `docker stats` reading is kept as a check.
   MongoDB operations a second from `serverStatus().opcounters`. Client side: round trip of every acknowledged event
   by name and game, and the wait for a computer's reply.
4. **Ramp in steps and stop at the first break**: p95 of the move round trip over 150 ms (NFR-3) or any error or
   refusal in a step.
5. **Limits for the test only.** The harness starts the server with `startServer({ limits, rooms })` like
   `load-moves.mjs`, raising only the per-address limits (guest sign-ins, `/api`, sockets and rooms per address),
   because every simulated player shares one address. The 2 000 room cap, the per-player event budget and every
   other rule stay as in production. There is no env var and no production switch: `apps/server/src/index.js` is
   unchanged and cannot raise them.
