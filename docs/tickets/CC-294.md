## Why

Render's settings for production (build and start commands, branch, auto-deploy, health check, plain env vars) live
only in the dashboard. Nobody reviews a change to them, and nothing records what they were. The dashboard had quietly
left auto-deploy on "On Commit", so a red `main` could still deploy, until the owner switched it to "After CI Checks
Pass". A Blueprint file puts those settings in the repository, where every change is a pull request.

## Research (written before any code)

Written 2026-10-20. Every Render page below was read on 2026-10-20 (the pages carry no date, footer "© Render 2026").

### 1. How our code does it today

1. There is no `render.yaml`. `docs/DEPLOYMENT.md` lists the dashboard settings by hand: Build Command
   `npm ci --include=dev && npm run build:web`, Start Command `npm start`, Health Check Path `/health`, branch `main`,
   Node version from `.nvmrc`, and the env vars.
2. The owner told us the dashboard today has auto-deploy "After CI Checks Pass" and the health check `/health`, both
   just set, and `HOST=0.0.0.0` (CC-287).
3. The env vars the server reads are all in `apps/server/src/config/index.js` (`loadConfig(env)`, called once from
   `apps/server/src/index.js` with `process.env`). A search of `apps/` and `packages/` for `process.env` finds only
   that call, plus `CLASSICADE_API` in `apps/web/vite.config.js` (the dev server proxy, not production) and
   `CC_SLOW_EFFECTS_MS` in a web test helper. The ten names, and what each one is:

   | Variable            | What it holds                                                   | In the Blueprint                     |
   | ------------------- | --------------------------------------------------------------- | ------------------------------------ |
   | `NODE_ENV`          | `production`                                                    | plain value `production`             |
   | `PORT`              | set by Render (default 10000)                                   | not declared, Render owns it         |
   | `HOST`              | `0.0.0.0` on Render (CC-287)                                    | plain value `0.0.0.0`                |
   | `LOG_LEVEL`         | default `info`                                                  | plain value `info`                   |
   | `MONGO_URI`         | the Atlas connection string with its password                   | `sync: false` (secret)               |
   | `SESSION_SECRET`    | signs session cookies                                           | `sync: false` (secret)               |
   | `ALLOWED_ORIGINS`   | `https://nocapgaming.onrender.com`, already public in this repo | plain value                          |
   | `WEB_DIST_DIR`      | `apps/web/dist`                                                 | plain value                          |
   | `TRUST_PROXY_HOPS`  | default `1` in production, the safe value (DEPLOYMENT.md)       | plain value `1`                      |
   | `ADMIN_ACCOUNT_IDS` | who may open the owner console                                  | `sync: false` (kept out of the repo) |

4. CI (`.github/workflows/ci.yml`) runs on every pull request and on every push to `main`, so a merge commit on
   `main` always has GitHub checks. That is what "After CI Checks Pass" waits for. The scheduled workflows (uptime,
   nightly, backup, WebKit) do not run on push.
5. Nothing in the repo parses YAML today, and there is no YAML parser in `package-lock.json`. `ajv` is there only as
   version 6, a dependency of ESLint, which does not support JSON Schema 2020-12.

### 2. How Render and other platforms do it (sources)

**Render Blueprints.**

1. Blueprint YAML Reference, https://render.com/docs/blueprint-spec:
   1. `name`: "If you add the name of an existing service to your Blueprint file, Render attempts to apply the
      Blueprint's configuration to that existing service." `type`: "You can't modify this value after creation."
      `region`: "You can't modify this value after creation." So adoption is by name, and type and region must match.
   2. `runtime: node` is a native runtime. `plan: free` is the free web service plan (0.1 CPU, 512 MB). `region`
      defaults to `oregon`.
   3. `autoDeployTrigger`: "`checksPass`: Trigger a deploy only if the linked branch's CI checks pass." It replaces
      the deprecated `autoDeploy`. "If you omit this field: Render uses `commit` for a new service. Render retains
      the current value for an existing service."
   4. `healthCheckPath`: "Web services only. The path of the service's health check endpoint. This value always
      starts with a `/` character."
   5. `branch`: when omitted, "Render uses the Blueprint's branch if the service uses the same repo as the Blueprint
      file". `repo`: "If omitted, Render uses the repo that contains the Blueprint file."
   6. Fields Render keeps when omitted for an existing service: `plan`, `numInstances`, `autoDeployTrigger`,
      `renderSubdomainPolicy`, `ipAllowList`, autoscaling. Fields that are **reset** when omitted: `buildFilter`
      ("If you omit this field for a service with existing build filter settings, Render replaces those settings
      with empty lists"), `previews.generation` ("If you omit this subfield, pull request previews are disabled for
      the service"), `rootDir` (repo root), `maxShutdownDelaySeconds` (30).
   7. Env vars: "A Blueprint can create new environment variables or modify the values of existing ones. Render
      preserves existing environment variables, even if you omit them from the Blueprint file."
   8. `sync: false`: "During the initial Blueprint creation flow in the Render Dashboard, you're prompted to provide
      a value for each environment variable with `sync: false`." "Render prompts you for these values only during
      the initial Blueprint creation. When you update an existing Blueprint, Render ignores any environment
      variables with `sync: false`."
   9. Validation: the spec is "served from SchemaStore.org" and "hosted in JSON Schema format" at
      https://render.com/schema/render.yaml.json. The Render CLI (2.7.0 or later) has `render blueprints validate`,
      and the API has a Validate Blueprint endpoint. Both need a Render login or API key.
2. Blueprints overview, https://render.com/docs/infrastructure-as-code:
   1. Setup ends with "Review the list of the changes that Render will apply based on the linked Blueprint ... If
      everything looks correct, click Deploy Blueprint." Nothing is applied before that click.
   2. Adding an existing resource: "Make sure to include all configuration options that are currently set for the
      resource in the Render Dashboard ... If you omit some of these options, your Blueprint will use a default value
      that almost definitely differs from your service's existing configuration." And: "When you next sync your
      Blueprint, Render applies the new configuration to the existing resource. The resource retains any existing
      environment variable values that aren't overwritten by the Blueprint."
   3. Generating a Blueprint from existing services: "This is useful if you want to start managing those exact
      resources with a Blueprint." The generated file "does not include environment variable values ... the
      generated file sets `sync: false` for all environment variables", and "If you use this render.yaml file to
      create a Blueprint with new services (instead of your existing ones), you'll need to provide values for these
      environment variables." So Render's own adoption path is a file in which every env var is `sync: false`, and
      only new services need values.
   4. Replicating a Blueprint: "The Blueprint creation flow displays a notice if your new Blueprint matches existing
      resources in your workspace ... Render appends a suffix to the name of each new resource to prevent collisions
      with your existing resources." This is the duplicate service risk.
   5. "Changes to a Blueprint never cause a resource to be deleted. If you remove a resource definition from your
      Blueprint file or even disconnect a Blueprint entirely, all existing resources remain intact." But "If you
      delete a Blueprint-managed resource, Render recreates it the next time you sync your Blueprint", and dashboard
      changes that conflict with the file are overwritten on the next sync.
   6. Auto sync: "By default, Render automatically updates affected resources every time you push Blueprint changes
      to your linked branch." It can be set to No, with a Manual Sync button.
3. Deploys, https://render.com/docs/deploys (Integrating with CI): "Render triggers a deploy only after all of your
   repo's CI checks pass." A GitHub check passes when its conclusion is "`success`, `neutral`, or `skipped`".
   "Render does not trigger a deploy if: Zero checks are detected for the new commit. At least one CI check fails
   for the new commit."
4. Health checks, https://render.com/docs/health-checks: a new deploy gets traffic only when its instances pass the
   check, and otherwise "Render cancels the deploy and continues routing traffic to your service's existing
   instances" after 15 minutes.

**Other platforms.**

1. Railway config as code, https://docs.railway.com/reference/config-as-code: "Configuration defined in code will
   always override values from the dashboard." The file covers build and deploy settings, not variables.
2. Fly.io `fly.toml`, https://docs.fly.io/reference/configuration: `[env]` is for "non-sensitive information", and
   "For sensitive information, such as credentials or passwords, use the secrets CLI command." Health checks live
   in the file (`http_service.checks`).
3. The pattern is the same everywhere: build, start, health and plain settings in a reviewed file, secrets only in
   the platform's secret store, and the file wins over the dashboard.

### 3. What is best for ClassiCade

1. One web service in `render.yaml` at the repo root, named exactly like the dashboard service (`NoCapGaming`), with
   every field the dashboard sets today written out, so adoption changes nothing: `type: web`, `runtime: node`,
   `plan: free`, `region: oregon`, `branch: main`, the two commands, `healthCheckPath: /health` and
   `autoDeployTrigger: checksPass`. No `repo` (the Blueprint's own repo is the service's repo).
2. Plain values only for settings that are not secret: `NODE_ENV`, `HOST`, `LOG_LEVEL`, `ALLOWED_ORIGINS`,
   `WEB_DIST_DIR`, `TRUST_PROXY_HOPS`. These are exactly the settings that must be reviewed. `TRUST_PROXY_HOPS`
   above the real number of proxies lets a script bypass every rate limit (DEPLOYMENT.md), so a change to it should
   be a pull request. `1` is the value the server already uses when it is not set.
3. `sync: false`, with no value, for every secret: `MONGO_URI`, `SESSION_SECRET`, `ADMIN_ACCOUNT_IDS`. Render keeps
   their dashboard values (sources 1.7, 1.8, 2.2, 2.3).
4. `PORT` is not declared: Render sets it and the server must listen on it.
5. Two checks:
   1. A unit test (offline, part of `npm test` and its coverage gates) parses `render.yaml` and checks our rules:
      the service settings, the exact set of env vars against the names `loadConfig` reads, every secret
      `sync: false` with no value, and that the plain values plus placeholder secrets pass `loadConfig` in
      production with `HOST` 0.0.0.0. A new env var in config then cannot ship without a decision in the file.
   2. Render's published JSON Schema, checked with Ajv in a CI job that runs on pull requests only. It needs the
      network (the schema is not copied into this repo: it carries no licence, and a copy would go stale). Running it
      on pull requests only matters: with "After CI Checks Pass", a failed check on a `main` commit stops that deploy
      (source 3), so a check that can fail because render.com is slow must never run on `main`. A skipped job
      counts as passed for Render.
      The Render CLI validator is out: it needs a Render API key in CI, and builders never call Render's API.
6. New dev dependencies, both latest stable with no native build: `yaml` (2.9.1, no dependencies) to parse the file,
   and `ajv` (8.20.0, four small dependencies) for JSON Schema 2020-12. Node has neither built in (ENGINEERING.md
   §5.2).

### 4. What could go wrong when the owner links it

Said plainly, because this is production:

1. **A duplicate service.** If Render does not match `NoCapGaming` (a different name, type or region), it plans a new
   web service, with a suffixed name if it sees a clash (source 2.4). A second service that got the secrets would run
   the same code against the production database next to the live one. The review page shows this before anything
   happens, and the owner steps stop there.
2. **Settings reset to defaults.** Fields the file leaves out that Render resets: build filters, PR previews, root
   directory, shutdown delay (source 1.6). Today none of them is set as far as DEPLOYMENT.md knows. The owner checks
   each in the dashboard first.
3. **Plain values overwritten.** The six plain values replace whatever the dashboard has. If the dashboard differs
   (for example a measured `TRUST_PROXY_HOPS`), the file must be changed first.
4. **Secrets.** Render's docs say existing env vars are kept and `sync: false` is ignored on updates, and its own
   adoption file is all `sync: false`. They do not say in so many words what the first creation screen does when a
   `sync: false` key already has a value on an adopted service. If that screen asks for a value, the owner leaves
   the field empty or cancels, and never pastes a secret. If a secret were blanked, the next deploy would fail its
   boot (`MONGO_URI` and `SESSION_SECRET` are required) and its health check, and Render keeps the live deploy, but
   the service could not deploy again until it is set back. `SESSION_SECRET` must then be the same value, or every
   player is logged out.
5. **Nothing is deleted.** Render never deletes a resource because of a Blueprint (source 2.5). Env vars missing
   from the file stay (source 1.7). The MongoDB data is not touched by any of this.
6. **Later dashboard edits are overwritten** on the next sync if they conflict with the file. After linking, plain
   settings change through pull requests only.

## Scope

1. In: `render.yaml`, its unit test, the schema check script and its CI job, `docs/DEPLOYMENT.md` (Blueprint

2. Out: linking the Blueprint (the owner does it), any Render API call, secrets, custom domains (CC-123), staging
   (CC-122).
