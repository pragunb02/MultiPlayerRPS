## Research

Written after the first version of the code, when the review of PR #61 found that the ticket had none. The working
agreement asks for it before code, so this section records what the first version did, what others do, and what
the review fixes chose.

### 1. How our code does it

1. Seating. `botComponent.playComputer` creates the room and seats the character at once. The limit of three games
   against computers per player (`MAX_COMPUTER_GAMES`) was checked only there, and only against games already
   playing. Two requests at the same moment both counted the games before either had started, so both fitted, and
   a rematch the computer accepted started a game with no check at all.
2. Thinking. `botDriver` chose each move inside a timer on the one Node process. A strong chess search takes up to
   about a quarter of a second, and nothing limited how many ran across the server, so a few guests with three
   strong games each could hold up every socket.
3. Lost plans. A plan dropped after three failed writes was made again only by the next saved room change or a
   restart, although the JSDoc said "now and then".
4. Rewards. Bot XP was kept off the boards only in `applyMatch` and the weekly recount. The all-time XP board is the
   player's total XP, so bot XP reached it with the next human game or quest bonus. Quest bonuses earned in bot
   games reached both XP boards. A guest's games moved into an account kept their bot XP without the account's own
   100 XP for that day being looked at.
5. Fairness lock. The browser hashed the move and key of a reveal and compared it with the lock in the same reveal,
   so a server that made a new lock after seeing the person's throw would still have been shown as "Lock checked".
6. History. Match records keep `{ playerId, displayName }`, so the profile showed "vs Rocky" with no sign that Rocky
   is a computer.

### 2. How other products do it (sources accessed 2026-10-18)

1. Seating and labels. Lichess makes a computer account a separate kind for good: upgrading an account to a BOT
   account "is irreversible" ([lichess-bot wiki](https://github.com/lichess-bot-devs/lichess-bot/wiki/Upgrade-to-a-BOT-account)).
   Our `bot` identity kind and the `bot_` id prefix follow the same idea: a computer is never a person's account.
2. Where the engine runs. Lichess does not run Stockfish on its web servers. Work goes to fishnet clients on
   volunteers' machines through queues, a "user queue" for jobs a person waits for and a "system queue" for the rest
   ([fishnet](https://github.com/lichess-org/fishnet)). The Node.js guide says CPU heavy work must either be
   partitioned, so that it "regularly yields (gives turns to) other pending events", or moved "off of the Event Loop
   onto a Worker Pool" ([Don't block the event loop](https://nodejs.org/en/learn/asynchronous-work/dont-block-the-event-loop)).
3. Proving fairness. Commit and reveal is the standard commitment scheme: a value is committed "while keeping it
   hidden to others" and revealed later, and binding stops the sender from changing it. The receiver must check the
   opening against the commitment it was sent earlier, as in the coin flip example
   ([Commitment scheme](https://en.wikipedia.org/wiki/Commitment_scheme)). A check against a commitment sent with the
   opening proves nothing.

### 3. What is best for ClassiCade

1. One thinking queue for the whole server (`thinkingQueue.js`): one computer move is chosen at a time, and after
   each the server rests as long as the thinking took, so computer players use at most half of the event loop and
   people are answered in every rest. This is the partitioning option of the Node.js guide at the level of whole
   searches, with no new dependency and no worker threads to deploy on Render. A worker pool (CC-038 item 4) stays
   the next step if the strong level ever needs more time. Yielding inside one search (between iterative deepening
   depths) was considered: the deepest depth takes most of the time, so it would shorten the longest block little,
   and the node budget already bounds it.
2. The three game limit holds on every start: a new game and a rematch the computer accepts both go through the bot
   component, one start per person at a time (an in-process line, enough because production is one process), and
   the count is taken again after the start, ending the oldest games.
3. The housekeeping sweep calls `botDriver.resume()` every minute. A room that already has the right plan keeps it,
   so this costs one read of the rooms.
4. Progress keeps `unrankedXp`, the part of the XP that came from games against computers and from quest bonuses
   those games earned. Every XP board shows `xp - unrankedXp`. The level still comes from all XP, because ADR-025
   lets bot games give XP. A guest's game against a computer that moves into an account gives only what the
   account had left of that day's 100 XP, and progression takes the rest out of the guest's totals before merging.
5. The fairness view names each seal by game and turn. The browser remembers the first lock it shows for each, and
   says "Lock checked" only when the reveal's lock is that one, its throw is the one in the round's result, and the
   hash matches. A page opened after the lock was shown says it cannot check, never that it matched.
6. History labels computer players (`computer: true`, worked out from the id on the server), and the profile shows
   "Rocky (computer)".

### Bugs found along the way

These are listed for the coordinator, who files them in KNOWN_ISSUES and on the board. All are fixed in this PR.

1. The limit of three games against computers could be passed by sending many starts at once, and by rematches.
2. Strong chess searches had no server wide limit and could block the event loop for every player.
3. A dropped computer plan was never made again until something else changed in the room.
4. Bot XP reached the all-time XP board, and quest bonuses from bot games reached both XP boards.
5. A guest's bot XP moved into an account without the account's 100 XP a day being applied.
6. The browser's "Lock checked" did not compare the reveal with the lock shown before the round.
7. Match history did not label computer opponents.
8. Found and fixed earlier in this PR: `useRoom` could replace a newer room view with an older answer (it now keeps
   the view with the higher `revision`).

## Why

A visitor who arrives alone needs someone to play at once. The bots of #47 (`packages/games/src/bots`) could choose
moves but could not sit in a room. ADR-025 sets the rules: a computer player is always labelled as one, its games
never count on a leaderboard or rating, and they give XP and quest progress only within the ADR-021 limits and a
daily XP budget of their own.

## Scope

- In: **identity.** `IDENTITY_KINDS.BOT` and `BOT_CHARACTERS` in `@classicade/shared` (Rocky for Rock Paper
  Scissors, Pip for Tic-Tac-Toe, Queen Vee for chess, each with level picks easy, medium, hard mapped to the bot
  levels). `models/botIdentity.js` gives each character and level a stable id `bot_<character>_<level>` and a `bot`
  label. No session can hold a bot: `createIdentity` has no pattern for the kind.
- In: **seating.** `domain/bots/botComponent.js` `playComputer` creates the room and seats the character, so the game
  starts at once. The seat keeps `bot { character, level }` and every RoomView carries it. A computer player stays
  connected after a restart, and a room with only computer players left closes as empty. A game whose person is away
  closes after the two hour away lifetime, because only people count as away (`roomLifetimes.js`). A player has at
  most 3 games against computers going (`MAX_COMPUTER_GAMES`): starting one more, a new game or a rematch the
  computer accepts, ends the oldest as a forfeit. Starts of one person run one at a time, so parallel requests
  cannot pass the limit.
- In: **driver.** `domain/bots/botDriver.js` watches every saved room change (new `ROOM_EVENTS.CHANGED`). When a
  computer player has something to do it waits a human-like pause (400 to 900 ms in production, zero in tests), reads
  the room again, checks the moment has not passed, and acts through the room component like a person: a move on its
  turn, a decline of a chess draw offer made on the person's own turn (new optional `Bot.answer`), or accepting a
  rematch the person asked for. It never asks for a rematch itself. It retries a failed write twice. On start up and
  at every housekeeping sweep it plans for every stored room, so a computer whose turn it was when the last process
  stopped, or whose plan was dropped, moves again. Every move is chosen in the server's one thinking queue
  (`thinkingQueue.js`), which rests after each search as long as it took.
- In: **pure rules.** `domain/bots/botTurns.js` decides what a computer player does from the room alone, with the
  move chosen from the bot seat's own `engine.viewFor` and an RNG seeded from the game's seed and the turn, so the
  same turn gives the same move after a restart.
- In: **rewards (ADR-025).** `fairPlay.js`: the opponent limit is a rolling 24 hours (ADR-021 amendment), each
  character counts as one opponent at every level, and games against computers count toward the hourly limit. A
  counted game against a computer gives at most what is left of `BOT_DAILY_XP` (100) for the UTC day, separate from
  quest XP. The verdict stores it as `credit.botXp [{ playerId, xp, left }]`, so every recount gives the same XP.
  `progress:updated` carries `botXpLeft`. Computer players get no progress, stats, quests or achievements, and
  games against them never move anyone on a leaderboard (`applyMatch`, the weekly XP recount, `countWins`). Their
  XP, and quest bonuses they earned, are kept as `unrankedXp` in progress and left out of every XP board. A guest's
  games against computers moved into an account give only what the account had left of that day's 100 XP.
- In: **web.** Seats label a computer as `computer · <level>`. The room shows "Rocky is a computer player. This game
  counts…". After the game the XP toast says what is left today, or that the game still counts once the 100 XP are
  used up. `useRoom` keeps the newest view by `revision`, because a computer's update can overtake the answer to the
  move it replies to.
- Out: adaptive difficulty (CC-150), more characters and their personalities (CC-190), quick match (CC-051), the
  history of earlier games for the pattern bot (`history` is empty, see notes).

## Acceptance criteria

- [x] A computer character sits in a room with a stable identity per character and level, labelled everywhere.
- [x] The driver moves on its turn after a pause, from its own view only, through the normal move path.
- [x] It survives a restart: rooms are in MongoDB, and its turn is played again on start up.
- [x] It never idles (draw offers are declined at once), never asks for a rematch, accepts one.
- [x] Games against computers never reach a leaderboard, give at most 100 XP a day, and count for the limits.
- [x] The opponent limit is a rolling 24 hours.
- [x] Unit tests for every branch, integration tests on MongoDB through the real server, browser tests.
- [x] `npm run lint`, `npm run format:check`, `npm run test:coverage`, `npm run test:e2e` pass.

## Plan / notes

- `roomComponent` changes are small and additive: an optional `botTurns` dependency (its default changes nothing),
  the `CHANGED` event, the `bot` label on seats and views, `markEveryoneAway` leaving computers connected, and a room
  with only computers closing. The gateway gets an optional `botComponent` and forwards `botXpLeft`.
- RoomViews now carry `revision` (the stored room's version). Found while testing: with a pause of zero, the
  computer's reply could reach the browser before the answer to the person's own move or join, and the older answer
  then replaced the newer view. `useRoom` keeps the newer one. The same race existed in principle between two people.
- Rock Paper Scissors levels: the RPS bot has two levels, so Rocky offers Easy (random) and Hard (pattern reader).
  Pip and Queen Vee offer three.
- The bots contract has `history` (earlier games in the room). The room keeps only the current game, so the driver
  passes an empty history. Reading earlier games from match history would need the match records, which are written
  in the background. Follow up with CC-190.
- When a guest's games move into an account (ADR-014), a game against a computer that still counts is given only
  what the account had left of that day's 100 XP. The part taken away is stored as `credit.botXp[].withdrawnXp` with
  `withdrawnFrom`, and progression takes it out of the guest's totals before merging (ADR-021 rules 5 and 6).
- Games against computers give quest progress and the quests' bonus XP (ADR-025 rule 3). A bonus completed by a game
  against a computer is unranked: it adds to XP and level but to no board. A bonus completed by a game between people
  is ranked as before. Decided in the review of PR #61 from ADR-025 rule 2 ("any leaderboard").
