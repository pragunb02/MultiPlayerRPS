## Problem

Once CC-174 to CC-176 count how the site is used, the owner still has nowhere to look. The CC-233 console shows
games and players from `matches`, not where people get stuck. When the owner adds a new banner or a longer home
page, they want to open one page and see whether visits still turn into games, which controls are dead or raged at,
which errors rose with the last build, and how slow pages and presses feel on phones.

## Job to be done

When the owner ships something new, they want one console page that shows funnels, click hotspots, errors, latency
and page speed for any range, with the build that changed them, so they can tell within days whether it made the
site harder to use.

## Appetite

M (up to 6 agent-hours). **Cut line:** first the "by build" view (keep by day), then the latency section (CC-240
may ship its own), then the CSV download. Funnels, click hotspots, errors and page speed are never cut.

## Proposed solution

1. **A console tab**, `/admin/ux` (ADR-036: allowlist, the same 404 for everyone else, `no-store`, `noindex`), one
   entry in `consolePages.js`, loaded lazily like the other views.
2. **The API**, `GET /api/admin/ux?from=&to=&section=`, answered from `telemetryReport.read` (CC-176) with `"<5"`
   already applied, cached in memory 5 minutes per range (ADR-036.4), nothing logged about who looked.
3. **Sections**, in this order, each with the range against the range before it:
   1. **Funnels.** Visit to play (landing `page_viewed` → `gameplay_started`) by entry type; link to seat
      (`room_link` landing → `join.guest` → `guest_started`); sign-up (`auth_form_viewed` → `submitted` →
      `account_created`), and `auth_form_rejected` by field and rule. Ratios of daily totals, labelled as such
      (no ids, ADR-034).
   2. **Clicks.** Top 10 dead click and rage click hotspots by route and control, each with its share of that
      route's presses.
   3. **Errors.** `client_errored`, `request_failed`, `socket_changed`, `server_errored` per day and by build.
   4. **Speed.** `page_speed_measured` p75 LCP, INP, CLS and TTFB by route and device, against the Core Web Vitals
      "good" lines; time to first move p75 by entry (CC-220).
   5. **Latency.** `action_waited` p50 and p95 per control (CC-240).
   6. **Interruptions** and the **weekly report**: a slot for CC-313.
4. **Charts** reuse `AdminPage/charts.jsx` (no chart library). Every number is text, never HTML.
5. **A "by build" switch** for errors and speed: the last 5 builds side by side.
6. **CSV download** of what is shown, `"<5"` kept as written.
7. **Behind the flag** `console_ux` (CC-312, admins audience).

## Non-goals

- Anything shown to players, or shared outside the console.
- Per-person paths, session replay, coordinate heatmaps.
- Ops dashboards: server timing and alerts stay in Grafana (ADR-055). This page shows the player's side.
- Statistical tests. It shows counts, ratios and percentiles; the owner judges.

## Rabbit holes

- **Funnels without ids.** Daily ratios can exceed 100 % (a reload counts a landing twice, a game started from an
  older page load). Cap the display at 100 %, say "ratio of totals" in the label, and never call it conversion.
- **Too many numbers.** Each section opens with one headline and its change; the tables are below it.

## Instrumentation

None added. Reads `telemetry_daily` through `telemetryReport.read` (CC-176). The flag's success event: the owner
opened the tab and a section loaded.

## Threat model

1. **What are we building:** an admin-only page over anonymous totals.
2. **What can go wrong:** someone else finds or reads it; a small total points at one player; a value stored by a
   forged event renders as HTML; the page leaks that it exists.
3. **What we do about it:** ADR-036 allowlist and identical 404; `"<5"` on the server; values come from closed lists
   and render as text; `no-store`, `noindex`, nothing logged about viewers.
4. **Good enough?** The same model as the CC-233 console, which passed its security review; no new data class.

## Privacy checklist

- **Data:** anonymous daily totals and percentiles; no person, no id.
- **Retention:** none added; reads 13 months of totals.
- **Who sees it:** admins in `ADMIN_ACCOUNT_IDS` only.
- **Minors (ADR-028):** nothing to change, no person is shown.
- **Defaults:** the tab is off until the flag is on; the range defaults to whole days, never a partial today.

## Alternatives considered

- **Grafana dashboards for product numbers:** would send product data to a third party and mix it with ops (ADR-055
  keeps them apart).
- **A separate admin app:** a second build and auth path for one page.

## Research (written before any code)

1. **Our code today.** The CC-233 console (`AdminPage/`, `consolePages.js`, `charts.jsx`, `domain/analytics/`) gives
   the allowlist, the `"<5"` rule, the range picker and charts. The Flags tab (CC-312, in review) adds a console
   page in the same way.
2. **Other products.** PostHog's web analytics and Plausible's dashboard both open on a short range with a
   comparison and a few headline numbers, then the tables
   ([plausible.io/docs/funnel-analysis](https://plausible.io/docs/funnel-analysis) for funnels of goals). Google's
   HEART framework (Rodden, Hutchinson and Fu, CHI 2010) groups metrics by Happiness, Engagement, Adoption, Retention
   and Task success; this page is mostly Task success (funnels, errors, dead clicks) and Engagement, with Retention
   left to the CC-233 statuses. Core Web Vitals use p75 and fixed "good" lines ([web.dev](https://web.dev/articles/vitals)).
3. **Best for ClassiCade.** One more console tab built from CC-176's totals, the same safety rules as CC-233, and a
   slot for CC-313's interruption section and weekly report.

## Build notes (2026-10-21, branch `cc-176-177-ux-console`, with CC-176 and CC-313's Week view)

Built on the recommended defaults of the open decisions (they apply 2026-10-22, the coordinator's brief asked for
them): the last 7 full India days against the 7 before; visit to play, link to seat and sign-up first; Core Web
Vitals lines with GROWTH 2.5 where stricter (none is stricter today); a by build view of the last 5 builds. The Status stays Spec review until the owner answers
or the defaults apply (the decision gate).

1. **API.** `GET /api/admin/ux?section=funnels|clicks|errors|speed|latency|interruptions|week|badge&from=&to=`, one
   section per request so each tab loads on its own. A range is whole India days ending yesterday at the latest, at
   most 400 days. Admins only, and the console's 404 also for an admin while `console_ux` (or `console_ux_week` for the
   week and the badge) is off. `domain/telemetry/uxReport.js` works out ratios and colours on exact totals and lets
   only masked values out; it is never told who asked.
2. **`"<5"`** applies to every count, to every share whose part or whole is 1 to 4 (stricter than ADR-036.2, so a
   shown share never gives a hidden count away) and to every percentile of fewer than 5 values. A route test checks
   the raw JSON.
3. **Page.** `/admin/ux` and `/admin/ux/<section>` (the server's admin page rule allows that one extra level), one
   lazily loaded chunk (`UxPage`, about 7 KB gzipped); the first route gains only the API method and the paths. Built
   from CC-323's `PageHeader`, `Sections`, `Section`, `Card`, `Tabs`, `Field`, `Skeleton`, `ErrorState` and
   `EmptyState` and the console's tables, each with its unit, its window and a CSV export. Colours are status roles
   with their word (`ColourBadge`).
4. **Funnels** are steps of daily totals with the ratio to the step before, capped at 100 % and labelled "a ratio of
   daily totals, not a conversion". Link to seat counts `join.guest` presses on room routes only.
5. **Flag** `console_ux` (admins, off, remove by 2027-02-28). Success: the first section that loads.
6. **Not built:** latency by CC-240's server timings (they are Grafana's, ADR-055); the browser test runs on the
   desktop project only, because the flags' rollout is shared.
7. **Tests:** AC-1, AC-2 `adminUxRoutes.test.js`; AC-3, AC-4, AC-5 and AC-7 (`flagPaths("console_ux")`)
   `UxPanel.test.jsx`; AC-6 `uxReport.test.js`; AC-8 `e2e/adminUx.spec.js` (E2E_PORT 4991, 2 passed). Screenshots of
   every tab at 1280x800 and 390x844 with the seeded totals of `e2e/uxTotals.js`. AC-1 to AC-5 and AC-7 were run red
   before the code (missing module, then the page); AC-6, AC-8 and the Week view tests were written with their code.

## Review fixes (2026-10-21, the coordinator's review of the branch)

1. **HIGH, ADR-036.** A rate per 100 (dead and rage clicks per 100 presses, errors per 100 pages, the budget's line)
   multiplied the part before the check, so 3 in 200 showed as 1.5 and gave the 3 away. `ratePer` checks the part and
   the whole first and scales after. Every rate uses it.
2. **No colour for a hidden value.** A colour worked out on exact counts narrows a hidden value, so a value shown as
   `"<5"` has no colour and the badge never counts it.
