## Problem

CLAUDE.md's decision-first rule 7 says a new player-facing feature ships behind a flag with a removal date, and
PROCESS.md has a Rolling out stage, but ClassiCade has no flags. Today a feature is either merged and live for
everyone at once, because merging to `main` deploys to production, or it waits on a branch. There is no way to show
a feature to the owner first, then to a tenth of players, and to turn it off again without a deploy, and no way to
see whether the players who got it did better than those who did not.

## Job to be done

When a builder merges a new feature, the owner wants to turn it on for a few players at a time from the console and
off again at once, so they can ship small changes to production safely and see whether each one helped.

## Appetite

L (up to 2 days of agent time). **Cut line:** first the success counts and the on/off split in the console (keep
exposures only), then the percentage slider (keep off, on and typed percentages), then the canary flag's own
"It works" button.

## Proposed solution

1. **One registry in code**, `packages/shared/src/flags.js`. Each flag: `name`, `description`, `ticket`,
   `default` (always `false`), `removeBy` (a day), `rollout` (`"off"`, `"on"` or a whole percentage 0 to 100),
   `audience` (`everyone`, `signed-in`, `adults`, `admins`), `client` (whether the web app may ask for it) and
   `success` (the one success event, in words). `assertFlagRegistry` checks the shape, and runs at boot and in a
   test.
2. **Buckets on the server only.** A new keyed id label, `KEYED_ID_LABELS.FLAG_BUCKETS`, gives its own key from the
   session secret (ADR-057). The bucket of a player for a flag is the first 4 bytes of
   `idOf([flagName, playerId])` modulo 10 000. A player is in a rollout of `p` % when the bucket is below `p × 100`,
   so raising the percentage only adds players and lowering it only removes them. The bucket is never stored,
   logged or sent.
3. **Overrides without a deploy.** A `feature_flags` collection holds one document per overridden flag:
   `{ name, rollout, updatedAt }`. The flag component reads all of it every 30 seconds into memory. If a read fails
   it keeps the last good overrides for up to 5 minutes, then uses the code's rollout, so a database outage never
   turns a flag on. A change from the console applies in that process at once.
4. **Helpers.** Server: `flags.isOn(name, player)` (a Promise of a boolean, `player` is `{ id, kind, admin }` or
   `undefined` for a visitor). Web: `useFlag(name)`, `false` until the server answers. An unknown name throws on
   both sides, the registry is checked at boot, and a test reads every `isOn("…")`, `useFlag("…")` and
   `flagPaths("…")` in the source and fails on a name that is not registered.
5. **The client API.** `GET /api/flags?names=a,b` answers `{ flags: { a: true, b: false } }` with
   `Cache-Control: no-store`, only for flags marked `client`. Nothing else about the flag is sent.
6. **Console tab.** `/admin/flags` (the allowlist and 404 of ADR-036): each flag with its description, ticket,
   audience, removal date (marked "past its removal date" when it is), the code's rollout, the rollout in use and a
   form to set Off, On or a percentage, or go back to the code's rollout. `GET /api/admin/flags`,
   `PUT /api/admin/flags/:name` `{ rollout }`, `DELETE /api/admin/flags/:name`.
7. **Counts.** For each flag, each India day and each side (on or off): exposures (each time the flag was worked
   out for someone) and successes (`POST /api/flags/:name/success`, counted on the side the server works out for
   that player). Kept in memory and added to a `feature_flag_counts` collection each refresh with `$inc`. No id of
   any kind. The console shows the last 30 India days with the small-group rule (`"<5"`).
8. **Hygiene.** A test fails when a flag is past its `removeBy` day. A test fails when a flag has no
   `flagPaths("name", …)` suite, the helper that runs a suite once with the flag on and once off. PROCESS.md gets
   "How a feature ships": behind a flag, ramp, remove.
9. **The first flag**, `console_flag_check`, admins only, off: a line on the Flags page that says the flag is on for
   you, with an "It works" button that counts its success. It proves the whole path in production before a real
   feature uses it, and is removed by 2026-12-31.

## Non-goals

- Changing a flag's audience, description or removal date from the console. Those are code, reviewed in a PR.
- Multivariate experiments (more than on and off), targeting by country or device, scheduled ramps.
- Statistical significance in the console. It shows counts and rates; the owner judges.
- Flags inside socket handlers' hot path that read the database per event. `isOn` reads memory, except for the
  adults audience, which asks the account store once per call.
- A hosted flag service (see Alternatives).

## Rabbit holes

- **Per-person exposure counts.** Counting people would need a per-player set, which ADR-034 rules out. We count
  evaluations and say so in the console.
- **Caching per player on the web.** `useFlag` asks once per mount. No client cache, so a change shows on the next
  page.
- **Writes per request.** Counts are kept in memory and written as one bulk `$inc` each 30 seconds.

## Instrumentation

Two anonymous counters per flag, per India day, per side (`on` or `off`): `exposures` and `successes`, in
`feature_flag_counts` (`flag`, `day`, `side`, `exposures`, `successes`, `expiresAt`). No player, session, device or
network id, no free text, no URL (ADR-034). They are product counts, not operations telemetry: nothing is added to
the OpenTelemetry instruments of ADR-055, and the flag names are not sent to Grafana.

## Threat model

1. **What are we building?** A registry, a server-side evaluator, three admin routes, two player routes and two
   collections.
2. **What can go wrong?** A player learns or chooses their bucket (and so who else is in a test); a non-admin
   changes a rollout; a player inflates success counts; the database is down and a flag flips; counts single out a
   person; an unknown name silently reads as off.
3. **What are we doing?** The bucket is an HMAC under a key only the server has and never leaves it; the client gets
   booleans only. Admin routes sit behind `requireAdmin` (404 for others), the CSRF guard and JSON-only bodies, and
   validate the name against the registry and the rollout against `off`, `on` or 0 to 100. Successes count only on
   the side the server works out, inside the API rate limit. Outage: last good, then code. Small counts are `"<5"`.
   Unknown names throw and fail tests.
4. **Good enough?** A player can still post successes up to the API limit; counts are a guide, not a ledger. Accepted
   and written in ADR-073.

## Privacy checklist

- **Data:** per flag, per day, per side, two numbers. Overrides: a flag name, a rollout and a time.
- **Retention:** counts 90 days (TTL on `expiresAt`); overrides until the owner clears them or the flag is removed.
- **Who sees it:** the owner in the console. Players see only whether a feature is on for them.
- **Minors (ADR-028):** the `adults` audience reuses `accountComponent.adultsAmong` (CC-152's age rule), so a minor
  or an account of unknown age never gets an adults-only flag. Guests are never adults.
- **Defaults:** every flag starts off (`default: false`, `rollout: "off"`); only an admin can change a rollout.

## Alternatives considered

- **PostHog, Unleash, GrowthBook or LaunchDarkly.** Good products, but each sends player ids (or a hash) to a third
  party or needs another service to host, and ADR-034 keeps analytics first party with no ids. Our flags need under
  500 lines and use the store we have.
- **Env vars per flag.** Needs a deploy (a Render restart) to change, which is what flags are for avoiding.
- **Bucket on the client** (a random number in web storage). The player could pick their bucket, and web storage is
  allowlisted (CC-103).
- **A hash of the plain player id** (SHA-1 like PostHog). Anyone could work out the buckets of known ids. The keyed
  HMAC of ADR-057 cannot be worked out without the key.

## Research (written before any code)

1. **How our code does it today.** There are no flags. Behaviour switches are constants in code
   (`REPLY_EMAIL_ONLY_FOR_ADULTS` in `domain/feedback`) or env vars read at boot (`config/index.js`), so every
   change is a deploy. The pieces a flag system needs exist: `utils/keyedIds.js` makes per-purpose HMAC ids under
   labels derived from the session secret (ADR-057); `accountComponent.adultsAmong` is CC-152's age rule;
   `service/http/adminAccess.js` is the console's allowlist and 404 (ADR-036); `@classicade/shared` `peopleCount`
   is the small-group rule; `utils/indiaTime.js` has India days (ADR-034.2). The gaps: nothing stores a
   changeable setting, nothing counts a product event (ADR-034 counts come from game records), and the console has
   no write besides the feedback inbox.
2. **How other products do it.**
   - **Martin Fowler's site, Pete Hodgson, "Feature Toggles (aka Feature Flags)", 9 October 2017,
     martinfowler.com/articles/feature-toggles.html.** Four kinds: release, experiment, ops and permission
     toggles, by how long they live and how dynamic they are. Decouple the decision point from the decision logic
     (a toggle router), keep toggles few, treat them as inventory with a carrying cost, and add expiry dates or
     "time bombs", tests that fail when a toggle outlives its date. Test both the on and the off configuration of
     each release toggle. Our registry is the router, `removeBy` is the time bomb, `flagPaths` is the two
     configurations.
   - **PostHog** (posthog.com/docs/feature-flags, read 2026-10-20; the open-source `posthog-node` evaluator):
     a percentage rollout hashes the flag key and the person's distinct id (SHA-1 of `"key.distinct_id"`, the first
     15 hex digits divided by 0xFFFFFFFFFFFFFFF), so the bucket comes from the flag and the person, not the
     condition, and stays the same as conditions change. Rollouts go down to 0.01 %. The hash is not keyed, and the
     distinct id goes to PostHog.
   - **Unleash** (docs.getunleash.io/reference/stickiness, read 2026-10-20): MurmurHash3 of the `groupId`
     (the flag name by default) and `userId` (or `sessionId`), normalised to 1 to 100. A user is in when their
     number is at most the rollout percentage, so raising it adds users, lowering it removes those above, and going
     back restores the same users. A shared `groupId` correlates flags. The SDKs keep the last fetched toggles
     and a backup file, so the app keeps working when the server is away.
   - **Google SRE, _The Site Reliability Workbook_, chapter 16 "Canarying Releases" (O'Reilly, 2018,
     sre.google/workbook/canarying-releases).** Release to a small, representative share first, compare it with a
     control group over the same time rather than with "before", choose a few metrics that matter, and keep the
     canary small and short so a bad change hurts few people and rolls back fast. Our on and off counts on the same
     days are that control comparison.
3. **What is best for ClassiCade.** A solo owner, one small Render instance, a privacy rule with no ids in analytics
   (ADR-034) and minors on the site (ADR-028). So: our own small evaluator on the server, keyed with an HMAC as
   ADR-057 already does for seat and match ids (stronger than PostHog's and Unleash's plain hashes, because nobody
   can work out a known player's bucket), per-flag buckets like Unleash's `groupId` so two experiments are
   independent, monotonic ramps like both, overrides in our own MongoDB read into memory with a last-good fallback
   like Unleash's SDKs, counts with no id at all (unlike both, which count persons), shown with our small-group
   rule, and Fowler's time bombs and both-path tests in CI. The console is the toggle router's control panel, behind
   the allowlist we already have.
