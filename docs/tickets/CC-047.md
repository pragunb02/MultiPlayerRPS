## Why

Invites travel as links in chat apps. Until now every link previewed as a bare "ClassiCade" with no picture, and
search engines saw the same title and description on every page, because crawlers read the HTML the server sends
and never run the app.

## Scope

- In:
  - A shared page list `packages/shared/src/site.js`: `describePage(pathname)` gives the share title, description,
    own path, whether to list it, and the preview image. `PUBLIC_PAGE_PATHS` lists the pages for the sitemap.
    `gameForSlug` moved here from `paths.js` (still re-exported there) so both sides read old game URLs the same.
  - Web: `PageTitle` also renders `<meta name="description">` and either `<link rel="canonical">` (home, lobbies,
    leaderboards, legal pages) or `<meta name="robots" content="noindex">` (rooms, account pages, old URLs, 404).
    No page had to change. `main.jsx` removes the server written tags at boot (`app/serverHead.js`) so they never
    describe the wrong page after the first navigation.
  - Server (`service/http/webApp.js`, `pageHead.js`): every HTML response carries that page's title, description,
    canonical or noindex, Open Graph and Twitter card tags, all values HTML escaped. An invite link previews as
    "Join my Chess game on ClassiCade" with the Chess image. Unknown pages answer **404** with the app, which still
    renders its own not found page. `/robots.txt` and `/sitemap.xml`. API routes are unchanged.
  - Preview images: `apps/web/public/og/{classicade,rock-paper-scissors,tic-tac-toe,chess}.png`, 1200 by 630, drawn
    from the app's own SVG art and tokens by `npm run og-images -w @classicade/web` (`apps/web/og/`).
- Out: server side rendering of page content, per room details in previews, structured data (JSON-LD), redirects
  with 301 for old URLs (the app replaces them, and they are `noindex`), smaller images (see follow-ups).

## ADR-0xx (proposed): one shared page list for head tags, written into index.html by the server

- **Context.** Crawlers and link preview bots do not run JavaScript. The web app already titles each page (React 19
  hoists `<title>`), but the HTML from the server was the same for every URL.
- **Decision.** Page descriptions live once, in `@classicade/shared` (`describePage`). The web router of the
  server reads the built `index.html` at boot, removes its default title and description (marked
  `data-server-head`), and for each request writes that page's tags before `</head>`. The same answer decides the
  status code: 404 where the app has no page. The web app renders the description and canonical from the same list,
  and removes the server's tags at boot.
- **Why.** No server side rendering framework, no second copy of the texts, no database lookup per page: a room
  preview names the game from the URL alone, so it says nothing about whether a room exists or who is in it, and
  link previews of rooms that have closed still read correctly. Escaping is in one place (`escapeHtml`).
- **Consequence.** `site.js` knows the URL shapes of `paths.js` (ADR-011). `paths.test.js` checks the two agree:
  every page in `PUBLIC_PAGE_PATHS` is a link the app builds, and every invite path matches `paths.room`.

## ADR-0xx (proposed): the site's public address is the first `ALLOWED_ORIGINS` entry

Previews, canonical links and the sitemap need absolute URLs. Instead of a new environment variable, the first
allowed origin (already required in production and already the site's own address) is used. Documented in
`docs/DEPLOYMENT.md`. Revisit if the site ever serves several public hosts with different canonical addresses.

## ADR-0xx (proposed): preview images are committed PNGs drawn from the app's art

The cards are React components (`apps/web/og/OgCard.jsx`) using the real art and design tokens, rendered by Vite
and screenshotted by Playwright's Chromium, which the browser tests already install. The PNGs are committed, so the
production build needs no browser and no image library. `apps/web/og/images.test.js` fails if a game has no image
or an image has the wrong size, so a new game cannot ship with a broken preview.

## Decisions on details

- Rooms are **not** disallowed in `robots.txt`: some preview bots obey it and would then show no preview for an
  invite. Rooms carry `noindex` instead and are never in the sitemap.
- A badly formed room code (not six letters and digits of the room alphabet) is a 404, a well formed but unknown one
  is 200 (we do not look rooms up for crawlers).

## Follow-ups (proposed tickets)

- The PNGs are about 300 KB each. Some apps (WhatsApp) prefer previews under 300 KB: compress them (for example
  with a palette PNG step in the script) once a suitable dependency free option is chosen.
- `og:locale` and translated descriptions when the site gets languages.

## Acceptance criteria

- [x] Meta description per page, canonical for listed pages, noindex for the rest (web and raw HTML)
- [x] Open Graph and Twitter card tags in the raw HTML of game and invite links, with self-hosted images
- [x] `/robots.txt`, `/sitemap.xml` (static pages and lobbies and leaderboards, no rooms)
- [x] 404 status for unknown pages, the app still shows its own page
- [x] Unit tests: `site.test.js`, `pageHead.test.js`, `webApp.test.js`, `PageTitle.test.jsx`, `serverHead.test.js`,
      `paths.test.js`, `og/images.test.js`. Browser tests: `e2e/crawler.spec.js`, `e2e/visitor.spec.js`
- [x] Existing browser tests that open unknown pages declare the 404 they now get
