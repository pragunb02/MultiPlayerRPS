## Research (written before any code)

### 1. How our code does it today (origin/main at `c35daaa`, read on 2026-10-18)

1. `apps/server/src/service/http/loginThrottle.js` (CC-117, ADR-035 point 5) keeps two maps in the server process.
   1. `failures`: keys `"<email>\n<address>"` and `"<email>\n"`, each with a count and when its 15 minute window
      ends.
   2. `known`: email to a map of up to 10 addresses that signed in to it, each with the time, kept 30 days.
2. `authRoutes.js` passes the normalised email and `clientIpKey(req)` (`ip:<address>`, IPv6 grouped by /56).
3. Nothing reads the maps from outside except `remembered()`, which returns two sizes for the pruning tests.
4. **The gap (CC-241 F3).** For 30 days the process holds, in plain form, which addresses each email signed in
   from. A heap dump, a crash report or a debugger attached in production would hand over a list of players' emails
   with their home and work addresses. The throttle only ever needs to ask "have I seen this same pair before", so
   it never needs the plain values.

### 2. How others do it (sources fetched 2026-10-18)

1. **OWASP Authentication Cheat Sheet:** "The counter of failed logins should be associated with the account itself,
   rather than the source IP address", and lockouts must not let an attacker lock other people out. Nothing in it
   needs the plain identifier kept, only a counter per identifier
   (https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html).
2. **Plausible Analytics** never keeps the address. It keeps `hash(daily_salt + domain + ip + user_agent)` and a
   random salt that is deleted after its time (https://plausible.io/data-policy).
3. **Cloudflare rate limiting** counts per characteristic (`ip.src`, a header, a visitor id) for the rule's period
   only (https://developers.cloudflare.com/waf/rate-limiting-rules/parameters/).
4. A plain SHA-256 of an email or an IPv4 address is not enough: both can be guessed by trying candidates. A keyed
   hash (HMAC) with a key the attacker does not have can not.

### 3. What is best for ClassiCade

1. **HMAC-SHA-256 with a random key made when the throttle is made**, kept only in the process. The throttle's
   counts already die with the process (ADR-035: a restart forgets them), so a key with the same life loses
   nothing, needs no env var and never has to be rotated by hand. Once the process ends, nobody can link a hash to
   an email.
2. Each key names what it is for, so a hash for "failures of this pair" can never collide with one for "failures of
   this email". The parts are joined as a JSON array, so no email or address can be split in a way that matches
   another.
3. `known` becomes the hash of the email to a map of hashes of the email and address pair. A hash of the address
   alone would let two emails that signed in from the same place be linked by their equal inner keys. With the pair
   hash nothing links one email's entries to another's.
4. Hashes are 16 bytes as base64url (22 characters). That is less memory than most emails and collisions are
   impossible in practice.
5. The rules, numbers and behaviour do not change. Every existing test stays as it is. A new public method `keys()`
   lists every key the throttle holds, so a test can prove none is an email or an address.
6. The HTTP rate limits (express-rate-limit) and the socket admission counts still key by address, for 1 to 60
   minutes or while connected. They are short lived and listed in DATA.md. They are not part of this ticket.

## Why

A memory dump of the server should not be a list of emails with the addresses they sign in from (CC-241 F3).

## Scope

- In: `loginThrottle.js` keeps HMAC hashes only. A test that the state holds no email and no address. DATA.md and
  the privacy page (with CC-248).
- Out: the other in-memory limits (point 6). Shared counters for a second instance (CC-061).

## Verification

1. Three tests in `apps/server/src/service/http/loginThrottle.test.js` were committed failing first: no key holds
   any part of an email or an address, every key is distinct (an address gets a different name per email), and two
   throttles give the same names only with the same random key. All 16 earlier tests pass unchanged, so the rules
   of ADR-035 point 5 behave as before. `authLockout.test.js` passes.
2. No env var was added. The key is 32 random bytes per throttle, so it dies with the counts.
3. Local, under heavy machine load (load average above 180): `npm run lint` and `npm run format:check` pass.
   `npm run test:coverage` ran the whole suite: 3574 passed, and 9 integration tests in
   `server.integration.test.js`, `server.restart.integration.test.js` and `bots.integration.test.js` timed out at
   5 seconds. Run again alone, all three files pass (33 tests), so the timeouts were the load. CI runs the full suite.
4. Browser tests touched by the page: `E2E_PORT=4978`, `visitor.spec.js` and `accessibility.spec.js` on desktop
   and mobile. 40 passed. One mobile focus check (Back focuses the heading) timed out once under the load and then
   passed 6 times in a row alone.
