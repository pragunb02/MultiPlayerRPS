## Why

The owner finished a game, waited a while, asked for a rematch and got "Room not found". Two causes, both
reproduced with tests that fail on `main`:

1. Rooms lived only in the server's memory (`createInMemoryRoomDao` in `server.js`). Every deploy, every crash and
   every time the free hosting plan put the idle server to sleep deleted every room. The browser then reconnected,
   rejoined and was told the room did not exist. Reproduced by `server.restart.integration.test.js` and
   `e2e/restart.spec.js`, which both fail when the composition root is switched back to the in-memory DAO.
2. Rooms closed far too early: a finished room 10 minutes after the last activity, and a room whose seats were all
   disconnected after 5 minutes. A phone that locks disconnects its socket, so a player who looked away for a few
   minutes lost the game. Reproduced by the two "(the bug)" tests in `roomComponent.lifetimes.test.js`.

When a room really was gone, the page said "There is no room with the code …", which reads like a broken link.

## Scope

In:

1. A MongoDB room DAO (`persistence/roomDao.js`, collections `rooms` and `closed_rooms`) with the same contract as
   the in-memory test double. A shared contract suite (`testing/roomDaoContract.js`) runs against both. Writes
   name the version they read (optimistic versioning is kept). Indexes: `code` (unique), `seats.playerId`, `dueAt`,
   `expiresAt`, and `closed_rooms.code` (unique), `closed_rooms.closedAt`, created at boot by `ensureIndexes`.
2. The room component is asynchronous now. Every change reads, decides and saves as of the version it read. When
   two requests change the same room at the same moment, the loser decides again on the winner's room (up to five
   attempts), so no update is lost. `GAME_FINISHED` is published only after the finished room is saved.
3. Room lifetimes in one place, `domain/rooms/roomLifetimes.js`:

   | Room                                    | Closes                                           | Reason                 |
   | --------------------------------------- | ------------------------------------------------ | ---------------------- |
   | waiting, nobody joins                   | 30 min after the last activity                   | `expired`              |
   | finished                                | 30 min after the game ended (the rematch window) | `rematch-window-ended` |
   | playing, every player away              | 2 h after the last activity                      | `abandoned`            |
   | playing, someone connected but no moves | 24 h after the last activity                     | `abandoned`            |
   | last player presses Leave               | at once                                          | `empty`                |
   | record of a closed room                 | forgotten 24 h after the room closed             |                        |

   The rematch window is fixed when the game ends and sent in the RoomView (`rematch.until`), so the result panel
   shows "Rematch available for 12:34". Asking for a rematch does not move it. A room whose time is up is closed
   the moment anyone touches it, so the window ends on time even between two sweeps.

4. Closed rooms leave a record (code, game, reason, time) for a day. Joining such a room answers the new error code
   `GONE` (HTTP 410 equivalent) with `details: { reason, gameId, closedAt }`. The web app shows "Room closed", the
   reason in plain words and "Start a new <game> game". New rooms never get a code that closed in the last day.
5. Restarts: the old process does not record its sockets being cut while it shuts down. The new process marks every
   seat as away (nobody is connected to a process that has just started) and applies any game deadline that passed
   while no server ran (a chess flag), before it accepts connections. Browsers reconnect and rejoin by themselves.
   Chess clocks keep counting from the stored timestamps, so the time the server was down counts as thinking time.
6. Test only options for `startServer`: `now` (the clock) and `rooms: { lifetimes, sweepIntervalMs }`. Production
   passes neither and runs on the standard lifetimes.

Out:

1. Several server instances at once (CC-061). During a deploy with overlap, players briefly connected to the old
   instance do not see updates made through the new one until they reconnect. Moves are never lost, because both
   instances write through versioned saves.
2. Persistent challenge links (CC-139).

## Acceptance criteria

- [x] A deploy, a crash or a sleep in the middle of a game, or while a rematch is asked for, keeps the room, the
      seats, the game state, the log, the rematch requests and the series. Players continue without reloading.
- [x] Chess clocks stay correct across a restart, and a flag that fell while the server was down is applied at
      startup.
- [x] A finished room can be rematched for 30 minutes, and the panel counts the time down.
- [x] A phone that comes back from the lock screen within 2 hours finds its game.
- [x] Opening a closed room explains why and offers a new game of the same kind.
- [x] Tests cover the change at every level, `npm run lint`, `npm run format:check`, `npm run test:coverage`,
      `npm run test:e2e` (twice) and `npm audit --audit-level=high` pass.

## ADR-017 (accepted 2026-10-17, recorded in DECISIONS.md): rooms are stored in MongoDB, with explicit lifetimes

**Context.** Rooms were kept in memory (CC-015) with a note that a Redis DAO would come for scaling (CC-061). On a
single free-plan instance that sleeps when idle, memory loses every room several times a day.

**Decision.** Store rooms in the MongoDB we already run (ADR-003), one document per room, written with optimistic
versioning. Keep lifetimes as named business rules in one module. Keep a small closed-room record for a day.

**Why MongoDB and not Redis now.** No new service, no new dependency, no new cost. A room is one small document and
changes a few times a minute. The DAO contract stays the same, so CC-061 can still swap in Redis for horizontal
scale without touching anything above the data layer.

**Consequences.** Every room action is one read and one write to MongoDB, a few milliseconds on the same region.
The every second deadline check asks only for rooms whose stored `dueAt` has come, using an index. Two new
collections appear in production. They are created on first use and need no migration, because there were no
stored rooms before.

## Plan / notes

1. Domain decisions are pure functions handed to one `change()` loop, so a retry after a concurrent save reruns
   only the decision.
2. `markEveryoneAway` keeps `lastActivityAt`, so a restart does not extend the life of an abandoned room.
3. The e2e server (`e2e/server.mjs`) now owns the in-memory MongoDB and runs the app as a child process
   (`e2e/app.mjs`). When the app stops, a new one starts on the same port and database. Tests restart it the way
   the platform does, with SIGTERM for a deploy and SIGKILL for a crash (`e2e/serverControl.js`). There is no admin
   endpoint. Short lifetimes for one test are passed to the next app process through the same control folder.
   Restart tests run after all other browser tests and one at a time (`playwright.config.js`).
4. Found by the browser tests: when both players' rematch countdowns ended together, one player could ask in the
   moment between the room being deleted and its closed record being written, and was told "Room not found".
   Closing now first marks the room document as closing (versioned), so a closing room always reads as closed.
   An integration test checks that in between state.
5. Found along the way: the browser test "a guest is invited to keep their name with an account" was flaky on
   mobile (it opened `/profile` before the guest session existed). It now waits for the guest name first.

## Verification

Unit, with an injected clock:

1. Every lifetime boundary: a moment before and exactly at the end, for waiting, finished, away and idle rooms,
   counted from the right moment (last activity, end of game), and the closed record forgotten after a day.
2. The owner's bug: a rematch asked for after 15 minutes on the result screen, and a phone back after 30 minutes.
3. A rematch can be accepted a moment before the window ends, and is refused with `GONE` at the end.
4. Two joins at the same moment both get a seat. A room that keeps changing fails after five attempts. A code taken
   a moment ago, or closed recently, is skipped. Rooms that closed or changed between being listed and being
   handled are skipped by the sweeps. Storage failures are reported, not hidden.
5. After a restart every seat is away and the last activity is unchanged.
6. Web: the rematch countdown in server time (whatever the device clock says), the room page rejoining when the
   window ends, every closed reason in words, a closed room before the join answered, and the new game link.

Integration on real MongoDB (`server.restart.integration.test.js`, `roomDao.integration.test.js`):

1. Restart in the middle of Rock Paper Scissors with a hidden choice pending, then finish the round.
2. Restart while a rematch is asked for, then accept it: the series is kept.
3. After a restart nobody shows as connected until their socket rejoins.
4. Chess: White thinks 50 seconds, 40 of them while the server is down. The clocks read 10:00 and 9:50 on rejoin
   and 9:10 for White after the next move.
5. A bullet flag that fell while the server was down is applied at startup, and the game ends on time.
6. A waiting room that expired answers `GONE` with the reason after a restart.
7. The DAO contract, nested state and empty objects round trip, other database errors pass through, indexes exist.
8. Startup fails cleanly when stored rooms cannot be settled.

Browser, desktop and mobile (`e2e/restart.spec.js`):

1. A deploy in the middle of Rock Paper Scissors: the hidden choice stays hidden (on screen and on the wire), the
   game goes on.
2. A crash during Tic-Tac-Toe: the board is kept, a reload shows it, and the game is played to a win.
3. A deploy while a rematch is asked for: after a reload the request is still there and accepting starts the game.
4. A long wait on the result screen with an 8 second window: the countdown shows, the room closes for both players
   with the reason, a reload and a friend opening the old link see the same, and "Start a new Rock Paper Scissors
   game" leads to the lobby.
