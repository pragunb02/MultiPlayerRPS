## Problem

The invite chooser moves focus to its heading on load, for screen readers, and Chromium and Firefox draw a large
focus ring around it before the player has pressed anything. **Still on `main` at 48f1511e:** CC-309 changed only
the home page's focus-ring test (its list count), and the design contract (#160, CC-314) says nothing about focus
moved in code. The new browser test failed on `main` in Chromium (outline `solid` on the chooser's heading on load)
and in Firefox (the same, and no ring on a new page's heading after Enter on a link).

**Root cause.** Each screen that focuses a `tabIndex={-1}` target styled it on its own, and relied on
`:focus-visible`, which browsers decide for themselves when code moves focus. Chromium matches it for a focus made
before any key or click, so `JoinChooser.module.css`'s `.heading:focus-visible` drew its ring on load. Firefox does
not match it for a heading focused after a key press, so keyboard players lost the ring there. The other targets
hid the ring for everyone, keyboard players too: the challenge page's heading (`.heading:focus { outline: none }`)
and the pass-and-play hand-over heading. The whole class, found by searching `apps/web` for `tabIndex={-1}`,
`tabindex` and `.focus(`:

| Target                                   | Focused when                    | Before                                  |
| ---------------------------------------- | ------------------------------- | --------------------------------------- |
| Invite chooser heading (`JoinChooser`)   | on load                         | ring on load in Chromium and Firefox    |
| Challenge page heading (`ChallengePage`) | on load                         | never a ring, not even for the keyboard |
| Hand-over heading (`PassAndPlayShell`)   | each hand-over                  | never a ring                            |
| A new page's `h1` (`PageAnnouncer`)      | after a press that changed page | browser's own `:focus-visible`          |
| The dialog (`Modal`), no controls        | on open                         | browser's own `:focus-visible`          |
| The board's region (`PassAndPlayShell`)  | each turn                       | off on purpose: the board draws it      |

## Fix

One shared rule: `app/inputModality.js` puts `using-keyboard` on the root element on a key press and takes it off
on a click or a touch, and `global.css` draws no ring on a focused `[tabindex="-1"]` unless that class is there.
The global focus rules sit in `@layer focus`, below every unlayered style, so a component's own ring or opt-out
(the chess squares' roving `tabindex`, the board region's `outline: none`) always wins, whatever order the
stylesheets load in. A first version used `:where()`, but then specificity tied and global.css, which loads after
the component modules, won: the review of this fix found the board region drawing a ring after a key press. The ad-hoc rules in the three screens are gone, and the design contract says how to do it.
No inline styles: the class is set with `classList`, which the strict CSP allows.

**Research.** How our code does it: the table above. Sources checked: the `:focus-visible`
heuristics leave focus moved by script to the browser (Selectors 4, `:focus-visible`, and the HTML standard's
focus steps), which is why the two engines differ, as this ticket's test measured. The WICG `focus-visible`
polyfill answers the same question by tracking whether the last input was a key or a pointer and marking the
page, which is the approach taken here. `focus({ focusVisible })` would be the native answer, but its support
differs between engines, so it is not relied on.

## Acceptance criteria

- **AC-1** Given a visitor opens an invite link, when the chooser moves focus to its heading on load, then the
  heading draws no outline, and after Tab the next control draws the 3 px focus ring.
- **AC-2** Given a visitor opens a challenge link, when the page moves focus to its heading on load, then the
  heading draws no outline, and after Tab the next control draws the 3 px focus ring.
- **AC-3** Given a new page's heading focused after a click, then no outline; after Enter on a link reached with
  Tab, the heading draws the 3 px ring.
- **AC-4** Given a pass-and-play game started with the keyboard, when the board's region takes the focus, then it
  draws no outline of its own (its board draws the ring).

## Test

`e2e/focus-ring.spec.js` (desktop Chromium, Firefox and WebKit): AC-1 failed on `main` in Chromium and Firefox,
AC-3 failed in Firefox; AC-4 failed in Chromium against the first `:where()` version. All pass after the fix. `app/inputModality.test.js` covers the class.
