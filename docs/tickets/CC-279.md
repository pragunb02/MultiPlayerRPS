## Research (written before any code)

Sources were read on 2026-10-19 unless another date is given. "General knowledge" carries a confidence level.

### 1. How our code does it today

1. The k-factor in [EVENTS.md](../analytics/EVENTS.md) §4 counts players brought by a link as a landing
   `page_viewed` with `entry = room_link`, then `join.guest`, then `guest_started`, against shares from
   `invite.copy` and `invite.share`. `entry` comes from the route (a room) or from the referrer's host checked
   against a fixed list.
2. CC-217's result share links to the game page (`/games/<slug>`), not a room, because a finished room closes after
   30 minutes. A game page landing is not `room_link`, and a link opened from the WhatsApp app usually has no
   referrer (general knowledge, medium confidence), so it lands as `direct`. Those players would be missing from k.
3. ADR-032.2 makes k of 0.15 or more for two weeks the gate for the public launch, so an under-count would hold the
   launch back for the wrong reason.
4. A `ref` parameter is already an idea in IDEAS.md (GROWTH.md §7.2). This ticket is the share-link half of it.

### 2. How others do it

1. Campaign parameters such as `utm_source` and `utm_medium` are the common way to tell channels apart (general
   knowledge, high confidence). They carry a channel, not a person.
2. Referral links in many apps carry a per-user code, which ties a new player to the inviter (general knowledge,
   high confidence). ADR-034 rules that out for us: no player, session or device id in any event.

### 3. What is best for ClassiCade

1. Every link our share UI builds gets `?via=` with one value from a fixed list: `wa` (the WhatsApp button), `share`
   (the device sheet), `copy` (Copy link). Nothing else, never an id, never the sharer.
2. The landing `page_viewed` gains `entry = shared_link` with `via` when the parameter is present and valid. An
   unknown value is ignored. The web app then replaces the address without the parameter, so a link copied again
   does not carry it on.
3. The k-factor in EVENTS.md counts `shared_link` landings beside `room_link`. This changes the event catalogue, so
   the owner accepts it before it is sent (ADR-034), and Growth and analytics owns the metric.
4. Game pages already have a canonical link (ADR-042), so `?via=` does not create duplicate pages for search.

## Why

Without it, the launch gate cannot see result shares, which are the main loop (GROWTH.md §3.8).

## Scope

- In: the parameter on our share links, the landing `entry` value, the address clean-up, the EVENTS.md change for
  the owner.
- Out: any per-player referral code (never), referral rewards (CC-149), the k-factor report itself (Growth, CC-176
  and the console).

## Acceptance criteria

- [ ] Every share link our UI builds carries `via` from the fixed list, and a unit test checks no other parameter.
- [ ] A landing with a valid `via` counts as `shared_link`; an invalid one is ignored.
- [ ] The address bar loses the parameter after landing.
- [ ] Tests cover the change. `npm run lint`, `npm run format:check`, `npm test` pass.
- [ ] Docs updated: EVENTS.md (owner accepted), BACKLOG, PROGRESS.
