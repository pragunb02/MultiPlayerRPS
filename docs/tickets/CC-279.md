## Research (written before any code)

Sources were read on 2026-10-19 unless another date is given. "General knowledge" carries a confidence level.

### 1. How our code does it today

1. The k-factor in [EVENTS.md](../analytics/EVENTS.md) §4 counts players brought by a link as a landing
   `page_viewed` with `entry = room_link`, then `join.guest`, then `guest_started`, against shares from
   `invite.copy` and `invite.share`. `entry` comes from the route (a room) or from the referrer's host checked
   against a fixed list.
2. CC-217's result share links to the game page (`/games/<slug>`), not a room, because a finished room closes after
   30 minutes. A game page landing is not `room_link`, and a link opened from the WhatsApp app usually has no
   referrer (general knowledge, medium confidence), so it lands as `direct`. Those players would be missing from k.
3. ADR-032.2 makes k of 0.15 or more for two weeks the gate for the public launch, so an under-count would hold the
   launch back for the wrong reason.
4. A `ref` parameter is already an idea in IDEAS.md (GROWTH.md §7.2). This ticket is the share-link half of it.

### 2. How others do it

1. Campaign parameters such as `utm_source` and `utm_medium` are the common way to tell channels apart (general
   knowledge, high confidence). They carry a channel, not a person.
2. Referral links in many apps carry a per-user code, which ties a new player to the inviter (general knowledge,
   high confidence). ADR-034 rules that out for us: no player, session or device id in any event.

### 3. What is best for ClassiCade

1. Every link our share UI builds gets `?via=` with one value from a fixed list: `wa` (the WhatsApp button), `share`
   (the device sheet), `copy` (Copy link). Nothing else, never an id, never the sharer.
2. The landing `page_viewed` gains `entry = shared_link` with `via` when the parameter is present and valid. An
   unknown value is ignored. The web app then replaces the address without the parameter, so a link copied again
   does not carry it on.
3. The k-factor in EVENTS.md counts `shared_link` landings beside `room_link`. This changes the event catalogue, so
   the owner accepts it before it is sent (ADR-034), and Growth and analytics owns the metric.
4. Game pages already have a canonical link (ADR-042), so `?via=` does not create duplicate pages for search.

### 4. Research before the code (2026-10-20)

Read on 2026-10-20 before writing any code.

1. **What exists in code today.** No product telemetry is built. EVENTS.md is Proposed and says "Nothing here is
   built or recorded yet". There is no `POST /api/telemetry` (CC-175) and no browser client (CC-174). ADR-036.4 says
   the owner console reads only what gameplay already stores. The social domain file (§2.2) says a Social ticket
   never adds an event and asks Growth for anything new. So this ticket cannot send or store a count, and must not
   build its own pipeline beside CC-175's. It builds everything up to the send: the marker on every link, the
   landing classified as `shared_link` from a fixed list, the address cleaned, and the landing kept for CC-174.
2. **The share code (CC-217, #103).** `ShareRoom.jsx` builds one room link and uses it for the input, Copy link,
   the WhatsApp message and the share sheet. `resultShare.js` builds one game page link for the WhatsApp message,
   the share sheet and the copied message. Each channel needs its own link, so the link is built per channel.
3. **A precedent for cleaning the address.** `app/staleBuild.js` (CC-181) already removes its own `reloaded`
   parameter with `history.replaceState(history.state, ...)` before the router reads the address, and remembers it
   only in memory. The marker follows the same pattern.
4. **Canonical links and previews.** The server writes the head from `req.path`, which has no query
   (`webApp.js`, `pageHead.js`), and the web app's `PageTitle` builds the canonical link from the path only. So
   `?via=` changes neither `og:url` nor `<link rel="canonical">` (ADR-011, ADR-042). A test pins it.
5. **History API** (https://developer.mozilla.org/en-US/docs/Web/API/History/replaceState): `replaceState`
   changes the current history entry's URL and state, does not add an entry, and "won't cause the browser to load"
   the new URL. So Back never returns to the marked address and nothing reloads.
6. **Campaign parameters** (https://support.google.com/analytics/answer/10917952): `utm_source` and `utm_medium`
   name the referrer and the medium ("google, newsletter4", "cpc, banner, email"). They name channels, not people.
   We use one short parameter of our own, `via`, so no tool reads it as someone else's campaign.
7. **Search and duplicate addresses**
   (https://developers.google.com/search/docs/crawling-indexing/consolidate-duplicate-urls): Google's own example of
   a duplicate is a page with a tracking parameter (`?gclid=ABCD`). A `rel="canonical"` link to the clean address
   consolidates them. Our game pages already have one.
8. **Referrers** (https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/Referrer-Policy): the default policy
   sends at most the origin across sites, and our own wa.me link is `noreferrer`. A link opened from the WhatsApp
   app usually carries no referrer at all (general knowledge, medium confidence). So the referrer cannot tell a
   WhatsApp landing apart, and a marker on the link is the only signal.
9. **Others.** Spotify and YouTube share links carry a per-share id (`si=`), which ties a listener to the sharer
   (general knowledge, high confidence). That is exactly what ADR-034.1 rules out, so our marker has three fixed
   values and nothing else.

## Design (2026-10-20, before code)

1. **One list, in `@classicade/shared`** (`shareChannels.js`): the parameter name `via`, the channels `wa`
   (WhatsApp), `share` (the device's share sheet) and `copy` (copied to the clipboard, or the link shown in the
   invite box), `isShareChannel(value)`, and the landing entry name `shared_link`. Shared, because CC-175's
   ingestion validator must check `via` against the same list.
2. **Links.** `paths.js` gets `withShareChannel(url, channel)`, which puts `via=<channel>` on a link and throws on
   anything not on the list, so a typo fails a test instead of shipping. ADR-011 keeps every URL in that module.
3. **ShareRoom.** The invite box and Copy link show and copy the `copy` link. The WhatsApp message carries the `wa`
   link. Share… hands the share sheet the `share` link. When the sheet refuses and the link is copied instead, the
   copied link is the `copy` one, because that is how it travels.
4. **ShareResult and resultShare.** `resultShare` returns one message per channel: `whatsapp` (wa.me with the `wa`
   link inside), `shareUrl` for the sheet, and `message` (with the `copy` link) for the copy fallback.
5. **Landing** (`app/landing.js`, called in `main.jsx` right after `recoverFromStaleBuild`, before the router):
   1. `shareChannelOf(href)` is pure. It returns the channel when the address has exactly one `via` with a value
      on the list, otherwise "". Two `via` values, or any other value, count as no marker.
   2. `takeLanding({ window, document })` reads the address once, removes every `via` from it with
      `replaceState` (keeping the history state, the other parameters and the hash), and returns the landing:
      `{ entry: "shared_link", via }` or `{ entry: "", via: "" }`. Any `via`, valid or not, is removed, so nothing
      foreign is re-shared or bookmarked. An address without `via` is left exactly as it is.
   3. It writes `data-cc-entry="shared_link"` and `data-cc-via` on the page's root element, as MatchFrame writes
      the phase "for tests and telemetry". CC-174 reads them for the landing `page_viewed`. Nothing is stored in
      web storage, cookies or on the server, and nothing is sent.
6. **EVENTS.md** gains `shared_link` in `page_viewed.entry` with a `via` field (one of the three), and the k-factor
   row counts `shared_link` landings beside `room_link`. Marked proposed (CC-279) for the owner, as ADR-034 asks.
7. **Owner console.** It shows no shares today (it needs telemetry, `sections.jsx`), so nothing changes there. When
   CC-176 and CC-177 add the totals, they follow ADR-036.2.
8. **Server.** No new route, collection, index or setting. A server test pins that `?via=` does not change the
   status code, the canonical link or `og:url`.

## Why

Without it, the launch gate cannot see result shares, which are the main loop (GROWTH.md §3.8).

## Scope

- In: the parameter on our share links, the landing `entry` value, the address clean-up, the EVENTS.md change for
  the owner.
- Out: any per-player referral code (never), referral rewards (CC-149), the k-factor report itself (Growth, CC-176
  and the console).

## Acceptance criteria

- [x] Every share link our UI builds carries `via` from the fixed list, and a unit test checks no other parameter.
- [x] A landing with a valid `via` counts as `shared_link`; an invalid one is ignored.
- [x] The address bar loses the parameter after landing.
- [x] Tests cover the change. `npm run lint`, `npm run format:check`, `npm test` pass.
- [ ] Docs updated: EVENTS.md (written, waiting for the owner's acceptance), BACKLOG, PROGRESS (the coordinator).

## Plan / notes

After CC-217's text PR and the telemetry client (CC-174). One small PR.

### What was built (2026-10-20)

1. `packages/shared/src/shareChannels.js`: `SHARE_CHANNEL_PARAM` (`via`), `SHARE_CHANNELS` (`wa`, `share`,
   `copy`), `isShareChannel` and `SHARED_LINK_ENTRY` (`shared_link`).
2. `apps/web/src/app/paths.js`: `withShareChannel(url, channel)`. It throws a `RangeError` for anything not on the
   list.
3. `ShareRoom.jsx`: the invite box and Copy link use the `copy` link, the WhatsApp message the `wa` link and Share…
   the `share` link. A share sheet that refuses falls back to copying the `copy` link.
4. `resultShare.js` and `ShareResult.jsx`: `shareUrl` for the sheet, `message` with the `copy` link for the copy
   fallback, `whatsappMessage` with the `wa` link. The `url` and `whatsapp` fields are gone, because nothing outside
   the tests read them.
5. `apps/web/src/app/landing.js`: `shareChannelOf(href)` and `takeLanding({ window, document })`, called in
   `main.jsx` right after `recoverFromStaleBuild` and before the router. It writes `data-cc-entry="shared_link"`
   and `data-cc-via` on `<html>`, then removes every `via` from the address with `replaceState`.
6. `docs/analytics/EVENTS.md`: `page_viewed.entry` gains `shared_link` with a `via` field, and the k-factor row
   counts `shared_link` landings beside `room_link`. Both are marked "proposed in CC-279" for the owner.

### What is not built, and why

1. **Nothing is sent or stored yet.** The telemetry client (CC-174) and ingestion (CC-175) do not exist, and
   ADR-036.4 and the domain rule (SOCIAL_AND_SHARING.md §2.2) keep this ticket from adding its own pipeline. The
   landing is classified and written on the page. CC-174 reads `data-cc-entry` and `data-cc-via` for the landing
   `page_viewed`, and CC-175's validator checks `via` with `isShareChannel`.
2. **The owner console** shows no shares today, so it is unchanged. When CC-176 and CC-177 add share totals, they
   hide groups under 5 (ADR-036.2).

### For the owner

1. Accept, change or cut the EVENTS.md change: `entry = shared_link` with `via`, counted in k beside `room_link`
   (ADR-034 asks for this before any event is sent).
2. The invite box now shows the link with `?via=copy` at the end, so a player sees the same link they copy.

### Deployment impact

None. No new route, collection, index, migration, setting or dependency. Links shared before this release have no
marker and land as they did. The server already builds the head and the canonical link from the path only, and a
new test pins it.
