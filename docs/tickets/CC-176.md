## Problem

CC-175 keeps raw events for 30 days only. The owner wants to compare this month's friction with the month a feature
shipped, and the weekly UX report (CC-313) needs last week next to the week before, every week, for a year. Reading
30 days of raw events on every console view would also be slow on the free instance. Nothing turns raw events into
small daily totals, and there is no scheduler: the server has no nightly job at all today.

## Job to be done

When an India day ends, the owner wants that day's events turned into small, anonymous daily totals kept 13 months,
so the console can show trends, weeks and before-and-after without keeping any single event longer than 30 days.

## Appetite

M (up to 6 agent-hours). **Cut line:** first the room event totals from CC-242 (they wait for CC-242), then p95
(keep p50 and p75), then the backfill command. The scheduler, catch-up, the rollup spec and the TTL are never cut.

## Proposed solution

1. **A rollup spec in code**, `apps/server/src/domain/telemetry/rollups.js`: for each event, the field groups it is
   totalled by (for example `control_pressed` by `route` and `control`; `dead_clicked` by `route` and `control` or
   `element`; `page_speed_measured` p50, p75 and p95 of each timing by `route` and `device`; CC-313's interruption
   events by `surface` and `outcome`). Only listed groups are totalled, so cardinality is known in advance. A test
   computes the worst-case rows per day from the catalogue's closed lists and fails above 20 000.
2. **Daily totals**, `telemetry_daily` collection: `{ day, event, group: { field: value }, count, p50?, p75?, p95? }`,
   unique on `day`, `event` and `group`, TTL 13 months (400 days). Counts are exact; percentiles are exact from the
   raw values of that day.
3. **When it runs.** An in-process scheduler in the composition root: at 00:30 India time, and on boot, and every
   hour, it finds the complete India days of the last 30 with no `telemetry_daily_runs` record (or the last 2 days
   always) and rolls them up. A lock document stops two processes doing the same day. The 10-minute uptime check
   keeps the free instance awake (DEPLOYMENT.md), and catch-up covers a sleep or a restart.
4. **Idempotent.** Each run replaces a day's rows in one bulk write, so re-running yesterday after late beacons gives
   the same totals.
5. **Room events.** When CC-242 exists, its room events are totalled into the same collection by the fields of
   EVENTS.md 3.4. No id leaves that collection.
6. **Read API for the console**, `telemetryReport.read({ from, to, event, group })`, applies ADR-036.2 (`"<5"`) on
   the server before anything leaves it.
7. **Backfill** `node apps/server/scripts/rollup-telemetry.mjs --from YYYY-MM-DD`, for the owner after a fix.
8. **Behind the flag** `telemetry_rollup` (CC-312, server-only). Off means the scheduler does not run.
9. **Ops signals** (ADR-055): `telemetry_rollup.runs` with `outcome` and a named log line `telemetry rollup failed`
   with `step`, so a stuck job alerts in Grafana with the other ops alerts.

## Non-goals

- The dashboard (CC-177) and the weekly report screen (CC-313).
- Per-person or per-visit joins across events (ADR-034: impossible by design).
- Hourly totals kept beyond 30 days. The busiest-hour chart reads raw events for the last 30 days.
- A queue or a separate worker service.

## Rabbit holes

- **Cardinality.** `route` times `control` times `device` times `player_kind` can explode. Only the spec's groups are
  built, and the worst-case test caps them.
- **Percentiles in MongoDB.** `$percentile` needs MongoDB 7 or later, on Atlas and on the in-memory test server
  alike. Check both versions first; otherwise sort and pick in Node per group, which is fine at 100 000 events a day.
- **India midnight in UTC.** 18:30 UTC. Every day key comes from one helper shared with CC-233.

## Instrumentation

Reads `telemetry_counts`, CC-175's hourly counters (no single events, review of 2026-10-21), and, later, the CC-242 room events. Writes `telemetry_daily`, anonymous totals
only. Ops: `telemetry_rollup.runs` by `outcome`, the named line `telemetry rollup failed` (ADR-055, no player
data). The flag's success event: a day rolled up.

## Threat model

1. **What are we building:** a scheduled job that turns raw anonymous events into totals kept 13 months.
2. **What can go wrong:** a total of one person kept for a year; the job blocks the event loop and lags games; two
   processes double-count; a broken run silently leaves gaps.
3. **What we do about it:** `"<5"` on read for every total; groups only from closed lists; batch reads with yields
   between groups; a lock and idempotent replace; a run record, a counter and a Grafana alert.
4. **Good enough?** Totals hold no id, so a year of them says nothing about a person beyond what a day already did.

## Privacy checklist

- **Data:** daily counts and percentiles per listed group. No id, no text.
- **Retention:** 400 days by TTL; raw events still go at 30 days (CC-175).
- **Who sees it:** the owner's console, with `"<5"`.
- **Minors (ADR-028):** nothing changes: totals carry no person.
- **Defaults:** the flag is off until CC-175 has stored a week; the spec decides every group in code review.

## Alternatives considered

- **`$inc` daily totals at ingestion:** no job, but no recompute after a fix and no percentiles.
- **GitHub Actions schedule:** works while the instance sleeps, but needs a secret admin endpoint reachable from the
  internet for a job the uptime check already makes unnecessary.
- **Render cron job:** a paid service.

## Research (written before any code)

1. **Our code today.** No scheduler. `domain/analytics/` (CC-233) computes India days from `matches` on read and
   caches 5 minutes; its day helper is reused. ADR-036's consequences already name this rollup as the place the
   per-player read should move to at about 500 000 matches.
2. **Other products.** Plausible keeps only aggregate-friendly event rows and computes stats on read in ClickHouse;
   PostHog keeps every event and queries on read. Neither fits 512 MB. Google's HEART paper (Rodden et al., CHI 2010)
   recommends tracking metrics over time against a goal rather than as one number, which is why 13 months and weeks
   matter. Core Web Vitals report at p75 ([web.dev](https://web.dev/articles/vitals)), hence p75.
3. **Best for ClassiCade.** A small in-process job with catch-up, a fixed rollup spec with a row budget, and the
   `"<5"` rule on read.

## Build notes (2026-10-21, branch `cc-176-177-ux-console`, with CC-177 and CC-313's Week view)

Built on the recommended defaults of the open decisions (they apply 2026-10-22, the coordinator's brief asked for
them): in process at 00:30 India time, on boot and hourly; p50, p75 and p95; the last 2 days redone; `"<5"` for every
telemetry total. The Owner answer column is left for the owner, so the Status stays Spec review: the decision gate passes a
built ticket once the owner answers or the defaults apply.

1. **Counters, not events.** Storage changed after review (ADR-034, amended 2026-10-21): the job reads CC-175's hourly
   counters (`telemetry_counts`), an India hour at a time with a pause between hours. Each counter is a value and how
   often it came, so a day's p50, p75 and p95 are exact by nearest rank (to the catalogue's 10 ms). A daily row also
   keeps its timing's bucket counters (fixed edges, every line the console judges against is an edge), and a range of
   days reads its percentile from them as the upper edge of the rank's bucket, never better than the true one.
2. **Rows** (`telemetry_daily`): `{ day, at, event, key, group, count, timings? }`, one row per group, with all of an
   event's timings in it (page speed has five) rather than one row per timing. A field the event left out is `null`,
   so every row of a group has the same fields.
3. **The row budget** is computed from the catalogue's closed lists: 7 746 rows a day at worst against 20 000. Open
   fields keep their busiest values per group (controls 25, elements 25, builds 5) and sum the rest as `(other)`, so a
   forged control name cannot grow the rows.
4. **Leases and runs** (`telemetry_daily_runs`): one record per day with a 10 minute lease, taken with an upsert that a
   second process loses on the unique `_id`. A failure gives the lease back and keeps no run record, so the next tick
   retries. `finishRun` marks it done.
5. **Clock.** `now` is injected (CC-325); the scheduler is `scheduleRollups`, tested with fake timers, one run at a
   time, stopped on shutdown before the database closes.
6. **Flag** `telemetry_rollup` (server-only, everyone, off, remove by 2027-02-28): the job asks it with no player, so
   only On runs it. Success: a day rolled up (the `ok` count).
7. **Backfill** is `scripts/bin/rollup-telemetry.mjs --from YYYY-MM-DD` (the lint config has Node globals there, not
   in `apps/server/scripts`). Room events (CC-242) are not built yet, so the spec has none.
8. **Tests:** AC-1 and AC-4 `rollups.test.js`, AC-2, AC-3, AC-7 (`flagPaths("telemetry_rollup")`) and AC-8
   `rollupJob.test.js`, AC-5 `telemetryDailyDao.integration.test.js`, AC-6 `telemetryReport.test.js`. AC-1 to
   AC-5, AC-7 and AC-8 were run red (missing module) before the code. AC-6 was written with its module.

## Review fixes (2026-10-21, the coordinator's review of the branch)

1. **Whole days only.** Catch-up and backfill roll up only days whose hourly counters are all still kept
   (`oldestFullDay`): the day 30 back has lost its first hours to the TTL, so it is never written short.
2. **Linear and polite.** `rollUpDay` groups counters in place (it was quadratic) and awaits a pause after each group
   of each event. An hour's counters are added one at a time, not spread into `push`.
3. **No half days.** `replaceDay` writes the new rows under a new `version`, switches the day's run record to it in
   one update, then deletes the old version. `read` takes each day in its run record's version and reads again if a
   version changed while it read, so nobody sees or caches a partial day.
4. **The database picks the group.** Rows carry `fields` (indexed with `event` and `day`), and a series leaves the
   timings' buckets in the database.
5. **Shutdown waits for one day at most.** The scheduler passes `isStopped`, asked before each day.
