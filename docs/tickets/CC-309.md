### 2. How other projects handle the same problems

1. Vitest merges the coverage of all projects into one istanbul map, and istanbul merges functions by their
   source location (`istanbul-lib-coverage` `FileCoverage.merge`, keyed by `decl`/`loc`). Two different source maps
   for one file give two entries for the same function. Vitest's own docs say the transform decides the map
   ("Source maps can change based on projectName and transform mode", `@vitest/coverage-v8` provider, v5.0.5).
2. `@vitejs/plugin-react` 6 defaults `include` to `/\.[tj]sx?$/` and passes it to Vite as `oxc.jsxRefreshInclude`.
   Vite 8's `vite:oxc` plugin transforms any id that filter matches (`node_modules/vite/dist/node/chunks/node.js`,
   `oxcPlugin`), so every plain `.js` file outside `node_modules` is reprinted by oxc in that project. The plugin's
   README documents `include` for exactly this: limiting which files it touches.
3. Playwright's guidance for shared state: a test must not depend on what other tests did before it
   (https://playwright.dev/docs/best-practices#make-tests-as-isolated-as-possible, read 2026-10-20).

### 3. What is best for ClassiCade

Fix each cause where it is, keep every check as strict as it was, and add no retries or longer timeouts.

## Root causes

### A. Coverage gate (latest run): one file counted twice

`packages/shared/src/build.js` (CC-303, #127) showed 66.66 % of functions, lines 22-53, although its own 21 tests
call every function. The web project's React plugin had oxc reprint every `.js` file, including the shared
packages the web tests load through `@classicade/shared`. oxc's source map is token-level; the node project keeps
the file as written with a fine map. For arrow functions the two maps put the start at different columns
(`parseCommit` at 21:27 in node, 21:13 in web), so the merged report had six functions instead of four, and the two
web copies were never called. Function declarations (`calendarVersion`, `isCalendarVersionOf`) map the same in
both and merged. Reproduced locally with `build.test.js` plus one web test (`paths.test.js`): 4/6 functions. This
is the same effect the CC-253 builder met with engine functions, and why the branch floor needed slack for
"shared files loaded by both projects" (CC-084).

Fix: the web project's plugin is `react({ include: /\.jsx$/ })`. JSX lives only in `.jsx` files (checked: no
`.js` file under `apps/web/src` has JSX), so `.js` files are no longer reprinted and both projects map them the
same. Same pair of tests after: 4/4. Full `npm run test:coverage` after: 375 files pass, functions 100 %,
statements 99.96 %, branches 99.76 % (from 99.39 %).
Merged in #134.

### B. Focus-ring test (Chromium and Firefox): the home page has a second list

`visual.spec.js` "the game cards can be reached and opened with the keyboard" began with
`expect(page.locator("main li")).toHaveCount(3)`. #123 (CC-144) added the "Daily puzzle" section after the games,
with its own `<ul>` and one card, so `main li` became 4. The page is right: the daily card is its own section,
reachable by keyboard after Chess with the same focus ring. The selector counted every list item on the page, not
the game cards. Fix: count the listitems of the "Games" region (3), and the "Daily puzzle" region's (1). The
keyboard walk and the ring check are unchanged. Failed first on `main` (`--project=desktop`, "Expected: 3,
Received: 4"); passes after on desktop and Firefox. #114's Feedback button is in the footer, not a list item, and
the walk stops after the three game names, so it does not touch this test.

### C. Leaderboard test (phone only): the player's own row left the top 50

`leaderboard.spec.js` "a guest who wins is on the boards…" checks that the account (Riya, who lost the game) sees
its own row as "you" on the overall board, with `getByRole("listitem").filter({ hasText: username })`. The board
lists the top 50. Riya has 10 XP, and since #118 (CC-291) guests are ranked too, so on the one server a CI part
shares, the phone project, which runs after the desktop one, found 95 players ahead: the error context shows
"Your rank: #96 You 10 XP" pinned under the list. That pinned row is the page doing the right thing
(`LeaderboardPage.test.jsx` "pins your row below the list when you are outside it"). The test assumed a young
server. Reproduced locally: `--repeat-each=60 -x` on `main` failed at the 26th run, on the same line.

Fix: Riya's own place is its list row marked `aria-current="true"`, or the pinned "Your rank: #N You X XP" row,
and exactly one of the two is shown, and no other row is marked current. The same 60 repetitions after passed the
line every time.

Left as is, and written down: the guest's own rows in the same test (Bob, 1 win and about 60 XP) must be in the top
50, because "everyone sees the guest under its Guest name" needs the row in the list. In the local repetitions Bob
left the RPS top 50 at the 51st run. In CI the parts run each spec once, so the board held far fewer, and the
test passed in both runs. If CI ever has 50 players with more wins than one, this test needs its own board
(the owner may want a ticket; not opened here, because of the freeze on new tickets that are not bugs).

### D. `chessRatings.integration.test.js` timed out (CC-306): the test read colours by player id

`playChess` picked White with `started.game.view.colors[joiner.id]`. Since #116 (CC-253, ADR-057) views name
players by opaque seat id, the viewer's own as `you`, so that lookup was always `undefined` and the host was
always taken for White. When the room's seed made the joiner White, the first move was refused with
`NOT_YOUR_TURN`, the ack was not checked, the game never ended, and `eventually` polled for a rating for 5 s, the
same as the test's own limit: a timeout, about half the time. Shown first: with only the ack checked, the test
failed fast with `{ code: "VALIDATION_FAILED", details: { reason: "NOT_YOUR_TURN" } }` on some runs and passed on
others.

Fix, without a longer timeout or retries:

1. The colour comes from `colors[started.you]`, and every move's ack must have no error.
2. One MongoDB and one server for the file (`beforeAll`), not one server per test: each start built every index,
   about 2.3 s on a laptop, more on a busy runner. The index test reads the indexes of that server's database.
3. No timer: the test waits for the pipeline's `chess ratings applied` line through a new `captureLogger().once(msg)`
   (resolves at once if the line was already written), then reads the rating once. `captureLogger.test.js` covers
   it.

After: 8 runs in a row, both tests pass, the main one in 323-350 ms (it had taken 1-5 s when it passed).

### E. `puzzleCatalog.test.js` timed out once: one test did over 6,000 chess.js moves

"is solved by playing each solution through the referee" walked all 406 puzzles in one test. chess.js finds every
move among all legal moves and writes its SAN, and the referee replays from the start on each call, so the test made
6,350 `move` calls and 3,960 `isCheckmate` calls (counted locally): 0.5 s on a free laptop core, 1.3 s with V8
coverage, and 5.2 s in the coverage job, where the runner's cores are shared by every worker. "is valid in every
field" took 1.8 s there for the same reason. Fix: both checks run one test per week of seven puzzles
(`it.each` over the 58 weeks), so every puzzle is still checked and each test does about 1/58 of the work (12 ms at
most locally). The referee itself is unchanged: in production it judges one move at a time.

### F. Lines gate after #136 (main run 39393642043): a load-harness line covered only by timing

With A to E on `main`, all 6284 tests passed and lines were 99.99 % against 100 %: `scripts/load/swarm.mjs` line
250 (CC-289, #126), where a player who played the computer and does not ask for a rematch leaves the room. No test
was sure to get there. The one swarm run with a computer mixes people and computers with `rematchShare: 0.5` and
stops once each kind of game has been counted, so whether a computer player turned a rematch down before then
was up to timing. The earlier main runs reached it by luck. Fix: a test "leaves the room when it does not ask for
a rematch, and starts a new game" with `computerShare: 1`, `rematchShare: 0` and only RPS, which waits (on the
recorder, not a timer) for a second `room:play-computer rps` and asserts a `room:leave`, no `room:request` and no
failures. It covers line 250 every time: 3 runs of the file, 14 passed, the new test in about 0.7 s.
