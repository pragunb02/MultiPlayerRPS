## Why

The bot strength and long contract tests in `packages/games/src/bots` made the CI unit job about 5.5 minutes. Every
pull request waits for that job, and almost all of the extra time is the chess bot playing whole games against itself.
Those games prove the bot is strong and never stuck, which matters, but it does not change from one unrelated pull
request to the next.

## Research

### How our code does it today

- Every `*.test.js` file runs on every pull request through one command, `npm run test:coverage` (`vitest run
--coverage`, `.github/workflows/ci.yml`, job "Lint, format, audit, unit + integration (coverage gates)"). There is
  no way to mark a test as slow, and no scheduled test workflow (the only schedules are `backup.yml` and `uptime.yml`).
- Measured on 2026-10-18 with `vitest run packages/games --reporter=json` on a shared laptop (load average 150, so
  every number is inflated, but the ranking holds). The games package takes 107 s of test time in total and the
  top eight tests are 104 s of it:

  | Test                                                                                    | Time   |
  | --------------------------------------------------------------------------------------- | ------ |
  | `chessBot.test.js` strength: Strong beats Beginner in every seeded game (3 games)       | 32.8 s |
  | `chessBot.test.js` levels: only ever plays moves the engine accepts (5 random games)    | 16.8 s |
  | `chessBot.test.js` contract: makes the same moves from the same seed                    | 16.6 s |
  | `chessBot.test.js` contract: plays only legal moves, finishes every game (4 + 2 + 1)    | 15.3 s |
  | `chessBot.test.js` strength: Club beats Beginner in every seeded game (4 games)         | 8.5 s  |
  | `chessEngine.test.js` position history (CC-180): random games against a chess.js replay | 6.2 s  |
  | `board.test.js` move generation: matches chess.js through many random games             | 4.0 s  |
  | `board.test.js` position fingerprints: matches the FEN fingerprint after every move     | 3.5 s  |

  Everything else in the package is under 1 s per test. The RPS and Tic-Tac-Toe bots are fast (the exhaustive
  "Unbeatable never loses" walk is 0.8 s for both starters) and stay as they are.

- Coverage gates are 100 % lines and functions, 99.9 % statements and 99 % branches over the whole repo
  (`vitest.config.mjs`). Today the slow tests are part of what reaches those numbers, so removing them without care
  could drop lines in `bots/chess/search.js`, `board.js` or `chessBot.js`.

### How other projects do it

- **Google test sizes.** Google sorts tests into small, medium and large by the resources they need and runs the
  large ones less often, on a schedule or before release, not on every change ("Software Engineering at Google",
  chapter 11 "Testing Overview", O'Reilly 2020, section "Test Size"). Confidence high, general knowledge.
- **Chess engines.** Stockfish runs a quick `bench` (a fixed node count over fixed positions, a few seconds) and
  `perft` move generation checks in its CI, and measures playing strength separately on Fishtest with thousands of
  games and a statistical stop rule (SPRT), never inside unit tests (github.com/official-stockfish/Stockfish
  `.github/workflows`, tests.stockfishchess.org, both as of 2025). Confidence high, general knowledge. Our split is
  the same idea at a much smaller scale: legal moves, determinism and mates on every change, strength games nightly.
- **Vitest test tags** (introduced in Vitest 4.1.0, we use 5.0.5). A test or a `describe` block gets
  `{ tags: ["slow"] }`, tags are declared in the config with their own options such as `timeout`, and
  `vitest --tags-filter="not slow"` leaves them out. Vitest refuses a tag that is not declared (`strictTags`, on by
  default), so a typo cannot quietly hide a test (vitest.dev/guide/test-tags, read 2026-10-18).
- **GitHub Actions schedules** run only on the default branch, can be delayed at busy times such as the start of
  every hour, and are switched off after 60 days without activity in a public repository. `workflow_dispatch` adds a
  "Run workflow" button once the file is on the default branch (docs.github.com, "Events that trigger workflows",
  read 2026-10-18).
- Other common ways, considered: a separate file suffix such as `*.slow.test.js` with its own config (works, but
  splits one subject over two files and needs a second config to keep in step), or an environment variable read in
  each test file (every file then needs its own switch, and nothing stops a typo).

### What is best for ClassiCade

1. Use Vitest tags. Tag the long tests `slow` where they are, next to their fast siblings, so one file still tells
   the whole story of a bot. Declare the tag once in `vitest.config.mjs` with the long timeout those games need.
2. `npm test`, `npm run test:coverage` and the PR job run with `--tags-filter="not slow"`. A new
   `npm run test:all` runs everything with coverage, and a new workflow `nightly.yml` runs it every night and on the
   "Run workflow" button. The nightly job uploads its coverage report too, so the full number is visible.
3. Keep a fast smoke set untagged on every PR: the bot contract with fewer games per level (legal moves, finishing,
   determinism, refusing unknown levels), the mate and promotion tests, a shorter random-position legality walk, and
   one Club beats Beginner game as the small strength check. The full contract, the long legality walk and every
   strength game run nightly.
4. Coverage on PRs must stay at the gates without the slow tests. Check it by running the PR command with coverage
   and reading the per-file numbers for `bots/chess`. If a line is only reached by a slow test, add a small fast test
   for it rather than lowering a gate.
5. Pin it with a test in `scripts/workflows.test.mjs`: the PR job runs the filtered command, the nightly workflow runs
   the full one on a schedule and on dispatch, so the two cannot drift apart silently.

## Scope

- In: Vitest tag, test scripts, the slow tests in `packages/games`, `ci.yml`, a new `nightly.yml`, workflow tests,
  ENGINEERING.md testing section.
- Out: app code, the browser suite (CC-184), changing what any bot does.

## Acceptance criteria

- [ ] The PR unit job no longer runs the long chess games. Every bot still has legal move, finishing and
      determinism checks on every PR.
- [ ] A nightly and manual workflow runs every test, including the slow ones, with coverage.
- [ ] Coverage gates still pass on the PR command alone.
- [ ] Tests cover the change (`scripts/workflows.test.mjs`)
- [ ] `npm run lint`, `npm run format:check`, `npm run test:coverage` pass
