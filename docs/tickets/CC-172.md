## Research (written before any code)

### 1. How our code does it today

The page is a normal scrolling document. Nothing is sized to the screen.

- `components/Layout/Layout.module.css`: `.shell { min-height: 100vh }` with header, main and footer rows. The header
  is at least 4.5rem (72 px) and wraps onto two rows under 40rem. `.main` has `max-width: 72rem` and
  `padding: 2rem 1rem`.
- `pages/RoomPage/RoomPage.module.css`: a room header (game name, Leave room), then `.layout` with
  `margin-top: 1.5rem` and two columns (`minmax(0, 1fr) 20rem`), one column under 48rem. The result, the request
  card (#67: the sticky `RequestBanner`), the board and the save progress card are stacked in the stage, so anything
  above the board pushes it down.
- Chess (`games/chess/ChessBoard.module.css`): a board column of up to 36rem and a 12 to 16rem panel; the board is
  `width: 100%; aspect-ratio: 1` (`Board.module.css`), so its height follows its width, never the screen. Player
  bars with clocks sit above and below it, Offer draw and Resign in the panel.
- RPS and TTT boards are cards with padding; their size follows their content.
- Viewport units in the web app: `100vh` in `Layout.module.css` and `styles/wakingUp.css`, `100dvh` once in
  `Modal.module.css` (`max-height`), `vh` in the confetti fall distances. No `svh`, no `env(safe-area-inset-*)`, and
  `index.html` has `width=device-width, initial-scale=1.0` without `viewport-fit=cover`.
- Buttons have no minimum height in `Button.module.css`; size comes from padding.

Rough budget at 1280×720 for chess, from the CSS above: header 72 + main padding 32 + room header about 48 + gap 24

- turn banner about 40 + top player bar about 48 + a 576 px board + bottom bar 48 is about 890 px, so the own clock
  and bottom rank fall about 170 px below the fold. This is finding **A8 (P1)**: "Your own clock and, on mobile, Offer
  draw and Resign are below the fold". `e2e/match-shell.spec.js` checks the main controls of every state at 1280×720
  and 390×844 and marks six chess states `test.fail` with "CC-172 has to fix this layout". On a phone, the result and
  the request (before #67) pushed the board down and the side panel fell under the board (MATCH_EXPERIENCE.md §1 A2,
  A7, and "the mobile popup covers the bottom two ranks of the chess board" for #42).

Open PR #67 (read 2026-10-18) adds three sticky strips at `top: 0`: `ConnectionBanner` (z-index 20, under the site
header, every page), `RequestBanner` (z-index 10, first in the room), and toasts held while a request is open. Its
own check: the banner "never covers the board (checked at 390×844)". The layout must give these strips a place in
the frame, not stack them over each other.

### 2. How others do it, and the platform rules (read 2026-10-18)

**Game sites.**

- **lichess** sizes the board from the height as well as the width. `ui/lib/css/abstract/_uniboard.scss`:
  `$col2-uniboard-max-height: calc(100vh - header - 1rem)` and
  `$col2-uniboard-max-size: min(max-width, max-height)`; the user's board scale multiplies it. On one column
  (`_layout.scss`) the main width is capped at `100vh − header − 2 × player and clock height − moves height`, so the
  board, both clocks and the move strip fit one phone screen. On wide screens, clocks, users and controls sit in a
  table column beside the board (`_app-layout.scss`), so the board gets the full height. The table hides parts on
  short screens (`@media (min-height: …)` around the move list).
- **lichess mobile** keeps a fixed bottom bar of actions (`_GameBottomBar`), player strips above and below the
  board, and the result as a dialog.
- **Board Game Arena**: "On mobile (vertical): stack secondary elements below the main action zone", no fixed width
  designs, playable at 100% zoom, an Action Bar of at most four buttons, tap targets of at least 32×32 px with
  40 to 44 px recommended (BGA Studio Guidelines).
- **Discord Activities**: respect the platform safe area, watch notches, curved edges and the bottom gesture area,
  keep controls away from the Android back gesture.
- **Poki**: "we strongly advise supporting portrait".
- chess.com and papergames.io: no layout source reachable today; we claim nothing.

**Viewport units** (MDN `length`, caniuse):

- `svh` is the small viewport (browser bars shown): "fixed, and therefore stable", content is never hidden behind
  the browser's bars. `lvh` (and plain `vh`, which equals `lvh`) can be covered when the bars come back. `dvh` "fits
  exactly" but "can cause the content to resize while a user is scrolling a page", with "a performance hit".
- Support: 95.94% globally; Chrome 108, Safari 15.4, Firefox 101, Samsung Internet 21.
- Container query units (`cqi`, `cqb`, `cqmin`): 95.89%; Chrome 105, Safari 16, Firefox 110, Samsung Internet 20.
- Chrome on Android 108 and later resizes only the visual viewport for the on-screen keyboard
  (`interactive-widget=resizes-visual` by default), so the layout does not jump when a keyboard opens
  (developer.chrome.com, "viewport resize behavior", updated 2022-10-28).

**Safe areas** (MDN `env()`): `env(safe-area-inset-bottom)` and friends are 0 on a rectangular screen and the size
of notches or system bars otherwise. Without `viewport-fit=cover` in the viewport meta, browsers letterbox the page
and the insets stay 0 (general knowledge, not on the MDN page).

**WCAG 2.2.**

- **1.4.10 Reflow (AA)**: content works at 320 CSS px wide (a 1280 px window at 400% zoom) without two-dimensional
  scrolling. Content that needs a two-dimensional layout, explicitly **games**, is exempt, but only that part; text
  and controls around it must still reflow. Sticky or fixed headers, footers and toolbars should become static at
  small sizes (technique C34), and fixed content must not cover the focused element (2.4.11 Focus Not Obscured).
  Note 1280×720 at 400% is 320×180: a fixed-height frame cannot fit that, so the frame must fall back to normal flow.
- **2.5.8 Target Size Minimum (AA)**: at least 24×24 CSS px, or spaced so a 24 px circle around each target does
  not touch another. **2.5.5 Target Size Enhanced (AAA)**: 44×44. ADR-020 already sets 44 px for touch targets.

**Our players' screens.** In India in September 2026, Chrome had 90.62% of mobile browsing, Safari 3.61%, Opera
3.51% (StatCounter). The most common mobile screen is **360×800 (15.28%)**, then 393×873, 384×832, 385×854. So
390×844 is not our smallest common phone; 360×800 with the browser's bars shown (roughly 360×690 to 360×730 of
small viewport) is the case to design for.

### 3. What is best for ClassiCade, and why

1. **A frame sized to the small viewport, with the board as the flexible part.** During a match the shell is a grid
   `height: calc(100svh - <header>)` (with a `100vh` line before it for old browsers), rows `banner | match bar |
stage (minmax(0, 1fr)) | action bar`. `svh` because it is stable and never hidden by the browser's bars; `dvh`
   would resize the board while the bars move (MDN), which is bad on budget phones. The stage is a size container
   (`container-type: size`) and a square board takes `inline-size: min(100cqi, 100cqb)`: lichess's
   `min(width, height)` rule, in CSS only, no script measuring, no inline style (CSP, ADR-012). Games declare
   `fit: "square"` (chess, TTT) or `"content"` (RPS) in the registry (CC-157 contract).
2. **Desktop (1280×720): presence, clocks, panel and requests beside the board.** As on lichess, the side column
   holds the presence chips with clocks (CC-168), the panel (moves) and the game's actions are in the action bar
   under the stage. The board gets about 720 − 72 (header) − 44 (match bar) − 56 (action bar) − 24 (gaps) ≈ 520 px,
   and nothing important is below the fold.
3. **Phone (390×844 and 360×800): strips above and below the board, a sticky action bar, a bottom sheet result.**
   - A compact match header (back, game name, sound) instead of the full two row site header while in a match,
     so the board gets about 60 px more. The phase 1 bottom tabs (PRODUCT_VISION §5.1) hide during a match.
   - Opponent strip above the board, your strip below (presence chip, and the clock for chess), as lichess and
     lichess mobile do.
   - The action bar is the frame's last row, so it is "sticky" without `position: fixed`, and it pads by
     `env(safe-area-inset-bottom)` for the gesture bar. At most four buttons (BGA), each at least 44 px high.
   - The request banner takes the match bar's row while a request is open, so the board does not move or shrink
     when a question arrives. Its answer stays 4 s, then the match bar returns.
   - The result is a **non-modal bottom sheet** over the lower part of the stage: headline with reason, series
     change, Rematch (main), New opponent. The board stays visible above it, dimmed, and "View board" lowers the
     sheet to a one line peek with Rematch, so the player can look at the final position. Non-modal, because an
     incoming rematch request in the banner must stay reachable and focus must not jump (ADR-020 item 1). Escape
     lowers it; the headline is announced assertively.
   - Budget at 360×800 (small viewport about 700 px): compact header 56 + match bar 40 + opponent strip 40 + board
     328 (360 − 2 × 16) + your strip 40 + action bar 60 ≈ 564 px. It fits with room for the banner's second line.
4. **Fall back to normal flow when the screen is too short.** Under a minimum height (proposed `max-height: 32rem`,
   which covers landscape phones and desktop zoom of 400%), the frame drops its fixed height, the action bar is
   static, the board takes its width, and the page scrolls. This meets 1.4.10 and C34 (sticky parts become static)
   and keeps 2.4.11 (nothing fixed covers the focus). Landscape phones (844×390) get two columns from the same rule
   as desktop when wide enough.
5. **`viewport-fit=cover` with insets** on the header and action bar, or leave it off. On Android Chrome (90% of our
   phone traffic) the page is letterboxed by default and insets are 0, so this matters mainly for iPhones. It
   touches every page, so it is an owner decision.
6. **Targets**: main controls at least 44×44 (ADR-020), nothing under 24×24 (2.5.8). Chess squares at 328 px are 41 px:
   above 24, under 44, allowed because the board is the game (and squares are adjacent targets within one grid).
7. **Tests make the layout stay right**: the existing fold check, plus 360×800 and a short landscape, plus a reflow
   check at 320 px wide, plus a target size check. Reduced motion: the sheet appears without sliding.

## Why

On a laptop the chess player cannot see their own clock without scrolling, and on a phone Offer draw and Resign are
below the board (A8). On phones generally, anything that appears (a request, the result, a card) pushes the board
around. Our main players are on budget Android phones in portrait (PRODUCT_VISION).

## Scope

- In: the frame grid and its fallback; board fit through container query units and the `fit` field; the desktop
  side column; phone strips, sticky action bar with safe area padding, the banner taking the match bar's row, the
  non-modal bottom sheet result with "View board"; the compact match header; target sizes; the browser test changes.
- Out: moving each game's own pieces into the slots (CC-166, CC-167, CC-168, which remove the last `test.fail`
  entries for chess); the layout check for clipping and overlaps (CC-154); screenshot baselines (CC-155); emotes.

## Acceptance criteria

- [ ] Every state's main controls are on screen without scrolling at 1280×720, 390×844 and 360×800 (the chess
      `test.fail` entries are removed once CC-168 lands).
- [ ] The board does not move or resize when a request opens or closes (checked by its bounding box).
- [ ] On a phone the result is a bottom sheet with Rematch on screen and the board visible above it; "View board"
      lowers it.
- [ ] At 320×180 (400% zoom of 1280×720) the page scrolls in one direction only, outside the board.
- [ ] Every control in the match is at least 24×24 px; main controls at least 44 px high.
- [ ] Reduced motion: no sliding sheet, no banner slide.
- [ ] Tests cover the change
- [ ] `npm run lint`, `npm run format:check`, `npm test` pass
- [ ] Docs updated (BACKLOG status, KNOWN_ISSUES, PROGRESS, MATCH_EXPERIENCE.md layout section)

## Plan / notes

- CSS only, in CSS modules over tokens (ADR-009, ADR-012): new tokens for the compact header height and the action
  bar height, so the frame's `calc` has no magic numbers. No inline style, no script measuring, no new dependency.
- `Layout` learns a "match" mode from the route (a React Router `handle` on the room route) to render the compact
  header; the footer stays below the frame.
- Order: after CC-157 and CC-161, before CC-166, CC-167 and CC-168 (CC-157 "Order of PRs").
- Tests:
  - `e2e/match-shell.spec.js`: add `360×800` to `VIEWPORTS` for the mobile project, and the board stability check
    (bounding box before and after a request in the two `request-asked*` states).
  - A reflow test at 320×180 (`document.scrollingElement.scrollWidth <= innerWidth`) on one state per game.
  - A target size test: every `[data-cc-control]` in `main` is at least 24×24, main controls at least 44 high.
  - Component tests for the sheet (non-modal, Escape lowers it, "View board", focus stays) and the frame's phase
    classes.
  - Keep CI time flat (CC-236): the new viewport reuses the fold test's states and runs only on the mobile project.
- Risks:
  - Old Chrome without `svh` or container units (about 4% of browsers globally, caniuse):
    fall back to `vh` and to a width-sized board (today's look).
  - Fixed-height frames and the browser's own bars on iOS Safari; tested only on the Desktop Safari project today.
  - The sticky banners from #67 (`ConnectionBanner`, `RequestBanner`) need explicit rows in the frame, or two
    sticky strips stack at `top: 0`.
  - Long names and big numbers in the compact match bar (CC-154 stress data) on a 360 px phone.

### Owner decisions

1. Design for **360×800** (India's most common phone screen) as well as 390×844, and add it to the fold test
   (recommended).
2. A **compact match header** on phones while in a match, and the phase 1 bottom tabs hidden during a match
   (recommended).
3. On a phone the **request banner takes the match bar's row** while open, so the board never moves (recommended),
   or it pushes the board down.
4. The phone result is a **non-modal bottom sheet** with "View board" (recommended), or a modal dialog like lichess
   mobile.
5. Desktop puts presence, clocks and the move list **beside the board**, lichess style (recommended), or above and
   below it.
6. Add **`viewport-fit=cover`** with safe area padding on every page (affects iPhones mostly), or leave it off.
7. `svh` for the frame height (recommended) rather than `dvh`.
