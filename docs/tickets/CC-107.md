## Why

SEC-13: any visitor could create rooms and open realtime connections without any cap. One script could fill
MongoDB with waiting rooms and hold thousands of sockets on the single small instance until it fell over. The event
budget was per socket, so opening more tabs bought more events.

## Scope

In:

1. All limits as named business rules in one module, `apps/server/src/domain/rooms/roomLimits.js`
   (`ROOM_LIMITS`, `roomLimits(overrides)` validates overrides like `roomLifetimes`). Production always runs the
   standard values. Tests, the load script and the browser tests pass overrides through `startServer({ rooms: {
limits } })`.
2. At most 3 waiting rooms per player. The fourth answers `CONFLICT` with the message "You already have 3 rooms
   waiting; close one first" and `details: { reason: "waiting-rooms", limit: 3 }` (`ROOM_LIMIT_REASONS` in
   `@classicade/shared`). A waiting room whose time is up does not count, even before the sweep closes it.
3. A global ceiling of 2000 open rooms. Past it, creating a room answers the new `SERVER_BUSY` code (HTTP 503 in
   the error mapping) with "The server is busy, try again in a minute" and `details: { reason: "server-full" }`.
   Joining existing rooms keeps working. The count is MongoDB's `estimatedDocumentCount`, which costs the same
   however many rooms there are.
4. At most 5 realtime connections per browser session and 30 per network address. The address is found the same
   way Express finds `req.ip` with `TRUST_PROXY_HOPS` (CC-106): `clientAddress` in `service/http/rateLimits.js`,
   pinned by a test that compares it with Express for several hop counts and forged chains. IPv6 addresses are
   grouped per /56 like the HTTP limits. A refused handshake answers `RATE_LIMITED` with a message that says what to
   do.
5. One event budget per player shared by all their tabs (burst 20, refill 10 per second, the old per socket
   numbers). A budget is kept after the player leaves until it has refilled, so reconnecting does not refill it.
   `service/realtime/socketAdmission.js` holds the counts.
6. The clock tick: `expireDue` already asks MongoDB only for rooms whose stored `dueAt` has come (CC-101,
   ADR-017). Only running timed games have a `dueAt` above 0. A new integration test pins that the query uses the
   `due_at` index and examines exactly the due room among forty waiting ones.
7. A room gauge in the structured logs every minute: `"room gauge"` with `rooms: { waiting, playing, finished,
open }`, `connections` and `players`.

Out:

1. Limits shared across several server instances (needs a shared store, CC-061).
2. A cap on rooms joined per player. Joining fills a room, it does not create one.
3. Showing a nicer screen for a refused realtime connection. The web app shows its usual "reconnecting" state.

## Limits chosen

| Rule                     | Value              | Why                                                                                       |
| ------------------------ | ------------------ | ----------------------------------------------------------------------------------------- |
| Waiting rooms per player | 3                  | One invite each to a few friends. More is almost always a script or forgotten tabs.       |
| Open rooms on the server | 2000               | About 4000 players, well above what one small instance serves. Rooms close by themselves. |
| Connections per session  | 5                  | One per open tab. Five tabs of one game is already more than anyone plays.                |
| Connections per address  | 30                 | A school or office behind one address stays inside. A script on one machine does not.     |
| Events per player        | burst 20, 10 per s | The numbers the old per socket budget had, now shared by all tabs.                        |

## Acceptance criteria

- [x] Fourth waiting room refused with the friendly typed error. Leaving one frees the place.
- [x] Server busy error past the global ceiling. Existing rooms can still be joined.
- [x] Sixth tab of a session refused. Thirty first connections per address, behind the trusted proxy, forged
      entries do not help.
- [x] One event budget per player across tabs.
- [x] Deadline query uses the index (pinned).
- [x] Room gauge in the logs every minute.
- [x] Limits in one module, configurable for tests and e2e.
- [x] Unit, integration (MongoDB through the real server) and browser tests.

## Plan / notes

1. `roomComponent.js` changes are additive (a `limits` dependency, one check in `createRoom`, `countRooms`), to
   stay out of the way of PR #53 and CC-204. The DAO gets `countOpen` and `countByStatus` at the end of its object.
2. Two rooms created at the very same moment can both pass the per player check. That only lets a player go one
   room over, and the per player event budget makes it hard to repeat. Accepted by the owner on 2026-10-17: no
   lock or unique index is added for it. The same holds for the server ceiling, which counts with
   `estimatedDocumentCount` and can be passed by the few rooms created in the same instant.
3. The counts live in the process. A restart drops every connection anyway.
