## Research (written before any code)

### 1. How our code does it today

1. `GET /health` (`service/http/app.js`) answers `{"status":"ok","database":"up"}`, or 503 with `"down"`. Render's
   health check and the uptime workflow (`scripts/uptime/probe.mjs`) read it, the probe by matching the two fields, so
   new fields do not break it. `GET /api/health` (`service/http/routes.js`) answers `{"status":"ok"}`.
2. The deployed commit is read in one place today, `config/telemetry.js`: `RENDER_GIT_COMMIT`, checked against
   `^[0-9a-f]{7,40}$`, cut to 12 characters as the telemetry service version, `"unknown"` otherwise (CC-286).
3. `render.yaml` and `scripts/renderBlueprint.test.mjs` already list `RENDER_GIT_COMMIT` beside `PORT` as set by
   Render, never declared in the file (ADR-063). Nothing to change there; a new test pins that the server reads it.
4. CC-290 (#114) stamps the web build as `0.1.0+<short sha>` for feedback. That string stays internal to feedback.
5. Nothing tells the owner which commit is live after a merge, short of opening Render's dashboard.

### 2. How others do it (read 2026-10-20)

1. Render sets `RENDER_GIT_COMMIT` (the full sha) at build time and at run time for Git-backed services
   (https://render.com/docs/environment-variables, "Render-provided values").
2. Spring Boot's actuator `/actuator/info` shows `git.commit.id` and `build.version`, written into a file during the
   build (`git.properties`, `build-info.properties`) and read at boot
   (https://docs.spring.io/spring-boot/reference/actuator/endpoints.html). The same split: the build knows git, the
   running process reads a file.
3. Calendar versioning, `YYYY.MM.DD` with a build part, is used by Ubuntu, pip and others (https://calver.org/).
   Taking the date from the commit, not the clock, makes it the same for every build of that commit.
4. Echoing environment values into a response is a classic leak (OWASP ASVS V14.3, unintended information
   disclosure). Only a value that has been checked to be a commit sha is echoed.

### 3. What is best for ClassiCade

1. **Two fields on both health routes**: `"commit"` (the full sha, or `"unknown"`) and `"version"` (the CalVer below,
   or `"unknown"`). Additive: the existing fields and status codes stay as they are.
2. **One config place.** `config/build.js` reads and checks the commit and the version once, at boot. The telemetry
   service version takes its commit from there, so there is one rule for what counts as a commit.
3. **The version, decided by the owner (2026-10-20): date-based and automatic on every deploy**, not a semver bumped by
   hand. It is the commit's UTC date and its short sha, e.g. `2026.10.20+a40ce5b`. The same commit always gives the
   same version, and there is no counter to keep.
4. **Written during the build, read at boot.** The commit's date needs git, and git is certain only in the build:
   Render builds from a checkout, while the Docker image copies no `.git` and a run time checkout is not promised.
   So `npm run build:web` ends with `scripts/build-info.mjs`, which writes `apps/server/build-info.json` (not in git)
   with the commit and its version. At boot the server uses that version only when the file's commit is the commit
   Render says is running, so a stale file can never claim another version. No file, no git or no
   `RENDER_GIT_COMMIT` (a laptop, CI, the Docker image) gives `"unknown"` and never stops the boot.
5. **Checked before echoed.** The commit must be 7 to 40 hex characters and the version must have the exact CalVer
   shape with that commit's short sha. Anything else is `"unknown"`: an arbitrary environment value is never sent.

**Security note.** The repository is public, so the commit sha is already public on GitHub and in every merge. Showing
it on `/health` tells nobody anything they cannot read there. The response holds nothing else from the environment.

## Why

After a merge the owner can see in a second whether the deploy is live, and which commit and day it is.

## Scope

- In: `config/build.js`, `scripts/build-info.mjs`, both health routes, the telemetry version from the same place,
  `build:web`, `.gitignore`, DEPLOYMENT.md (the check after a merge).
- Out: release notes, showing the version in the web app, tagging releases.

## Acceptance criteria

- [x] `/health` and `/api/health` answer `commit` (full sha or `"unknown"`) and `version` (CalVer or `"unknown"`).
- [x] Missing or invalid values give `"unknown"`, never a crash and never the raw value.
- [x] The same commit always gives the same version.
- [x] `RENDER_GIT_COMMIT` stays Render-owned in `render.yaml` and its test.
- [x] DEPLOYMENT.md: compare `/health`'s commit with `git rev-parse origin/main` after a merge.
- [x] Tests that failed first, targeted runs only.

## Decisions

1. **Owner, 2026-10-20:** `/health` shows the deployed commit id and the version as two fields. The version was first
   to be the root `package.json` version (it stays `0.1.0` until releases are versioned). Options put to the owner:
   a semver bumped by hand per release, or a date-based version per deploy.
2. **Owner, 2026-10-20, final:** date-based and automatic on every deploy, from the commit: its UTC day and short sha
   (`2026.10.20+a40ce5b`). No counter, no hand bump. The combined `0.1.0+<short sha>` of CC-290 stays internal to
   feedback.
3. **Built, not computed at boot** (Research 3.4): git is certain only during the build.

## Verification

1. **Tests first.** `packages/shared/src/build.test.js` (21 cases), `config/index.test.js` (the new `build` block and
   the defaults), `service/http/app.test.js` (both health checks, unknown, a bad `RENDER_GIT_COMMIT` never echoed),
   `scripts/build/buildInfo.test.mjs` and the new case in `scripts/renderBlueprint.test.mjs` were run red first.
   `config/build.test.js` was written together with `config/build.js`. Targeted runs only (owner, 2026-10-20):
   165 passed. The new and changed files are fully covered by those tests.
2. **The build step for real:** with `RENDER_GIT_COMMIT` set to the branch head, `node scripts/bin/build-info.mjs`
   wrote `{"commit":"2e23187e…","version":"2026.10.20+2e23187"}`, and without the variable
   `{"commit":"unknown","version":"unknown"}`.
3. **Before (production, 2026-10-20):** `GET /health` → `{"status":"ok","database":"up"}`, `GET /api/health` →
   `{"status":"ok"}`. **After (local, the test app wired as in production):**
   `{"status":"ok","database":"up","commit":"2e23187e7e77d55e64d502eec252a6e866988c14","version":"2026.10.20+2e23187"}`,
   and `"unknown"` for both without Render or with a bad value. The uptime probe still passes the longer body
   (new test).
