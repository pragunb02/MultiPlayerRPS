## Problem

The first route was 203.3 kB gzip of JavaScript (main chunk 191.3 kB plus four preloads; Vite printed 192.79 kB for
the main chunk), against the 150 kB budget. Nothing in CI checked it. Two root causes: every page was imported
eagerly in `app/App.jsx`, and `games/daily/dailyKinds.js` imported `colourName` and `opposite` from
`games/chess/chessGame.js`, which imports chess.js, so home carried the whole chess library. Separately, Lighthouse
measured CLS 0.373 on `/games/chess`. The audit put this down to the lobby, but the layout-shift attribution (below)
shows the cause is in the shell, on every page: the app's own "Waking up" screen (`WakingUp`, CC-232) sat in the
page's flow above `<Outlet />`. While it waits its 600 ms before showing it is invisible but still takes about
340 px, so when the session answers and it goes, the whole page jumps up. Home measured 0.379 and the daily puzzle
0.180 for the same reason, plus its board loading into a one-line placeholder.

## Fix

1. **Lazy pages.** Every page except home is a `lazyRoute` (`app/lazyRoute.jsx`, `app/routePages.js`): `React.lazy`
   with a `preload()`, a `Suspense` fallback of `RouteSkeleton` that is at least a screen tall, so the footer
   stays out of view while the page downloads. The shell (`Layout`, providers, toasts, site requests) and home
   stay eager. The not-found page and the console's gate are lazy too.
2. **Prefetch on intent, as a hint only.** One capture listener on the document (`app/routePrefetch.js`) reacts
   to `pointerover`, `focusin` or `touchstart` on any same-site link. It calls `prefetchRouteFor(pathname)`, which
   adds `<link rel="modulepreload">` for the page's scripts and `<link rel="prefetch">` for its stylesheets
   (`app/routeFiles.js`). Nothing is imported or run. The file list comes from a JSON data block that the build
   writes into index.html (`scripts/build/routeFiles.mjs`, about 0.95 kB gzip of HTML). A data block is never run,
   so the CSP does not change. A hint whose file fails (a stale tab after a deploy, or a dropped connection) only
   fails its own link, which is removed. There is no `vite:preloadError`, so no stale-build reload (review
   finding 1). An earlier version called `import()` on hover, so a stale tab reloaded under a player who had only
   pointed at a link.
3. **One route table.** `APP_ROUTES` in `app/routePages.js` lists every route: its page and props, or a redirect.
   `App.jsx` draws `<Routes>` from it, and `pageFor(pathname)` reads it with React Router's `matchRoutes` and
   follows redirects. So `/leaderboards`, `/u/:username/userprofile` and `/login-signup.html` fetch the page they
   land on, not the not-found page (review finding 2).
4. **Direct loads render the page, not the skeleton.** `main.jsx` awaits `preloadRouteFor(location.pathname)`
   before the first render, which is what React Router's data-router lazy routes do (they load the matched route
   before rendering). Until then the index.html waking screen stays, so nothing flashes or moves.
5. **chess.js out of home.** `colourName` and `opposite` moved to `games/chess/chessColours.js` (no imports).
   `chessGame.js` re-exports them, so its callers are unchanged.
6. **CLS.** The app's waking screen now lies over the top of the page in a zero-height holder
   (`styles/wakingUp.css`, `.wake-holder`), so it takes no room and its removal moves nothing. The daily puzzle's
   board fallback keeps the board's square (`.boardWaiting`).
7. **CI gate** (CC-135). The Vite plugin `scripts/build/bundleReport.mjs` writes `apps/web/bundle-report.json`
   (outside `dist`, never served, git-ignored): each chunk, its imports and CSS, and each source file's share of
   the minified code, split with the chunk's source map. `scripts/bin/check-bundle.mjs` (logic in
   `scripts/build/bundleBudget.mjs`) reads it and `dist/index.html`, and fails when: the entry script plus its
   `modulepreload`s is over 150 kB gzip; chess.js or Motion is on the first route; an effect scene or theme is on
   the first route; the effect registry's own code there is over 0.5 kB; an effect's chunk with its CSS is over
   6 kB or its registry `budgetKB`; the particle module's chunk is over 1.5 kB. The registry does not exist yet
   (CC-099), so the effect rules pass with nothing to check and start working the day it lands. It runs as the step
   **Bundle size budget** in the existing `checks` job (`Lint, format, audit, unit + integration (coverage
gates)`), so the ruleset's seven required check names do not change.

**Research note.**

1. Our code: boards and the console were already lazy (`games/lazyBoard.js`, `pages/AdminPage/AdminRoute.jsx`),
   with the stale-deploy reload rule of CC-181. `lazyRoute` reuses that rule (`RELOADING`). The router is the
   declarative `<BrowserRouter>`/`<Routes>`. React Router's `route.lazy` exists only for data routers
   (`createBrowserRouter`), so using it would mean moving the app to a data router: a larger change across every
   test that renders `App` with `MemoryRouter`. We take its behaviour instead (load the matched route before the
   first render) with `React.lazy` and `matchRoutes`. Moving to a data router stays possible later.
2. Others: React's docs (react.dev, `lazy`) recommend lazy routes behind a `Suspense` boundary; React Router's docs
   ("Lazy loading", reactrouter.com) load the matched route before the initial render; Remix and Next.js prefetch a
   link's route on hover or when it enters the viewport (Remix `prefetch="intent"`, Next.js `<Link prefetch>`).
   web.dev's CLS guide: reserve space for late content, and content that appears without moving existing content
   is not a shift. Hover prefetch is the cheap, low-waste choice here: viewport prefetch would download most pages
   from home's game list.
3. Best for us: intent prefetch, no viewport prefetch (data costs on Indian mobile plans), page code fetched before
   the first render on a direct visit, skeletons only after a click (where input-led shifts do not count for CLS).

**Tool used once, not committed.** The per-module split came from a throwaway Vite plugin (renderedLength per module)
and then from the committed report itself. No `vite-bundle-visualizer` install was needed.

## Acceptance criteria

- **AC-1** Given a production build, when CI runs, then the first route (entry plus preloads) is at most 150 kB
  gzip, or the `checks` job fails.
- **AC-2** Given an effect scene, theme, chess.js or Motion on the first route, or an effect over its budget, when
  CI runs, then the job fails and names it.
- **AC-3** Given a player on any page but home, when they open it by its address, then the page renders without a
  skeleton or a jump, and when they point at, focus or touch a link to it, its code starts downloading.
- **AC-4** Given `/games/chess`, `/` or `/daily/chess` on a phone, then Lighthouse CLS is under 0.1.

   incompressible entry, which exits 1 and says by how much (and a 20 kB one, which passes).

   resolves to its own page, redirects resolve to the page they land on, router ranking, failure settles),

   no `vite:preloadError`, no download, a later hint retries), `scripts/build/routeFiles.test.mjs` (the build's
   file list and the escaped data block), `app/routePrefetch.test.js` (each intent event, other sites, stop),
   `app/App.test.jsx` (hovering a game card hints the lobby and runs none of its code, redirects draw their page), `games/chess/chessColours.test.js`, `scripts/workflows.test.mjs` (the CI step).
4. `e2e/waking-up.spec.js`, "sees the lobby stay where it is when the screen goes": with a slow session check,
   the lobby's heading keeps its place when the app's waking screen goes. On main's CSS it fails on a phone (the
   heading jumps from y 474 to y 130). Passes on desktop and mobile here.
5. `e2e/browserNoise.test.js`: WebKit's "preloaded but not used" hint for a page prefetched on hover is engine
   advice, as it already was for boards. The pattern now allows a dot in the file name
   (`illustrations.module-*.js`), which failed `accessibility.spec.js` on WebKit in the first CI run.
6. `e2e/deploy.spec.js`, "pointing at a link does nothing when the page's files fail to arrive", for a file
   gone after a deploy (404) and a dropped connection: no page load, same address, no error page. Both fail with
   the earlier `import()` prefetch (the page reloaded) and pass now in Chromium, Firefox and WebKit.
7. `testing/render.jsx` preloads every lazy page before the tests, as a browser does for the page it opens, so the
   46 test files that render `App` see pages, not skeletons.

## Found along the way (follow-ups, not done here)

1. **The game registry is on the first route** (about 5 to 7 kB gzip): `components/SiteRequests` and
   `RequestBanner` import `games/roomUpdates.js`, which imports `games/registry.js`, which imports every game's
   options form, alerts, how-to-play text and pass-and-play helpers. Splitting request texts from the registry
   would take that off home. It touches the registry contract (ADR-049), so it needs its own ticket.
2. **The Feedback dialog** (about 2.5 kB) could load when it is first opened. It lives in `Layout.jsx`, which the
   header rebuild is changing, so it is left to that work.
3. **Socket.IO** (about 16.6 kB) loads on every first visit. Connecting lazily would be the largest single saving.
4. The headroom is about 3.6 kB. CC-323's Skeleton and the header rebuild add to the shell, so they should check
   `node scripts/bin/check-bundle.mjs` locally. `RouteSkeleton` carries a `TODO(CC-323)` to use the shared
   Skeleton.
